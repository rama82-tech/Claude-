ATTACK 1 [MAJOR] Floor-footprint closing zeroes a band along any image edge the walls touch
Where: `closed = cv2.morphologyEx(walls, cv2.MORPH_CLOSE, ..., borderType=cv2.BORDER_CONSTANT, borderValue=0)` with `kc = int(round(a.max_door_m * ppm)) | 1`
Problem: Closing is dilate then erode. With an explicit constant border of 0, the erode step treats everything outside the image as background. Every pixel within about kc/2 (32 px at 50 px/m, roughly 0.65 m) of the image border is therefore erased from `closed`. Counterexample: a tightly cropped plan or screenshot whose outer walls sit at the image edge (very common for cropped scans). The footprint contour then shrinks inward, `fp` is missing a strip of floor under and inside those walls, and the "blue region covers rooms" acceptance check fails. The test plan hides this: it has 45-50 px margins, which are larger than the 32 px half-kernel. The "tested" claim therefore does not cover this case. The OpenCV default border (neutral for erode) would not have this problem. There is no warning and no margin padding in the code.

ATTACK 2 [MAJOR] The built v0.1 does not implement the architecture the plan says is its core
Where: "Build a pipeline in which geometry is extracted once into a small, human-checkable JSON file (the 'plan IR')..." versus "v0.1 ... skips the JSON IR"
Problem: The headline recommendation is IR-first, but the only runnable code produces a GLB straight from raw pixel contours. It has no centre-lines, no wall or opening objects, no `needs_review`, no `report.md` and no editable intermediate. The user cannot correct a wrong wall without editing pixels. The "fix -> re-run" loop shown in the architecture diagram does not exist in the minimal version. The IR schema is given, but nothing consumes or produces it. Walls from `polys_from_mask` are blobs, not the `walls[]` the schema defines.

ATTACK 3 [MAJOR] A wrong scale that stays inside 3-60 m passes silently
Where: `if not (3 <= max(w, d) <= 60): warns.append(...)` and `--px-per-m` being the only scale input
Problem: This is the "biggest accuracy lever" by the plan's own words, yet the only guard is a 20x-wide plausibility band. If the user mis-measures by 2x (the plan itself notes a 2 px click error is 5% on a 40 px door), an 8 m house becomes 16 m or 4 m and no warning fires. v0.1 has no way to cross-check against a second dimension. The "spread above about 3%" check exists only in prose, and no code implements it. The script also gives the user no way to supply two points or a second dimension. It exits 0 and writes the GLB either way.

ATTACK 4 [MAJOR] Stated input types and the scale step cannot actually be done with v0.1 in the stated environment
Where: Task: "an image, scan or PDF, with dimensions". Plan: "Open the image in any viewer that shows pixel coordinates", and `pip install opencv-python-headless numpy shapely trimesh mapbox_earcut scipy`
Problem: PDF input is described (PyMuPDF) but PyMuPDF is not in the install line and the script only calls `cv2.imread`, so a PDF fails with "cannot read". The scale step tells the user to read pixel coordinates in "any viewer", but the user is in a headless cloud session. No helper is provided (for example a Playwright or OpenCV click-to-measure page, or a script that prints image size and candidate dimension line endpoints). The user is left to guess how to get the one number the whole run depends on. "Dimensions" are never read by v0.1 (OCR deferred), so the dimensions in the input are not used.

ATTACK 5 [MAJOR] Materials, lighting and renders are prose only, and the key tools are not set up
Where: Section 6 and extension step 6: "`blender -b -P render.py -- house.glb`", and assumption 5: "Blender and Tesseract were not found"
Problem: The task asks how to get "materials and lighting" and what the "renders" are. `render.py` is never written. No Blender install command is given (the `apt-get install tesseract-ocr` line is, but `apt-get` working through the sandbox proxy is not checked either). The viewer HTML is not provided. Nothing is said about whether a headless Blender can run CPU Cycles here. The deliverable list promises `top.png`, `iso.png`, `eye_*.png` and `walkthrough.mp4`, but no step in the plan produces any of them at the tested level. The room-to-material table is described but not wired to anything, because v0.1 has no rooms.

ATTACK 6 [MINOR] Failures warn but do not fail, so bad geometry is still written
Where: `warns.append(...)` for the 35% wall fraction, the low-resolution kernel and the implausible footprint; `main()` ends with exit code 0
Problem: With a coloured or hatched plan the script prints "WARNING" after already writing `house.glb` and `overlay.png`. A scripted or Claude-driven run that does not read stdout carries on with a garbage model. The wall-fraction warning is described in the plan as untested on any real fill. `overlay.png` is always written to the current directory, ignoring `-o`, so a second plan overwrites the first plan's overlay.

ATTACK 7 [MINOR] `min_area=0.05` m2 silently drops real structure
Where: `def polys_from_mask(mask, px_per_m, H, min_area=0.05)` and `if p.area > min_area`
Problem: A 0.2 x 0.2 m column or pier has an area of 0.04 m2 and is removed from the walls. Short wall returns or stubs of 0.25 m x 0.15 m (0.0375 m2) are also removed. The plan lists no warning and no mention of this threshold in the risks table. The tests do not exercise it, since the test plan has only long walls.
