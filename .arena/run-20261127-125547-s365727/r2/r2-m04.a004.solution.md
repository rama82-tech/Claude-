# Build plan: 2D floor plan to 3D model

## Recommendation in one paragraph

Do not go straight from the image to 3D. Go image -> **plan.json** (a small, validated, human-checkable description of walls, openings, rooms and scale) -> 3D. Everything upstream of plan.json (PDF handling, computer vision, OCR, a vision LLM) is untrusted and gets checked. Everything downstream (geometry build, glTF export, renders, a three.js viewer) is deterministic code that reads only plan.json. Generative image models are used only for an optional "pretty preview", never as the source of geometry, because they invent walls and furniture and cannot hold dimensions.

The design fails loudly. If the scale cannot be established, the exterior does not close, a gap has no evidence of what it is, or a door has no wall, the pipeline stops and says what is wrong. It does not produce a plausible-looking but wrong house. The rule that makes this real: **nothing is invented to make a check pass.** A gap in a wall becomes a door, window or arch only when the drawing shows evidence for it or a human confirms it.

The first version already takes an image or PDF and ends in a .glb. The fastest image-to-plan.json route in a Claude Code session is Claude's own vision, so v1 uses it as a *proposal*, then requires every proposed wall to be snapped to measured line evidence and the whole result to pass a validator and a human-reviewed 2D overlay.

## Assumptions

1. Input is one storey per file: a PNG/JPG scan or photo, or a PDF page. Multi-storey is a later extension (one plan.json per level).
2. Scale can be recovered from at least one of: a user-supplied real distance, printed dimensions, or a scale bar. If none exists, the pipeline asks for one measured distance. It may fall back to a door-width prior only when the user opts in, and the result is marked "approximate" everywhere.
3. Walls are mostly orthogonal. Curved and diagonal walls are phase two. Diagonal walls are flagged, not silently straightened.
4. Each printed dimension has its own reference type: `face` (interior face to face, typical for room dimensions), `outer` (outside face to outside face, typical for overall dimensions), `centre` (gridline or chain to centrelines), or `unknown`. The reference is recorded per dimension, not per plan. Printed room areas are assumed to be net (interior) areas.
5. Units: input may be feet-inches or metric; internal storage is metres.
6. Defaults, overridable and never read from the drawing: wall height 2.7 m, door head 2.1 m, window sill 0.9 m and head 2.1 m, slab 0.1 m.
7. The container has Python, Node, Chromium and Playwright, and probably no GPU. Rendering is CPU. Blender availability is not assumed; step 0 tests it.
8. A human (you) reviews a 2D overlay before the 3D build. Unattended conversion of arbitrary plans is not reliable, and this plan does not pretend otherwise.

## Architecture

```
input (PNG/JPG/PDF)
  -> 1 ingest + normalize (rotate, rasterize, hash)
  -> 2 scale calibration (tiered policy, per-dimension reference)
  -> 3 wall segments (CV, or vector paths from PDF) + separate thin-stroke layer; gaps kept
  -> 4 evidence-based gap resolution into openings; wall runs; rooms
  -> 5 plan.json  <-- the contract; schema-validated
  -> 6 validation (errors block, warnings report) + 2D overlay for human review
  -> 7 geometry build (Blender headless, or the no-Blender fallback)
  -> 8 materials, lights, cameras
  -> 9 export + renders + fidelity checks + web viewer + report
```

Three rules hold the design together:

- **plan.json is the only interface.** It can be hand-edited, produced by CV, or proposed by a vision model. The 3D stage does not care.
- **Every item carries a confidence and a source** (`user`, `vector`, `cv`, `vision`). Low-confidence or unsupported items are flagged on the overlay, not silently kept.
- **Stop on failure.** Non-zero exit and a `report.md` listing every failed check. No "best effort" 3D.

## Geometry conventions (these make every check well-defined)

- A wall is stored as a **centreline** `a`-`b` plus `thickness`. Its solid is the rectangle of that width around the line.
- A **wall run** is a maximal straight chain of collinear walls whose gaps have each been resolved to an opening. Run coordinate `t` is the distance along the run's centreline from its start point `t = 0`.
- **Opening position:** an opening occupies `[offset, offset + width]` in run coordinate `t`. `offset` is the centreline coordinate of its start edge.
- **Clear span:** `[t0, t1]` is the stretch of the run between the inner faces of the perpendicular walls at each end. If a run ends at a perpendicular wall of thickness `T`, that end is `T/2` in from the centreline end. A free end contributes `0`. Example: w1 runs (0,0) to (4.2,0), end walls 0.2 m thick, so the clear span is `[0.1, 4.1]`. A 0.9 m door at offset 3.15 ends at 4.05, which is inside, so it is valid. A door at offset 0.05 starts inside the corner wall and fails.
- Wall footprints are merged with a Shapely union. At corners and T-junctions the footprints overlap by design; that is not an error.
- A **room** has a net polygon: the area enclosed by the union of wall footprints, measured to the interior faces. `area_net` is the area compared with any printed area. Centreline area is never used for comparison.
- Each printed dimension is compared using its **own** `ref`: `face` against the face-to-face distance, `outer` against the outside-face distance, `centre` against the centreline distance. `unknown` is compared with the tolerance widened by one wall thickness.
- Expected model bounds = bounds of the union of wall footprints (thickness included).

## Tool choices

| Job | Use | Why / caution |
|---|---|---|
| PDF | PyMuPDF (`fitz`) | Extract vector paths first (lines are real walls, text has exact coordinates). Rasterize at 300 dpi only if the PDF is a scanned image. |
| Raster cleanup | OpenCV, scikit-image | Rotation fix, threshold, morphology. |
| Wall/line extraction | OpenCV (Canny, Hough, `LSD`), skimage skeletonize, Shapely | Classical CV is predictable and debuggable; prefer it for the CV route. |
| Dimension text | Tesseract (`pytesseract`), or PaddleOCR / EasyOCR | Dimension strings (`12'-6"`, `3.45 m`, `4200`) need a custom parser and a sanity check against measured pixels. Misreads (`6` vs `8`, `'` vs `"`) are the top scaling failure. |
| Semantic proposal | Claude vision: read the image, return JSON in the plan.json schema | Good at labels ("Kitchen"), door swings, rough topology. Poor at exact coordinates. It proposes; CV snap and validators decide. |
| Trained detectors (later) | CubiCasa5k and similar floor-plan models | Heavy. Only if classical CV fails on your plan style. |
| 2D geometry | Shapely (`unary_union`, `polygonize`, `polylabel`) | Footprints, rooms, slab, interior points. |
| 3D build, primary | **Blender 4.2 LTS headless, Python `bpy`** | Deterministic, glTF export, Cycles/EEVEE. |
| 3D build, fallback | Shapely + `trimesh` (+ `mapbox_earcut`), export .glb | Works without Blender. See Environment. |
| Live driving (optional) | Blender MCP add-on | Needs a GUI Blender reachable from the session, which a cloud container usually lacks. A convenience, not the architecture. The batch `blender -b -P build.py` path must work without it. |
| Web viewer and fallback renders | three.js `GLTFLoader`, `OrbitControls`; Playwright screenshots | Chromium headless uses software WebGL, which is slow but works. |
| AI image generators | Optional last step: a clay render fed to image-to-image for a styled mood image, labelled "concept, not to scale" | Never a source of geometry. |

## Environment (step 0, run once, before anything else)

A `check_env.py` prints a pass/fail table:

- Python imports: `cv2, fitz, shapely, trimesh, jsonschema, numpy`.
- `tesseract --version` (optional; only needed for OCR).
- Blender: `blender --version`, else `python -c "import bpy"`.
- Network reachability for the download hosts (the container egresses through a proxy; a failed download is a common cause of a missing Blender).

Pinned primary path: Blender 4.2 LTS Linux tarball (it bundles its own Python, so no ABI mismatch), run as `blender -b -P build.py -- plan.json out/`. The pip `bpy` wheel is an alternative only if its required Python minor version matches the container's Python; check this first because the wheel is large and version-locked. `build.py` must not hard-code render engine names: it reads the installed enum (`bpy.types.RenderSettings.bl_rna.properties['engine'].enum_items`) and picks the EEVEE variant that exists, because the identifier changed between releases. glTF export options are likewise passed by checking which keywords the installed `export_scene.gltf` accepts.

If Blender cannot be installed, the pipeline selects the fallback. What each path can do:

| Output | Blender path | Fallback path |
|---|---|---|
| plan.json, overlay, report | yes | yes |
| `house.glb` | yes | yes |
| `house.blend` | yes | no |
| Top-down and isometric stills | Cycles / EEVEE | three.js + Playwright screenshot |
| Procedural PBR materials, Nishita sky | yes | no: flat colours, simple lights |
| Photoreal eye-level renders | yes | basic only |
| Walkthrough mp4 | yes | no (v1) |

Fallback build rule (no booleans, so nothing to fail): for each wall run, cut the length at every opening edge. For a door, emit a full-height pier for each solid span, and a header from head to wall top above the opening. For a window, emit the pier, a sill block from floor to sill height, and a header from head to top. Each piece is `trimesh.creation.box` or `extrude_polygon` from the footprint. The same piece-based construction can also be used in Blender, which removes the boolean failure mode entirely; use Blender booleans only if you want a single watertight wall mesh.

## plan.json (the contract)

```json
{
  "schema": 2,
  "source": {"file": "plan.pdf", "sha256": "...", "page": 1},
  "units": "m",
  "scale": {"m_per_px": 0.0121, "method": "user|ocr_multi|ocr_single|scale_bar|door_prior",
            "evidence": [{"label": "4200", "px": 347, "ref": "face", "ok": true},
                         {"label": "8600", "px": 710, "ref": "outer", "ok": true}],
            "single_source": false, "confirmed_by_user": true, "confidence": 0.9},
  "levels": [{"id": "L0", "elevation": 0.0, "height": 2.7}],
  "walls": [{"id": "w1", "a": [0,0], "b": [4.2,0], "thickness": 0.2,
             "kind": "exterior|interior", "source": "cv|vector|vision|user",
             "cv_support": 0.9, "confirmed": false, "confidence": 0.95}],
  "openings": [{"id": "o1", "wall": "w1", "type": "door|window|arch",
                "offset": 3.15, "width": 0.9, "sill": 0.0, "head": 2.1,
                "swing": "left-in", "evidence": "arc|glazing_lines|user",
                "confirmed": false, "confidence": 0.8}],
  "rooms": [{"id": "r1", "label": "Kitchen", "polygon_net": [[0.1,0.1]],
             "area_net": 14.2, "printed_area": 14.0, "floor": "tile"}],
  "flags": ["w14 unsupported by CV", "dimension 3'-8\" disagrees with geometry by 9%"]
}
```

Pixel coordinates are kept next to metric ones (`a_px`, `b_px`) so the overlay can be redrawn from plan.json alone. An opening with no `evidence` must have `confirmed: true`, or validation fails.

## Pipeline stages

**0. Environment check.** As above. Do not discover a missing Blender halfway.

**1. Ingest.** Hash the file. PDF: count vector path objects; many means the vector route, otherwise rasterize at 300 dpi. Image: warn below roughly 1200 px on the long side; refuse below about 800 px.
Orientation: estimate the dominant line angle from a length-weighted histogram of Hough/LSD segments, take it modulo 90 degrees, and rotate to make it axis-aligned. This fixes any scan rotation, including 15 degrees and 90 degrees (a 90-degree rotation is detected by text orientation from OCR and corrected). Perspective is a different problem: it is detected when lines that should be parallel spread by more than about 3 degrees, or when the page quadrilateral is not a rectangle. A flat rotated scan is therefore never rejected. Perspective input (a phone photo) requires four user-clicked corners for a homography, or is rejected with that instruction. If no orthogonal pair of angle peaks exists, flag "non-orthogonal plan" and do not snap angles. Crop title block and legend.
*Gate:* normalized image and thumbnail written; unreadable or password-protected files stop here.

**2. Scale (tiered policy, per-dimension reference).** Candidates, in order of authority:
- (a) A **user-supplied real distance** (two points and a length). Authoritative. Other evidence is compared against it and disagreements are flagged, not used to override it.
- (b) **Two or more printed dimensions** with their dimension lines measured in pixels. Only dimensions with a known `ref` of `face` or `centre`-between-known-gridlines are fitted at first; the fit is a median with outliers discarded. `outer` dimensions are not used for the first fit, because wall thickness is not yet known. After walls are measured, each `outer` dimension is converted (add one thickness per end as appropriate) and checked against the fit. `unknown` dimensions are checked with the tolerance widened by one wall thickness.
  Agreement tiers on the surviving values: **up to 2 percent**, accept. **Over 2 and up to 5 percent**, accept but record a warning and require the overlay ruler to be confirmed (`confirmed_by_user`). **Over 5 percent**, stop: "scale ambiguous: here are the candidates; give me one real distance".
- (c) **One printed dimension or a scale bar.** Accepted, but `single_source=true`, a warning is recorded, and the overlay draws a ruler with its length so you must confirm it. A printed "1:100" is never trusted alone, since scanning and resizing break it; it is only a cross-check.
- (d) **Door-width prior** (0.8 to 0.9 m). Only with an explicit opt-in flag; stamped "approximate" in plan.json, report and render captions.
*Gate:* exactly one of these must resolve, or the pipeline stops.

**3. Wall segments and the thin-stroke layer (gaps kept).** Binarize. Separate thick wall strokes from thin strokes by stroke width (distance transform) and solid fill or hatch. **Thin strokes are not discarded.** They are written to a second layer, classified as dimension lines, text, furniture, or "candidate glazing" (short thin parallel pairs aligned with a wall direction). Skeletonize the thick layer, fit lines, snap to dominant angles (only within tolerance), estimate thickness from the distance transform, round to a plausible 0.1-0.4 m. Remove segments shorter than 0.15 m and log them. Output is wall segments with their gaps intact, plus the thin-stroke layer. This stage does not close any gap.

**4. Gap resolution, wall runs and rooms.** Bridging is driven by evidence, never by gap width alone.
1. Group segments by supporting line (same angle, perpendicular offset within half a wall thickness). For consecutive segments in a group, each separation is a **candidate gap** with width `g`.
2. Look for evidence in the gap:
   - **Door:** an arc (swing) found by Hough circles or arc fitting adjacent to the gap, or a leaf line plus arc.
   - **Window:** thin parallel lines from the thin-stroke layer crossing the gap (the common "break in the wall with glazing lines" convention), or a thinner stroke inside a continuous wall (the "thin wall" convention). Both produce a window with default sill and head.
   - **Arch / cased opening:** only by user confirmation, or a drawn jamb pair with no leaf.
3. **Resolution rules:**
   - Evidence found: the segments merge into one run and the gap becomes an opening of that type, with `evidence` recorded. Width comes from the measured gap.
   - No evidence and `g` between 0.7 and 1.2 m on an **interior** wall: propose a door with `evidence: none`, confidence 0.3. It is shown on the overlay as a question and is a build-blocking item until `confirmed`.
   - No evidence in any other case, or any gap on an **exterior** wall over 1.2 m, or any gap over 1.2 m anywhere: **unresolved gap**. It is not bridged. It is an error that names the location and width, with the question "missing wall, opening, or two separate walls?" The user answers by adding an opening, adding a wall, or marking the two walls as separate.
   - Two collinear walls that the user marks "separate" (a corridor end or a courtyard) are never merged.
4. Rooms: polygonize the resolved wall network (Shapely `unary_union` of centrelines, then `polygonize`), subtract the wall footprint union to get `polygon_net`, and match OCR labels by point-in-polygon. Because evidenced doors are bridged first, a door no longer leaves the network open. Counterexample handled: a rectangle split by a partition with a 0.9 m door that has a swing arc. Stage 3 returns two partition segments; stage 4 finds the arc, bridges the gap into one partition with a door record, polygonize returns two rooms.
*Gate:* the exterior must form a closed ring using only evidenced or confirmed openings. A closed ring that depends on an unconfirmed or evidence-free bridge does not count. Unlabeled rooms are flagged, not guessed.

**5. Write plan.json.** Validate against JSON Schema. Fill every confidence and source value. For vision-sourced walls, `cv_support` is the fraction of the wall's length within 15 px of a detected thick-stroke segment.

**6. Validation and review.** Automated checks with explicit severities (below), then draw the **overlay PNG** on the original: walls red, openings blue (door) and green (window), room labels, flags yellow, unconfirmed or unsupported items dashed, scale ruler. Review it before any 3D is built; edit plan.json where wrong and rerun from stage 6 (stages 1-5 are cached by file hash). Any error blocks the build; warnings go into the report.

**7. Geometry build.**
- Walls per run, joined at corners by union (or extending to intersection) so corners are not notched. Openings are cut by piece construction (preferred; see Environment) or by an exact-solver boolean with a cutter slightly larger than the opening. Add a door leaf or frame, and window frame plus glass pane, as separate named objects.
- **Slab:** one slab mesh, thickness 0.1 m, from `unary_union(all polygon_net + all wall footprints)`. This puts floor under doorway thresholds and under walls, so no void shows at a door sill or at the exterior edge.
- **Finishes:** each room's floor finish is a thin layer (or a material-assigned face set) on top of its `polygon_net`, so the slab is continuous and the finish stops at the door line. A door threshold strip uses the finish of the room the door swings into.
- Ceiling or roof optional (off for top-down views).
- Names: `Wall_w1`, `Door_o1`, `Slab`, `Floor_Kitchen`, so edits and exports are traceable.
*Gate (builder self-check):* the model bounding box equals the footprint-union bounds within 5 mm, and meshes are manifold; failures list object names. This only proves the builder did what plan.json says. It does not prove plan.json matches the drawing; the fidelity checks below do.

**8. Materials and lighting.**
- Materials: a small library keyed by a plan.json tag (`wall_plaster`, `floor_wood`, `floor_tile`, `glass`); Principled BSDF with procedural textures (no external image dependency). Defaults by room label (bathroom to tile), always overridable; unknown labels get a neutral material and a flag.
- Lighting: sun plus sky (Nishita) for daylight through windows; area lights or emissive panels inside rooms; for clean clay renders, a white world and ambient occlusion. Window openings must have glass or be open holes. Check the render is not black.
- Cameras: top-down orthographic (the "3D floor plan"); isometric cutaway (hide the roof and the walls facing the camera, or clip with a box); eye-level at 1.6 m. Eye-level position is the room's **pole of inaccessibility** (Shapely `polylabel` on `polygon_net`), not the centroid, because the centroid of an L or U shape can fall inside a wall or another room. Check the point has at least 0.5 m clearance from walls; if not, pick the best-clearance sample. Aim along the room's longest axis, but never at a wall closer than 1 m; if the room is too small, use a wide-angle lens.
- Render: EEVEE for speed, Cycles (denoise, 64-128 samples) for finals, with sample and time caps for CPU.

**9. Export, fidelity checks and report.** Write the outputs below. Then run the fidelity checks, which compare the model with the **source drawing**, not with plan.json:
1. **Mask overlap:** render the top-down orthographic view with walls only, map it to source pixels with the scale, register it to the source wall mask (translation only), and compute IoU of wall pixels. Below 0.7 is an error, 0.7 to 0.85 a warning. The IoU also lists wall segments of the source mask that have no model wall (missed walls) and model walls that have no source support (phantom walls).
2. **Independent dimension:** compare the model's overall width and depth with an overall printed dimension that was not used in the scale fit (convert by its `ref`). Disagreement above 2 percent is an error; if no independent dimension exists, the report says "no independent check available" in bold.
3. **Door/window count:** openings in the model match the symbol count detected in the thin-stroke and arc layers; a mismatch is a warning with locations.
`report.md` lists scale evidence and whether it was single-source, every flag, every unconfirmed item, per-stage status, fidelity results and anything assumed.

## Validation severity table

| Check | Definition | Severity |
|---|---|---|
| Schema valid | JSON Schema | error |
| Opening without evidence | `evidence` empty and `confirmed` false | error |
| Unresolved gap | Candidate gap with no evidence and not a confirmed interior door (see stage 4) | error |
| Unsupported wall | `source: vision` and `cv_support` below 0.6 and not `confirmed` | error |
| Exterior ring closed | Union of exterior footprints has one outer ring using only evidenced or confirmed openings | error |
| Duplicate / collinear overlap | Two walls on the same line overlapping along their length by more than one thickness | error |
| Corner / T-junction overlap | Footprints overlapping only at a junction (up to thickness x thickness) | allowed, no flag |
| Wall crosses another without a junction | Footprints intersect in an X with no shared node | warning |
| Opening inside clear span | `t0 <= offset` and `offset + width <= t1` (clear span defined in Geometry conventions) | error if outside |
| Opening near a corner | Opening edge within 5 cm of a clear-span end | warning |
| Overlapping openings in a wall | Two openings overlapping in offset range | error |
| Opening height | `head <= level height`, `sill < head` | error |
| Room area | `area_net` below 0.25 m2 or invalid polygon | error |
| Small room | `area_net` below 1 m2 (pantry, shaft, closet are normal) | warning |
| Large room | `area_net` above 150 m2 | warning |
| Printed dimension vs measured | Difference above 2 percent using that dimension's own `ref` (above 5 percent is an error if it is scale evidence) | warning |
| Printed area vs `area_net` | Difference above 5 percent | warning |
| Unlabelled room | No label matched | warning |
| Low confidence item | Confidence below 0.5 | warning, highlighted on overlay |
| Fidelity: mask IoU, independent dimension | See stage 9 | error / warning as stated |

## Accuracy: how the numbers stay honest

- Final geometry is **measured, or confirmed by a human against the drawing**. In the v1 route, a vision model proposes coordinates, but a wall survives only if it is snapped to a detected line in the source (`cv_support`) or a person confirms it on the overlay. Each wall records its `source`, and the report states how many walls came from each source.
- Printed dimensions are evidence compared against measured values using their own reference type, not truth: plans are often "not to scale".
- Angles and thickness snap only within tolerance, so a real 4.37 m wall is not forced to 4.0 m.
- Nothing is invented to satisfy a check: no gap is bridged without evidence or confirmation, no scale is defaulted without opt-in.
- Idempotent builds: same plan.json gives the same model. Keep 3-5 sample plans with expected net room areas for regression.

## Risk and failure table

| Risk / failure | What happens | Defence |
|---|---|---|
| Wrong scale (OCR misread, not-to-scale plan, resized scan) | Whole house wrong by a constant factor, looks fine | Tiered policy with 2/5 percent tiers; single-source scale is flagged and needs confirmation; independent overall-dimension check at stage 9 |
| Missed wall segment (faded scan, hatch misread) | Gap in a wall that looks like an opening | No bridging without evidence; unresolved-gap error names location and width; mask-IoU check lists missed walls |
| Door gaps break room detection | Rooms merge or fail to polygonize | Evidence-based bridging (swing arc); confirmed interior door proposals |
| Window drawn as a break with glazing lines | Becomes a doorway | Thin-stroke layer kept in stage 3; glazing lines in a gap classify it as a window |
| Gap wider than 1.2 m (garage door, open plan) | Free wall end, exterior not closed | Stop with the gap location; user adds an `arch`/`door` opening, a wall, or marks the walls separate |
| Furniture, hatch, text, dimension lines read as walls | Phantom walls | Stroke-width classification; crop title block; overlay review; mask-IoU lists phantom walls |
| Walls drawn as double lines, solid fill or hatch | Thickness wrong or missed | Fill-ratio test; thickness sanity range |
| Door/window symbols vary (sliding, bifold, pocket) | Missed or misplaced openings | Evidence rules first; unknown opening stays an unresolved gap, never silently an arch |
| Mixed dimension references (interior vs overall) | False disagreement stops the pipeline | Per-dimension `ref`; outer dimensions only checked after thickness is known |
| Photographed plan with perspective | Skewed geometry | Detect converging parallels; require four corners for homography, or reject. A flat rotated scan is not rejected |
| Low-resolution or JPEG-artifact scans | Broken lines | Resolution check; upscale only for display |
| Handwritten or non-Latin dimensions | OCR fails | User-supplied distance path; never guess |
| Vision LLM hallucinated coordinates | Wrong plan | Image downscaled/tiled to model input size; CV snap within 15 px or flagged unsupported; validator and overlay decide |
| Boolean failures (coplanar faces, slivers) | Holes or broken meshes | Piece-based wall construction avoids booleans; if booleans are used, overscale the cutter, merge by distance, manifold check |
| Floor voids at door sills / under walls | Gaps visible in renders | Continuous slab from union of net polygons and wall footprints |
| Black or dim renders | Glassless openings, no sun, flipped normals | Mean-luminance check, auto fallback to clay world light |
| Blender not installable (proxy, version, size) | Primary build cannot run | Step-0 check; pinned tarball path; specified fallback with its limits stated |
| Cloud CPU render is slow | Timeouts | EEVEE default, low-sample previews, background run with hard timeout |
| AI mood image looks right but is wrong | User trusts invented rooms | Label as concept; never feed back into plan.json |
| Privacy of a real home's plan | Leak | Process locally; no third-party upload without consent |
| Multi-storey, stairs, curved walls, slanted ceilings | Out of scope | Detect as unsupported where possible; state the limit in the report |
| L/U-shaped room camera placement | Camera inside a wall | `polylabel` plus clearance check |

## Minimal first version (image or PDF in, .glb out)

Goal: one rectilinear one-storey plan, given as an image or PDF, becomes a correct, viewable .glb and a top-down render, with a human confirming the proposal.

1. **Fixtures first (half a day).** Hand-write one `plan.json` (10-20 walls, 3-4 openings) as a test fixture, and write `validate.py` (schema plus the severity table) and `build.py` against it. This proves the 3D half and the checks. It is a fixture, not the product.
2. **Image to plan.json via Claude vision, with CV evidence (the v1 front end).** `propose.py` does the following:
   - Prepares the image for the model: downscale (or tile with overlap) so the long side is at most about 1500 px, then draw a labelled grid every 100 px **of the downscaled image**. Model coordinates are mapped back to source pixels by the known scale factor.
   - Asks Claude for JSON in the plan.json schema (wall endpoints, openings, room labels, `a_px`, `b_px`) and converts to metres with the tiered scale.
   - Runs an LSD/Hough pass on the full-resolution image. Each proposed wall endpoint is snapped to the nearest detected line end within 15 px, and `cv_support` is computed. Walls below 0.6 are flagged unsupported and block the build until confirmed.
   - Runs the stage 3 thin-stroke layer and stage 4 evidence rules, so openings carry `evidence` or are flagged.
   - For a **vector PDF**, reads PyMuPDF path objects and text with exact coordinates instead, groups thick strokes into walls (`source: vector`), and uses printed dimension text for scale; this is more accurate than vision and needs no OCR.
3. **Overlay and fix loop.** Run `validate.py` and render `overlay.png`. Edit plan.json (or tell Claude what is wrong) and re-run until there are no errors.
4. **Build.** `build.py` produces the .glb and a top-down PNG (Blender if the step-0 check passed, else the fallback), with the builder self-check, then the stage 9 fidelity checks.
5. **Viewer.** `viewer/index.html` with three.js `GLTFLoader` and `OrbitControls`; Playwright screenshot as a check.
6. Then automate in order of payoff: (a) OCR-based scale with the tiers above, (b) CV wall detection replacing vision proposals, (c) CV door and window detection, (d) isometric and eye-level cameras, (e) vision kept only for labels and as a second opinion.

Success tests for v1:
- The fidelity mask IoU is at least 0.85 on the reference plan, and an independent printed overall dimension matches the model within 2 percent.
- Each room's `area_net` matches its printed area within 5 percent where a printed area exists.
- The .glb opens in the viewer and the screenshot shows the right number of rooms and doors, with no floor void at any doorway.
- Deliberately broken inputs stop with a clear message and no model. These include the **silent cases**: (1) a 2.5 m segment of exterior wall erased from the source image, which must produce an unresolved-gap error and not an arch; (2) two collinear walls either side of a 3 m corridor, which must not be merged; (3) a window drawn as a wall break with glazing lines, which must become a window and not a door; (4) a single-source scale with no confirmation; (5) an opening that extends past its clear span; (6) a vision-proposed wall with no matching line in the source.

## Decision summary

- Blender 4.2 `bpy` in batch for the full-quality build, with a specified Shapely/trimesh/three.js fallback; three.js for viewing; MCP only as an optional convenience.
- Claude vision proposes in v1 (downscaled, gridded image in, plan.json out); classical CV and PDF vector extraction measure and snap; a validator and a human overlay decide. Final geometry is measured or confirmed, never a bare model guess.
- Gaps are kept in stage 3 and resolved in stage 4 only with evidence (arc, glazing lines) or human confirmation, so a missed wall can never silently become an opening.
- Per-dimension reference types, one defined offset origin and clear span, and tiered 2/5 percent scale tolerances make every check agree with a correct build.
- Fidelity checks compare the model to the source drawing, not to its own plan.json.
- Generative AI is for mood images only.
- plan.json with confidences, sources and severity-graded checks means bad input gives a clear error, not a convincing wrong house.
