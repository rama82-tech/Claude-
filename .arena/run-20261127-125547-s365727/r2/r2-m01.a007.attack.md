ATTACK 1 [MAJOR] Every exterior corner is built with a missing square (notched corners)
Where: stage 6 `fp = lambda w: LineString(...).buffer(w["thickness"]/2, cap_style=2, join_style=2)`, then `ext = unary_union([fp(w) for w in real if ...])`
Problem: cap_style=2 (flat) ends each wall exactly at its centreline endpoint. `join_style` only affects bends inside one linestring, not the meeting of two separate walls. At each outer corner, the square (t/2 x t/2) beyond both endpoints is never covered. I ran the code's footprint on the document's own 8 x 5 box with 0.2 m walls. The area is 5.16 m2 where a closed ring should be 5.20 m2, and the point (8.05,-0.05) is outside the footprint. Every house gets four 10 cm x 10 cm bites out of its outer corners. The solution says this was "Tested on an 8 m by 5 m plan" and the checklist only asserts watertightness, so the defect passes every listed test. A mesh with notched corners also breaks the "accurate walls" goal, and the render shows the notches.

ATTACK 2 [MAJOR] The GLB is exported Z-up, which the glTF format does not allow, so it opens on its side in Blender and other viewers
Where: stage 6 `sc.export(sys.argv[2])`; stage 9 "`house.glb` (primary)"; stage 6 "Material names ... set so Blender or three.js can re-skin them"; viewer.html `cam.up.set(0,0,1); // plan is Z-up`
Problem: glTF is defined as +Y up. trimesh writes the raw Z-up coordinates without rotating them. The custom three.js viewer hides this by setting the camera up-vector to Z. Blender's glTF importer converts from Y-up to Z-up, so it will lay the house on its side (walls rise along -Y). The same goes for any generic GLB viewer or model-viewer. The plan names the primary deliverable and says Blender will take it. It never says to rotate -90 degrees about X on export or to set up-axis metadata. The user would hit this on the first Blender import with no hint why.

ATTACK 3 [MAJOR] The "minimal first version" is not an automated pipeline and its accuracy goal contradicts its own risk list
Where: Assumptions "'Accurate' means within about 2 cm or 1% of printed dimensions"; Risks #1 "Claude's pixel reads can be off by 1 to 2%"; Minimal first version "**no CV, no OCR**", step 3 "Claude writes `plan.json` by hand"
Problem: The task asks for CV/OCR for walls, doors, windows and dimensions and a first version the user could build. In v1 every wall coordinate, opening and dimension is typed by a Claude Code session reading pixels off a grid image. On an 8 m wall, a 1-2% error is 8-16 cm, which is 4-8 times the 2 cm acceptance tolerance. The only fix offered in v1 is repeated manual edits of plan.json until the checker passes. The least-squares dimension solver is deferred to "Then add... (a)". So the "done when" criterion (dimensions within 2 cm) is reached by hand-fitting, not by the pipeline. A user who hands over a new plan gets nothing without a Claude session. This is a manual drafting aid, not what the idea asked for.

ATTACK 4 [MINOR] Environment claim contradicts the stated context and hard-codes one browser path
Where: Assumptions "Python playwright is not preinstalled" and shot.py `executable_path="/usr/bin/google-chrome"`; stage 0 `pip install ... playwright`
Problem: The task says Chromium and Playwright are pre-installed. In this container `import playwright` already succeeds, so the "checked" claim is wrong or stale. shot.py has no fallback to Playwright's bundled Chromium. If `/usr/bin/google-chrome` is absent, the screenshot step fails at launch. The user has to rewrite the script to get any render, and that includes the "smoke test" the plan says to run first.

ATTACK 5 [MINOR] Dimension checker silently gives wrong results for any wall pair that is not perpendicular to the chosen axis
Where: `check_dims`: `abs(wb["a"][ax]-wa["a"][ax])` with the comment "orthogonal walls: constant coordinate"
Problem: It reads only the start point `a` of each wall. Take axis 0 and a horizontal wall such as w1 (0,0)-(8,0), whose x is not constant. The wall pair in the schema example `["w4","w2"]` with axis 0 only works if both are vertical walls. If the user or Claude lists a horizontal wall, the value is garbage and either a correct plan is flagged or a wrong one passes. No validation rejects a non-perpendicular pair, and a wall drawn with `a`/`b` reversed also changes the result. The plan leaves this to the reader's care, and it says "Every printed dimension checks within 2 cm" is a pass gate.

ATTACK 6 [MINOR] Reader A is referenced but never defined
Where: stage 3 "**Merge rule:** semantics (type, label, swing) come from the reader that sees them (A). Each A wall snaps to a B wall..."
Problem: The bullets are named "Interactive", "Automated" and "Reader B (classical CV, later)". No bullet is labelled "Reader A". The user cannot tell whether A is the interactive Claude reader, the API reader, or both. The merge rule (angle under 5 degrees, 10 cm, overlap) cannot be implemented without that.

ATTACK 7 [MINOR] Cutaway builder crashes for low cut heights
Where: build(): `cut = trimesh.creation.box(extents=[..., min(o["height"], H-o["sill"])])` with `H = cut_height`
Problem: With the suggested window sill of 0.9 m, any cut_height of 0.9 or less gives a zero or negative box extent. That fails or gives a degenerate cutter instead of skipping the opening. The docs call `house_cut.glb` a general low-wall variant ("1.2 m"). A user trying a 0.9 m or 0.6 m cut (a common "see the layout" height) gets an exception.
