# 2D Floor Plan to 3D Model: Build Plan

## Recommendation in one paragraph

Do not make a computer "understand" the plan in one step. Split the job into two stages joined by a small, human-checkable JSON file. Stage 1 (perception) turns the image or PDF into a plan description: wall segments, openings, rooms and a scale. Stage 2 (generation) turns that JSON into geometry with deterministic code. Build Stage 2 first and feed it hand-written JSON, so the 3D output is correct by construction and any perception error shows up as a visible, fixable edit to one text file. Use Python with `shapely` and `trimesh` to write a GLB. Preview it with three.js (pinned version, vendored locally) served over local HTTP and screenshot it with Playwright. Add Blender later for photoreal renders. AI image generators should not produce geometry. Use them, if at all, for optional styled renders checked against the plan.

## Assumptions

- One storey. A clean, mostly orthogonal drawing: architect PDF, CAD export or clear scan. Not a hand sketch or an angled photo.
- A scale is obtainable: two clicked points plus a metres value, or a printed dimension, scale bar or ratio such as "1/4 in = 1 ft".
- Accurate and editable model first, pretty renders second.
- Cloud container: Linux, Python, Node, Chromium, Playwright, no GPU. Network may be limited by a proxy, so version 1 may need only pip and npm registry access (both normally reachable) and nothing from a CDN, apt or a large model download (see Preflight).
- Defaults when the plan is silent: ceiling 2.4 m, door height 2.0 m, window sill 0.9 m, window head 2.1 m, interior wall 0.115 m, exterior wall 0.23 m.
- Multi-storey is out of scope for version 1 (run once per plan and stack later).

## Preflight (2 minutes, run first)

```
which tesseract blender; python -c "import fitz, cv2, shapely, trimesh, mapbox_earcut"; id -u; node -v; npm view three@0.160.0 version
```

- No `tesseract`: version 1 does not need it. If you add OCR later, try `apt-get install -y tesseract-ocr`, or `pip install easyocr`, or have Claude read printed dimension text from the image and type it in.
- No `blender`: skip it. Version 1 is complete without it. Later, try `apt-get install blender` or the official tarball. If neither works, render with three.js and Playwright.
- `pip install` or `npm` blocked: use the pre-installed packages only, report what is missing, and fall back to the hand-written JSON path.

## Architecture

```
 PDF/PNG/JPG
     |
 [1 Ingest]   rasterize (and extract vectors if PDF), deskew, crop
     |
 [2 Scale]    manual two-point or printed dimension (v1)  ->  OCR (v2)
     |
 [3 Detect]   vector or raster detectors -> plan.json  (or Claude transcribes dimensions into plan.json)
     |                                              ^
 [4 Review]   overlay plan.json on image -----------|  (human fixes JSON)
     |
 [5 Build]    plan.json -> 2D polygons -> extrusions (Z-up) -> rotate once to Y-up
     |
 [6 Export]   model.glb
     |
 [7 Show]     three.js viewer over http, Playwright screenshots
     |
 [8 Render]   (later) Blender or three.js stills, walkthrough
```

Why the JSON sits in the middle:

1. It isolates the hard, error-prone step (reading a drawing) from the easy, reliable one (extruding walls).
2. You can swap detectors (classical CV, vector parsing, a trained model, a vision LLM) without touching 3D code.
3. A wrong wall is one line of JSON, not a re-run of a black box.
4. Hand-written plans become regression tests for the generator.

Second-order effects: a scale error silently resizes everything, a wrong wall style silently returns zero walls, and a wall-end error silently notches corners or openings. So scale, detector source per wall, and geometry checks are each explicit, reported in `report.md`, and shown in the overlay.

## The data contract: plan.json

Units are metres. Plan frame: origin at the top-left of the plan, x right, y down, as in the image. The build step flips y once and rotates to glTF's Y-up once (see Step 5).

```json
{
  "units": "m",
  "scale": {"m_per_px": 0.0123, "source": "manual:2pt", "confidence": 1.0},
  "wall_height": 2.4,
  "walls": [
    {"id": "w1", "a": [0, 0], "b": [8.0, 0], "thickness": 0.23, "kind": "exterior", "src": "vector"}
  ],
  "openings": [
    {"id": "d1", "type": "door",   "wall": "w1", "offset": 1.2, "width": 0.9, "height": 2.0, "sill": 0.0},
    {"id": "n1", "type": "window", "wall": "w1", "offset": 4.0, "width": 1.2, "height": 1.2, "sill": 0.9}
  ],
  "rooms": [
    {"id": "r1", "name": "Kitchen", "label_xy": [2, 1.5], "floor": "tile"}
  ],
  "dims": [
    {"label": "Kitchen width", "value": 3.00, "basis": "inside", "walls": ["w2", "w4"]},
    {"label": "Overall width", "value": 8.23, "basis": "outside", "walls": ["w2", "w6"]}
  ]
}
```

Rules:

- Walls are centrelines plus thickness. Openings are placed by `offset` along the wall's centreline from `a`, so nudging a wall moves its doors.
- `dims` records each printed dimension with its basis: `inside` (face to face), `outside` (outer extent) or `centre`. The accuracy check measures the built geometry on that basis, never the raw centreline length.
- Room polygons are not stored by hand. They are computed from the walls (Step 5), and a room is named by the label point that falls inside it.
- Anything the detector is unsure of gets `"confidence"` below 0.7 and is drawn red in the overlay. `src` records which detector produced the wall.

## Step-by-step pipeline

### Step 1. Ingest
- PDF: always try vectors first. Run `page.get_drawings()`. If the page has more than about 200 line, rect or curve items, treat it as vector and use the vector path in Step 3. Also render a raster at 200 to 300 dpi for the overlay and the raster fallback.
- Image: grayscale, deskew by the dominant Hough angle, Otsu or adaptive threshold.
- Crop away title block, legend and notes with `--crop x1,y1,x2,y2`. Multiple plans or elevations on one sheet must be cropped to one plan.
- `grid.py image.png` writes `image_grid.png` with a labelled pixel grid every 100 px (and minor ticks every 20 px). Use it for every manual read-off of pixel positions, whether by the user or by Claude.

### Step 2. Scale (the number that decides accuracy)

Scale is fixed before detection, so every later size limit can be expressed in pixels.

Version 1 (default, no dependencies): manual two-point scale. Pick two pixel points on the gridded image and give the real length, for example `--scale-from "x1,y1,x2,y2,3.20"`. Better, give two pairs on different axes. Report the two implied scales. If they differ by more than 2 percent, stop and say so (skewed scan, or non-uniform scaling). When Claude is the one reading the image, the points must come from a gridded image and be confirmed on the overlay. A pixel read-off from a clean grid is good to about 5 to 10 px, which is why the scale pair should span a long dimension (at least 500 px), keeping the error under about 2 percent.

Version 2: automatic scale from OCR, with an explicit association method.

1. Run OCR at 0, 90, 180 and 270 degrees (vertical dimensions are rotated text) and keep numeric tokens with their boxes and orientation. Parse with strict regexes: plain mm integers like `4200`, decimals with `m`, and imperial `12'-6"`. Reject anything unparseable.
2. Detect dimension lines: long thin lines with end ticks or arrowheads, found by LSD, that sit outside the wall mask.
3. Associate each number to a dimension line: take lines parallel to the text direction, within about 2 text heights perpendicular to the text, whose span covers the text centre. If more than one qualifies, take the nearest. Drop numbers with no match.
4. Compute metres per pixel per match as parsed length over line pixel length. Take the median. Discard matches more than 10 percent off the median, then report the spread.
5. Accept only if at least 3 matches agree within 2 percent. Otherwise fall back to the manual two-point scale.

Vector PDFs: also check the sheet's declared scale and units. Page units are points (1/72 in), so metres per unit equals the plan ratio times 0.0254 divided by 72. Cross-check against one manual measurement.

Fallback ruler (only after walls and doors exist): median door gap width in pixels set to 0.9 m, flagged low confidence. Not used in version 1.

### Step 3. Detect walls and openings

With scale known, wall thickness is bounded: 0.08 to 0.45 m converted to pixels. Every detector below uses that range, so none of them needs a thickness measured first.

Do not classify the whole plan as one wall style, because plans mix them (solid exterior, double-line interior). Run every detector below, tag each wall with the detector that found it (`src`), merge results by removing walls that overlap an existing one by more than 80 percent of length within one thickness, and colour the overlay by `src`. The human prunes in the overlay step. If two detectors disagree on the same stretch, keep both and mark them red.

**Vector path (best, for CAD PDFs):**
1. Extract segments and fills from `get_drawings()` with stroke width, fill and layer colour. Drop items shorter than 10 cm after scaling, hairline dimension, grid and furniture strokes by width and colour, and any item whose box falls inside a text box from `get_text("dict")`.
2. Solid fills (Style A). Convert each filled path to a `shapely` polygon, with holes. Then branch:
   - Rectangular fill (polygon area at least 0.9 of its minimum rotated rectangle): one wall, centreline along the long axis, thickness from the short side.
   - Compact blob (area under about 0.5 m2 and aspect ratio under 2): a column. Record it under `columns`, do not make a wall.
   - Anything else (L-, T- or ring-shaped, or one polygon holding the whole wall network): rasterize it alone at 1 cm per pixel and send it through the raster Style A path below (distance transform on the skeleton for thickness). This handles merged CAD fills where a single long axis is meaningless.
3. Double lines (Style B), pairing algorithm: bucket segments by angle (snap within 3 degrees to horizontal and vertical). For each segment, find partners that are parallel, overlap in projection by at least 50 percent of the shorter one, and sit at a perpendicular gap between 0.08 and 0.45 m. Each accepted pair makes one wall: centreline is the midline over the overlapping span, thickness is the gap. Resolve ties by smallest gap. Merge collinear results and close gaps under one thickness.

**Raster path (scans, images):**
1. Style A, solid: erode with a kernel of about 60 percent of the minimum thickness (0.08 m in pixels) repeated until thin lines vanish, then dilate back by the same amount. What survives is the wall mask. Skeletonize it, fit segments (`HoughLinesP` or LSD), snap to horizontal and vertical within 3 degrees, merge collinear segments, close small gaps, and take thickness as twice the distance transform on the skeleton, snapped to a standard value.
2. Style B, double line: do not close and do not erode. Run LSD on the binary image to get line segments, then feed them to the same pairing algorithm as the vector path, with gaps converted to pixels. This avoids any morphological kernel, so door openings and thin rooms such as a 0.9 m closet (below the 0.08 to 0.45 m gap range, and with unrelated segments on its two sides) are not filled.
3. Style C, single line: off by default for raster, because dimension lines, grids and furniture edges all look like single strokes. Enable it with `--single-line` only when the user says walls are single strokes. Thickness then comes from the defaults.
4. Reject mask components whose area is far greater than skeleton length times the maximum thickness (these are room interiors or filled regions).

**Openings (both paths):**
- Walls are a continuous stroke, openings are interruptions. A gap in the wall line that is crossed by a swing arc (a quarter circle, found by contour or Hough circle) is a door, and the arc gives hinge and swing. A gap containing two or three thin parallel lines is a window. A plain gap is a doorway. Record offset and width along the wall.
- In vector data, door arcs are `curve` items in `get_drawings()` and are easy to find.

**Rooms and semantics:**
- Rooms come from the wall network (Step 5), not from detection.
- Send the image plus the overlay to a vision model and ask: list rooms, count doors and windows, and flag anything wrong. Compare with the detector's counts. Disagreements are marked in the review.

### Step 4. Review overlay (do not skip)
Draw `plan.json` on the original image (colours by `src`, openings green and orange, low-confidence red) and save `overlay.png`, plus the gridded version. Look at it, or have Claude look at it, and fix the JSON by hand. For version 1 this is the entire editor.

### Step 5. Build geometry

Coordinate rule, stated once. Build everything in a Z-up frame where the plan lies on the XY plane, y flipped from the image (`y_plan_up = -y_image`) and height is +Z. This is what `trimesh.creation.extrude_polygon` produces. Before export, apply one fixed rotation: plan x to glTF x, plan y to glTF -z, height to glTF y. In trimesh: rotate by -90 degrees about the x axis (`trimesh.transformations.rotation_matrix(-np.pi/2, [1,0,0])`) and verify with the test below. Do not rotate anywhere else.

1. **Wall footprints with corner extension.** Each wall is a rectangle `LineString.buffer(t/2, cap_style='flat')`. A flat cap leaves a t/2 by t/2 notch at every L-corner, so extend ends before buffering:
   - At an endpoint shared with another wall's endpoint (L-corner), extend this wall along its own direction by half the thickness of the other wall. Both walls do this, so the corner square is filled for equal or different thicknesses.
   - At a T-junction (endpoint on another wall's interior), snap the endpoint onto the through wall's centreline and extend by 0. The overlap fills the join.
   - Free ends stay flat.
   Snap endpoints to a 5 cm grid before this step so junctions are detected with a tolerance of 5 cm.
2. Union all footprints into one polygon (`shapely.ops.unary_union`).
3. **Rooms (net floor):** take a bounding polygon around the whole plan (the union's envelope, slightly grown), subtract the wall union, and keep the interior pieces that do not touch the outside. Each piece is a room net of wall thickness. Drop slivers under 1 m2. A label point inside a piece names it. Open-plan areas missing a wall get a virtual `"kind": "boundary"` segment of zero height.
4. **Openings without 3D booleans.** Keep wall identity by building each opening from its own wall's frame before extruding:
   - Valid interval for an opening on wall `w`: from `da` to `L - db`, where `da` and `db` are the half-thicknesses of the walls meeting at each end (0 at a free end) plus a 10 cm margin. An opening outside it is flagged and not built.
   - For each opening make a rectangle in the wall's frame: `offset` to `offset + width` along the wall, thickness equal to the wall's own thickness, intersected with the wall union.
   - Main wall solid: extrude (wall union minus all opening rectangles) from 0 to `wall_height`.
   - For each opening add back the lintel, extrude (rectangle) from `sill + height` to `wall_height`, and, if `sill` is above 0, the sill piece, extrude (rectangle) from 0 to `sill`.
   - Because this is all 2D polygon work, no `manifold3d` is needed. The pieces share faces, which is invisible in the viewer. If a watertight single mesh is required later, union the pieces with `manifold3d`.
5. Optional: door leaf and window glass as thin boxes at each opening. Ceiling off by default so top views work.
6. **Floors:** extrude each net room polygon downward 0.1 m, and put a floor slab under the wall footprint too so doorways have no holes.
7. Materials by name (`wall`, `floor_tile`, `floor_wood`, `glass`, `door`) with simple PBR colours from `materials.json`.

Tests for this step (in `tests/`):
- Rotation: load the exported GLB and assert that the bounding box height (glTF y extent) equals `wall_height` within 1 cm, and the plan footprint matches width and depth in x and z.
- Corners: for a closed rectangular room with centreline sides W and D and thickness t, the wall-union area equals `(W+t)(D+t) - (W-t)(D-t)` within 1e-6 (no notches, no overshoot).
- Openings: a window at the minimum valid offset next to a corner leaves the adjoining wall's face untouched (the footprint area of the main wall solid changes only by the opening rectangle).

### Step 6. Export
- `model.glb` is the main output (compact, materials, loads in three.js, Blender, most viewers).
- `plan.json` is the editable source of truth. Keep it with the model.
- Later: `.obj` via `trimesh`, `.blend` by building in Blender, `.ifc` only if BIM tooling is needed.

### Step 7. Preview and screenshots
- Pin and vendor three.js so the import graph resolves. In a scratch folder run `npm pack three@0.160.0`, unpack, and copy the `build/` folder and the whole `examples/jsm/` folder (or at least `loaders/`, `controls/`, `utils/`) into `web/vendor/three/`, keeping their relative paths. Version 0.160.0 predates the `three.core.js` split, so `build/three.module.js` is self-contained. Do not copy single files flat, because `GLTFLoader.js` imports `../utils/BufferGeometryUtils.js`.
- `viewer.html` uses an import map:
  `{"imports": {"three": "./vendor/three/build/three.module.js", "three/addons/": "./vendor/three/examples/jsm/"}}`
  and imports `GLTFLoader` and `OrbitControls` from `three/addons/...`. It loads `model.glb`, and sets `window.ready = true` after the model is added and one frame is rendered.
- If you ever upgrade three.js past r171, also copy `build/three.core.js` and re-run the console test below.
- File URLs do not work, because Chromium blocks `fetch` of the GLB from `file://`. `shot.py` starts `python -m http.server 8123` in the output folder (as a subprocess, killed at the end) and opens `http://localhost:8123/viewer.html`.
- Playwright launches Chromium with `--use-gl=angle --use-angle=swiftshader --ignore-gpu-blocklist` (no GPU). It records every network response and console message, fails at once on any 404 or console error, and otherwise waits for `window.ready` with a 60 second timeout that prints the browser console.
- Three shots: `top.png` (orthographic, from above), `iso.png` (isometric, ceiling hidden), `eye.png` (1.6 m eye height inside the largest room, field of view 70 degrees).

### Step 8. Photoreal renders (version 2, optional)
- Only if Preflight found Blender. Run `blender -b -P render.py`: import `model.glb`, sun or sky plus one area light per room, EEVEE for speed or Cycles with low samples and denoise (CPU only).
- Walkthrough: a camera path through room centroids, frames joined with `ffmpeg`.
- Without Blender: raise the three.js quality (shadow maps, SSAO, tone mapping) and keep the Playwright shots.

## Getting each element right

**Walls.** Take thickness from the plan where possible (stroke width or pair gap after scaling) and snap to a standard value (0.1, 0.115, 0.15, 0.2, 0.23 m). Snap endpoints to a 5 cm grid, apply the corner extension rule, then union before extruding.

**Openings.** Place by wall and offset inside the valid interval. Take sizes from a door or window schedule if the plan has one, else defaults. Swing arcs give hinge side.

**Floors and rooms.** Net polygons (wall-complement), so areas match printed room areas.

**Materials.** Flat colours by room type first (wet rooms tile, living areas wood). Free CC0 PBR textures from Poly Haven later.

**Lighting.** Viewer: hemisphere light, one shadow-casting directional light. Blender: sky plus sun, one area light per room. Windows are real holes, so daylight enters.

**Furniture.** Leave it out of version 1. Furniture symbols are the main source of false walls, so filtering them out is the goal.

## Accuracy checks (automatic, with thresholds)

1. Net room areas versus printed room areas (or a printed total area): each within 5 percent. Areas are net, so centreline math is never used. Worked check: a 3.0 x 4.0 m room with 0.115 m walls gives 12.0 m2 net, not 12.8.
2. Each printed dimension in `dims`, versus the built geometry measured on its stated basis within 2 percent: `inside` is the face-to-face distance between the two named walls, `outside` is the outer extent of the wall union along that axis, `centre` is the centreline spacing. Example: a 3.00 m inside-width room between 0.23 m walls has centreline spacing 3.23 m and passes as `inside`. The same dimension tested as centreline would fail by 7.7 percent, which is why basis is mandatory.
3. Walls form closed loops: no dangling end longer than one wall thickness except deliberate boundary segments.
4. Every opening lies within its wall's valid interval: at least 10 cm of wall clear on each side, measured from the faces of the adjoining walls, not the centreline ends. A window at offset 0.10 on a 0.23 m wall that ends in a corner fails.
5. Door width 0.6 to 1.2 m, window width 0.3 to 3 m. Anything else is flagged.
6. Orientation test: GLB height equals `wall_height` within 1 cm.
7. Corner area test (Step 5) passes on the synthetic rectangle.
8. Viewer test: no 404 and no console error while loading.
9. The overlay is viewed by a person or a vision model before the build is trusted.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Wrong or missing scale | Whole model the wrong size. | Two manual pairs on different axes, agreement within 2 percent, stop on mismatch. |
| Mixed or wrong wall styles | Zero or phantom walls. | Run all detectors, tag each wall by source, merge, colour by source in the overlay, prune by hand. Single-line is opt-in. |
| Thickness unknown at the start | Wrong kernel, closed doorways, filled closets. | Scale first so thickness is a bounded pixel range. Style B uses LSD plus pairing, no closing kernel. |
| Furniture, hatching, text, stairs, columns read as walls | Phantom walls. | Width, colour and shape filters, text-box subtraction, compact-blob rule for columns, area-to-perimeter filter, review overlay, `--ignore-box`. |
| One merged CAD polygon for all walls | One wrong wall. | Non-rectangular fills are rasterized and skeletonized, never given a single long axis. |
| Hand sketches, photos, skewed scans | Detection collapses. | Deskew and perspective-correct. If that fails, use the dimension-transcription path. |
| Curved or diagonal walls | Snap to orthogonal breaks them. | Version 1 straight walls only. Keep a diagonal only if the angle is stable, otherwise flag. |
| Open-plan areas without walls | Rooms fail to close. | Virtual `"kind": "boundary"` segments of zero height. |
| Corner notches from flat-capped walls | Missing wedges at outer corners. | End extension rule plus exact area test. |
| Openings near corners | Notch in the adjoining wall. | Valid interval measured to the adjoining wall's face, per-wall 2D construction. |
| Printed dimension compared to the wrong basis | False failures on correct plans, or correct walls moved. | `dims` carries basis, and the check measures on that basis. |
| Z-up GLB loaded as Y-up | Building lies on its side. | One fixed rotation, plus the height test. |
| three.js import graph broken | Viewer and all screenshots fail. | Pin 0.160.0, keep directory structure, import map, fail on any 404. |
| Viewer fetch fails on `file://`, CDN blocked | Screenshots hang. | Local HTTP server, vendored three.js, console dump on timeout. |
| Imperial strings misread by OCR | Silent factor errors. | Strict regex, reject unparseable, cross-check. |
| Multi-storey sheets, sections, elevations on one page | Mixed content. | Crop to one plan. |
| AI image generators used for geometry | They invent walls and move doors. | Use only for styled renders, checked against the overlay. |
| Plan privacy | A client's drawing leaves the machine. | Keep detection local. Tell the user before sending a plan to any external API. |

## Minimal first version (build this today)

Goal: one command takes a plan image or PDF plus a manual scale and a `plan.json` and writes a GLB and three screenshots. Everything not automated is manual and said so in the report. No OCR, no Blender, no CDN.

Order of work. Times are for a developer with the packages installed, and each step has a pass check.

1. **Preflight and a sample plan (20 min).** Run the Preflight. Make a test plan with a small script that draws a two-room flat as a double-line image and as a solid-fill image (a known-truth source for both styles), and hand-write its `plan.json`.
2. **Generator (2 to 3 hours).** `build.py plan.json -> model.glb` with corner extension, union, net rooms, 2D opening construction, the rotation, and the tests (orientation, corner area, opening interval). Pass: the area check on the sample is within 1 percent and all tests pass.
3. **Viewer and shots (1 to 1.5 hours).** Pinned and vendored three.js, local server, `shot.py` with the 404 check. Pass: three PNGs, no console errors, and `top.png` shows the plan from above, not a side elevation.
4. **Manual scale and grid helper (45 min).** `grid.py` plus `--scale-from`, two pairs, 2 percent agreement. Pass: wrong input is refused.
5. **Overlay (45 min).** Draw `plan.json` on the image, with and without grid.

Subtotal for steps 1 to 5: about 5 to 6.5 hours. This is the usable core, because it already turns a hand-written or transcribed `plan.json` into a model and checks it against the image.

**Fast path to a real model from a real plan (no detector):** Claude does not read pixel coordinates here. Instead, Claude reads the printed dimensions and room labels from the plan image and writes `plan.json` directly in metres: a rectangle of outer walls from the overall dimensions, interior walls placed from the printed room dimensions (using `dims` with their basis), and each door and window by wall and offset from its printed or visible position (offset read as "metres from the nearer corner", judged against the printed dimension chain). No scale step is needed for this, because the numbers are already metres. The overlay (Step 4) is then drawn with the scale from `--scale-from`, and Claude and the user fix mismatches by editing the JSON, using `overlay_grid.png` only to locate which wall is off, never to measure. For a typical one-storey flat this takes minutes per iteration once steps 1 to 5 exist, and gives a correct, editable model the same day.

6. **Wall detector (3 to 5 hours, after the fast path works).** Vector path if the input is a PDF with vectors, raster path otherwise, with all detectors and merging as in Step 3. Output `plan.json` with walls only. Pass: on the synthetic double-line and solid-fill samples every wall is found, with endpoints within 5 cm after scaling and no phantom walls.
7. **Openings (2 to 3 hours).** Gap detection, door by swing arc, window by parallel lines, or set `type` by hand in the JSON. Pass: all openings on the samples are found, widths within 10 cm.
8. **Report (30 min).** Print the scale, detector counts, the counts and the checks.

Total with the detector: about 11 to 15 hours of focused work. The useful result, a working model from a real plan with a human-in-the-loop JSON, is available after about 5 to 6.5 hours.

## Decision summary

- JSON plan as the contract between reading and building. Build the generator first.
- Vector extraction first for PDFs, with decomposition of merged fills. Raster CV for scans, using LSD plus pairing for double lines and erosion for solid fills, all detectors merged and tagged.
- Manual two-point scale in version 1, verified on two axes, with a grid helper. OCR scale later.
- Claude transcribes printed dimensions in metres for the fast path and never measures pixels.
- `shapely` and `trimesh`, corner-extended walls, per-wall 2D opening construction, one explicit Z-up to Y-up rotation, net room polygons, GLB output.
- three.js pinned to 0.160.0, vendored with its directory structure, served over HTTP, Playwright with software GL for shots.
- Blender and OCR are optional and gated by the preflight.
- Always show the overlay before trusting a build.
