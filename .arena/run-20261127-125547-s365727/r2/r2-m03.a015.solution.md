# Turning a 2D floor plan into a 3D model: build plan

## 1. Recommendation in one paragraph

Do not make an AI image generator, or a live Blender session, the core of the system. Make the core a deterministic geometry pipeline around one reviewable intermediate file, `plan.json`. The pipeline is: raster or PDF in, vectorised walls, openings and rooms with a calibrated scale, human-confirmed, then built into a 3D model (named per-wall meshes plus one merged watertight solid), then rendered. A floor plan is a measurement document, and generators invent walls. Pixel-to-geometry code can be checked against the drawing. Blender and AI renderers are optional back ends that read `plan.json` or the GLB and are never the source of truth.

The contrarian sequencing choice: build the back end first (plan.json to GLB to render), because it is deterministic and gives the user something visible on day one. Detection (the hard, failure-prone part) comes second and may be partly done by Claude reading a gridded image, with a mandatory review.

## 2. The obvious answer, and why most of it does not survive

| Obvious default | Argument against | What I keep |
|---|---|---|
| Feed the plan to an image generator ("make this a 3D render") | It redraws instead of measuring. It moves walls, invents furniture and text, and gives a picture with no model, no dimensions and no editability. | Only as a final optional "beauty pass" over a clay render made from the real geometry, with the geometry as control image. Never as the model. |
| Drive Blender through MCP | The MCP add-on needs a live Blender GUI on localhost:9876. The cloud container has none. It is also slow for hundreds of simple prisms. | Headless Blender (`blender -b -P script.py`, preferred over pip `bpy`) as an optional stage for Cycles renders and `.blend`. Blender MCP only if the user has desktop Blender attached. |
| Train a wall-segmentation network (CubiCasa5k style) | Large effort, needs GPU and data, still fails on unusual drawings. | Not in v1. A pluggable `detector` interface lets a pretrained model be swapped in later for messy scans. |
| OCR the dimension strings to get scale | OCR gets dimension text wrong most often (`12'-6"`, `3.25`, rotated text, `l` vs `1`), and one wrong digit silently scales the whole house. | For vector PDFs, read the text layer directly (exact, no OCR). For images, OCR only suggests. Scale is confirmed by a visible two-point calibration and cross-checked against a held-out second dimension. |
| Full automation | A fully automatic result looks done and is silently wrong. | Automatic first draft, quick correction, then build. Review is a feature. |
| three.js vs Blender as either-or | Each is better at something. | three.js (Chromium already installed) for viewer and quick renders, `trimesh` + `manifold3d` for the geometry, Blender headless for photoreal stills and video. All fed from the same JSON. |
| "Vector PDF means detection is easy" | CAD PDFs mix walls with furniture, grids and dimensions, and walls are usually pairs of lines. | Vector input gives exact coordinates, exact text and style filtering. Deciding what is a wall still needs a method (Stage 3, vector route). |
| "A verify overlay proves the model is right" | An overlay drawn with the same scale used to build the model always lines up, even if the scale is wrong. | Verify checks only detection fit. Scale is checked separately (stage 9b). |
| "Stop if the check dimension disagrees" | The plan may be stretched, not to scale, or have different x and y scale. Stopping leaves the user with nothing. | A decision table (Stage 2) that falls back to per-axis scale or an honest "unverified" model, never a dead end. |

## 3. Assumptions

1. Input is a single-storey floor plan as PNG/JPG/scan or PDF, ideally with some printed dimensions. Multi-storey is an extension (the schema has `levels`).
2. The plan is drawn to scale or has at least one reliable dimension. If it is stretched or not to scale, Stage 2 detects that and degrades to per-axis scale or an `unverified` model with the errors listed.
3. Walls are thick filled bands, outlined double lines, or hatched bands (all normal for architect drawings). Single-line sketches get a default thickness.
4. Default heights: wall 2.7 m, door 2.05 m, window sill 0.9 m, head 2.1 m. Editable.
5. "3D model" means a viewable, exportable model (GLB, optional OBJ/STL/`.blend`) plus renders. IFC/BIM is an extension.
6. Runtime is the Claude Code cloud container: Linux, Python, Node, Chromium and Playwright. No GPU, no desktop Blender. Packages come from pip, npm and apt (apt availability depends on the environment's network settings; if apt is blocked, skip OCR and Blender).
7. The user knows the building, so ambiguous items can be resolved in minutes.
8. The plan is private. Processing is local; nothing is uploaded to third-party services without the user's say.

## 4. Architecture

```
input.pdf / .png / .jpg
        |
 [1 Ingest]         Rasterise (250 DPI) and straighten. Vector PDF: also dump raw vectors + text words.
        |            Writes page.png (full drawing incl. dimensions), grid.png, ingest.json, vectors.json
 [2 Calibrate]      px_per_m (or per axis) from user-confirmed lengths; a second length is held out
        |
 [3 Detect]         walls, openings, rooms in plan space (raster or vector route, same pair-matcher)
        |
 [4 plan.json]      the single source of truth, human-readable, versioned
        |
 [5 Review]         overlay.png (and optional HTML editor); user or Claude fixes plan.json
        |
 [6 Build]          disjoint per-wall meshes (named, materialled) + one merged watertight solid; floors
        |
 [7 Export]         model.glb (named nodes, Y-up), model_solid.stl/.glb (merged), optional obj/.blend
        |
 [8 Render]         three.js via Playwright (default), Blender headless Cycles (optional)
        |
 [9 Verify]         (a) detection fit vs source ink, (b) scale check by held-out dimension and priors
```

Every stage reads and writes plain files, so each can be tested alone, retried or replaced. No detection happens before calibration is possible: Ingest only extracts, Detect interprets.

### 4.1 Coordinate conventions (decided once, because mixing them breaks renders)

- Image pixels: origin top-left, y down. All pixel coordinates the user or tool handles live in the single frame stored in `ingest.json` (the output pixel grid of `page.png`). Straightening and any crop are applied once during ingest, and the transform is stored, so coordinates read from `grid.png` are always valid.
- `plan.json`: metres, x right, **y up** (`y_m = (H_px - y_px) / px_per_m`). This is the Z-up convention of the build step, with plan y as the world's horizontal axis.
- Build: Z-up (walls extrude along +Z).
- GLB export: glTF and three.js are Y-up and `trimesh` does not convert. Apply one proper rotation of -90 degrees about X when exporting, mapping (x, y, z) to (x, z, -y). This is a rotation, not a flip, so the plan is not mirrored. A test checks the exported bounds have the wall height on Y.

### 4.2 `plan.json` schema (the contract)

```json
{
  "version": 1,
  "units": "m",
  "scale": {"mode": "isotropic", "px_per_m": 94.2, "px_per_m_x": 94.2, "px_per_m_y": 94.2,
            "source": "user_calibration",
            "ref": {"px": [[102,88],[1034,88]], "m": 9.9, "kind": "outer_face"},
            "check": {"px": [[130,500],[570,500]], "m": 4.7, "kind": "face_clear", "error_pct": 0.6}},
  "defaults": {"wall_h": 2.7, "wall_t": 0.15, "door_h": 2.05, "sill_h": 0.9, "head_h": 2.1},
  "levels": [{
    "name": "ground", "elevation": 0.0,
    "walls": [{"id":"w1","a":[0,0],"b":[6.2,0],"t":0.2,"h":2.7,"kind":"exterior"}],
    "openings": [
      {"id":"o1","wall":"w1","type":"door","offset":1.1,"width":0.9,"h":2.05,"sill":0,"swing":"in-left"},
      {"id":"o2","wall":"w1","type":"window","offset":3.4,"width":1.5,"h":1.2,"sill":0.9}
    ],
    "rooms": [{"id":"r1","label":"Kitchen","polygon":[[0,0],[4,0],[4,3],[0,3]],"floor":"tile"}]
  }],
  "confidence": {"w1": 0.97, "o2": 0.6},
  "scale_status": "verified | unverified | estimated | per_axis"
}
```

Walls are centre-line segments with thickness, so openings and joins are simple and edits are one-line. Printed dimensions, however, are usually face to face (see Stage 2), so every reference carries a `kind` and the code converts. Every detected item carries a confidence so review can start with the weakest.

## 6. Step-by-step pipeline

### Stage 1: Ingest (extract only, no interpretation)

**1a. Raster (PNG/JPG/scan, or PDF rasterised at 250 DPI).**
1. Crop only the sheet margin and, if recognisable, the title block (a large text-dense rectangle touching the sheet edge). **Do not crop to the wall envelope and do not keep only the largest connected region**: dimension chains, extension lines and dimension text sit outside the walls and are separate components, and calibration needs them. The wall-bounding box is computed later and used only as a detection region of interest (ROI), never to produce `page.png`.
2. Rotation: estimate the dominant line angle (Hough) and rotate to axis-aligned. A flatbed scan rotated by any angle is simply corrected, silently.
3. Perspective is a different problem and is tested separately, after the rotation fix: collect near-axis lines and measure the spread of their angles (spread above about 1.5 degrees means non-parallel walls) and check whether opposite outer edges are parallel. If perspective is likely (typical of phone photos), ask for the four corners of a known rectangle and apply a homography, or refuse and say why.
4. Binarise: Otsu for clean drawings, adaptive threshold for scans.
5. Write `page.png` (the full drawing including dimensions), `ingest.json` (all transforms) and `grid.png`: the same image with a labelled grid every 100 px, so that coordinates for calibration, review and Claude-assisted tracing can be read off by eye instead of guessed.

**1b. Vector PDF: extract, do not interpret.** Dump `get_drawings()` to `vectors.json` (each path: points or Bezier control points, stroke colour, width, fill, layer if present) and `get_text("words")` to `texts.json` (string, bounding box, rotation). Also write `page.png` and `grid.png` by rasterisation, so every later stage shares one pixel frame (vector coordinates convert with the stored page-to-pixel matrix). Inventory only: group paths by (layer, stroke colour, stroke width, fill colour) and write `vector_groups.png`, a contact sheet with one thumbnail per group, so Claude or the user can see what each group is. Scale-dependent decisions (the wall band, pairing) are deferred to Stage 3. This keeps Ingest testable without calibration.

### Stage 2: Calibrate scale (the step that decides accuracy)

**What a printed dimension measures.** Plans print clear room dimensions (inner face to inner face) and overall dimensions (outer face to outer face). The model stores centre lines. A printed 3.00 m clear width between 0.20 m walls is 3.20 m centre to centre, and an overall 9.9 m outer dimension differs from the centre-line span by one wall thickness. Mixing these makes a correct model fail a 2 percent gate or a wrong one pass. Rules:
- Every reference has a `kind`: `face_clear`, `outer_face`, or `centreline` (only if the drawing dimensions to centre lines, common in structural plans).
- Click points snap to the nearest wall **face** edge (ink boundary) within 6 px, not to a line end or centre line. The tool prints exactly which edge it took ("snapped to inner face of wall at x=412 px") and the user can reject it. Preferably the reference follows the printed dimension's own extension lines or arrow ends, which already sit on the intended faces.
- Scale from a face-snapped pair is simply px distance divided by the printed length, with no thickness conversion. The `kind` matters for the check: after building, the held-out dimension is measured on the model in the same sense (face to face on the wall footprints, not centre to centre) before comparing.
- Tolerance is the larger of 2 percent and two pixels expressed in metres, plus half the printed rounding step (a "3.0" printed to the nearest 0.1 m).

Priority order for the reference source:
1. Two-point: the user (or Claude from `grid.png`) gives two points and the true length. Command: `calibrate --ref x1,y1,x2,y2 --len 9.9 --ref-kind outer_face`, coordinates in the ingest pixel frame read from `grid.png`. An optional tiny click-to-pick HTML page does the same where the user has a browser.
2. Vector PDF: take dimension strings from `texts.json` (exact, no OCR), pair each with its nearest dimension line or extension-line ends in `vectors.json`, and propose reference pairs with confidence. The user confirms.
3. A drawn scale bar: its two ends and its stated length.
4. A stated scale ("1:100") plus the source DPI. Valid only for original-size prints or PDFs. Warn that photos and screenshots break it.
5. OCR-suggested dimensions on images: detect strings like `3.20`, `10'-4"`, `4200`, pair them with dimension lines and propose a scale. Require two independent dimensions that agree within tolerance, otherwise ask.
6. Fallback: assume a standard door is 0.9 m (3 ft), set `scale_status: "estimated"` and print "scale estimated" on every render.

**Held-out check and what happens when it fails (a decision table, not a stop).** Ask for a second known length on the other axis if possible (`--check x1,y1,x2,y2 --len 4.7 --check-kind face_clear`).

| Observation | Action |
|---|---|
| One reference only | `scale_status: "unverified"`; plausibility priors (9b) decide whether to warn. |
| Check agrees within tolerance | `scale_status: "verified"`. |
| Reference on x and check on y (or vice versa) disagree, and a second check on each axis is internally consistent | Plan is stretched. Store `px_per_m_x` and `px_per_m_y`, `mode: "per_axis"`, `scale_status: "per_axis"`, and report both factors. Pixel coordinates are divided by the matching axis scale. |
| Disagreement within one axis, or several dimensions disagree in no pattern | Plan is not drawn to scale (typical of brochure plans). Build at the best-fit scale (least squares over all confirmed dimensions), set `scale_status: "unverified"`, list every dimension with its error in `report.md`, and stamp "not to scale: dimensions approximate" on renders. The user may continue or abort. A v2 mode solves wall coordinates from the printed dimensions by least squares so printed numbers win over pixels. |
| The user wants to proceed anyway | Always allowed. The pipeline never halts on its own. |

### Stage 3: Detect (the hard part; works in pixels first, metres second)

All detection derives its thickness band from the drawing itself, in pixels, so it does not need scale. After calibration the band is only sanity-checked against 0.08 to 0.4 m.

**3.0 Wall style.** `--wall-style auto|solid|double|hatched`. Autodetect: compute the distance transform of the ink and the histogram of perpendicular distances between overlapping parallel LSD segments. If the ink contains many thick bands (distance-transform ridge height consistent over long runs) it is `solid`. If there are many long, thin parallel pairs with a repeating gap and white between them, it is `double`. If the band interior has regular diagonal strokes, it is `hatched`. The chosen style and the evidence are printed, and the user can override.

**3.1 Solid bands.** Skeletonise the ink; at each skeleton pixel read the distance transform. Take the mode of 2 x that value over long straight runs as `wall_t_px`. The wall band is 0.6 to 1.5 times the mode; keep ink regions whose local thickness falls in the band, drop text, thin dimension lines and blobs under an area threshold.

**3.2 Outlined double lines (the common case).** Each line alone is far below any wall band, so a thickness filter would delete every wall. Instead run the pair-matcher, which is the same code for raster and vector inputs:
1. Get segments: LSD or probabilistic Hough on the raster, or straight segments from `vectors.json`.
2. For every axis-aligned (or common-angle) segment, find parallel segments with at least 50 percent overlap along the axis and perpendicular distance d. Histogram all d values in pixels. The strongest peak between about 3 and 60 px (the real wall thickness, because outlines repeat at one gap while stray line pairs do not) is `wall_t_px`; accept pairs within 0.6 to 1.5 times it.
3. Each accepted pair becomes a centre line with thickness equal to the gap, and the space between is filled as the wall footprint. Closed filled dark polygons (poche) are taken directly and fitted by minimum rotated rectangle or skeleton.
4. In a vector PDF, restrict the segments to the wall style groups the user or the heuristic picked from `vector_groups.png` (`--walls-groups 3,5`; the default heuristic is the group with the most long axis-aligned segments that form parallel pairs). If groups cannot be separated, rasterise only the selected groups and run the raster route on that clean image.

**3.3 Hatched walls.** Morphologically close along the hatch direction with a kernel slightly larger than the hatch spacing, then treat the result as solid bands (3.1).

**3.4 Common steps.** Skeletonise or take pair centre lines, merge collinear pieces, snap endpoints into T/L/X junctions within about half a wall thickness, snap to orthogonal within about 3 degrees, cluster measured thicknesses into two or three classes (exterior, interior, partition) because per-wall thickness is noisy.

**3.5 Openings.**
- Doors: `get_drawings()` returns arcs as Bezier curve items. Fit a circle from the endpoints and mid-point, accept a roughly 90 degree arc whose radius matches an adjacent straight segment (the door leaf), and record door width = radius and hinge side from the leaf position. On rasters, find the arc by Hough circle on the ROI.
- Windows: three or more thin parallel lines spanning a gap in a wall pair.
- Neither: classify as "opening, type unknown".
- Measure width and offset along the wall in metres.

**3.6 Rooms and labels.** Polygonise; attach text (vector text layer, else OCR) positions inside each polygon.

**3.7 Discard.** Furniture, stairs (a flagged region only in v1), dimension lines, hatch patterns outside walls.

**Claude-assisted alternative (also the v0 detector):** Claude views `grid.png` and writes a draft `plan.json` by tracing; the overlay and review stage then show how far off it is. Reading coordinates by eye is imprecise (a few pixels at best), so snap to the wall mask and treat this as a first draft only.

### Stage 4 and 5: Write `plan.json` and review
Render `overlay.png`: the original plan with detected walls in red, openings in blue and green, low-confidence items dashed. In Claude Code, Claude can look at the image and report problems. For a human, an optional HTML editor (canvas plus drag handles) moves endpoints, deletes or adds walls, changes an opening's type and width, and sets room materials. Walk through the low-confidence list first.

### Stage 6: Build the geometry (tested code)
Rules that avoid the usual failures:
- Each opening is cut only from its own wall's footprint, with a rectangle of exactly the opening width. It is never subtracted from the union of all walls, which would notch neighbouring walls at T-junctions and corners.
- Per-wall height `h` and per-opening `sill` and `h` are used. A door is the opening with sill 0.
- Wall ends that touch another wall are extended by **half the neighbour's thickness**, not the wall's own, so L-corners close exactly at the outer face of the other wall even when thicknesses differ (0.30 m exterior against 0.10 m partition). Free ends are not extended.
- Footprints are made disjoint by priority (each wall minus the footprints of walls earlier in the list; sort exterior first). This keeps one clean named mesh per wall with no overlapping or coplanar faces, so no z-fighting in the viewer and per-wall materials work.
- A second, merged solid is built with `manifold3d` from the per-wall pieces, used for the watertight test and for STL/printing.

```python
import numpy as np, trimesh
from shapely.geometry import LineString, Point, Polygon

def prism(poly, z0, z1):                       # extrude a (Multi)Polygon from z0 to z1, Z-up
    if poly.is_empty or z1 - z0 < 1e-6: return []
    out = []
    for g in (poly.geoms if hasattr(poly, "geoms") else [poly]):
        if g.area < 1e-8: continue
        m = trimesh.creation.extrude_polygon(g, height=z1 - z0)
        m.apply_translation([0, 0, z0]); out.append(m)
    return out

def touching_t(p, w, walls, tol=1e-3):         # thickness of the thickest OTHER wall that p touches
    ts = [o["t"] for o in walls if o is not w and
          LineString([o["a"], o["b"]]).distance(Point(p)) <= o["t"] / 2 + tol]
    return max(ts) if ts else 0.0

def wall_footprint(w, walls):
    a, b = np.array(w["a"], float), np.array(w["b"], float)
    d = (b - a) / np.linalg.norm(b - a)
    a2 = a - d * touching_t(a, w, walls) / 2   # extend by the NEIGHBOUR's half thickness
    b2 = b + d * touching_t(b, w, walls) / 2
    return LineString([a2, b2]).buffer(w["t"] / 2, cap_style=2)

def opening_rect(w, o):                        # exactly o["width"] wide, across this wall only
    a, b = np.array(w["a"], float), np.array(w["b"], float)
    d = (b - a) / np.linalg.norm(b - a); n = np.array([-d[1], d[0]]); h = w["t"] / 2 + 0.01
    p0, p1 = a + d * o["offset"], a + d * (o["offset"] + o["width"])
    return Polygon([p0 - n*h, p1 - n*h, p1 + n*h, p0 + n*h])

def build_walls(level, H=2.7):
    walls, taken, per_wall = level["walls"], Polygon(), {}
    for w in walls:                            # walls sorted exterior first; footprints made disjoint
        full = wall_footprint(w, walls)
        fp = full.difference(taken); taken = taken.union(full)
        cuts = [opening_rect(w, o).intersection(fp) for o in level["openings"] if o["wall"] == w["id"]]
        ops = [o for o in level["openings"] if o["wall"] == w["id"]]
        body = fp
        for c in cuts: body = body.difference(c)
        wh = w.get("h", H); parts = prism(body, 0, wh)
        for c, o in zip(cuts, ops):
            parts += prism(c, o["sill"] + o["h"], wh)               # lintel / above window
            if o["sill"] > 0: parts += prism(c, 0, o["sill"])       # below window
        if parts: per_wall[w["id"]] = trimesh.util.concatenate(parts)
    solid = trimesh.boolean.union(list(per_wall.values()), engine="manifold")  # merged, watertight
    return per_wall, solid

def to_gltf_yup(mesh):                          # Z-up plan space -> glTF Y-up, a proper rotation (no mirroring)
    m = mesh.copy()
    m.apply_transform(trimesh.transformations.rotation_matrix(-np.pi / 2, [1, 0, 0]))
    return m
```

This code was run. Test A, L corner with a 0.30 m wall along x and a 0.10 m wall along y meeting at (0,0): merged bounds start at x = -0.05 (the thin wall's true outer face, no protruding stub), the solid is watertight, and the sum of per-wall volumes equals the merged volume (5.13), proving the footprints are disjoint. Test B, 6 m by 4 m room with an interior T-wall (0.10 m) and a door in the opposite wall beside the T-junction: watertight, per-wall volumes sum to the merged volume (11.457), bounds height 2.7 on Z and the T-wall intact. Run both as the first unit tests, plus the Y-up bounds test after `to_gltf_yup`.

Remaining build steps:
1. Floors: one slab per room polygon, 0.1 m thick, with the room's material. Fill any area inside the outer walls not covered by a room (corridors). Floors stay separate meshes in the GLB so materials differ.
2. Ceiling: optional, off by default so top-down views work; the viewer has a roof toggle.
3. Door leaves (thin boxes, open 90 degrees using the swing hint), window frames (four thin bars), glass (a transparent plane, alpha 0.25). All simple primitives.
4. Naming and materials: each GLB node is named by id (`wall_w1`, `door_o1`, `floor_r1`) and carries a material by `kind` (exterior and interior walls get different materials). Renders and the viewer use `model.glb`, which holds these separate nodes. `model_solid.glb`/`.stl` is the merged solid and is for the watertight test and 3D printing only.
5. UVs for textures: `extrude_polygon` produces none. For textured walls and floors, unmerge vertices and assign box-projected UVs per face (pick the dominant normal axis, use the other two coordinates in metres divided by the texture tile size). Skip in v0; v1 uses flat PBR colours.

### Stage 7: Export
- `model.glb` (required, Y-up, named per-wall, per-opening and per-floor nodes with materials), `model_solid.stl` and `model_solid.glb` (merged, scale-correct, for printing and the watertight check), optional `model.obj`/`.mtl`, `model.blend` if Blender is available.
- `plan.json` (editable source), `overlay.png` and `verify.png` (audit trail).

### Stage 8: Render
Default, always works: Playwright opens `viewer.html?model=model.glb&view=...` and saves:
- `top_down.png` (orthographic, roof off, rooms labelled)
- `iso_cutaway.png` (orthographic 35 degrees, ceiling hidden)
- `eye_level_<room>.png` (perspective, 1.6 m eye height, 70 degree field of view)
- `walkthrough.mp4` (optional: a path through room centres, frames captured with Playwright then `ffmpeg`)

Lighting: a hemisphere light for ambient fill, one directional sun with soft shadows (PCFSoft or VSM, 2048 map), `ACESFilmic` tone mapping, sRGB output, `RoomEnvironment` for reflections, and a point light per room at 2.3 m scaled by area. Keep ambient high enough that a closed room never renders black.

Materials: a table maps `floor` and `wall` tags (and wall `kind`) to simple PBR values (white walls roughness 0.9; oak or tile floors by room label, wet rooms from labels else wood; glass with alpha), with optional tileable textures using the UVs above. Appearance only, never geometry.

Photoreal (optional): import the GLB in headless Blender, Principled BSDF materials, a sun lamp plus an area light per room, Cycles 64 to 128 samples with denoise at 1600 px wide. Expect minutes per image on CPU.

### Stage 9: Verify (two separate checks, because they catch different errors)

**9a. Detection fit (does the model match the drawing's linework?).** Rasterise the model's wall footprints into the ingest pixel frame and compare with the source wall mask: report the fraction of source wall ink covered, and of model area that has no ink under it, and write `verify.png`. Flag anything off by more than half a wall thickness. This checks detection and editing mistakes only. It cannot detect a wrong scale, because the model and the image share the same px_per_m.

**9b. Scale check (is the size right?).**
1. Held-out dimension from stage 2, measured on the built model in the same sense as the printed one (face to face, or outer to outer, or centre to centre). If within tolerance, scale is "verified".
2. If none, plausibility priors against the built model: median door width should be 0.7 to 1.1 m, wall thickness 0.1 to 0.3 m, bedrooms 7 to 20 m2, and the overall footprint of a dwelling in a plausible range. Failing a prior sets `scale_status: "unverified"` with the reason in `report.md`.
3. Where text is available (vector text layer or OCR), compare printed room areas and dimension strings to the model ("kitchen 4.2 m on plan, 4.18 m in model"). Disagreement is reported, not auto-corrected.
4. Stamp the scale status on every render.

**9c. Structural failures (fail loudly).** Unclosed room polygons, zero-width walls, openings wider than their wall, overlapping openings, more than one disconnected exterior shell, and a merged solid that is not watertight per `manifold3d`/`trimesh` (test the merged solid, not the pieces).

## 7. How accuracy is achieved

- Walls: thickness mode derived from the drawing, solid or pair-matched or hatched-closed detection, centre-line fitting, orthogonal snapping, junction merging, thickness classes, disjoint footprints with neighbour-thickness corner extension.
- Openings: measured along the wall in metres (offset and width), cut in 2D so edges are exactly straight. Unknown types are flagged, not guessed.
- Floors: derived from polygonised closed regions, so they match the walls by construction.
- Scale: face-aware human-confirmed calibration, a held-out second dimension measured in the same sense, per-axis or best-fit fallbacks, plausibility priors, and a visible status on every output.
- Detection fit: an overlay and a coverage metric against the source ink.
- Materials and lighting: assigned from labels with transparent defaults; appearance only.

## 9. Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Wrong scale | Everything is the wrong size yet looks fine, and an overlay with the same scale will still line up | Face-aware two-point calibration, held-out second dimension in the same sense, priors, status stamped on renders |
| Face versus centre-line mismatch | A correct model fails the check, or a wrong one passes | `ref_kind`, face snapping, check measured on the model in the same sense |
| Dimensions cropped away at ingest | Nothing to calibrate from | Full-drawing `page.png`, wall crop only as ROI |
| Stretched or not-to-scale plan | Check fails and the pipeline would dead-end | Per-axis scale or best-fit unverified build with per-dimension error list |
| Phone photo with perspective | Walls are not parallel, scale varies across the image | Perspective test by angle spread and edge parallelism, four-corner homography, otherwise refuse |
| Rotated flatbed scan | Not a perspective problem | Rotation corrected silently |
| Outlined double-line, hatched or filled walls | A thickness filter alone deletes outlined walls | Wall-style autodetect, pair-matcher with pixel-derived thickness mode, hatch closing, `--wall-style` override |
| Text, furniture and dimension lines touching walls | False walls | Area and thickness filters, vector group selection, erase-by-region in review |
| Vector PDF with mixed layers | Furniture and grids treated as walls | Style-group inventory with contact sheet, group selection, rasterise-selected-groups fallback |
| Curved or diagonal walls | Orthogonal snapping flattens them | Snap only within the angle tolerance, keep true angles beyond it, arcs as short segments in v2 |
| Door/window symbols vary by country and drafter | Misclassified openings | Evidence-based classification, "unknown opening" fallback, one-click type change |
| Low-resolution or faded scans | Broken or missing walls | Warn below about 150 DPI equivalent, upscale only for detection, never invent walls |
| Multiple floors or sections on one sheet | Detection mixes them | Crop one drawing at a time in v1 |
| Stairs, split levels, sloped roofs, balconies | Not represented | Out of v1; listed in `report.md` as "not modelled" |
| Unequal wall thickness at corners | Protruding stub if each wall extends by its own half thickness | Extend by the neighbour's half thickness (tested) |
| Boolean or coplanar-face problems | Holes, z-fighting, broken STL | Per-wall cuts, disjoint footprints, merged manifold solid tested for watertightness |
| Merged mesh loses wall identity | No per-wall selection or materials | `model.glb` keeps named per-wall nodes; merged solid is a separate export |
| Axis convention error | Walls extrude toward the camera, or the plan is mirrored | One documented convention, one proper rotation at export, a bounds test |
| Headless WebGL without GPU | Black or failing renders | SwiftShader/ANGLE flags, a smoke-test render, fallback to a software rasteriser (`pyrender` OSMesa or `trimesh`) |
| Missing system packages | `pytesseract` fails without the binary | `apt-get install tesseract-ocr`, or skip OCR in v1 (vector PDFs do not need it) |
| AI beauty pass changes layout | Misleading imagery | Optional, labelled illustrative, geometry-conditioned |
| Plan privacy | Home plans are sensitive | Local processing, no third-party upload without consent |
| Overpromising automation | User trusts a wrong model | Mandatory review plus the two verify checks and the scale status |

## 10. Minimal first version

Honest scoping: the detection stage is the hard part and will take real iteration. It is not a one-day job, and it will work reliably only on clean plans. So the first version is split so that something correct and visible exists very early.

**v0 (back end first; this is the smallest thing that is useful).**
1. `build`: `plan.json` to `model.glb` using the tested code in stage 6 (walls, door and window cuts, a floor from the outer boundary), including the Y-up export and the merged solid test.
2. `render`: a roughly 60-line `viewer.html` with three.js and `OrbitControls`, and a Playwright script saving `top_down.png` and `iso.png`.
3. `plan.json` source: hand-written for a sample, or drafted by Claude tracing `grid.png` (from `ingest`), then checked with `overlay.png`.
4. `calibrate`: coordinates read from `grid.png` with `--ref-kind`, and the `--check` held-out dimension.
5. `verify`: detection fit and the scale status.

Skip in v0: OCR and room labels, materials and textures, the editor UI, Blender, AI, perspective correction, multi-storey, per-axis solve.

**v1 (automatic detection for one clean plan).** Add the raster detector for solid bands and the pair-matcher for outlined walls (the same code serves the vector route), gap-and-arc opening detection, and the vector group inventory for CAD PDFs. Target: one clean, single-floor, straight-walled plan. Expect to tune thresholds per drawing style.

Starter commands:
```bash
pip install pymupdf opencv-python-headless scikit-image shapely trimesh mapbox_earcut manifold3d rtree numpy
# optional OCR: apt-get install -y tesseract-ocr && pip install pytesseract
npm i three playwright    # Chromium is already present
python plan2model.py ingest plan.pdf                    # writes page.png, grid.png, ingest.json (+vectors.json, texts.json for vector PDFs)
python plan2model.py calibrate --ref 102,88,1034,88 --len 9.9 --ref-kind outer_face \
       --check 130,500,570,500 --check-len 4.7 --check-kind face_clear
python plan2model.py detect --wall-style auto           # or solid | double | hatched
python plan2model.py build && python plan2model.py render && python plan2model.py verify
```

Acceptance test for v1:
1. A held-out printed dimension (not the one used to calibrate), measured on the model in the same sense (face to face, or outer to outer), is within tolerance.
2. Every door and window in the drawing exists as an opening in the right wall.
3. The merged solid is watertight, per-wall volumes sum to the merged volume, and the exported GLB has wall height on the Y axis.
4. The T-junction test (a door beside a perpendicular wall) leaves the neighbouring wall intact, and the unequal-thickness L-corner test has no stub.
5. `verify.png` shows the model aligned with the source linework.
6. An outlined double-line fixture produces a non-empty plan with the right wall count.
Keep sample plans as regression fixtures: a clean CAD PDF, a scanned print, an outlined-wall PNG, a stretched image, and a hand sketch (expect the last to need manual correction).

## 11. Roadmap after v1

1. Review/editor UI with drag handles, then OCR for room labels and dimension suggestions.

## 12. Decision checklist for the user

- Do you have the PDF or vector source? If yes, accuracy is much higher: text and coordinates are exact.
- Which two dimensions on the plan do you trust, and are they wall-face-to-face or centre-to-centre? One calibrates the scale and the other checks it.
- Do you need an accurate model (design, permits, 3D printing) or an attractive image (marketing)? The first uses this pipeline as is. The second adds the optional beauty pass on top.
- Is a desktop Blender available? If yes, Blender MCP can drive it for finishing, but the pipeline works without it.
