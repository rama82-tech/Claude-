ATTACK 1 [MAJOR] Ingest crop can delete the printed dimensions that calibration depends on
Where: Stage 1a step 1: "Crop to the drawing's linework bounding box; remove title block and border by keeping the largest connected linework region." Then Stage 2: "the user (or Claude from `grid.png`) gives two points and the true length, for example the overall width printed on the plan", and 2.4 OCR of dimension strings.
Problem: Dimension chains, extension lines and dimension text on CAD or architect plans sit outside the wall envelope and are normally separate connected components (extension lines stop short of the wall). Keeping only the largest connected region throws them away. `page.png` and `grid.png` are the cropped frame, so the user and Claude read calibration points from an image that no longer shows the printed dimension. OCR (2.4) and the held-out check have nothing to read. The plan never says to keep dimension text outside the crop.

ATTACK 2 [MAJOR] No rule for whether a printed dimension is wall-face to wall-face or centreline to centreline
Where: Stage 2 two-point calibration and held-out check (`--ref`, `--check ... --len 5.3`, "Under 2 percent: verified. Otherwise stop"); the acceptance test "outer dimension ... within 2 percent"; schema "Walls are centre-line segments with thickness".
Problem: Plans print clear room dimensions (face to face) and overall dimensions (outer face to outer face), but the model's walls are centrelines. A printed 3.00 m clear width between 0.20 m walls is 3.20 m centre to centre, a 6.7 percent gap. The overall footprint differs by one full wall thickness, 0.2 m on 9.9 m, which is 2 percent. A correct model therefore fails the "within 2 percent" gate and the "stop" rule, or a wrong snap passes it. The tool snaps clicked points to "the nearest line end", which could be either face. The doc never says which reference to snap to or how to convert, so the verified/unverified status is unreliable.

ATTACK 3 [MAJOR] Raster wall detector fails on double-line walls, and the promised switch does not exist
Where: Section 5 "Wall detection (raster): keep dark regions whose local stroke width is in the wall band ... drop text, hatching and dimension lines"; Stage 3.1 "thickness filter"; risk table "`--wall-style solid|double|hatched`".
Problem: Outlined walls (two thin lines with white between them) are the most common drawing convention. Each line is far below the wall band, so the filter discards every wall. The only fix, "pair-match and fill", is specified for vector PDFs (1b.3) and not for rasters. `--wall-style` appears only in the risk table. It is not in the starter commands or in Stage 3. A scanned PNG with 1 px outlined walls yields an empty plan. The band itself has no number or method (pixels or metres, how derived), so the "hard part" cannot be implemented without guessing.

ATTACK 4 [MAJOR] Plans whose pixel proportions or printed dimensions disagree have no path, only "stop"
Where: Stage 2 held-out check "Otherwise stop"; schema `"px_per_m"` as a single isotropic scale; assumption 2 "drawn to scale".
Problem: The task says the plan comes "with dimensions" but not that it is to scale. Brochure plans, stretched images and scans with different x and y scale are common. A 5 percent mismatch on the check dimension halts the pipeline, and there is no per-axis scale or per-wall constraint mode to continue. The user ends up with no model and no instruction beyond "ask". The "unverified" fallback only covers the case of a single printed dimension, not a failed check.

ATTACK 5 [MAJOR] Vector-PDF method needs a metric thickness band before scale exists, and does detection inside "ingest"
Where: Stage 1b.3: "within the wall-thickness band (0.08 to 0.4 m once scale is known; before calibration use the band relative to the page, shown to the user)". Architecture: stage 1 is Ingest, stage 2 is Calibrate, stage 3 is Detect.
Problem: Pairing, arc fitting and window detection (1b.3 to 1b.5) are detection, yet they run in Stage 1, before Stage 2 produces `px_per_m`. The fallback "band relative to the page" gives no value, so the user cannot run it. The ordering contradicts the diagram and the claim that each stage can be tested alone.

ATTACK 6 [MINOR] Build code adds a protruding stub at corners and T-junctions of unequal thickness, despite "tested"
Where: `wall_footprint`: `a2 = a - d * t / 2 if joined(a)`, `b2 = b + d * t / 2 if joined(b)`; "Wall ends that meet another wall are extended by half the wall thickness so L-corners are closed."
Problem: A wall is extended by its own t/2. The correct extension is the neighbour's half thickness. I ran the function on an L-corner with a 0.30 m wall along x and a 0.10 m wall along y, both starting at (0,0). The union bounds start at x = -0.15, but the thin wall's outer face is at x = -0.05. That leaves a 0.10 m nub past the corner. Stage 3 clusters thicknesses into exterior, interior and partition classes, so unequal thicknesses are expected input. The only reported test used equal thicknesses.

ATTACK 7 [MINOR] The single merged wall solid contradicts the per-node naming and the wall materials the doc promises
Where: Stage 6 `return trimesh.boolean.union(meshes, engine="manifold")  # one solid`; step 4 "Name every mesh node (`wall_w1`, `door_o1`, `floor_r1`) so the model stays selectable"; Stage 8 materials table with a `wall` tag and "optional tileable textures".
Problem: After the union there is one wall mesh. `wall_w1` nodes cannot exist, and exterior and interior walls cannot get different materials. Textures need UVs, which `extrude_polygon` does not produce, and no UV step is given. The doc half-admits this ("keep the per-wall meshes ... in a second export") but never says which file the renders and the viewer use.
