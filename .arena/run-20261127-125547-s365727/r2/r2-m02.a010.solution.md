# Turning a 2D floor plan into a 3D model: build plan

## The answer in one paragraph

Build a small Python pipeline that turns the plan into a plain JSON description of the building (walls, openings, rooms, scale). A second step turns that JSON into 3D geometry. Do not ask an AI image generator to draw the 3D result: generators invent walls and ignore dimensions. Use computer vision only to propose the JSON, and let a human confirm it on an overlay image. Build geometry with shapely 2D operations and trimesh extrusion (no 3D boolean library needed), export a GLB, view and render it with three.js in headless Chromium, and optionally render it with Blender for materials and lighting. The JSON is the one thing everything else depends on, so make it good first. Version 1 uses no AI and no OCR: a plan (vector PDF preferred), one scale reference, automatic wall extraction, hand-confirmed doors and windows, a GLB and two renders.

## Assumptions

- Input is a PNG/JPG, a scan, or a PDF page, mostly orthogonal, with dimensions printed on it (feet-inches or metric). Vector PDFs exported from CAD are the best case; phone photos are the worst.
- Single storey. Multi-storey is the same pipeline run once per floor and stacked.
- Defaults used only when measurement fails: walls 0.115 m interior and 0.2 m exterior, height 2.7 m.
- Someone reviews the result. "Accurate" means within 2 percent of printed dimensions that were not used to set the scale. It is not survey grade.
- The environment is the Claude Code Linux container: Python, Node, Chromium and Playwright are present, `pip install` and `npm install` work through the proxy. Blender is not assumed. Version 1 does not need it.
- A terminal has no mouse. Anything that would be "click a point" is done with a labelled grid image. Claude can read that image in the session and fill in coordinates, or the user reads them off.
- Coordinate conventions, fixed once: plan.json is in metres, x to the right, y up the page (north), z up. The GLB is exported Y-up as glTF requires (see step 7).

## Three viewpoints, and how the disagreements were settled

- **Computer-vision engineer** wants a trained wall and opening detector. Pretrained floor-plan models generalise badly to new drawing styles. Verdict: not for v1. Use geometry from vector paths when available, classical line and morphology methods on rasters. Add a detector only if real plans show those failing.
- **3D/Blender artist** wants everything in Blender. Verdict: Blender is for the pretty render (materials, lighting, camera). Geometry comes from Python so it is testable headless and works if Blender cannot be installed.
- **Architect / product owner** wants right dimensions and trust. Verdict: scale comes from one printed dimension, accuracy is tested against other printed dimensions, and every detection is drawn on an overlay with wall indices before 3D is built.
- **AI image generators**: only as an optional final step to stylise a finished clay render. Never the source of geometry.

## Architecture

```
plan.pdf / plan.png
  1 ingest    -> normalised image, or vector paths from the PDF
  2 scale     -> metres per pixel (or per PDF point)
  3 extract   -> continuous wall centre-lines + thickness + opening hints
  4 plan.json <- single source of truth, hand-editable
  5 review    -> overlay.png (walls numbered, opening hints drawn)
  6 build     -> shapely bands -> trimesh -> rotate to Y-up -> house.glb (+ house_cutaway.glb)
  7 render    -> three.js via Playwright (v1), Blender (stage 2)
```

Build reads only plan.json. Tests can write plan.json by hand, and when detection fails the user can still hand-trace.

### plan.json

```json
{
  "units": "m",
  "wall_height": 2.7,
  "cut_height": 1.2,
  "walls":    [{"id":0, "a":[0,0], "b":[6.0,0], "t":0.2}],
  "openings": [{"wall":0, "type":"door",   "at":1.2, "w":0.9, "h":2.1, "sill":0},
               {"wall":0, "type":"window", "at":3.5, "w":1.2, "h":1.2, "sill":0.9}],
  "rooms":    [{"name":"Kitchen", "floor":"tile", "label_point":[2.0,1.5]}],
  "delete":   []
}
```

Walls are centre-lines with a thickness. A wall is continuous through its doors and windows: an opening is a cut in a wall that exists, never a gap between two walls. `at` is the distance of the opening centre from point `a` along that wall, so it always lands on real wall. `delete` lists wall ids to drop (fake walls found on review). Room polygons are derived, not stored; only names and floor types are stored, matched by a label point.

## Tools and libraries

| Job | Use | Why |
|---|---|---|
| PDF to image or paths | PyMuPDF (`fitz`) | `page.get_pixmap(dpi=300)` for raster; `page.get_drawings()` returns exact paths for vector PDFs |
| Image processing | OpenCV, NumPy, scikit-image | threshold, distance transform, skeleton, LSD or Hough line segments |
| 2D geometry | shapely | wall union, opening cuts, room rings |
| Mesh and export | trimesh + `mapbox_earcut` | `trimesh.creation.extrude_polygon`, GLB export |
| Browser viewer | three.js (`npm install three`) | GLTFLoader, OrbitControls |
| Headless screenshots | Playwright Chromium | with software WebGL flags (below) |
| Fallback top-down | matplotlib | draws polygons from plan.json, no WebGL at all |
| Render with materials | Blender background mode | stage 2 |
| Text and dimensions | Tesseract or PaddleOCR | stage 2: read printed dimensions and room labels |

## Step-by-step pipeline

### 1. Ingest
- Vector PDF: use `get_drawings()`, no rasterising needed.
- Raster or scanned PDF: rasterise at 300 dpi, grayscale, deskew from the dominant Hough angle, crop title block and margins.
- Phone photo: find the sheet corners (largest quadrilateral contour, or four coordinates read from `grid.png`) and apply `cv2.getPerspectiveTransform` before anything else. Without this step the photo test case is expected to fail, and the tool says so.

### 2. Scale (no clicking, and independently tested)
Scale is set by one printed dimension and tested with others.

1. **Vector CAD PDF with a stated drawing scale (for example 1:100):** PDF points to millimetres is `pt * 25.4 / 72 * scale_denominator`. No reference points are needed, and the printed overall dimension then acts as an independent check.
2. **Reference by coordinates:** `extract.py` writes `grid.png` (plan with labelled pixel grid; also zoomed 25 px crops of any area asked for). The user, or Claude reading the image, gives `--ref "x1,y1,x2,y2=12'-6\"" --ref-face outer`. Meaning of the face flag: after walls are extracted, each reference point is **snapped to the nearest wall-face line of the declared kind** (`outer` face, `inner` face, or `centre` line) within 15 px, and the scale is real length divided by the snapped pixel distance. The flag therefore says which line the printed dimension runs between (overall dimensions are normally outside face to outside face; room dimensions are usually inside face to inside face), and eyeballing error of a few pixels is removed by the snap. If no face line is within 15 px the tool stops and asks for better points. No thickness correction is applied.
3. **OCR (stage 2):** find dimension strings and their extension lines automatically.

`parse_length()` handles `12'-6"`, `12' 6 1/2"`, `12.5ft`, `3.6m`, `3600mm`, `360cm` and returns metres.

**Acceptance check (not circular):** the user supplies at least two other printed dimensions with `--check "x1,y1,x2,y2=3.6m" --check-face inner`. They are measured on the built wall geometry, not on pixels, and each must be within 2 percent of the printed value. A wrong wall, missed wall or wrong thickness shifts these, so the test can fail. The overall outer bounding box compared to the reference is printed as a sanity line only, because it agrees with the reference by construction.

### 3. Walls (three styles, tried in order)
- **Solid or poche-filled walls:** threshold, then a morphological opening with a kernel slightly thinner than the wall removes text, dimension lines and furniture. Skeletonise, snap to horizontal and vertical, merge collinear pieces. Thickness comes from the distance transform at the skeleton.
- **Double-line walls (the usual CAD look), vector:** decompose every PDF drawing item into segments: `l` items are segments, polylines are split per segment, `re` and `qu` items are split into 4 segments, except a **filled thin rectangle** (short side within the wall thickness range, long side at least 0.5 m), which is taken directly as a wall poche. Keep axis-aligned segments of at least 0.3 m. Pair parallel segments whose perpendicular distance is 0.08 to 0.35 m and whose projections overlap by at least 0.8 m. Each pair gives a centre-line with thickness equal to the gap.
- **Double-line walls, raster:** the same pairing, with segments from `cv2.createLineSegmentDetector` (or `HoughLinesP`).

**Symbol and furniture filters (applied after pairing):**
1. Short perpendicular lines under 0.3 m (door jambs, wall caps) are ignored.
2. Window symbols (2 or 3 thin parallel lines across a wall gap) lie on the same line as the wall, so they merge into the wall instead of becoming a new one. This is correct, because the wall continues under a window.
3. Build a graph of paired walls that touch within one wall thickness. Keep only the components that contain the outermost ring; drop any component with less than 2 m of total length (bookshelves, counters, stair treads, hatch).
4. Anything left that is wrong is removed by the user through `delete` after reading overlay.png.

This reduces false walls but does not remove the need for review on symbol-rich plans; the overlay is the safety net, not an afterthought.

**Gaps and opening hints:** after pairing, collinear wall pieces separated by a gap of up to 3 m are merged into one continuous wall, so doors and windows never split a wall. Each bridged gap is written to the overlay as a numbered **opening hint** with the wall id, `at` and width already computed, and shown in plan.json as a suggested entry the user keeps, retypes as door or window, or deletes. This makes step 4 mostly a labelling job.

**Auto selection and the stop rule:** `--wall-style auto` tries solid first. The result is accepted only if the wall union has a closed outer ring enclosing at least one interior ring of at least 4 square metres, and total wall length is at most 3 times the perimeter of the outer bounding box. Otherwise it retries with paired lines using the same test. If both fail it stops with "no plausible walls detected, trace walls by hand in plan.json", and still writes overlay.png and a skeleton plan.json. It always prints wall count, total length, ring count and component count, so a bad extraction is visible.

Thickness is stored per wall as measured, rounded to the median for exterior and interior walls. The defaults apply only when measurement fails.

### 4. Openings
- **v1:** the user confirms the opening hints (type, width, height, sill) in plan.json. Wall numbers and a ruler in metres along each wall are printed on overlay.png. Doors are told apart from windows by the user, or in stage 2 by a quarter-circle swing arc (door) versus a thin double line (window).
- **Stage 2:** automatic classification from those symbols.

### 5. Rooms (from geometry, not from the image)
Do not flood fill the raster. Using plan.json only:
1. Build the wall footprint: union of each wall buffered with `cap_style=square` so corners close. Doors and windows do **not** cut this union, so every room is a closed ring and nothing leaks.
2. The interior rings are the rooms. The outside is not a ring, so it falls out automatically.
3. Name each room by the label point inside it (typed by the user, OCR later). A door between two rooms simply has both rooms touching the same wall; floors are built per ring, and the door sill region is covered by the wall's own footprint floor (step 7.5).

### 6. Review
Write overlay.png: plan.json drawn over the original, walls numbered, opening hints numbered and coloured, room names and areas written in. The y axis points up the page, as in plan.json. The user fixes plan.json. This step is where trust comes from.

### 7. Build the geometry (no 3D booleans)
trimesh cannot subtract solids on its own (its `boolean` module needs `manifold3d`, Blender or OpenSCAD). Avoid the need:

1. Collect every z breakpoint: 0, each opening's `sill`, each `sill + h`, `wall_height`, and, for the cutaway build only, `cut_height`. Sort them. Consecutive pairs are horizontal bands.
2. For each band `[z0, z1]`, the footprint is `walls_union.difference(union of opening boxes that fully cover that band)`. An opening box is the opening rectangle in plan, extended slightly beyond the wall faces so the cut is clean.
3. Extrude each band with `trimesh.creation.extrude_polygon(footprint, z1 - z0)` and translate by `z0`. The result is a lintel above every door, a sill below every window, and full-height wall between.
4. **Cutaway:** `house_cutaway.glb` uses the same build with `cut_height` (default 1.2 m) as an extra breakpoint and all bands above it dropped, so the cut lands exactly on a band edge.
5. Floor slab: extrude the whole wall-union bounding region, minus nothing, from z = -0.1 to 0 for each room ring plus the wall footprint, so door thresholds have floor under them. Optional ceiling at `wall_height`.
6. Windows get a thin glass box inside the opening. Doors can get a thin leaf box, optional.
7. **Axis fix, required:** everything above is built Z-up. Before export apply `trimesh.transformations.rotation_matrix(-np.pi/2, [1,0,0])` to every mesh, which maps plan (x, y, z) to glTF (x, z, -y), so height becomes the Y axis. Then group meshes by material name (walls, floor, glass, door) and export. A self-test asserts that the exported bounding box height (Y extent) equals `wall_height` plus slab, and the footprint spans X and Z.
8. Validate with `mesh.is_watertight` per band and `footprint.is_valid` per footprint (repair with `buffer(0)`).

## Outputs

- `plan.json` (editable model), `grid.png`, `overlay.png`
- `house.glb`, `house_cutaway.glb` (Y-up; open in any viewer, three.js or Blender)
- `topdown.png`, `iso.png`, later `room_*.png`
- `index.html` plus the GLBs: a self-contained orbit viewer

## Rendering in the container

### three.js with Playwright (v1)
- `npm install three` in the project folder so no CDN is needed. Serve the folder with `python -m http.server 8000`. Do not open `file://`: Chromium blocks the GLB fetch there.
- Launch Chromium with software WebGL:
  `args=["--use-gl=angle","--use-angle=swiftshader","--enable-unsafe-swiftshader","--ignore-gpu-blocklist"]`.
- In `index.html`, set `window.__ready = true` after the first rendered frame. In Playwright, `page.wait_for_function("window.__ready === true")`, then `page.screenshot(path="iso.png")`.
- Cameras (scene is Y-up; plan x is scene X, plan y is scene -Z):
  - **Top-down:** `OrthographicCamera` at (cx, 20, cz) looking at (cx, 0, cz) with `camera.up.set(0, 0, -1)`. The up vector must be set because the view direction is parallel to the default (0,1,0); with (0,0,-1) plan x runs right and plan y runs up the screen, matching overlay.png. Frustum size about 1.1 times the larger plan dimension.
  - **Iso:** orthographic camera at centre + (d, d, d), `up = (0,1,0)`, loading `house_cutaway.glb`.
  - **Eye level:** perspective camera at height 1.5 m (scene Y = 1.5), FOV 70 degrees, `up = (0,1,0)`.
- Fallback top-down with no WebGL: matplotlib draws the wall footprint, openings and room fills from plan.json with correct aspect ratio and y up.

Blender install (stage 2): try `pip install bpy` first (the wheel must match the Python version), otherwise download the Linux tarball from blender.org if the proxy allows it, otherwise skip and stay on three.js. Blender importing the GLB handles Y-up itself. If a Blender MCP server is connected, send the same render script through it. Plan for Blender being unavailable.

## Accuracy: what keeps it right

- Scale from one printed dimension with a declared face convention and snapped reference points.
- Accuracy proven by at least two other printed dimensions, held out of the scale step, each within 2 percent.
- Measured thickness per wall, never a silent default.
- Snap to horizontal and vertical and merge collinear pieces, so corners are clean.
- Dimensions in the model come from numbers in plan.json, not pixels. Typing 3.60 makes the room 3.60.
- Room area compared with any area printed on the plan.
- Openings are data the human confirms, not AI guesses.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Double-line or hatch walls | Solid-wall opening deletes them | Paired-line extraction, closed-ring acceptance test, hard stop |
| Window, door symbols and furniture read as walls | Fake walls | Length, connectivity and component filters, `delete` list, overlay review |
| Door gaps | Wall split, opening points at nothing | Walls merged across gaps; gaps become opening hints on real wall |
| Printed dimension is outer face, model is centre-line | Systematic 2 to 3 percent error | Reference points snapped to the declared face line |
| Circular accuracy check | Bad geometry passes | Held-out dimensions tested on geometry |
| GLB axis | House lies on its side | Rotate to Y-up on export, bounding-box self-test |
| Top-down orientation | Mirrored or rotated render | `camera.up = (0,0,-1)`, matches overlay |
| Phone photo, keystone | Skewed lengths | Perspective warp before scale |
| Hand-drawn, curved or diagonal walls | Snapping distorts them | Per-wall opt-out of snapping; hand-trace |
| Odd units (ft-in fractions) | Wrong scale | `parse_length`, show the computed scale |
| Low resolution scan | Thin walls vanish | 150 dpi minimum; warn when walls are under 4 px |
| Doors misread as windows | Wrong openings | User confirms types on overlay |
| Polygon errors | Non-watertight band | `is_valid`, `buffer(0)`, per-band watertight check |
| No WebGL in container | Blank screenshots | SwiftShader flags; matplotlib top-down fallback |
| Stairs, roofs, multi-storey | Missing | Out of scope for v1; parametric blocks later |
| AI generator used for geometry | Wrong walls | Not used for geometry |

## Minimal first version (build this first)

Goal: one plan in, a correct GLB and two renders out, in an afternoon or two.

1. `pip install opencv-python-headless shapely trimesh mapbox-earcut numpy pymupdf matplotlib`, `npm install three`, and `pip install playwright` if not present.
2. `extract.py plan.pdf [--scale-denom 100 | --ref "x1,y1,x2,y2=12'-6\"" --ref-face outer] --check "...=3.6m" --check "...=4.2m" [--wall-style auto]` writes `plan.json` (walls plus suggested openings), `overlay.png` and `grid.png`.
3. The user confirms or edits openings and the `delete` list in plan.json, using the numbers on overlay.png.
4. `build.py plan.json` writes `house.glb` and `house_cutaway.glb` with the band method and the Y-up rotation.
5. `shot.py` serves the folder, opens `index.html` in Playwright with SwiftShader flags, and saves `topdown.png` and `iso.png`.

Done when, on a plan with known dimensions: at least two held-out printed dimensions match the built geometry within 2 percent; every band mesh is watertight and every footprint valid; the GLB bounding-box self-test passes; every opening in plan.json is visible as a hole in iso.png; topdown.png has the same orientation as overlay.png; and the iso image shows the cutaway.

Stage 2: OCR for dimension strings; automatic door and window classification; room labels; Blender renders with the materials above; perspective correction as a built-in step.
Stage 3, only if needed: a trained detector for messy scans; stairs; multiple storeys; stylised AI images from a finished render.

## Test checklist

- A synthetic plan drawn by script with exact dimensions, double-line walls, window symbols, a bookshelf and door arcs (ground truth, including the fake-wall filters).
- A solid-wall plan, to exercise the other extraction style.
- A real CAD export as a vector PDF.
- A scan, then a phone photo. The photo is expected to pass only after perspective correction. If it fails, the failure should be visible on overlay.png, not hidden.
- For each: overlay is right, held-out dimension check passes, per-band watertight, bounding-box orientation test passes, openings visible, topdown matches overlay, GLB loads in three.js.
