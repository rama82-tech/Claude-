ATTACK 1 [MAJOR] Acceptance check (e) cannot be performed: the GLB walls carry no ids
Where: Section 11 (e): "open `model.glb` in Blender, select the wall for `w0`, and compare its length..."; viewer.html: `const m = new THREE.Mesh(g, wallMat); m.rotation.y = ...` (no `m.name` is ever set).
Problem: Every wall is an anonymous Mesh in the exported GLB, so "the wall for w0" cannot be found. The user gets Mesh, Mesh_1, ... in an arbitrary order with no link to plan.json ids. The only check that ties the exported 3D file back to the source plan is therefore not runnable as written. The fix is one line (`m.name = w.id`), but it is missing, and section 11 says "Pass only if all five hold".

ATTACK 2 [MAJOR] The semantics count gate refuses every door/window label in exactly the cases the plan says need manual fixes
Where: apply_semantics.py `if not (len(ops) <= n <= len(ops) + len(p["gaps"])): ... ok = False`; section 8 rows "double-line walls ... those windows are missed: add by hand" and "Door drawn open with no gap".
Problem: The gate demands that the doors+windows counted in the image be at least the number of extractor openings and at most openings plus wide gaps. Take a hollow-style plan where the extractor misses one window (the documented failure) and finds 5 openings, while Claude correctly counts 6 symbols. 6 <= 5 + 0 gaps is false, so the check fails and NO opening types are applied. All openings stay `door`, sill 0, height 2.05, so windows render as full-height door holes. A false-positive opening, such as a 0.5 m niche between two stubs, fails the lower bound the same way. The only way out is `--force`, which turns the gate off. So the safety check fails in the situations it exists for, and the MVP then outputs wrong 3D with no further warning.

ATTACK 3 [MAJOR] Documented tuning loop overwrites hand edits and invalidates ids
Where: Section 5 diagram "you review overlay.png + warnings, edit JSON, re-run only the 3D step"; step 2 "re-run with `--max-hole 2.4`"; plan2ir.py `ap.add_argument("--out", default="plan.json")` and ids `f"w{i}"`, `f"o{i}_{j}"`.
Problem: The recommended fix for a wide window left open is to re-run plan2ir.py. That rewrites plan.json from scratch, wiping every edit, room name and semantics applied earlier. Wall and opening ids come from list position after sorting, so one changed flag renumbers them. An existing semantics.json (keyed on "o0_0", "o2_0") then points at the wrong openings, or at ones that no longer exist. Nothing in the plan says to write to a new file, or to keep a merge or lock mechanism, so a user following the plan loses their work.

ATTACK 4 [MAJOR] Scan input is a stated case, but the MVP silently mis-measures a slightly rotated scan
Where: Assumption 2 and step 0 "Deskew ... Not in the MVP"; plan2ir.py bars come from `connectedComponentsWithStats` bounding boxes `(o, y + h/2, x, x + w, h)`; risk table "Scan skew ... Mitigation: Deskew".
Problem: The task names "an image, scan or PDF". A real scan is rarely better than 0.5 to 1 degrees off. At 0.5 degrees an 8 m wall at 100 ppm drifts about 7 px, and the bounding box height is thickness plus drift. A 15 px wall is then measured as about 22 px (0.22 m), and at 1 degree about 29 px (0.29 m, still under `--wall-max` so no warning). Bar centres are also shifted. Scale `--check` only warns above 2%, and the overlay rectangles are axis-aligned, so the error shows as a vague misfit. The risk table lists deskew as the mitigation, but no code or command for it is given and the MVP does not use it. The first real scan breaks silently.

ATTACK 5 [MAJOR] The quickstart's scale cross-check is the same segment as the scale reference, so it proves nothing
Where: Section 9 command: `--dim 120,40,920,40,8.0 --check 120,40,920,40,8.0`; plan.json example `"check_error_pct": 0.0`; section 11 (a) "from `--check` on every printed dimension other than the one used for `--dim`".
Problem: `--check` with the exact segment used by `--dim` gives 0.0% by construction. The example output then displays a passing scale check, which contradicts the acceptance test's own wording in 11(a). A user copying the command pattern believes uniform scale was verified when no independent dimension was tested.

ATTACK 6 [MINOR] PDF input has no path in the runnable MVP
Where: Section 9 quickstart and plan2ir.py (`cv2.imread(a.image, cv2.IMREAD_GRAYSCALE)`); step 0 describes `pymupdf` only in prose and says the vector path is "not written or tested".
Problem: The task lists PDF as an input. The MVP install line omits pymupdf, there is no command or script to rasterise the PDF, and `cv2.imread` cannot read a PDF. The user must work out the conversion and the resulting `--dim` pixel coordinates at 300 dpi alone. Also, the common case of a CAD-exported vector PDF is deferred to Phase 2.

ATTACK 7 [MINOR] Dimensions are metres-only, with no way to enter imperial values
Where: plan2ir.py `seg(spec)` parses `x1,y1,x2,y2,metres` with `float(...)`; assumption 3 "a printed dimension ... or one length you can type in".
Problem: Many plans carry feet-inches strings such as 12'-6" or 41' 3 1/2". The tool accepts only a decimal metre value. The user has to convert by hand for the scale and for every `--check`, and the plan never says so. A conversion slip gives a plausible but wrong-sized model, and the 2% check passes if the same wrong factor is used each time.
