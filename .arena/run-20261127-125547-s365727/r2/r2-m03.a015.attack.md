ATTACK 1 [MAJOR] The "within 1% of printed" acceptance test fails on the document's own tested example, and the dimension datum is never defined
Where: "Done when: the model's overall dimensions match the printed dimensions within 1%" versus the worked example ("Result (tested): ... bounds x -0.10..9.25 ... z -7.42..0.10 m") and the extraction prompt "pick the two longest printed dimension lines and give their end pixels".
Problem: The calibration ends are mapped straight onto wall CENTRELINES (x0 = left calibration pixel becomes wall centreline x=0). The model then adds half the wall thickness outside them. In the example, the printed 30'-0" (9.144 m) becomes a model 9.35 m wide, 2.2% over. The printed 24'-0" (7.3152 m) becomes about 7.52 m, 2.8% over. Both fail the 1% test. Real plans usually dimension to outer faces, finished faces or centrelines, and the doc never says which one the calibration pixels must sit on. The prompt tells Claude to pick the longest dimension lines, which are normally outer-face. Every plan therefore carries a systematic 2-3% error that the test then flags, or the test is quietly measured some other way.

ATTACK 2 [MAJOR] px2m.py crashes with a single printed dimension, which the Assumptions say is enough
Where: Assumptions: "at least one printed dimension (e.g. 30'-0") or a scale bar". Code: `sx = c["x"][2]/...; sy = c["y"][2]/...`. Step 2, mode D: "fall back to a standard 3'-0" door width".
Problem: px2m.py requires both calibration.x and calibration.y. A plan with one dimension, a scale bar only, or only a door width (mode D) raises KeyError on `c["y"]`. The schema has no field for a scale bar, a single isotropic scale or a door-width estimate. The user would have to edit the script. Mode A (uniform scale) is described but not implemented, because the code always uses separate scales. Mode C (per-wall printed lengths) is "manual in v1" with no schema, code or example. Three of the four scale modes, and the stated input assumption, have no working path.

ATTACK 3 [MAJOR] Rooms and floors depend on exactly-touching centrelines, but the only snapping step is not written
Where: build.py `polygonize(unary_union([LineString...]))`, and pipeline step 4 "Snap and clean (code, not AI)". The doc admits "Not run: ... OpenCV snapping".
Problem: The "tested" example is hand-authored with perfectly matching coordinates. Real vision output has endpoints a few pixels off. If W5's end stops 2 px short of W3, the lines are not noded. polygonize then returns one merged face instead of two. Living, Bed 1 and Bed 2 collapse into one polygon, and `next(q ... r.contains(...))` assigns only the first label. The floors get one material and the area report is wrong, with no error raised. The 1.5x-thickness snap rule is given as prose with no algorithm or code. Snapping is the main accuracy mechanism beyond the overlay, and the "one to two days" estimate treats it as a small leftover.

ATTACK 4 [MAJOR] Everything rests on a vision model returning pixel coordinates precise to about 1%, with no grid, no snap-to-ink and no handling of image resizing
Where: "The vision model never does arithmetic: it reports pixel positions"; the extraction prompt "Use pixel coordinates of the image I attached"; "re-run on zoomed quadrant crops for dense plans".
Problem: Images are downscaled before the model sees them. A PDF rasterised at 200-300 dpi (about 4000 px wide) is reduced, so reported coordinates are in the resized frame while overlay.py draws on the original. The overlay then looks shifted or scaled, and px2m calibrates wrongly if the two frames are mixed. Crops return coordinates in the crop frame, and nothing stores the crop offset or merges the results. The calibration end pixels, which set the scale for the whole house, are the least reliable output of a model asked to localise to within 10 px on a 1000 px span. The solution gives no reference grid, no snap of calibration points to detected line ends, and no held-out second dimension. The mandatory overlay cannot catch a wrong scale, because the overlay uses the same calibration.

ATTACK 5 [MAJOR] Walls float 0.1 m above the slab, because nothing fills the wall footprint between z=-0.1 and z=0
Where: "Z-levels: slab -0.2 to -0.1, floor -0.1 to 0, walls 0 to 2.7 m"; build.py `add(fl, -0.1, 0, ...)` where `fl = r.difference(foot)`; `add(slab, -0.2, -0.1, "slab")`.
Problem: The floor pieces are cut by the wall footprint, and walls start at z=0. Under every wall the column from -0.1 to 0 is therefore empty. The slab's outer ring is flush with the exterior wall face, so this 0.1 m gap is open along the whole outside perimeter. Only door and window openings get a `threshold` fill. Per-mesh watertightness does not detect this. The claim that the isometric screenshot looked right does not cover a thin shadowed slit.

ATTACK 6 [MAJOR] Listed outputs and several required renders have no code or procedure behind them
Where: Output files table: `room_*.png`, `report.md`, `house.blend`, `.obj`/`.fbx`, `walkthrough.mp4`. Step 10 "one eye-level view per main room". Step 9, Blender lighting. Table row "Dimensions / text: pytesseract or easyocr".
Problem: shot.mjs and viewer.html produce only top.png and iso.png. `view()` has two modes and no eye-level camera. No script writes report.md, even though step 5's checks and "Show the error" depend on it. There is no Blender script for materials, a Nishita sky, area lights or `.blend` export, no OCR code, and no OpenCV code. The task asks for "materials and lighting" and "output files and renders". The photoreal path and the OCR/CV path are only named, so the user cannot act on them without guessing. The "tested" label covers only the Python-to-GLB-to-two-screenshots subset.

ATTACK 7 [MINOR] Every free wall end is lengthened by half the wall thickness
Where: build.py `rect(w)`: `LineString([a-d*w["t"]/2, b+d*w["t"]/2])`, with the claim "corners and T joints come from the shapely union".
Problem: The extension is applied to all wall ends, including free ones such as a partition that stops in an open plan, a half-wall or a kitchen peninsula. Each such wall comes out 0.057 m (interior) or 0.10 m (exterior) too long per free end. This breaks the "centreline model" accuracy claim and the 3-inch snapping check. The extension should apply only to ends that meet another wall.
