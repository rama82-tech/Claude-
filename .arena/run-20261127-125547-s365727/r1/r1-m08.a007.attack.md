ATTACK 1 [MAJOR] Option A (the v0 path) has no way to get accurate coordinates, and the spec cannot be mapped back onto the image
Where: "Have Claude look at the image and produce `plan.json` in the schema above, in metres" (Minimal first version, step 3); schema "Coordinates are metres, origin at the plan's top-left"; Step 4 "Draw `plan.json` over the original"
Problem: Step 2 produces metres-per-pixel, but step 3 asks a vision model to emit metres directly. Vision output is not pixel-accurate, so wall endpoints will drift. The plan never says how pixels become metres in step 3. The JSON also stores no scale or origin (no px_per_m, no pixel offset), and "origin at the plan's top-left" is ambiguous between the image corner and the building corner. overlay.py in step 4 therefore cannot invert metres back to pixels from the file alone. The "done" criterion of 2 percent is unreachable by this route without many manual overlay-edit loops. The plan does not budget those loops or describe how to do them.

ATTACK 2 [MAJOR] Centreline model conflicts with printed dimensions, so the automated accuracy checks will fail on correct models
Where: schema "Walls are centreline segments with a thickness"; "Automated checks: every wall length against any printed dimension"; Done criteria "measured wall lengths in the GLB are within 2 percent of the printed dimensions"
Problem: Printed dimensions on plans are normally to wall faces (exterior overall, or interior clear). They are not to centrelines. Take a 0.3 m exterior wall on a 4.0 m clear room: the centreline length is 4.3 m, which is 7.5 percent off the printed value. A correct model fails the check, or the user is pushed to distort the spec to pass it. The plan gives no rule for converting between the face and centreline conventions.

ATTACK 3 [MAJOR] Scale tolerance contradicts the accuracy target
Where: "If the two disagree by more than 3 percent, stop" vs 'Assumptions: "Accurate" means every wall within about 2 percent'
Problem: A 2.9 percent disagreement between two dimensions passes the gate, yet the result already violates the stated 2 percent standard. The "stop and report" branch also gives no next action for a plan that is labelled but not drawn to scale. The plan says this is common, but the user is left with no path forward.

ATTACK 4 [MAJOR] Builder A produces holes only, so the claimed door, window and glass elements do not exist
Where: "Cut openings: subtract a rectangle ... Materials: ... glass transparent. Name each mesh (`wall_w1`, `door_d1`)"; spec fields `"swing":"in"`, `"floor":"wood"`
Problem: The build steps create wall bands, floor slabs, headers and sills. They create no door leaves, no window frames and no glass panes. The `door_d1` meshes and the transparent glass material therefore have nothing to attach to. `swing` is never used. The `floor` value ("wood") has no mapping to a colour or material. The v0 output will show doorless, glassless openings, so the claimed materials step is only partly met. The task asks how to get accurate "materials and lighting", and this is thin on both: flat colours, plus one hemisphere light and one directional light.

ATTACK 5 [MAJOR] Renders promised in the outputs are not covered by the v0 plan, and the viewer will not load as written
Where: Outputs table "`top.png`, `iso.png`, `room_*.png`"; Renders in v0 "a self-contained `viewer.html` ... opened by Playwright"
Problem: Only top and iso cameras are described. No method is given to place eye-level cameras per room for `room_*.png`. A page opened by Playwright over file:// cannot fetch `plan.glb` through GLTFLoader, because browsers block file-origin XHR/fetch. It needs a local HTTP server or an inlined base64 GLB. Neither is mentioned, and "self-contained" is contradicted by loading the model and three.js from outside the file. The first run will show a blank page, and the plan lists only GPU stalls as the render failure.

ATTACK 6 [MINOR] Room-closure test and thickness rule are underspecified or inconsistent
Where: "run `shapely.ops.polygonize` on the wall lines. Unclosed rooms ... will not form polygons"; "Measure from the image, then round to those standards"
Problem: `polygonize` needs noded lines, so `unary_union` must run first. Walls that meet in a T or X without a shared endpoint produce no polygons, and the check then falsely reports an unclosed room. "Measure, then round to standards" throws away the measured value. A 0.18 m partition and a 0.35 m masonry wall both get overwritten, which is the opposite of the accuracy goal.
