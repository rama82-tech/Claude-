ATTACK 1 [FATAL] Floor slab is built from the wall polygon's exterior ring, so any plan with an open exterior doorway gets no floor
Where: build(): `env = unary_union([Polygon(g.exterior) for g in geoms])` and the claim "a door drawn as a gap in the wall becomes a gap in the 3D wall, so doors work if the drawing leaves a gap"
Problem: The tested plan only has a gap in an interior partition, so the outer ring stays closed and the ring has a hole. If the plan has a gap in the outer wall (a front door drawn as a gap, which almost every house has), the wall union becomes one C-shaped polygon with no interior hole. Its `.exterior` is just the wall footprint, so the "floor slab" is a thin slab under the walls only. The rooms get no floor at all, and nothing warns about it. The same C-shape breaks the "closed room polygon" acceptance check. The minimal version, which the plan describes as "built and tested", fails on the most common real input. The test plan was chosen so that this case never occurred.

ATTACK 2 [MAJOR] GLB is exported Z-up, but glTF, three.js and the viewer step assume Y-up, and the plan never converts
Where: IR `"up": "z"`, `extrude_polygon(g, height)` then `sc.export(a.o)`, and Extension step 1 (three.js viewer, `top.png`, `iso.png`)
Problem: trimesh extrudes along +Z and writes the GLB without rotating axes. glTF is Y-up, so in three.js the house lies on its side: walls extend along the horizontal axis and the "top-down" render shows a wall elevation. Blender's importer also assumes Y-up and will rotate it wrongly relative to the Sun/area lights the plan describes. The "bounds matched the drawing" test only measured numbers inside trimesh. It never loaded the GLB in any viewer, and the plan admits that was not tested. There is no rotate-to-Y-up step, no `up` handling in the viewer and no orientation check in the acceptance test. The user will see a sideways model on the first viewer run and be given no hint why.

ATTACK 3 [MAJOR] The minimal version does not fail loudly, and the acceptance test needs outputs it never produces
Where: "Acceptance test for each real plan" items 1 and 3 versus the `plan2glb.py` output (only prints wall area and bounds)
Problem: Item 1 requires `overlay.png` and item 3 requires room polygons and room areas. The minimal script writes neither (they arrive in extension step 3 or later), so the user cannot run the stated acceptance test on the first version. The script has no sanity guards. It does not check bounds against plausible house size, wall count or area ratio. It does not check that the mask is not mostly black (an Otsu threshold on a plan with coloured or hatched floor fills turns the floor into one giant "wall" and the script still writes a GLB). It does not check that the `--px-per-m` result is plausible. A wrong scale, a fill-in-everything mask or a title-block frame all produce a valid-looking, watertight GLB with only a printed area to give them away. For a plan whose stated principle is "verification step the user can see", the first build has none.

ATTACK 4 [MAJOR] The required `--px-per-m` input is something the user cannot supply, and the plan does not say how to get it
Where: `plan2glb.py plan.png --px-per-m 50` and "scale from one number"
Problem: The user has an image or PDF with dimensions, not a pixel scale. The plan gives no way to get this number in version 1: no click-two-points helper, no "measure wall A to B in an image viewer, then divide" recipe, and no PDF DPI conversion. OCR and scale detection are deferred to extension step 2. The user must guess, and a wrong guess scales everything. The plan calls scale "the single biggest accuracy lever" and then leaves the first version's only scale input unspecified. The default `--min-wall-m 0.08` also silently depends on that guess. At a low-resolution scan of about 20 px/m, k is clamped to 3 px and the 0.1 m interior partitions (2 px) are erased with no message.

ATTACK 5 [MAJOR] Vector-PDF claim is overstated and sends the user down a path the plan does not explain
Where: Table row "Vector paths extracted directly" and Intake: "`page.get_drawings()`... gives exact geometry; check for it first... it removes most error"
Problem: `get_drawings()` returns every stroke on the page (walls, dimension lines, furniture, hatching, door arcs, text outlines) with no semantics. Architectural double-line walls come out as pairs of parallel lines, not walls. The plan gives no method for classifying these or pairing them into wall centre-lines and thickness, and none of the vector path gets prototyped. "Removes most error" is asserted, with no support. Many CAD exports also embed the drawing as scaled form XObjects or with a transformation matrix, which need handling for correct scale. A user who finds a vector PDF is told it needs no CV and is left without a next step.

ATTACK 6 [MINOR] Door and window openings in the minimal version are cut full height, and windows are not handled
Where: "no openings beyond what the wall mask already contains" versus the IR, which specifies `sill` and `head`
Problem: A gap in the mask extrudes as a slot from floor to the 2.7 m top, so there is no lintel above the door and no 2.1 m head. A window drawn as thin lines inside the wall survives the opening step and stays as solid wall. A window drawn as a gap becomes a floor-to-ceiling slot, which is wrong for sill height. The plan presents this as "doors work" without noting that the result will not match the IR's own dimensions. Fixing it is deferred to extension step 4.

ATTACK 7 [MINOR] Unsupported numeric confidence figures presented as guidance
Where: "Confidence in this architecture: high (about 85%)", "about 90% on clean crops in my estimate", "40 to 60% of professional plans use hatching", "about 75%", "about 80%", "about 30%"
Problem: None of these figures comes from a test, a source or a stated sample. The only things actually run are one synthetic plan and its wall area. The user cannot act on "75%" or "85%", and the numbers invite false precision, notably for the claim that classical CV suffices on clean plans, which was tested on a single synthetic rectangle.
