# 2D Floor Plan to 3D Model: Build Plan

## Recommendation in one paragraph

Do not make a computer "understand" the plan in one step. Split the job into two stages joined by a small, human-checkable JSON file. Stage 1 (perception) turns the image or PDF into a plan description: wall segments, openings, rooms and a scale. Stage 2 (generation) turns that JSON into geometry with deterministic code. Build Stage 2 first and feed it hand-written JSON, so the 3D output is correct by construction and any perception error shows up as a visible, fixable edit to one text file. Use Python with `shapely` and `trimesh` to write a GLB. Preview it with three.js served over local HTTP and screenshot it with Playwright. Add Blender later for photoreal renders. AI image generators should not produce geometry. Use them, if at all, for optional styled renders checked against the plan.

## Assumptions

- One storey. A clean, mostly orthogonal drawing: architect PDF, CAD export or clear scan. Not a hand sketch or an angled photo.
- A scale is obtainable: the user can give one known length (two clicked points plus a metres value), or the sheet has a dimension, scale bar or ratio such as "1/4 in = 1 ft".
- Accurate and editable model first, pretty renders second.
- Cloud container: Linux, Python, Node, Chromium, Playwright, no GPU. Network may be limited by a proxy, so nothing in version 1 may need a CDN, apt or a large download (see Preflight).
- Defaults when the plan is silent: ceiling 2.4 m, door height 2.0 m, window sill 0.9 m, window head 2.1 m, interior wall 0.115 m, exterior wall 0.23 m.
- Multi-storey is out of scope for version 1 (run once per plan and stack later).

## Preflight (2 minutes, run first)

```
which tesseract blender; python -c "import fitz, cv2, shapely, trimesh"; id -u; node -v
```

- No `tesseract`: version 1 does not need it (manual scale, no OCR). Skip it. If you add OCR later, try `apt-get install -y tesseract-ocr` (needs root and apt network), or `pip install easyocr` (needs a model download), or have Claude read the dimension text from the image and type it in.
- No `blender`: skip Blender. Version 1 is complete without it. If you want it later, try `apt-get install blender`, or download the official Linux tarball if its host is reachable. If neither works, render with three.js and Playwright instead.
- `pip install` blocked: use the pre-installed packages only and report what is missing.

## Architecture

```
 PDF/PNG/JPG
     |
 [1 Ingest]   rasterize (and extract vectors if PDF), deskew, binarize
     |
 [2 Scale]    manual two-point (v1)  ->  OCR dimensions (v2)
     |
 [3 Detect]   wall style -> walls, openings   ->  plan.json
     |                                              ^
 [4 Review]   overlay plan.json on image -----------|  (human fixes JSON)
     |
 [5 Build]    plan.json -> geometry (Z-up) -> rotate once to Y-up
     |
 [6 Export]   model.glb
     |
 [7 Show]     three.js viewer over http, Playwright screenshots
     |
 [8 Render]   (later) Blender or three.js stills, walkthrough
```

Why the JSON sits in the middle:

1. It isolates the hard, error-prone step (reading a drawing) from the easy, reliable one (extruding walls).
2. You can swap detectors (classical CV, vector parsing, a trained model, a vision LLM) without touching 3D code.
3. A wrong wall is one line of JSON, not a re-run of a black box.
4. Hand-written plans become regression tests for the generator.

Second-order effect: a scale error silently resizes everything, and a wrong wall style silently returns zero walls. So scale and wall style are each explicit, reported in `report.md`, and shown in the overlay.

## Tools and libraries

| Job | Choice | Why |
|---|---|---|
| PDF to image, and vector extraction | `pymupdf` | `page.get_drawings()` returns exact line endpoints, widths and fills. Far more accurate than pixels. |
| Image cleanup, line detection | `opencv-python-headless`, `numpy`, `scikit-image` | Threshold, deskew, morphology, skeleton, LSD or Hough. |
| OCR (version 2) | `pytesseract` with the tesseract binary, or `easyocr` | Reads "4200", "3.20 m", "12'-6\"". |
| Vision LLM | Claude with image input | Labels rooms, spots door swings, sanity checks the overlay. Poor at pixel coordinates, so never use it to measure. |
| Geometry | `shapely` (2D polygons, buffer, union, difference) and `trimesh` (extrude, export) | Pure Python, exports GLB. |
| Preview | three.js vendored locally, `GLTFLoader`, `OrbitControls`, served by `python -m http.server`, shots by Playwright | Works offline in the container. |
| Photoreal (later) | Blender 4.x `blender -b -P script.py`, or Blender MCP when the user drives Blender on their own machine | Cycles or EEVEE stills, camera path video. |
| Optional ML detector | Segmentation model trained on CubiCasa5k or similar | Only if classical methods fail on your plans. Not a starting point. |

## The data contract: plan.json

Units are metres. Plan frame: origin at the top-left of the plan, x right, y down, as in the image. The build step flips y once and rotates to glTF's Y-up once (see Step 5).

```json
{
  "units": "m",
  "scale": {"m_per_px": 0.0123, "source": "manual:2pt", "confidence": 1.0},
  "wall_height": 2.4,
  "walls": [
    {"id": "w1", "a": [0, 0], "b": [8.0, 0], "thickness": 0.23, "kind": "exterior"}
  ],
  "openings": [
    {"id": "d1", "type": "door",   "wall": "w1", "offset": 1.2, "width": 0.9, "height": 2.0, "sill": 0.0},
    {"id": "n1", "type": "window", "wall": "w1", "offset": 4.0, "width": 1.2, "height": 1.2, "sill": 0.9}
  ],
  "rooms": [
    {"id": "r1", "name": "Kitchen", "label_xy": [2, 1.5], "floor": "tile"}
  ]
}
```

Rules:

- Walls are centrelines plus thickness. Openings are placed by `offset` along a wall, so nudging a wall moves its doors.
- Room polygons are not stored by hand. They are computed from the walls (Step 5), and a room is named by the label point that falls inside it.
- Anything the detector is unsure of gets `"confidence"` below 0.7 and is drawn red in the overlay.

## Step-by-step pipeline

### Step 1. Ingest
- PDF: always try vectors first. Run `page.get_drawings()`. If the page has more than about 200 line or rect items, treat it as vector and use the vector path in Step 3. Also render a raster at 200 to 300 dpi for the overlay and for the raster fallback.
- Image: grayscale, deskew by the dominant Hough angle, Otsu or adaptive threshold.
- Crop away title block, legend and notes with `--crop x1,y1,x2,y2`. Multiple plans or elevations on one sheet must be cropped to one plan.

### Step 2. Scale (the number that decides accuracy)

Version 1 (default, no dependencies, no circular ordering): manual two-point scale. The user, or Claude reading the image, picks two pixel points and a real length, for example `--scale-from "x1,y1,x2,y2,3.20"`. Better, give two such pairs on different axes. Report the two implied scales. If they differ by more than 2 percent, stop and say so (skewed scan, or non-uniform scaling).

Version 2: automatic scale from OCR, with an explicit association method.

1. Run OCR at 0, 90, 180 and 270 degrees (vertical dimensions are rotated text) and keep numeric tokens with their boxes and orientation. Parse with strict regexes: plain mm integers like `4200`, decimals with `m`, and imperial `12'-6"`. Reject anything unparseable.
2. Detect dimension lines: long thin lines with end ticks or arrowheads, found by LSD, that sit outside the wall mask.
3. Associate each number to a dimension line: take lines parallel to the text direction, within a distance of about 2 text heights perpendicular to the text, whose span covers the text centre. If more than one qualifies, take the nearest. Drop numbers with no match.
4. Compute metres per pixel per match as parsed length over line pixel length. Take the median. Discard matches more than 10 percent off the median, then report the spread.
5. Accept only if at least 3 matches agree within 2 percent. Otherwise fall back to the manual two-point scale.

Fallback ruler (only after walls and doors exist): median door gap width in pixels set to 0.9 m, flagged low confidence. This is not used in version 1.

Vector PDFs: also check the sheet's declared scale and units. Page units are points (1/72 in), so metres per unit equals the plan ratio times 0.0254 divided by 72. Cross-check this against one manual measurement.

### Step 3. Detect walls, openings

First classify the wall style, because one detector does not fit all. Sample the thick structures: fraction of dark pixels in the area between candidate parallel lines.

- Style A, solid fill: walls are thick filled black or grey strokes.
- Style B, double line: two thin parallel lines with empty inside, or a hatch or poché fill between them.
- Style C, single line: walls are single strokes. Take thickness from the defaults.

If the style is unclear, ask or show both overlays. Do not guess silently.

**Vector path (best, for CAD PDFs):**
1. Extract line segments from `get_drawings()` with stroke width and layer colour. Drop short items (under 10 cm after scaling) and hairline dimension, grid and furniture strokes by width and colour.
2. Style A: filled rectangles and polygons wider than 0.08 m are wall pieces. Take each piece's long axis as a centreline and its short side as thickness.
3. Style B, pairing algorithm: bucket segments by angle (snap within 3 degrees to horizontal and vertical). For each segment, find partners that are parallel, overlap in projection by at least 50 percent of the shorter one, and sit at a perpendicular gap between 0.08 and 0.45 m. Each accepted pair makes one wall: centreline is the midline over the overlapping span, thickness is the gap. Resolve ties by smallest gap. Merge collinear results and close gaps under one thickness.

**Raster path (scans, images):**
1. Style A: erode with a kernel about the wall thickness to remove thin lines, then dilate back. What survives is the wall mask.
2. Style B: do not erode. Instead, close the interior of each wall: apply a morphological closing with a kernel about the wall thickness along each orientation (for example horizontal then vertical line kernels), then fill. The gap between the two lines becomes solid, giving the same kind of mask as Style A. Then remove thin leftovers by an opening of about half the wall thickness. Check that the mask is not filled by room interiors (reject components with area much greater than perimeter times thickness).
3. Style C: use the thin-line mask directly and attach default thickness.
4. Skeletonize the mask, fit segments (`HoughLinesP` or LSD), snap to horizontal and vertical within 3 degrees, merge collinear segments, close small gaps, and estimate thickness from the distance transform on the skeleton.

**Openings (both paths):**
- Walls are a continuous stroke, openings are interruptions. A gap in the wall line that is crossed by a swing arc (a quarter circle, found by contour or Hough circle) is a door, and the arc gives hinge and swing. A gap containing two or three thin parallel lines is a window. A plain gap is a doorway. Record offset and width along the wall.
- In vector data, door arcs are `curve` items in `get_drawings()` and are easy to find.

**Rooms and semantics:**
- Rooms come from the wall network (Step 5), not from detection.
- Send the image plus the overlay to a vision model and ask: list rooms, count doors and windows, and flag anything wrong. Compare with the detector's counts. Disagreements are marked in the review.

### Step 4. Review overlay (do not skip)
Draw `plan.json` on the original image (walls blue, doors green, windows orange, low-confidence red) and save `overlay.png`. Look at it, or have Claude look at it, and fix the JSON by hand. For version 1 this is the entire editor.

### Step 5. Build geometry

Coordinate rule, stated once. Build everything in a Z-up frame where the plan lies on the XY plane, y flipped from the image (`y_plan_up = -y_image`) and height is +Z. This is what `trimesh.creation.extrude_polygon` produces. Before export, apply one fixed rotation: plan x to glTF x, plan y to glTF -z, height to glTF y. In trimesh: rotate by -90 degrees about the x axis (`trimesh.transformations.rotation_matrix(-np.pi/2, [1,0,0])`) and check the result with a test (below). Do not rotate anywhere else.

1. Each wall becomes a rectangle with `LineString.buffer(t/2, cap_style='flat')` (cap_style=2).
2. Union all walls into one polygon (`shapely.ops.unary_union`) so corners and T-junctions are clean.
3. Rooms (net floor): take a bounding polygon around the whole plan (the union's convex hull or envelope, slightly grown), subtract the wall union, and keep the interior pieces that do not touch the outside. Each piece is a room net of wall thickness. Drop slivers under 1 m2. A label point inside a piece names it. Open-plan areas missing a wall get a virtual `"kind": "boundary"` segment of zero height.
4. Extrude the wall union to `wall_height`.
5. Cut openings. For each opening, make a box through the wall thickness at `offset`, `width`, `height` and `sill`, and subtract it with `trimesh` boolean using `manifold3d`. Fallback that always works: build the wall in pieces around each opening (left piece, lintel above, sill below, right piece) on the 2D elevation.
6. Optional: door leaf and window glass as thin boxes. Ceiling off by default so top views work.
7. Floors: extrude each net room polygon downward 0.1 m, and put a floor slab under the wall footprint too so doorways have no holes.
8. Materials by name (`wall`, `floor_tile`, `floor_wood`, `glass`, `door`) with simple PBR colours from `materials.json`.

Test for the rotation (run in `tests/`): after export, load the GLB and assert that the bounding box height (glTF y extent) equals `wall_height` within 1 cm, and that the plan footprint matches the width and depth in x and z.

### Step 6. Export
- `model.glb` is the main output (compact, materials, loads in three.js, Blender, most viewers).
- `plan.json` is the editable source of truth. Keep it with the model.
- Later: `.obj` via `trimesh`, `.blend` by building in Blender, `.ifc` only if BIM tooling is needed.

### Step 7. Preview and screenshots
- Vendor three.js locally: `npm pack three`, unpack, copy `build/three.module.js`, `examples/jsm/loaders/GLTFLoader.js`, `examples/jsm/controls/OrbitControls.js` and its imports into `web/vendor/`. No CDN, which also avoids the proxy.
- `viewer.html` uses an import map (`"three": "./vendor/three.module.js"`) and loads `model.glb`. It sets `window.ready = true` after the model is added and one frame is rendered.
- File URLs do not work, because Chromium blocks `fetch` of the GLB from `file://`. `shot.py` starts `python -m http.server 8123` in the output folder (as a subprocess, killed at the end) and opens `http://localhost:8123/viewer.html`.
- Playwright launches Chromium with `--use-gl=angle --use-angle=swiftshader --ignore-gpu-blocklist` (no GPU). It waits for `window.ready`, with a 60 second timeout that prints the browser console on failure.
- Three shots: `top.png` (orthographic, from above), `iso.png` (isometric, ceiling hidden), `eye.png` (1.6 m eye height inside the largest room, field of view 70 degrees).

### Step 8. Photoreal renders (version 2, optional)
- Only if Preflight found Blender. Run `blender -b -P render.py`: import `model.glb`, sun or sky plus one area light per room, EEVEE for speed or Cycles with low samples and denoise (CPU only).
- Walkthrough: a camera path through room centroids, frames joined with `ffmpeg`.
- Without Blender: raise the three.js quality (shadow maps, SSAO, tone mapping) and keep the Playwright shots.

## Getting each element right

**Walls.** Take thickness from the plan where possible (stroke width or pair gap after scaling) and snap to a standard value (0.1, 0.115, 0.15, 0.2, 0.23 m). Snap endpoints to a 5 cm grid and merge near-collinear ends. Always union before extruding.

**Openings.** Place by wall and offset. Take sizes from a door or window schedule if the plan has one, else defaults. Swing arcs give hinge side.

**Floors and rooms.** Net polygons (wall-complement), so areas match printed room areas.

**Materials.** Flat colours by room type first (wet rooms tile, living areas wood). Free CC0 PBR textures from Poly Haven later.

**Lighting.** Viewer: hemisphere light, one shadow-casting directional light. Blender: sky plus sun, one area light per room. Windows are real holes, so daylight enters.

**Furniture.** Leave it out of version 1. Furniture symbols are the main source of false walls, so filtering them out is the goal.

## Accuracy checks (automatic, with thresholds)

1. Net room areas versus printed room areas (or a printed total area): each within 5 percent. Areas are net, so centreline math is never used. Worked check: a 3.0 x 4.0 m room with 0.115 m walls gives 12.0 m2 net, not 12.8.
2. Each OCR'd or manually measured dimension versus the matching wall length, within 2 percent.
3. Walls form closed loops: no dangling end longer than one wall thickness except deliberate boundary segments.
4. Every opening lies fully inside its wall, with at least 10 cm of wall on each side.
5. Door width 0.6 to 1.2 m, window width 0.3 to 3 m. Anything else is flagged.
6. Orientation test: GLB height equals `wall_height` within 1 cm.
7. The overlay is viewed by a person or a vision model before the build is trusted.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Wrong or missing scale | Whole model the wrong size. | Two manual pairs on different axes, agreement within 2 percent, stop on mismatch. |
| Wrong wall style assumed | Zero or phantom walls (for example erosion deletes double-line walls). | Classify style first, separate paths for A, B and C, show the style in the report. |
| Furniture, hatching, text, stairs read as walls | Phantom walls. | Width and colour filters, area-to-perimeter filter, review overlay, `--ignore-box`. |
| Hand sketches, photos, skewed scans | Detection collapses. | Deskew and perspective-correct. If that fails, use the manual JSON path. |
| Curved or diagonal walls | Snap to orthogonal breaks them. | Version 1 straight walls only. Keep a diagonal only if the angle is stable, otherwise flag. |
| Open-plan areas without walls | Rooms fail to close. | Virtual `"kind": "boundary"` segments of zero height. |
| Boolean failures when cutting openings | Non-manifold mesh. | Piece-wise wall construction fallback. |
| Z-up GLB loaded as Y-up | Building lies on its side. | One fixed rotation, plus the height test. |
| Viewer fetch fails on `file://`, CDN blocked | Screenshots hang. | Local HTTP server, vendored three.js, console dump on timeout. |
| Imperial strings misread by OCR | Silent factor errors. | Strict regex, reject unparseable, cross-check. |
| Multi-storey sheets, sections, elevations on one page | Mixed content. | Crop to one plan. |
| AI image generators used for geometry | They invent walls and move doors. | Use only for styled renders, checked against the overlay. |
| Plan privacy | A client's drawing leaves the machine. | Keep detection local. Tell the user before sending a plan to any external API. |

## Minimal first version (build this today)

Goal: one command takes a plan image or PDF plus a manual scale and writes a GLB and three screenshots. Everything not automated is manual and said so in the report. No OCR, no Blender, no network needed.

Order of work. Times are for a developer with the packages installed, and each step has a pass check.

1. **Preflight and a sample plan (20 min).** Run the Preflight. Make a test plan with a small script that draws a two-room flat as a double-line image and as a solid-fill image (this gives a known-truth source for both styles), and hand-write its `plan.json`.
2. **Generator (2 to 3 hours).** `build.py plan.json -> model.glb` with union, net rooms, openings, the rotation and the orientation test. Pass: the area check on the sample is within 1 percent, and the height test passes.
3. **Viewer and shots (1 to 1.5 hours).** Vendored three.js, local server, `shot.py`. Pass: three PNGs, and `top.png` shows the plan from above, not a side elevation.
4. **Manual scale (20 min).** `--scale-from`, two pairs, 2 percent agreement. Pass: wrong input is refused.
5. **Wall detector for Style A and Style B (3 to 5 hours).** Vector path if the input is a PDF with vectors, raster path otherwise. Output `plan.json` with walls only. Pass: on the synthetic double-line and solid-fill samples, every wall is found, with endpoints within 5 cm after scaling and no phantom walls.
6. **Overlay (45 min).** Draw `plan.json` on the image.
7. **Openings (2 to 3 hours).** Gap detection, door by swing arc, window by parallel lines, or set `type` by hand in the JSON. Pass: all openings on the samples are found, widths within 10 cm.
8. **Report (30 min).** Print the scale, style, counts and the checks.

Total: about 10 to 14 hours of focused work for the full minimal version. A faster path that is useful in about 4 hours: steps 1 to 4 and 6, with the walls and openings written by Claude from the image into `plan.json` and corrected using the overlay. That already gives the user a real 3D model from a real plan today, and the detector can replace the manual step later.

Directory layout:

```
floorplan3d/
  preflight.sh
  ingest.py     # pdf/image -> clean binary, vectors, scale
  detect.py     # style classification + vector and raster detectors -> plan.json
  overlay.py    # plan.json + image -> overlay.png
  build.py      # plan.json -> model.glb (Z-up build, one rotation, Y-up export)
  shot.py       # serves folder, Playwright screenshots

```

- On the synthetic double-line and solid-fill plans and on at least one real plan you supply (any clean CAD PDF, or a CubiCasa5k sample), after at most 10 edited JSON lines per plan, the overlay shows every wall within 5 cm (synthetic) or 10 cm (real) of its true position.
- Net room areas are within 5 percent of printed areas where printed.
- All doors and windows are present, with widths within 10 cm.
- `model.glb` passes the height test, and `top.png`, `iso.png` and `eye.png` are produced without a timeout.

## Decision summary

- JSON plan as the contract between reading and building. Build the generator first.
- Vector extraction first for PDFs. Raster CV for scans, with a wall-style switch (solid, double-line, single-line).
- Manual two-point scale in version 1, verified on two axes. OCR scale later.
- `shapely` and `trimesh`, one explicit Z-up to Y-up rotation, net room polygons, GLB output.
- three.js vendored locally and served over HTTP, Playwright with software GL for shots.
- Blender and OCR are optional and gated by the preflight.
- Always show the overlay before trusting a build.
