# Turning a 2D floor plan into a 3D model: build plan

## The answer in one paragraph

Build a small Python pipeline that turns the plan into a plain JSON description of the building (walls, openings, rooms, scale). A second step turns that JSON into 3D geometry. Do not ask an AI image generator to draw the 3D result: generators invent walls and ignore dimensions. Use computer vision only to propose the JSON, and let a human confirm it on an overlay image. Build geometry with shapely 2D operations and trimesh extrusion (no 3D boolean library needed), export a GLB, view and render it with three.js in headless Chromium, and optionally render it with Blender for materials and lighting. The JSON is the one thing everything else depends on, so make it good first. Version 1 uses no AI and no OCR: a plan (vector PDF preferred), one scale reference, automatic wall extraction, hand-listed doors and windows, a GLB and two renders.

## Assumptions

- Input is a PNG/JPG, a scan, or a PDF page, mostly orthogonal, with dimensions printed on it (feet-inches or metric). Vector PDFs exported from CAD are the best case; phone photos are the worst.
- Single storey. Multi-storey is the same pipeline run once per floor and stacked.
- Defaults used only when measurement fails: walls 0.115 m interior and 0.2 m exterior, height 2.7 m.
- Someone reviews the result. "Accurate" means within 2 percent of printed overall dimensions, not survey grade.
- The environment is the Claude Code Linux container: Python, Node, Chromium and Playwright are present, `pip install` and `npm install` work through the proxy. Blender is not assumed. Version 1 does not need it.
- A terminal has no mouse. Anything that would be "click a point" is done with a labelled grid image (see Scale). Claude can read that image in the session and fill in coordinates, or the user reads them off.

## Three viewpoints, and how the disagreements were settled

- **Computer-vision engineer** wants a trained wall and opening detector. Pretrained floor-plan models generalise badly to new drawing styles. Verdict: not for v1. Use geometry from vector paths when available, and classical line and morphology methods on rasters. Add a detector only if real plans show those failing.
- **3D/Blender artist** wants everything in Blender. Verdict: Blender is for the pretty render (materials, lighting, camera). Geometry comes from Python so it is testable headless and works if Blender cannot be installed.
- **Architect / product owner** wants right dimensions and trust. Verdict: scale comes from one printed dimension with a declared face convention, is cross-checked, and every detection is drawn on an overlay with wall indices before 3D is built.
- **AI image generators**: only as an optional final step to stylise a finished clay render. Never the source of geometry.

## Architecture

```
plan.pdf / plan.png
  1 ingest    -> normalised image, or vector paths from the PDF
  2 scale     -> metres per pixel (or per PDF point)
  3 extract   -> wall centre-lines + thickness
  4 plan.json <- single source of truth, hand-editable
  5 review    -> overlay.png (walls numbered, openings drawn)
  6 build     -> shapely bands -> trimesh -> house.glb (+ house_cutaway.glb)
  7 render    -> three.js via Playwright (v1), Blender (stage 2)
```

Step 6 reads only plan.json. Tests can write plan.json by hand, and when detection fails the user can still hand-trace.

### plan.json

```json
{
  "units": "m",
  "wall_height": 2.7,
  "walls":    [{"id":0, "a":[0,0], "b":[6.0,0], "t":0.2}],
  "openings": [{"wall":0, "type":"door",   "at":1.2, "w":0.9, "h":2.1, "sill":0},
               {"wall":0, "type":"window", "at":3.5, "w":1.2, "h":1.2, "sill":0.9}],
  "rooms":    [{"name":"Kitchen", "floor":"tile"}]
}
```

Walls are centre-lines with a thickness (easy to extrude and edit). `at` is the distance of the opening centre from point a along the wall. Room polygons are derived, not stored; only names and floor types are stored, matched by a label point added later.

## Tools and libraries

| Job | Use | Why |
|---|---|---|
| PDF to image or paths | PyMuPDF (`fitz`) | `page.get_pixmap(dpi=300)` for raster; `page.get_drawings()` returns exact line paths for vector PDFs |
| Image processing | OpenCV, NumPy, scikit-image | threshold, distance transform, skeleton, LSD or Hough line segments |
| 2D geometry | shapely | wall union, opening cuts, room rings |
| Mesh and export | trimesh + `mapbox_earcut` | `trimesh.creation.extrude_polygon`, GLB export |
| Browser viewer | three.js (installed with `npm install three`) | GLTFLoader, OrbitControls |
| Headless screenshots | Playwright Chromium | with software WebGL flags (below) |
| Fallback top-down | matplotlib | draws polygons from plan.json, no WebGL at all |
| Render with materials | Blender background mode | stage 2 |
| Text and dimensions | Tesseract or PaddleOCR | stage 2: read printed dimensions and room labels |

## Step-by-step pipeline

### 1. Ingest
- Vector PDF: use `get_drawings()`, no rasterising needed.
- Raster or scanned PDF: rasterise at 300 dpi, grayscale, deskew from the dominant Hough angle, crop title block and margins.
- Phone photo: find the sheet corners (largest quadrilateral contour, or four coordinates read from `grid.png`) and apply `cv2.getPerspectiveTransform` to remove keystone before anything else. Without this step the photo test case is expected to fail, and the tool should say so.

### 2. Scale (no clicking)
Three routes, in order of preference:
1. **Vector CAD PDF with a stated drawing scale (for example 1:100):** PDF points to millimetres is `pt * 25.4 / 72 * scale_denominator`. No reference needed. Still cross-check one printed dimension.
2. **Reference by coordinates:** `extract.py` writes `grid.png`, the plan with a labelled pixel grid every 100 px. The user (or Claude reading the image) gives `--ref "x1,y1,x2,y2=12'-6\"" --ref-face outer`.
3. **OCR (stage 2):** find dimension strings and their extension lines automatically.

A small `parse_length()` handles `12'-6"`, `12' 6 1/2"`, `12.5ft`, `3.6m`, `3600mm`, `360cm` and returns metres. The `--ref-face` option (`outer`, `inner` or `centre`) says which wall faces the printed dimension measures. The default is `outer`, because overall dimensions on plans are normally outside-face to outside-face. Then compare two or three other printed dimensions with measured ones and warn above 3 percent; this catches non-uniform scaling and bad scans.

### 3. Walls (three styles, tried in order)
Walls on plans are drawn three ways, and the extractor handles each explicitly:

- **Solid or poche-filled walls:** threshold, then a morphological opening with a kernel slightly thinner than the wall removes text, dimension lines and furniture. Skeletonise, snap to horizontal and vertical, merge collinear pieces. Thickness comes from the distance transform at the skeleton.
- **Double-line walls (the usual CAD look), vector:** take the line segments from `get_drawings()`, keep axis-aligned segments longer than about 0.3 m, then pair parallel segments whose perpendicular distance is within the plausible thickness range (0.08 to 0.35 m) and whose projections overlap. Each pair gives one centre-line with thickness equal to the gap. Unpaired segments (dimension lines, furniture) are dropped.
- **Double-line walls, raster:** the same pairing algorithm, with segments from `cv2.createLineSegmentDetector` (or `HoughLinesP`) instead of PDF paths.

`--wall-style auto` (default) tries solid, and if total wall length is under a sanity threshold (for example under 4 times the page diagonal in metres divided by 10), it retries with paired lines. If it still finds nothing, it stops with the message "no walls detected, trace walls by hand in plan.json" and still writes overlay.png and a skeleton plan.json. It never silently emits an empty model.

Thickness is stored per wall as measured, rounded to the median for exterior and interior walls. The defaults above apply only when measurement fails.

### 4. Openings
- **v1:** the user lists them in plan.json. This is easy because overlay.png prints the wall index and a ruler in metres along each wall.
- **Stage 2:** gaps in the wall mask along a wall are openings; a quarter-circle swing arc confirms a door; a thin double line inside the gap marks a window.

### 5. Rooms (from geometry, not from the image)
Do not flood fill the raster. Doors are gaps, so the fill leaks into every room and the outside. Instead, using plan.json only:
1. Build the wall footprint: union of each wall buffered with `cap_style=square` so corners close.
2. For every door or opening in the plan, add a bridging rectangle (opening width by wall thickness) to the union. Windows do not need bridging because the footprint is never cut for them.
3. The interior rings of that union are the rooms. The outside is not a ring, so it falls out automatically.
4. Name each room by the label point inside it (OCR text later, or typed by the user).

### 6. Review
Write overlay.png: plan.json drawn over the original, walls numbered, openings coloured, room names and areas written in. The user fixes plan.json. This step is where trust comes from.

### 7. Build the geometry (no 3D booleans)
trimesh cannot subtract solids on its own (its `boolean` module needs `manifold3d`, Blender or OpenSCAD). Avoid the need:

1. Collect every z breakpoint: 0, each opening's `sill`, each `sill + h`, and `wall_height`. Sort them. Consecutive pairs are horizontal bands.
2. For each band `[z0, z1]`, the footprint is `walls_union.difference(union of opening boxes that fully cover that band)`. An opening box is the opening rectangle in plan, extended slightly beyond the wall faces so the cut is clean.
3. Extrude each band with `trimesh.creation.extrude_polygon(footprint, z1 - z0)` and translate by `z0`. The result is a lintel above every door, a sill below every window, and full-height wall between.
4. Windows get a thin glass box inside the opening. Doors can get a thin leaf box, optional.
5. Floor slab: extrude each room ring (plus the bridge area) by 0.1 m below z=0. Optional ceiling at `wall_height`.
6. Group meshes by material name (walls, floor, glass, door) and export `house.glb`.
7. `house_cutaway.glb` is the same build with every band clipped at 1.2 m. This gives the "dollhouse" view with no runtime hiding logic.

Each band is its own watertight body. Validate with `mesh.is_watertight` per band and `footprint.is_valid` per footprint (repair with `buffer(0)`).

## Outputs

- `plan.json` (editable model), `grid.png`, `overlay.png`
- `house.glb`, `house_cutaway.glb` (open in any viewer, three.js or Blender)
- `topdown.png`, `iso.png`, later `room_*.png`
- `index.html` plus the GLBs: a self-contained orbit viewer

## Rendering in the container

### three.js with Playwright (v1)
- `npm install three` in the project folder so no CDN is needed. Serve the folder with `python -m http.server 8000`. Do not open `file://`: Chromium blocks the GLB fetch there.
- Launch Chromium with software WebGL:
  `args=["--use-gl=angle","--use-angle=swiftshader","--enable-unsafe-swiftshader","--ignore-gpu-blocklist"]`.
- In `index.html`, set `window.__ready = true` after the first rendered frame. In Playwright, `page.wait_for_function("window.__ready === true")`, then `page.screenshot(path="iso.png")`.
- Top-down: `OrthographicCamera` placed above the bounding-box centre looking down, frustum size about 1.1 times the larger plan dimension. Iso: orthographic camera at the direction (1, 1, 1) from the centre, loading `house_cutaway.glb`.
- Fallback top-down with no WebGL: matplotlib draws the wall footprint, openings and room fills from plan.json with `fill` and the correct aspect ratio.

If a Blender MCP server is connected, send the same render script through it. Plan for Blender being unavailable.

## Accuracy: what keeps it right

- Scale from a printed dimension with a declared face convention, cross-checked against others.
- Measured thickness per wall, never a silent default.
- Snap to horizontal and vertical and merge collinear pieces, so corners are clean.
- Dimensions in the model come from numbers in plan.json, not pixels. Typing 3.60 makes the room 3.60.
- Automated check: the outer-face bounding box of the wall union must match the printed overall width and length within 2 percent, and each room's area is compared with any area printed on the plan.
- Openings are data the human confirms, not AI guesses.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Double-line or hatch walls | Solid-wall opening deletes them | Paired-line extraction, auto fallback, hard stop on zero walls |
| Door gaps leak room fill | Rooms merge | Rooms from plan.json with bridging rectangles |
| Printed dimension is outer face, model is centre-line | Systematic 2 to 3 percent error | Declared `--ref-face`, outer-face validation |
| Phone photo, keystone | Skewed lengths | Perspective warp before scale |
| Hand-drawn, curved or diagonal walls | Snapping distorts them | Per-wall opt-out of snapping; hand-trace |
| Furniture, text touching walls | Fake walls | Line pairing, opening filter, overlay review |
| Odd units (ft-in fractions) | Wrong scale | `parse_length`, show the computed scale |
| Low resolution scan | Thin walls vanish | 150 dpi minimum; warn when walls are under 4 px |
| Doors misread as windows | Wrong openings | Overlay shows them; edit plan.json |
| Polygon errors | Non-watertight band | `is_valid`, `buffer(0)`, per-band watertight check |
| No WebGL in container | Blank screenshots | SwiftShader flags; matplotlib top-down fallback |
| Stairs, roofs, multi-storey | Missing | Out of scope for v1; parametric blocks later |
| AI generator used for geometry | Wrong walls | Not used for geometry |

## Minimal first version (build this first)

Goal: one plan in, a correct GLB and two renders out, in an afternoon or two.

1. `pip install opencv-python-headless shapely trimesh mapbox-earcut numpy pymupdf matplotlib`, `npm install three`, and `pip install playwright` if not present.
2. `extract.py plan.pdf [--scale-denom 100 | --ref "x1,y1,x2,y2=12'-6\"" --ref-face outer] [--wall-style auto]` writes `plan.json` (walls only), `overlay.png` and `grid.png`.
3. The user adds doors and windows to plan.json, using the wall numbers on overlay.png.
4. `build.py plan.json` writes `house.glb` and `house_cutaway.glb` using the band method.
5. `shot.py` serves the folder, opens `index.html` in Playwright with SwiftShader flags, and saves `topdown.png` and `iso.png`.

Done when, on a plan with known dimensions: the outer-face bounding box matches the printed overall size within 2 percent; every band mesh is watertight and every footprint valid; every opening listed in plan.json is visible as a hole in the render; and the iso image shows the cutaway.

Stage 2: OCR for dimension strings; automatic door and window detection; room labels; Blender renders with the materials above; perspective correction as a built-in step.
Stage 3, only if needed: a trained detector for messy scans; stairs; multiple storeys; stylised AI images from a finished render.

## Test checklist

- A synthetic plan drawn by script with exact dimensions and double-line walls (ground truth).
- A solid-wall plan, to exercise the other extraction style.
- A real CAD export as a vector PDF.
- A scan, then a phone photo. The photo is expected to pass only after perspective correction. If it fails, the failure should be visible on overlay.png, not hidden.
- For each: overlay is right, scale check passes, outer-face dimensions within 2 percent, per-band watertight, openings visible, GLB loads in three.js.
