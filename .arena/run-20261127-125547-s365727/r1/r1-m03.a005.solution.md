# Floor plan to 3D model: build plan

## Recommendation in one paragraph

Do not go straight from pixels to a 3D mesh. Put one small, versioned, human-readable file in the middle: `plan.json`, a description of walls, openings, rooms, printed dimensions and a real-world scale. Everything before it (image reading) is replaceable and may be wrong. Everything after it (3D geometry, renders) is deterministic code. You can open `plan.json`, fix a wrong wall, and rebuild. Extraction works in pixel coordinates, which a person can read off a gridded image, and one tested function converts pixels to metres using the scale. This keeps the project maintainable as detection methods change.

```
image/PDF -> [1 ingest] -> [2 scale] -> [3 extract: pixels] -> plan_px.json
                                                                   | to_metres (tested)
                                                                   v
                 [7 renders] <- [6 viewer] <- model.glb <- [5 geometry] <- [4 validate + overlay review] <- plan.json
```

## Assumptions

- One floor plan (PNG, JPG, or one PDF page), one storey, drawn top-down, with at least one printed dimension.
- "3D model" means walls, floors, door and window openings, simple materials, lighting. Not furniture, roofs or structural accuracy.
- Cloud Linux container: Python, Node, Chromium and Playwright, no GPU, no live Blender GUI. A person reviews one overlay image per plan.
- Metric internally (metres), whatever units the plan prints.
- Accuracy target for v1: each printed dimension reproduced within 2% when measured at the datum the plan uses (see below), and every opening in the right wall.
- Privacy: if Claude reads the image to draft the plan, the image goes to Anthropic like any file in this session. For a confidential plan use the fully local manual mode (below). Nothing else uploads the plan.

## Hard constraints and what they force

| Constraint | Consequence |
|---|---|
| Headless container, no GPU | No GUI Blender MCP. Geometry in pure Python (`trimesh`, `shapely`). Renders via headless Chromium with software WebGL (SwiftShader), plus a pure-Python top-down fallback. Blender is optional, behind the same `plan.json`. |
| Output must be inspectable and shareable | `.glb` is the primary output: opens in three.js, Blender, any viewer. |
| Dimensions are the truth, pixels are not | Scale comes from a printed dimension and records which datum it refers to. |
| Scans are noisy and skewed | Extraction may be wrong, so a gridded overlay and a validator sit before geometry. |
| Maintainable for 6+ months | One schema, pinned dependencies, golden-file tests, no stage reaching into another's internals. |
| Privacy | Local CV and manual entry by default; any vision-LLM step is explicit and named as an upload. |

## Tools and why

- **Schema and validation:** `pydantic` models that emit JSON Schema, with `schema_version` and one migration function per version.
- **Image prep:** OpenCV (deskew, threshold); PyMuPDF for PDFs.
- **Text and dimensions:** Tesseract (`pytesseract`) for strings like `12'-6"`, `3.80`, `3800`. A tested parser handles feet-inches, mm, m and fractions.
- **Walls and openings:** (a) manual entry in pixel coordinates read from the gridded image (fully local); (b) Claude drafts `plan_px.json` from the image (upload, flagged); (c) OpenCV detection (probabilistic Hough, morphological thinning, door-arc plus gap detection) as it matures. All three produce the same file and all go through review.
- **Rooms:** `shapely` `polygonize` over wall centrelines; labels from OCR text inside each polygon.
- **Geometry:** `shapely` for 2D, `trimesh` for extrusion and GLB export.
- **Viewer and renders:** three.js pinned and vendored (including `GLTFLoader` and `OrbitControls` from its addons folder) with an import map, served by `python -m http.server` on localhost, screenshotted by Playwright.
- **Optional photoreal path:** Blender via `bpy`, reading `plan.json`, for Cycles renders and walkthrough video. A second backend, not the core. AI image generators make stylised pictures but invent walls, so they never supply geometry.

## The `plan.json` contract

```json
{
  "schema_version": 1,
  "source": {"file": "plan.png", "sha256": "..."},
  "scale": {"metres_per_pixel": 0.0123, "method": "dimension", "from_dimension": "d1", "confidence": "measured"},
  "dimensions": [
    {"id": "d1", "value_m": 3.81, "datum": "inner", "between": {"walls": ["w4", "w2"], "axis": "x"}, "printed": "12'-6\""}
  ],
  "wall_height": 2.4,
  "walls": [{"id": "w1", "a": [0.0, 0.0], "b": [3.96, 0.0], "thickness": 0.15, "kind": "exterior"}],
  "openings": [{"id": "o1", "wall": "w1", "type": "door", "offset": 1.0, "width": 0.9, "height": 2.1, "sill": 0.0}],
  "rooms": [{"id": "r1", "label": "Kitchen", "floor": "tile"}],
  "materials": {"floor:tile": "#bfb8a8", "wall": "#f2efe9"}
}
```

Rules:
- Walls are centrelines plus thickness. Printed dimensions are not centrelines. Each dimension carries `datum`: `inner` (face to face), `outer` (outside face to outside face) or `centre`. The datum is read from the drawing or asked, never assumed. A 3.81 m inner dimension with 0.15 m walls is a 3.96 m centreline. The dimension checker converts using wall thickness before comparing.
- Metres, origin bottom-left of the plan, x right, y up. Elevation z up.
- Mapping to glTF (Y-up, right-handed): plan (x, y, z) becomes glTF (x, z, -y). Defined once in `to_gltf()` and used by nothing else.
- Openings reference a wall by id plus an `offset` along the centreline from point `a` to the opening's start, so moving a wall moves its doors.
- Unknown fields are preserved. Guessed values carry `"confidence": "guessed"` and show in a different colour in the overlay.
- `plan_px.json` is the same shape with coordinates in image pixels (origin top-left, y down) and no scale. `to_metres(plan_px, scale)` flips y and scales. It is one function with its own tests.

## Pipeline, step by step

1. **Ingest.** Rasterise to 300 DPI, deskew by the dominant Hough angle, record the hash. Write `grid.png`: the source with labelled pixel gridlines every 100 px, so a person can read coordinates. Reject images with no dominant straight lines (curved sketches, photos at an angle).
2. **Scale.** Priority: (a) the person gives two pixel points on a printed dimension, its value and its datum; (b) OCR matches a dimension string to the nearest dimension line, still confirmed by the person; (c) a standard door width (0.9 m) as a last resort, flagged `guessed`, stated in the first line of `report.md`. Never silently assume a scale. If two dimensions disagree after conversion by more than 3%, warn.
3. **Extract** in pixel coordinates to `plan_px.json`: wall centrelines, thickness (dark band width, snapped to 0.1, 0.15, 0.2, 0.3 m after scaling), openings, room labels. Snap endpoints to a 5 cm grid and merge endpoints within 10 cm so rooms close.
4. **Overlay and review.** After `to_metres`, render `overlay.png`: walls red, openings blue, room polygons translucent, guessed values orange, with a metre grid and a scale bar drawn on the source image. A person approves or edits. Required for anything but a throwaway.
5. **Validate**, failing with the id of the offending item (tests 2 to 4).
6. **Geometry** (all pure Python, no mesh booleans):
   - Each wall is its own solid. Its footprint is the centreline buffered by half the thickness with square caps and mitre joins (`cap_style="square"`, `join_style="mitre"`), so outer corners stay square and a free end extends half a thickness. Rounded styles are wrong here.
   - Overlaps at corners and T-junctions are resolved by a fixed priority: exterior walls first, then ascending id. Later walls are clipped by the footprints of earlier ones, so pieces are disjoint, nothing is coplanar, and each piece keeps its wall's identity.
   - Openings split a wall along its length into segments: solid full-height segments either side, and in the opening span a sill piece (0 to `sill`) and a lintel (`sill + height` to `wall_height`). Pieces with zero height are not created, so a door with `sill: 0` has a lintel only. Each piece is an extruded polygon, watertight on its own.
   - Windows add a thin transparent glass pane in the span. Doors are left open by default; a door leaf mesh is optional.
   - Floors: one 0.1 m slab per room polygon, material from `rooms[].floor`. Ceiling off by default.
   - Export `model.glb` with named nodes (`wall_w1_seg0`, `wall_w1_lintel_o1`, `door_o1`, `floor_r1`).
7. **Viewer.** `viewer.html` loads three.js through an import map from `/vendor/` and fetches `model.glb` over HTTP. Start the server (`python -m http.server --directory out 8765`) before Playwright, and never use `file://`, where Chromium blocks the fetch. Launch Chromium with `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`. The page exposes `window.projectToPixel(x, y, z)` for calibration and sets `window.__ready = true` after the first frame.
8. **Renders** via Playwright, waiting for `__ready`:
   - `topdown.png`: orthographic camera over the plan bounds plus a 5% margin.
   - `iso_cutaway.png`: walls clipped at 1.2 m.
   - `eye_<room>.png`: camera at 1.6 m placed at `representative_point` of the room polygon (always inside it), nudged to be at least 0.3 m from any wall, looking toward the room's farthest wall.
   - Fallback if WebGL cannot start: a `matplotlib` top-down render straight from the shapely footprints.
   - Also `overlay.png` and `report.md` (scale source and datum, counts, warnings, guessed values).
9. **Optional Blender pass.** `blender --background --python build_from_plan.py -- plan.json` for Cycles renders and a walkthrough.

## Output files

`plan.json` (source of truth), `plan_px.json` (what extraction produced), `grid.png`, `overlay.png`, `model.glb`, `viewer.html` plus `vendor/`, `renders/*.png`, `report.md`.

## Tests first (acceptance checks; write before the code)

Fixtures: (A) a clean 4 m by 3 m rectangle with one door; (B) an asymmetric L-shaped three-room plan with doors, windows and a marker door on the west wall only, so a mirror shows; (C) a skewed, noisy scan; (D) a photo of a hand sketch.

1. **Scale and datum:** On A, the inner dimension 3.81 m is reproduced within 2% measured face to face. The same file with the datum changed to `outer` fails. With no dimension, `scale.confidence` is `guessed` and `report.md` says so on line 1.
2. **Schema:** A zero-length wall, an opening wider than its wall, or an opening pointing to a missing wall fails with that id in the message. Unknown fields survive load and save.
3. **Closure:** Every room polygon is closed. Room areas plus wall area are within 3% of the outer footprint area.
4. **Openings:** Each opening lies inside its wall's centreline span and at least 0.2 m from either end, and two openings on a wall do not overlap.
5. **Corner shape:** The union of wall footprints of fixture A has exactly 4 outer vertices, and its area equals the analytic value to 1e-6. (This catches round joins.)
6. **Geometry:** `model.glb` loads. Each piece is watertight (`trimesh.is_watertight`). No piece has zero volume. The bounding box is within 1 cm of `plan.json` after the `to_gltf` mapping. Pieces of different walls do not overlap (pairwise volume of intersection is 0). Every wall, opening and room has at least one named node.
7. **Handedness:** On fixture B, the marker door's centre in the GLB, mapped back by the inverse of `to_gltf`, equals its `plan.json` position within 1 cm, so a mirrored model fails.
8. **Determinism:** The same `plan.json` produces a byte-identical GLB (golden file; update it on purpose).
9. **Round trip:** Moving wall `w1` moves its doors; tests 3, 4 and 6 still pass. `to_metres` followed by the inverse returns the input pixels within 0.5 px.
10. **Render:** A WebGL smoke test first (one cube renders, or the fallback is used and logged). PNGs are non-blank (more than 3 distinct colours, size above a threshold). Console errors fail the test; warnings are allowed only if they match an explicit list of known SwiftShader messages. In `topdown.png`, projected wall corners from `window.projectToPixel` match the overlay's wall pixels within 3 px.
11. **Eye cameras:** On a concave room in B, every `eye_*` camera is inside the room polygon and 0.3 m or more from walls.
12. **Failure behaviour:** Fixture D is rejected with a clear message. An image with no scale produces output flagged `guessed`.
13. **Pinned environment:** `pip install -r requirements.lock`, `npm ci` and `make test` pass on a clean container.

Pass means all green. Each real-world bug becomes a new fixture and a test.

## Minimal first version (about one to two days)

No computer vision.

1. Write the `pydantic` schema, `to_metres`, `to_gltf`, and the validator.
2. Pick one real plan. Run ingest to get `grid.png`. Write `plan_px.json` by reading pixel coordinates off the grid (local, nothing uploaded), or have Claude draft it from the image if the plan is not confidential. Give the scale step two pixel points, the printed value and the datum.
3. Run `to_metres`, make `overlay.png` with the metre grid, and correct by hand until it matches.
4. Write `build_glb.py` as in step 6.
5. Write `viewer.html` (import map, vendored three.js), the localhost server, and the Playwright script for `topdown.png` and `iso_cutaway.png`, with the matplotlib fallback.
6. Run tests 1 to 11 on fixtures A and B.

This proves the parts that are hard to fix later (schema, datum, axes, geometry) and delivers a real result. Add extraction automation once you have 5 to 10 reviewed plans to measure it against.

## Roadmap

- **v2:** OCR dimensions and automatic scale; Hough wall detection; door-arc detection; accuracy reported as wall precision and recall against reviewed plans.
- **v3:** Materials, furniture from a symbol library, ceilings, multi-storey (`levels[]`), Blender backend for photoreal renders and video.
- **Later:** a small web editor that drags walls over the overlay. The schema is what it edits.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Wrong scale or datum | Everything the wrong size, looks plausible | Datum recorded; cross-check a second dimension, warn above 3%; shown in the report |
| Curved walls, diagonals | Hough gives staircase segments | v1 straight walls only; flag arcs and ask for manual entry |
| Scan noise, hatching, furniture symbols | False walls | Overlay review; drop short isolated segments; filter by thickness |
| Open-plan or unclosed rooms | `polygonize` returns nothing | Validator names the gap and coordinates; allow `kind: "virtual"` walls |
| Door symbols vary by country | Missed openings | Manual opening entry is first class; detection only suggests |
| Mirrored or rotated model | Passes size checks, wrong plan | `to_gltf` in one place; asymmetric fixture test |
| Mesh failures | Holes, non-manifold walls | Disjoint extruded pieces, no booleans; per-piece watertight test |
| No WebGL in container | Blank renders | SwiftShader flags, smoke test, matplotlib fallback |
| AI-generated 3D images | Invented walls | Never a geometry source; labelled illustrative |
| Vision-LLM drafts | Plausible but wrong coordinates | Pixel grid, overlay, validation, `guessed` flag |
| Private plans | Upload to a model provider | Local manual mode; the upload is named, not hidden |
| Dependency drift | Breaks in six months | Lock files, vendored three.js, golden files, schema migrations |
| Several storeys, very large plans | Slow, wrong stacking | Out of v1; schema leaves room for `levels` |

## Trade-offs made on purpose

- GLB plus three.js over Blender-first: runs headless here, easy to share. Blender stays optional because it reads the same file.
- Human review is a required step: plans vary too much for automatic accuracy, and an overlay with a metre grid turns silent errors into fixable ones.
- A boring schema over clever detection: detection tools will change, the data contract should not.
