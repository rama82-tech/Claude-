# Turning a 2D Floor Plan into a 3D Model: Build Plan

## The short answer

Build a pipeline in which **computer vision reads the plan into a small JSON file, and a script builds the 3D model from that JSON**. Do not ask an AI image generator to draw the 3D model. Use the generator only as an optional last step for pretty pictures.

The one idea to remember: **the JSON file is the product.** Everything before it is "reading the plan". Everything after it is "building and rendering". You can fix, hand-edit and re-run either half without touching the other.

```
plan image/PDF -> [1 Prepare] -> [2 Scale] -> [3-5 Read: walls, doors, windows, text]
   -> plan.json (you review and fix it) -> [7 Build 3D] -> model.glb / .blend
   -> [9 Render] -> PNG images, video, web viewer
```

## Assumptions

- The plan is a typical architect's or agent's drawing: top-down, mostly straight walls, with at least one printed dimension or a length you can type in.
- One floor per image in version 1. Multi-storey is a later version (see "Multi-storey").
- "3D model" means a walkable, extruded house (walls with door and window holes, floors, optional ceilings and furniture), not a surveyed CAD model.
- Environment: Claude Code cloud container with Linux, Python, Node, Chromium and Playwright. No GPU, no desktop.
- Version 1 uses no paid services and no Blender.
- A human spends two minutes checking the overlay before the result is trusted.

## Two opposing answers, and what I keep from each

**Answer A: "Be exact. Detect the walls with CV, build real geometry."**
Strength: right dimensions, real door holes, files that open in Blender, game engines and viewers, and the model is editable.
Weakness: real plans are messy (tilted scans, varied symbols, hatching, furniture). Pure CV can fail silently.

**Answer B: "Feed the plan to an AI image model or vision LLM and let it make the 3D picture."**
Strength: works on any style, no tuning, looks good in seconds.
Weakness: it invents walls, moves doors, changes room sizes, and cannot guarantee scale. The output is a picture, not a model.

**Synthesis (what this plan does):**
1. Geometry comes from deterministic code (A), because accuracy is the point.
2. A vision LLM (Claude) is a reader and checker, not a drawer: it names rooms, spots openings the CV missed, and compares a render with the plan.
3. A human confirms a flat 2D overlay before any 3D work.
4. An AI image generator is used only after the model exists, from a clean render, and its output is labelled "illustrative, not to scale".

## Tools

| Job | Tool | Why |
|---|---|---|
| PDF to image | PyMuPDF (`fitz`) | Rasterises at 300 dpi. For vector PDFs it can also read the lines directly, which is more accurate than pixels. |
| Cleanup and wall finding | OpenCV, scikit-image | Deskew, threshold, morphology, Hough, skeletonize (`skimage.morphology.skeletonize`). |
| Text and dimensions | Tesseract via `pytesseract`, or EasyOCR | Reads dimensions and room names. |
| Optional ML wall segmentation | A pretrained floor-plan model (for example CubiCasa5k-based) | Fallback for messy scans. Heavy, so not in version 1. |
| Reading and checking | Claude vision | Names rooms, finds missed openings, compares render to plan. |
| Geometry | `shapely` (2D polygons), `trimesh` + `manifold3d` (meshes and boolean cuts), `mapbox-earcut` | Light, pure Python, no Blender. |
| Full-quality renders (later) | Blender headless with `bpy`, **Cycles on CPU** | Materials, lights, quality images. See "Blender in the container". |
| Web viewer and previews | three.js with `GLTFLoader`, Playwright | Interactive viewer and quick preview images. |
| Pretty pictures (optional) | Image-to-image AI model (for example via Scenario or Higgsfield, if connected) | Photoreal styling of a render. |

Blender through an MCP server fits when you have a desktop Blender open. In the cloud container use `blender -b -P build.py` instead.

### Blender in the container (untested until you smoke-test it)

Try in this order: (1) `pip install bpy` (the official wheel, needs a matching Python version), (2) download the official Blender Linux tarball and run `./blender -b`. Smoke test: render a default cube with Cycles at 16 samples and note the time. Do not promise Blender outputs until this passes. EEVEE needs an OpenGL context and is unreliable without a GPU, so plan on **Cycles only**. Expect roughly a minute or more per image at moderate samples with the denoiser on CPU, and measure it on your machine.

## The pipeline, step by step

### Step 1. Prepare the input

1. PDF to PNG at about 300 dpi. Keep vector data if the PDF has it.
2. Deskew: find the dominant line angle (Hough) and rotate so walls are horizontal and vertical.
3. Crop margins and the title block.
4. Greyscale, adaptive threshold (not a single global threshold), remove specks.
5. Save the cleaned image and a log of what was done.

### Step 2. Set the scale (first, because everything depends on it)

Choose one source, in this order:
1. **You name it:** "this wall, from point P to point Q, is 4.2 m". The tool takes two pixel points (or a wall id after detection) and a length. Most reliable.
2. **A printed dimension line:** OCR the number, detect the two tick marks, compute pixels per metre.
3. **A scale bar** drawn on the plan.
4. **A standard door** (about 0.9 m or 36 in). Rough fallback only, labelled "approximate, plus or minus 15 percent".

Apply it: `metres = pixels / px_per_m`. Compute scale from several dimensions when you have them and compare. If they disagree by more than 3 percent, stop and show both numbers.

**Axis rule (write this into the code once):** image y runs downward, 3D Y runs upward. Convert with `Y_world = (image_height - y_px) / px_per_m` and `X_world = x_px / px_per_m`. Without this flip the model is a mirror image of the plan.

**Sanity check (door-width only):** the median detected door width should fall between 0.6 and 1.2 m. If not, print "scale looks wrong" and stop for confirmation. Room sizes are only warnings (a 1.2 x 1.5 m closet or a 20 m garage is legitimate), and the user can always confirm and continue. Wall and ceiling heights are not on a plan, so they are defaults, never a scale check.

### Step 3. Find the walls

1. **Measure stroke widths first.** Compute a distance transform of the dark pixels and histogram the stroke half-widths. You will see peaks: thin lines (dimensions, furniture, hatching), then wall thicknesses (for example 0.1 m partitions, 0.23 m or 0.4 m outer walls).
2. **Open, don't erode to the wall width.** Apply a morphological opening with a kernel just wider than the thin-line peak and clearly narrower than the thinnest wall peak (for example, thin lines 2 px, thinnest wall 12 px, use a 5 px kernel). Thin lines vanish; every wall thickness survives. Do not use a kernel equal to the wall width, because that deletes the walls.
3. Skeletonise the result (`skimage.morphology.skeletonize`) into centre-lines.
4. For each centre-line, read **its own thickness** as twice the median distance-transform value along it.
5. Snap to horizontal or vertical only if within about 3 degrees. Merge nearly collinear lines. Connect endpoints that nearly touch.
6. Record each wall as `a`, `b`, `thickness`. Angled and curved walls (kept as short polyline segments) are not snapped.

If walls are drawn as solid-filled or hatched regions, use "region mode": treat large dark connected components as wall polygons instead of lines.

### Step 4. Find doors and windows

- **Doors:** a gap in a wall run plus a quarter-circle arc next to it (`cv2.HoughCircles` or contour fitting). The arc gives hinge side and swing.
- **Windows:** a gap with two or three thin parallel lines.
- **Sliding doors, bifolds, garage doors:** "opening, type unknown", with a default.
- **Claude vision pass:** show the crop with numbered detected openings and ask "which are missing or wrong?" Merge the answers.

Each opening records `wall`, `offset` along the wall, `width`, `type`, and for windows `sill` and `head`.

### Step 5. Rooms and text

1. Turn walls into polygons with `shapely.polygonize` to get enclosed rooms.
2. OCR text and assign each label to the room polygon that contains it.
3. Printed room sizes are a **cross-check**: a mismatch becomes a warning, never a silent fix.

### Step 6. Write `plan.json` and review it

```json
{
  "units": "m",
  "scale_source": "user:P-Q=4.20m",
  "wall_height": 2.7,
  "walls": [
    {"id": "w1", "a": [0, 0], "b": [6.0, 0], "thickness": 0.23, "kind": "exterior"}
  ],
  "openings": [
    {"id": "d1", "wall": "w1", "offset": 1.2, "width": 0.9,
     "type": "door", "swing": "in-left", "confidence": 0.92},
    {"id": "n1", "wall": "w1", "offset": 3.5, "width": 1.5,
     "type": "window", "sill": 0.9, "head": 2.1, "confidence": 0.85}
  ],
  "rooms": [
    {"id": "r1", "label": "Kitchen", "polygon": [[0,0],[6,0],[6,4],[0,4]], "floor": "tile"}
  ],
  "warnings": ["Room r3 area differs 7% from printed size"]
}
```

**Review (the most important quality control):** draw `plan.json` over the original image as coloured lines with opening ids and warnings. The user types corrections ("move d1 left 0.2") or edits the JSON, the overlay is redrawn, and only then do you continue.

### Step 7. Build the 3D geometry

1. **Corners and junctions.** Make each wall a 2D rectangle from its centre-line with **square caps**: `LineString(...).buffer(t/2, cap_style=3)` (shapely: 1 round, 2 flat, 3 square), or extend each end by t/2 yourself. Flat caps (style 2) leave a t/2 by t/2 notch at every L corner and T-junctions that stop short. Then `unary_union` all rectangles and extrude **once**. Corners come out clean because the squared ends overlap at joints.
   - Where a wall ends at a free end (not a joint), a square cap makes it t/2 too long. Trim free ends back by t/2, or accept the small error and note it. When walls were measured from outer faces, use the faces for overall dimension checks.
2. **Openings.** Subtract a box for each door or window: width `o.width`, z from 0 (door) or `sill` (window) to `head`, depth `thickness + 0.02`, centred on the wall at `offset`. `trimesh` boolean difference with the `manifold3d` backend.
3. **Floors.** Extrude each room polygon down 0.1 m, with a material per room.
4. **Ceilings.** Optional, hidden by default so you can look in from above.
5. **Door and window objects.** Simple frames, a door leaf at the swing angle, a glass plane for windows.
6. **Stairs.** A run of equal steps, marked "approximate".

### Step 8. Materials and lighting

- Walls white plaster, floors by room type (tile in kitchen and bath, wood elsewhere), glass for windows. Start with flat colours, then free PBR textures (for example ambientCG).
- Daylight: a sun lamp plus sky. Soft area light behind each window. Night: a point light per room.
- Cameras: top-down orthographic ("3D floor plan"), 45 degree isometric cutaway (ceiling hidden, front walls lowered), eye level (1.6 m) in each room.

### Step 9. Export and render

| Output | File | Used for |
|---|---|---|
| Interactive model | `model.glb` | Web viewer, Blender, most tools |
| Editable scene | `model.blend` | Further work in Blender (later version) |
| Plain mesh | `model.obj` or `.stl` | 3D printing, other software |
| Overlay check | `overlay.png` | Proof walls match the plan |
| Renders | `topdown.png`, `iso.png`, `room_<name>.png` | Sharing |
| Walkthrough | `tour.mp4` | Frames along a camera path, joined with `ffmpeg` |
| Viewer | `index.html` (three.js) | Orbit and click rooms |
| Data | `plan.json` | The single source of truth |

Previews in version 1 come from three.js in headless Chromium. Quality renders come later from Blender Cycles on CPU.

### Step 10. Automatic self-check

- Render the top-down view at the same scale and position as the source image, then overlay the outlines and count how many wall pixels agree.
- Ask Claude vision: "Here are the plan and the render. List differences."
- Fail and print the differences if agreement is under a threshold.
- **Mirror test:** the overlay is drawn in image space, so it cannot catch a flipped model. Check the 3D render against the plan using an asymmetric feature (an L-shaped corner or the front door position), not only wall pixel overlap.

## Accuracy summary

1. Scale from the user or several sources that must agree, with the axis flip applied once.
2. Walls from stroke-width analysis and opening, thickness per wall.
3. Openings from gap plus symbol.
4. Every number in `plan.json` carries a source and confidence. Low-confidence items are listed for review.
5. Human overlay review before any 3D.
6. Render-versus-plan check afterwards, including the mirror test.

## Stress test: hostile inputs and patches

**1. Tilted phone photo with shadows and a curved page.** Deskew does not fix perspective, and shadows break thresholding. Patch: four-point perspective correction (user clicks the four corners, or code finds the largest quadrilateral), adaptive threshold, and if wall confidence stays low, ask for a flatter scan instead of building a confident model.

**2. No dimensions and no scale bar.** Patch: refuse to continue until the user gives one known length, or offer the door estimate labelled "approximate, plus or minus 15 percent". The label stays in every output file name and render.

**3. Cluttered plan (hatched walls, furniture, dimension strings, grids, big title block).** Patch: crop the title block; the opening removes thin lines; hatched or filled walls use region mode; short segments (under about 0.4 m) not connected to the wall network are dropped; the overlay review catches the rest.

**4. Curved or angled walls, spiral stairs, open-plan layouts.** Patch: curves kept as polylines with no snapping above 3 degrees; open plans get user-drawn "virtual dividers" (zero-height lines) so labels map to the right area; spiral stairs become a labelled placeholder block; the tool lists what it could not model.

**5. Multi-page PDF with several floors, a site plan and a legend, in feet and inches, with OCR errors ("5'-6" read as "56").** Patch: classify each page first (Claude vision: floor plan, elevation, site plan, legend), process only floor plans, ask which page is which floor, parse feet-inches with a strict pattern, and use the door-width sanity check to catch a 10x scale error.

**6. Two wall thicknesses in one plan (0.1 m partitions, 0.4 m outer walls).** Patch: stroke-width histogram and a kernel narrower than the thinnest wall, with thickness read per wall.

**7. Mirrored output.** Patch: the axis rule in Step 2 and the mirror test in Step 10.

**8. Blender will not install or is too slow.** Patch: version 1 does not need it. Keep trimesh plus three.js as the baseline.

## Multi-storey (version 3, not version 1)

- Process each floor page separately, producing one `plan.json` per floor.
- **Alignment:** pick a shared anchor present on every floor (a stair void, a lift shaft, or two column positions) or have the user click the same two points on each page. Translate each floor so the anchors coincide. Require per-floor scales to agree within 3 percent, otherwise stop.
- **Heights:** a `storey_height` setting (default 2.7 m wall plus 0.3 m slab). Floor n sits at `n * storey_height`.
- **Stairs:** cut a stair opening in the slab above using the stair polygon from the lower floor, and place a stepped run joining the two levels.
- Roofs are out of scope until a roof plan or elevation is supplied.

## Risks and honest limits

| Risk | How bad | What to do |
|---|---|---|
| Wrong scale | High | Several sources, door-width check, refuse to guess |
| Mirrored model | High, and invisible in the overlay | Axis rule and mirror test |
| Missed or false walls | High | Overlay review, self-check render |
| Door and window types vary by country and style | Medium | Default type plus Claude vision pass; user edits JSON |
| Plans contain no heights | Medium | Defaults (wall 2.7, sill 0.9, head 2.1), editable |
| AI-image renders look right but are wrong | High if shared as fact | Label "illustrative"; never measure from them |
| Blender or bpy in the container is unproven | Medium | Smoke test first; baseline works without it |
| Copyright or privacy of the plan | Low to medium | Process locally; do not upload someone else's plans to third parties without permission |
| Not for construction | Legal | Visualisation only, not an engineering document |

## The smallest version you can build first

**Goal:** one clean plan image plus one typed length in; one `.glb` and one `preview.png` out. About a day. No Blender, no AI image generation.

Scope:
- Input: a clear PNG with thick black walls. You supply the scale as two pixel points plus a length (for example from the overlay tool, or by reading pixel coordinates in an image viewer).
- Walls only, found with OpenCV. Doors and windows are cut where you list them in a small hand-written file (version 1 does not detect them).
- Output: `model.glb`, `overlay.png`, `preview.png`.

Steps:
1. Install: `pip install opencv-python-headless scikit-image shapely trimesh manifold3d numpy mapbox-earcut` (add `pytesseract` and `apt install tesseract-ocr` only when you add OCR; `playwright` and Chromium are already present).
2. `read_plan.py`: threshold, opening with a kernel chosen from the stroke-width histogram, `skimage.morphology.skeletonize`, Hough lines, snap, apply scale and axis flip, write `plan.json`.
3. `overlay.py`: draw the JSON on the image. Look at it. Fix the JSON by hand if needed.
4. `build.py`: buffer centre-lines with square caps, union, extrude, subtract door and window boxes, add a floor slab, export `model.glb`.
5. `preview.html` loads the GLB with `GLTFLoader` and `OrbitControls`. **Serve it over HTTP** (`python -m http.server 8000`), because Chromium blocks `fetch` of the GLB from a `file://` page. A Playwright script opens `http://localhost:8000/preview.html` and saves `preview.png`. Launch Chromium with software WebGL flags (for example `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`; exact flags vary by Chromium version) and check the screenshot is not blank. If WebGL fails, fall back to a `trimesh` scene rendered to an image with matplotlib.

Core of `build.py` (sketch):

```python
import json, trimesh
from shapely.geometry import LineString
from shapely.ops import unary_union

plan = json.load(open("plan.json"))
H = plan["wall_height"]

# cap_style=3 is SQUARE, which closes corners (2 is flat and notches them)
footprint = unary_union([
    LineString([w["a"], w["b"]]).buffer(w["thickness"] / 2, cap_style=3)
    for w in plan["walls"]
])
walls = trimesh.creation.extrude_polygon(footprint, H)

for o in plan["openings"]:
    w = next(x for x in plan["walls"] if x["id"] == o["wall"])
    cutter = make_cutter(w, o)   # box: along wall at o["offset"], width o["width"],
                                 # z sill..head, depth w["thickness"] + 0.02
    walls = walls.difference(cutter)   # needs manifold3d

walls.export("model.glb")
```

**Version 1 works when:**
- the overlay lines sit on the walls of the original image;
- the model's outer width equals your typed length when that length was measured between the same faces (check the corners are closed, not notched);
- the L-shaped or other asymmetric feature appears on the same side as in the plan (not mirrored);
- the preview shows holes where doors and windows should be.

## Decision checklist

- Do I have one trusted real-world length? If not, stop and get one.
- Does the overlay match the plan? If not, fix `plan.json` first.
- Is the 3D render the same way round as the plan (not mirrored)?
- Do the corners close and the outer size match? If not, check cap style.
- Does the render match the plan? If not, do not share it.
- Are AI-generated images labelled "illustrative"?
