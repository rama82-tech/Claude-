ATTACK 1 [MAJOR] The code labelled "exactly what was tested" fails on the stated install
Where: Assumptions: "tested in a fresh Python venv (`shapely`, `trimesh`, `numpy`, `scipy`)"; build.py calls `trimesh.creation.extrude_polygon`; the install line appears only later, in the minimal first version.
Problem: In a venv with exactly those four packages, `extrude_polygon` raises `ValueError: No available triangulation engine!`. It needs `mapbox-earcut` (or manifold3d or triangle). I reproduced this. A user who follows the verified-environment claim and runs build.py gets a crash on the first extrusion. The claim of what was tested is therefore false as written. It only works after the separate install line in the "Minimal first version" section.

ATTACK 2 [MAJOR] The GLB is Z-up, but glTF and three.js are Y-up, and the plan never says so
Where: build.py extrudes along Z (`extrude_polygon(p, z1 - z0)`, walls "0 to 2.7 m"), then `trimesh.Scene(meshes).export(out)`. Step 5 and the viewer.html / shot.py steps load that GLB in three.js and screenshot "top-down and isometric" views.
Problem: I loaded the exported file and the 2.7 m wall height is still on the Z axis (bounds z from -0.2 to 2.7). trimesh does not rotate to Y-up. In a three.js viewer with Y-up, the house lies on its side, so walls point toward the camera and the "top-down" shot is really a side elevation. The plan has no rotation step and no mention of axes. The other plan states "Y-up for GLB (Z-up inside Blender)". So the stated Done-when ("you can orbit it in a browser", a top-down PNG) fails on first run until the user debugs the orientation.

ATTACK 3 [MAJOR] Floor is missing under every doorway, leaving a 10 cm trench
Where: build.py: `fl = r.difference(foot)` then `ext_poly(fl, -0.1, 0, "floor", ...)`. `foot` is the full wall footprint, uncut by openings.
Problem: The floor layer (-0.1 to 0) is room polygon minus the entire wall footprint, including the part of the footprint under each door opening. Under D1, D2 and D3 no floor mesh exists between rooms or at the exterior door. Only the slab top at -0.1 m is there. Every doorway in the tested example therefore has a 10 cm gap in the floor. The "17 pieces, watertight" and area checks do not catch this, because they test validity and room areas, not coverage.

ATTACK 4 [MAJOR] Step 8 is not implementable with the code given: meshes are unnamed and the colours are not PBR
Where: Step 8: "Name every mesh by role (`wall_ext`, `wall_int`, `floor_Living`, `glass`, `door`), then map roles to materials ... flat PBR colours exported in the GLB". Code: `ext_poly(poly, z0, z1, name, color)`.
Problem: `name` is never used. The exported scene's geometries are `geometry_0`, `geometry_1`, and so on. There is also no wall_ext / wall_int split: all walls are one unioned `walls` mesh with a single colour, so exterior and interior walls cannot get different materials as step 8 and the "slightly darker exterior" claim require. The colours are `face_colors` (vertex colours), not PBR materials. The role-to-material mapping the plan relies on for materials has no hook in the working code.

ATTACK 5 [MAJOR] The core accuracy mechanism, "Claude reads the plan into JSON", is under-specified for the user
Where: Pipeline step 3 ("Ask the vision model for walls as centreline segments in pixel coordinates ... Convert to metres in code") and the Minimal first version, step 2.
Problem: The only schema shown is the metre-based JSON for a hand-made example. There is no pixel-coordinate schema, no prompt, no converter script, and no `overlay.py`, `viewer.html` or `shot.py`. The scale-and-flip formula appears only inline for the example. A non-specialist cannot go from "my PNG" to a `plan.json` that `build.py` accepts without inventing all of this. The step also presents the "one to two days" estimate as covering this missing code.

ATTACK 6 [MAJOR] The 2% two-dimension rejection rule breaks on common real plans
Where: Step 1 and Risks: "Reject images where the two printed dimensions disagree by more than 2%". Step 2 also says "(d) refuse and ask".
Problem: Many floor plans are explicitly "not to scale", or are marketing or brochure plans where printed dimensions are authoritative and the drawing is distorted. Many photos and scans also have non-uniform scale. For these plans the rule hard-rejects the input rather than falling back to per-wall use of printed dimensions. The plan's own advice, "Prefer printed numbers to measured pixels", conflicts with rejecting on pixel mismatch. Its Done-when ("within 1% of the printed dimensions") also cannot be met on such inputs.

ATTACK 7 [MINOR] build.py crashes on disconnected walls, and the open-plan "thickness 0 divider" fix is not valid in the code
Where: `ext_poly(Polygon(foot.exterior), -0.2, -0.1, "slab", ...)`; the Risks row "Add an invisible 'room divider' segment with thickness 0".
Problem: If the footprint union is a MultiPolygon, for example a detached garage wall or an unconnected partial wall extracted by mistake, `foot.exterior` raises AttributeError. The input the plan itself calls likely (stray segments) therefore crashes the build. Separately, a divider with `t=0` is not a documented schema entry. `buffer(0)` of a line is empty, and the code gives no `kind: divider` handling, so the stated mitigation is not supported by the code.
