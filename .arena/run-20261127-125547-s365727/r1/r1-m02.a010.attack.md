ATTACK 1 [MAJOR] The headline v1 command cannot run as specified (--known depends on rooms that do not exist yet)
Where: Section 1 `python fp23d.py plans/house.pdf --page 1 --known "Living room width=14'-6\""` and Step 4 "the user picks the room, the pipeline measures that room's inner width in px"; Section 9 v1 item 3 "Scale from --known only (no OCR)" and "(v1.3) rooms + names + materials".
Problem: Scale is step 4 but rooms are only polygonised in step 6, and room names come from OCR of labels, which v1 explicitly excludes (rooms and names arrive in v1.3, OCR in v1.2). In v1 there is no "Living room" to look up, so `--known` cannot be resolved and `px_per_m` cannot be computed. The user is told this command works on day 1. No fallback is given, such as two clicked points like "x1,y1,x2,y2,length". The plan never says how v1 identifies the measured span.

ATTACK 2 [MAJOR] The web viewer and its Playwright test fail as written (file:// fetch, wrong relative path, CDN dependency)
Where: Step 9 "`page.goto("file:///.../viewer/index.html")`", with `viewer/index.html` loading `house.glb` and three.js from an import map at `cdn.jsdelivr.net`. The Section 1 table puts `house.glb` in `out/house/` and the viewer in `out/house/viewer/`.
Problem: GLTFLoader loads the file with fetch/XHR. Chromium blocks that from a `file://` origin ("Cross origin requests are only supported for protocol schemes http, https..."), and module scripts from `file://` are blocked too. The screenshot will show an empty scene unless Chromium gets `--allow-file-access-from-files` or a local `http.server`. Neither is mentioned. The viewer sits in `viewer/` while the GLB is one level up, and the path is never specified. The import map needs outbound access to jsdelivr, and the task only says Python, Node and Chromium are installed. There is no vendored three.js and no offline fallback. The one "test the glb" step the plan offers is therefore not actionable as written.

ATTACK 3 [MAJOR] Isometric cutaway logic contradicts the wall-union step
Where: Step 8 item 4 "Join all walls with one Boolean UNION into one mesh per storey", versus the `iso_cutaway.png` bullet "any wall whose outward normal faces the camera and is taller than 1.2 m is set to 1.2 m tall".
Problem: After the union there is a single mesh, so there are no per-wall objects to lower. Re-heighting would mean re-running the build with per-wall heights, and the plan does not say so. Lowering a wall that already has window cutters applied (window head at 2.03 m, sill 0.91 m) leaves a window cut that runs through the new 1.2 m top. This gives a notch or sliver, not a clean cut-away. The "outward normal faces the camera" test is also undefined for interior walls, which have no outward side. This is one of the three renders the user asked for, and the described method does not produce it.

ATTACK 4 [MAJOR] Room-area check compares the wrong areas, so it gives false warnings on small rooms
Where: Step 6 "`shapely.ops.polygonize` over wall centreline linework ... If area differs more than 8% from a printed `NNN SF`/`m²` label"; Section 7 item 2.
Problem: Polygons built from centrelines include half a wall thickness on every side. Printed room areas are normally clear interior areas. A 1.5 x 2.4 m bathroom (3.6 m² printed) bounded by 0.115 m interior walls and one 0.20 m exterior wall comes out near 4.0 m², about 11% over, and trips the 8% warning with nothing wrong. Larger rooms drift by several percent. The plan never insets the polygon by half the wall thickness, so the check will cry wolf on small rooms and cannot detect a missed wall reliably. Section 7 also says "within 8%, warn above 3%", which contradicts the 8% threshold in Step 6.

ATTACK 5 [MINOR] Wall-thickness kernel sizes are wrong for the stated scales, and thickness is needed before it is measured
Where: Step 3 "morphological opening with a kernel just under wall thickness (about 0.6 x measured thickness, usually 5-9 px at 300 DPI)"; thickness measured "median distance-transform value ... times 2" after the walls are found.
Problem: At the common 1/4"=1'-0" (1:48), a 4.5 in wall is 0.094 in on paper, about 28 px at 300 DPI. An 8 in wall is about 50 px. At 1/8" scale a 4.5 in wall is about 14 px. "5-9 px" is off by 2 to 5 times, so a kernel taken from it removes nothing useful. The kernel also needs the thickness before the walls exist, because thickness is measured from the skeleton and distance transform. No bootstrap is given, such as a histogram of run lengths. A user who copies the numbers gets bad masks.

ATTACK 6 [MINOR] The CubiCasa5K fallback is not usable as described
Where: Step 3 item 3 "CubiCasa5K pretrained network (open weights ... Run on CPU; a 1000 px plan takes a few seconds)"; Section 3 "No internet-hosted model needed for v1".
Problem: There is no weight download source and no install or inference steps, and the weights are not on pip. They have to be fetched from an external host that the sandbox proxy may block. The model also outputs room and icon classes on a fixed dataset style (Finnish residential plans) with no metric scale. The plan names no `pip` package, repo or script entry point, so the user cannot act on this fallback. The "85-95% wall segmentation quality" figure that justifies the human-in-the-loop design is unsourced.

ATTACK 7 [MINOR] Materials and doors do not match what the delivered files can carry
Where: Step 8 "Materials ... all procedural" (Wave, Noise, Brick textures) and Section 1 "`house.glb` ... Opens in any viewer"; schema `"swing": "in-left"`; Step 8 item 3 "door frame is a 0.05 m reveal".
Problem: glTF export does not bake Blender procedural node textures. The GLB, and so the three.js viewer, loses the oak grain and brick tile and shows flat base colours, with no texture-baking step. The `swing` field is in the schema, but nothing builds a door leaf or uses `swing`. The doors are bare holes plus a frame, which contradicts the door rendering implied by the swing field and the "hinged leaf" intent.
