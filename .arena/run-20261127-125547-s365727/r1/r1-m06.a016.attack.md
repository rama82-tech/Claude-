ATTACK 1 [MAJOR] The minimal first version builds walls from the reader the document itself calls unreliable, with no reconcile step
Where: "Vision models and image generators are good at recognising things and bad at exact geometry" versus v1 step 3: "send the image to Claude with the JSON schema; save plan.json ... Run OpenCV Hough as a cross-check and flag mismatches (no merging logic yet; only report)"
Problem: Step 4 says accepted walls take "B's coordinates (more precise)". The v1 skips that merge, so every wall coordinate in v1's plan.json is a VLM pixel guess. The check only reports mismatches. It does not correct them. The v1 therefore does the thing the Recommendation rejects. The Assumptions also say "A vision model API is available from the session", which is never verified for a Claude Code cloud container. If it is not available, v1 has no extractor at all, because Reader B is described only as a cross-check, and the only fallback is hand-writing plan.json.

ATTACK 2 [MAJOR] The reconcile rule would reject most VLM walls, and unconfirmed walls are not built, so the result is a near-empty model
Where: Step 4: "tolerance (default 1.5 percent of the plan's longest side, or 3 wall thicknesses, whichever is smaller)"; "Unconfirmed walls ... are not built unless the user confirms"
Problem: On a 1500 px plan with 100 mm walls at about 50 px/m, 3 thicknesses is about 15 px. VLM-reported pixel coordinates routinely drift by more than that. Reader A gives centre-lines and Reader B gives thick-stroke edges, and the document never defines how a wall from A is matched to a wall from B (distance between centre-lines? overlap? angle?). Many walls will fail to match, so the build gets few walls and the user must confirm each one by hand. The pipeline's central automation is unspecified, and the user would have to guess at the matching metric.

ATTACK 3 [MAJOR] The round-trip verification is circular and its thresholds contradict each other
Where: Step 9: "compare to the source's wall mask: intersection-over-union ... passes only if IoU is above ... 0.85 and no wall is more than 100 mm out"; the risk table: "Generated model 'looks right' but is wrong | Round trip check | Fails loudly"
Problem: (a) The "source wall mask" has to come from the same CV extraction that fed plan.json. Phantom walls (furniture, hatching) are then in both masks and the check passes. It can catch build bugs only. It cannot catch extraction errors, yet the table presents it as the safeguard for a wrong-but-plausible house. (b) IoU 0.85 on thin strokes is nearly impossible to hit. A 100 mm wall at 50 px/m is 5 px wide, so a 1 px edge offset already costs about 30% IoU. A 100 mm positional tolerance for a 100 mm wall would mean zero overlap. These two criteria cannot both be meaningful.

ATTACK 4 [MAJOR] The v1 build and render depend on Blender, which is only assumed to be installable, and the Eevee claim is optimistic
Where: Assumptions: "Blender can be installed in the container (apt or the official tarball)"; Step 8: "Blender's Eevee in headless mode is fast enough for these on a CPU-only container"
Problem: Nothing was checked. A plain `apt` Blender is often old, and a tarball download needs network access to its host. Recent Eevee needs OpenGL 4.3, which a headless CPU container often cannot give, and this is commonly where it crashes. The document says "may need software GL" but still gives "fast enough" as the headline. v1 steps 5 and 6 (`build.py`, `render.py`, GLB export) all require Blender, so the whole first version has no tested path in the stated environment. The trimesh/three.js fallback is mentioned only as an assumption, with no pipeline step and no code.

ATTACK 5 [MAJOR] The bare-number rule refuses the most common metric plan format
Where: Step 2: "Bare numbers with no unit are refused, not guessed. A bare '3750' could be mm, but a '12' could be feet or inches."
Problem: Metric architectural plans print dimensions as bare millimetres (3750, 4200) with the unit stated once in a title block or note, or not at all. Under this rule such a plan is refused. No mechanism is given for declaring a plan-wide unit, such as a CLI flag or the unit field, apart from the user-supplied reference length. The text also contradicts itself, because it says the "3750" is plausibly mm and then refuses it.

ATTACK 6 [MAJOR] The "vector PDF fast path" skips the hard part and is scored as if it did not exist
Where: Options table row F: "Geometric accuracy 5 ... Add as a fast path"; Step 0: "If vector lines exist, use them directly and skip most of CV"
Problem: A CAD-exported PDF puts walls, furniture, dimension lines, hatching, grid lines and the title block into one set of drawing paths. Walls are usually double outlines with fill, not centre-lines. Having vector lines does not tell the pipeline which lines are walls, so classification, double-line to centre-line conversion and thickness recovery are all still required. They are the same problems Reader B has on rasters. The document gives no method for any of this, so "skip most of CV" is wrong, and the 5/5 accuracy score is unearned.

ATTACK 7 [MINOR] The intake gate and the acceptance test contradict the pipeline's own deskew
Where: Step 0: "is at least about 1500 px on the long side"; test (c): "rotated 12 degrees ... Expected results: (c) clear REJECT or WARN"; Step 1: "Deskew"; risk table: "REJECT if skew is above 10 degrees"
Problem: A plain 12 degree rotation is exactly what Step 1 deskew fixes, so rejecting it is inconsistent. It also makes test (c) unable to tell a correct pipeline from a broken one. The 1500 px minimum is arbitrary and rejects typical real-estate listing floor plan images, which are often 800 to 1200 px wide, without saying that these are expected to fail.
