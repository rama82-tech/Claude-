# Build plan: 2D floor plan to 3D model

## Recommendation in one paragraph

Do not go straight from the image to 3D. Go image -> **plan.json** (a small, validated, human-checkable description of walls, openings, rooms and scale) -> 3D. Everything upstream of plan.json (PDF handling, computer vision, OCR, a vision LLM) is untrusted and gets checked. Everything downstream (geometry build, glTF export, renders, a three.js viewer) is deterministic code that reads only plan.json. Generative image models are used only for an optional "pretty preview", never as the source of geometry, because they invent walls and furniture and cannot hold dimensions.

The design fails loudly: if the scale cannot be established, the exterior does not close, or a door has no wall, the pipeline stops and says what is wrong. It does not produce a plausible-looking but wrong house.

The first version already takes an image or PDF and ends in a .glb. The fastest image-to-plan.json route in a Claude Code session is Claude's own vision, so v1 uses it, then lets a validator and a 2D overlay catch its mistakes.

## Assumptions

1. Input is one storey per file: a PNG/JPG scan or photo, or a PDF page. Multi-storey is a later extension (one plan.json per level).
2. Scale can be recovered from at least one of: a user-supplied real distance, a printed dimension, or a scale bar. If none exists, the pipeline asks for one measured distance. It may fall back to a door-width prior only when the user opts in, and the result is marked "approximate" everywhere.
3. Walls are mostly orthogonal. Curved and diagonal walls are phase two. Diagonal walls are flagged, not silently straightened.
4. Printed dimensions are assumed to run between wall faces (typical for room dimensions) unless `dim_reference` is set to `centre` in plan.json. Printed room areas, when present, are assumed to be net (interior) areas.
5. Units: input may be feet-inches or metric; internal storage is metres.
6. Defaults, overridable and never read from the drawing: wall height 2.7 m, door head 2.1 m, window sill 0.9 m and head 2.1 m, slab 0.1 m.
7. The container has Python, Node, Chromium and Playwright, and probably no GPU. Rendering is CPU. Blender availability is not assumed; step 0 tests it (see Environment).
8. A human (you) reviews a 2D overlay before the 3D build. Unattended conversion of arbitrary plans is not reliable, and this plan does not pretend otherwise.

## Architecture

```
input (PNG/JPG/PDF)
  -> 1 ingest + normalize (rotate, rasterize, hash)
  -> 2 scale calibration (tiered policy)
  -> 3 wall segments (CV, or vector paths from PDF), gaps kept
  -> 4 wall-run merge: bridge gaps into continuous walls + opening records; rooms
  -> 5 plan.json  <-- the contract; schema-validated
  -> 6 validation (errors block, warnings report) + 2D overlay for human review
  -> 7 geometry build (Blender headless, or the no-Blender fallback)
  -> 8 materials, lights, cameras
  -> 9 export + renders + web viewer + report
```

Three rules hold the design together:

- **plan.json is the only interface.** It can be hand-edited, produced by CV, or proposed by a vision model. The 3D stage does not care.
- **Every item carries a confidence.** Low-confidence items are flagged on the overlay, not silently kept.
- **Stop on failure.** Non-zero exit and a `report.md` listing every failed check. No "best effort" 3D.

## Geometry conventions (these make every check well-defined)

- A wall is stored as a **centreline** `a`-`b` plus `thickness`. Its solid is the rectangle of that width around the line.
- A **wall run** is a maximal straight chain of collinear walls bridged across openings. Openings belong to a run and are positioned by `offset` from the run's start along the centreline.
- Wall footprints are merged with a Shapely union. At corners and T-junctions the footprints overlap by design; that is not an error.
- A **room** has a net polygon: the area enclosed by the union of wall footprints, i.e. measured to the interior faces. `area_net` is the area compared with any printed area. Centreline area is never used for comparison.
- Expected model bounds = bounds of the union of wall footprints (thickness included).
- Printed dimension checks use `dim_reference` (face by default): a printed 4000 mm room dimension is compared with the face-to-face distance, not the centreline distance.

## Tool choices

| Job | Use | Why / caution |
|---|---|---|
| PDF | PyMuPDF (`fitz`) | Extract vector paths first (lines are real walls, text has exact coordinates). Rasterize at 300 dpi only if the PDF is a scanned image. |
| Raster cleanup | OpenCV, scikit-image | Rotation fix, threshold, morphology. |
| Wall/line extraction | OpenCV (Canny, Hough, `LSD`), skimage skeletonize, Shapely | Classical CV is predictable and debuggable; prefer it for the CV route. |
| Dimension text | Tesseract (`pytesseract`), or PaddleOCR / EasyOCR | Dimension strings (`12'-6"`, `3.45 m`, `4200`) need a custom parser and a sanity check against measured pixels. Misreads (`6` vs `8`, `'` vs `"`) are the top scaling failure. |
| Semantic proposal | Claude vision: read the image, return JSON in the plan.json schema | Good at labels ("Kitchen"), door swings, rough topology. Poor at exact coordinates, so give it an image with a labelled pixel grid and have CV snap the result. Proposes; validators decide. |
| Trained detectors (later) | CubiCasa5k and similar floor-plan models | Heavy. Only if classical CV fails on your plan style. |
| 2D geometry | Shapely (`unary_union`, `polygonize`, `polylabel`) | Footprints, rooms, interior points. |
| 3D build, primary | **Blender 4.2 LTS headless, Python `bpy`** | Deterministic, glTF export, Cycles/EEVEE. |
| 3D build, fallback | Shapely + `trimesh` (+ `mapbox_earcut`), export .glb | Works without Blender. See Environment. |
| Live driving (optional) | Blender MCP add-on | Needs a GUI Blender reachable from the session, which a cloud container usually lacks. A convenience, not the architecture. The batch `blender -b -P build.py` path must work without it. |
| Web viewer and fallback renders | three.js `GLTFLoader`, `OrbitControls`; Playwright screenshots | Chromium headless uses software WebGL, which is slow but works. |
| AI image generators | Optional last step: a clay render fed to image-to-image for a styled mood image, labelled "concept, not to scale" | Never a source of geometry. |

## Environment (step 0, run once, before anything else)

A `check_env.py` prints a pass/fail table:

- Python imports: `cv2, fitz, shapely, trimesh, jsonschema, numpy`.
- `tesseract --version` (optional; only needed for OCR).
- Blender: `blender --version`, else `python -c "import bpy"`.
- Network reachability for the download hosts (the container egresses through a proxy; a failed download is a common cause of a missing Blender).

Pinned primary path: Blender 4.2 LTS Linux tarball (it bundles its own Python, so no ABI mismatch), run as `blender -b -P build.py -- plan.json out/`. The pip `bpy` wheel is an alternative only if its required Python minor version matches the container's Python; check this first because the wheel is large and version-locked. `build.py` must not hard-code render engine names: it reads the installed enum (`bpy.types.RenderSettings.bl_rna.properties['engine'].enum_items`) and picks the EEVEE variant that exists, because the identifier changed between releases. glTF export options are likewise passed by checking which keywords the installed `export_scene.gltf` accepts.

If Blender cannot be installed, the pipeline selects the fallback. What each path can do:

| Output | Blender path | Fallback path |
|---|---|---|
| plan.json, overlay, report | yes | yes |
| `house.glb` | yes | yes |
| `house.blend` | yes | no |
| Top-down and isometric stills | Cycles / EEVEE | three.js + Playwright screenshot |
| Procedural PBR materials, Nishita sky | yes | no: flat colours, simple lights |
| Photoreal eye-level renders | yes | basic only |
| Walkthrough mp4 | yes | no (v1) |

Fallback build rule (no booleans, so nothing to fail): for each wall run, cut the length at every opening edge. For a door, emit a full-height pier for each solid span, and a header from head to wall top above the opening. For a window, emit the pier, a sill block from floor to sill height, and a header from head to top. Each piece is `trimesh.creation.box` or `extrude_polygon` from the footprint. Floors are `extrude_polygon` from the net room polygon. The same piece-based construction can also be used in Blender, which removes the boolean failure mode entirely; use Blender booleans only if you want a single watertight wall mesh.

## plan.json (the contract)

```json
{
  "schema": 1,
  "source": {"file": "plan.pdf", "sha256": "...", "page": 1},
  "units": "m",
  "dim_reference": "face",
  "scale": {"m_per_px": 0.0121, "method": "user|ocr_multi|ocr_single|scale_bar|door_prior",
            "evidence": [{"label": "4200", "px": 347, "ok": true}],
            "single_source": false, "confirmed_by_user": true, "confidence": 0.9},
  "levels": [{"id": "L0", "elevation": 0.0, "height": 2.7}],
  "walls": [{"id": "w1", "a": [0,0], "b": [4.2,0], "thickness": 0.2,
             "kind": "exterior|interior", "confidence": 0.95}],
  "openings": [{"id": "o1", "wall": "w1", "type": "door|window|arch",
                "offset": 1.1, "width": 0.9, "sill": 0.0, "head": 2.1,
                "swing": "left-in", "confidence": 0.8}],
  "rooms": [{"id": "r1", "label": "Kitchen", "polygon_net": [[0.1,0.1]],
             "area_net": 14.2, "printed_area": 14.0, "floor": "tile"}],
  "flags": ["w14 low confidence", "dimension 3'-8\" disagrees with geometry by 9%"]
}
```

Pixel coordinates are kept next to metric ones (`a_px`, `b_px`) so the overlay can be redrawn from plan.json alone.

## Pipeline stages

**0. Environment check.** As above. Do not discover a missing Blender halfway.

**1. Ingest.** Hash the file. PDF: count vector path objects; many means the vector route, otherwise rasterize at 300 dpi. Image: warn below roughly 1200 px on the long side; refuse below about 800 px.
Orientation: estimate the dominant line angle from a length-weighted histogram of Hough/LSD segments, take it modulo 90 degrees, and rotate to make it axis-aligned. This fixes any scan rotation, including 15 degrees and 90 degrees (a 90-degree rotation is detected by text orientation from OCR and corrected). Perspective is a different problem: it is detected when lines that should be parallel (one angle family) spread by more than about 3 degrees, or when the page quadrilateral is not a rectangle. A flat rotated scan is therefore never rejected. Perspective input (a phone photo) requires four user-clicked corners for a homography, or is rejected with that instruction. If no orthogonal pair of angle peaks exists (plan with many diagonals), flag "non-orthogonal plan" and do not snap angles. Crop title block and legend.
*Gate:* normalized image and thumbnail written; unreadable or password-protected files stop here.

**2. Scale (tiered policy).** Candidates, in order of authority:
- (a) A **user-supplied real distance** (two points and a length). Authoritative. Used even if nothing else agrees; other evidence is compared against it and disagreements are flagged, not used to override it.
- (b) **Two or more OCR/printed dimensions** with their dimension lines measured in pixels. Fit by median; discard outliers. Accept if the surviving values agree within **5 percent** (the same threshold as the stage 6 printed-versus-measured check; rounded plan dimensions routinely differ by a few percent, so 3 percent would reject valid plans).
- (c) **One printed dimension or a scale bar.** Accepted, but `single_source=true`, a warning is recorded, and the overlay draws a ruler with its length so you must confirm it (`confirmed_by_user`). A printed "1:100" is never trusted alone, since scanning and resizing break it; it is only a cross-check for (b) or (c).
- (d) **Door-width prior** (0.8 to 0.9 m). Only with an explicit opt-in flag; stamped "approximate" in plan.json, report and render captions.
*Gate:* exactly one of these must resolve. If none does, or (b) candidates disagree by more than 5 percent, stop with "scale ambiguous: here are the candidates; give me one real distance".

**3. Wall segments (gaps kept).** Binarize. Separate thick wall strokes from thin dimension, furniture and text lines by stroke width (distance transform) and solid fill or hatch. Skeletonize, fit lines, snap to dominant angles (only within tolerance), estimate thickness from the distance transform, round to a plausible 0.1-0.4 m. Remove segments shorter than 0.15 m and log them. Output is a set of wall segments with their gaps intact. This stage does not close door gaps.

**4. Wall-run merge, openings and rooms.** This is the step that connects stages 3 and 4.
1. Group segments by supporting line (same angle, perpendicular offset within half a wall thickness).
2. Within a group, for every pair of consecutive segments separated by a gap, compute gap width `g`. If `g <= 3.5 m`, **bridge it**: the two segments merge into one continuous wall run, and the gap becomes an opening record. Larger gaps are not bridged; they stay as a free end and trip the closure check.
3. Classify each bridged gap. Door: an arc (swing) found by Hough circles or arc fitting adjacent to the gap, or a gap of about 0.7 to 1.2 m with no other evidence (confidence lowered). Wide gap with no door symbol: `arch` (cased opening). Windows: a place where the wall run is continuous but the drawing shows thin parallel lines or a thinner stroke inside it; the run is kept whole and a window record is added with sill and head defaults.
4. Opening `offset` and `width` come from the measured gap, not a default.
5. Rooms: polygonize the **bridged** wall network (Shapely `unary_union` of centrelines, then `polygonize`), shrink each cell by half-thickness to get `polygon_net` (or subtract the wall footprint union), and match OCR labels by point-in-polygon. Because gaps were bridged first, a door no longer leaves the network open and no longer merges two rooms.
Counterexample handled: a rectangle split by a partition with a 0.9 m door. Stage 3 returns two partition segments plus the exterior; the merge bridges the 0.9 m gap into one partition with a door record; polygonize returns two rooms.
*Gate:* the exterior must form a closed ring after bridging, else stop (the slab and roof would be wrong); unlabeled rooms are flagged, not guessed.

**5. Write plan.json.** Validate against JSON Schema. Fill every confidence value.

**6. Validation and review.** Automated checks with explicit severities (below), then draw the **overlay PNG** on the original: walls red, openings blue/green, room labels, flags yellow, scale ruler. Review it before any 3D is built; edit plan.json where wrong and rerun from stage 6 (stages 1-5 are cached by file hash). Any error blocks the build; warnings go into the report.

**7. Geometry build.**
- Walls per run, joined at corners by union (or extending to intersection) so corners are not notched. Openings are cut either by piece construction (preferred; see the Environment section) or by an exact-solver boolean with a cutter slightly larger than the opening. Add a door leaf or frame, and window frame plus glass pane, as separate named objects.
- Floors: one mesh per room from `polygon_net`, thickness 0.1 m; ceiling or roof optional (off for top-down views).
- Names: `Wall_w1`, `Door_o1`, `Floor_Kitchen`, so edits and exports are traceable.
*Gate:* assert the model bounding box equals the footprint-union bounds within 5 mm, and check mesh manifoldness; failures list the object names.

**8. Materials and lighting.**
- Materials: a small library keyed by a plan.json tag (`wall_plaster`, `floor_wood`, `floor_tile`, `glass`); Principled BSDF with procedural textures (no external image dependency). Defaults by room label (bathroom to tile), always overridable; unknown labels get a neutral material and a flag.
- Lighting: sun plus sky (Nishita) for daylight through windows; area lights or emissive panels inside rooms; for clean clay renders, a white world and ambient occlusion. Window openings must have glass or be open holes. Check the render is not black.
- Cameras: top-down orthographic (the "3D floor plan"); isometric cutaway (hide the roof and the walls facing the camera, or clip with a box); eye-level at 1.6 m. Eye-level position is the room's **pole of inaccessibility** (Shapely `polylabel` on `polygon_net`), not the centroid, because the centroid of an L or U shape can fall inside a wall or another room. Check the point has at least 0.5 m clearance from walls; if not, pick the best-clearance sample. Aim along the room's longest axis, but never at a wall closer than 1 m; if the room is too small, use a wide-angle lens.
- Render: EEVEE for speed, Cycles (denoise, 64-128 samples) for finals, with sample and time caps for CPU.

**9. Export and report.** Write the outputs below plus `report.md`: scale evidence and whether it was single-source, every flag, per-stage status, and anything assumed.

## Validation severity table

| Check | Definition | Severity |
|---|---|---|
| Schema valid | JSON Schema | error |
| Exterior ring closed | After wall-run merge, the union of exterior footprints has one outer ring | error |
| Duplicate / collinear overlap | Two walls on the same line overlapping along their length by more than one thickness | error |
| Corner / T-junction overlap | Footprints overlapping only at a junction (up to thickness x thickness) | allowed, no flag |
| Wall crosses another without a junction | Footprints intersect in an X with no shared node | warning |
| Opening inside its run | `0 <= offset` and `offset + width <= run length`, where run length is measured between the inner faces of the perpendicular end walls (so corner thickness is excluded) | error if outside |
| Opening near a corner | Opening edge within 5 cm of a corner face | warning |
| Overlapping openings in a wall | Two openings overlapping in offset range | error |
| Opening height | `head <= level height`, `sill < head` | error |
| Room area | `area_net` below 0.25 m2 or invalid polygon | error |
| Small room | `area_net` below 1 m2 (pantry, shaft, closet are normal) | warning |
| Large room | `area_net` above 150 m2 | warning |
| Printed dimension vs measured | Difference above 5 percent, using `dim_reference` | warning (error if it is the scale's own evidence and fails the 5 percent agreement rule) |
| Printed area vs `area_net` | Difference above 5 percent | warning |
| Unlabelled room | No label matched | warning |
| Low confidence item | Confidence below 0.5 | warning, highlighted on overlay |

## Accuracy: how the numbers stay honest

- Geometry comes from measurement (pixels times an established scale) or from the user's own plan, never from an AI model's guess.
- Printed dimensions are evidence compared against measured values, not truth: plans are often "not to scale".
- Angles and thickness snap only within tolerance, so a real 4.37 m wall is not forced to 4.0 m.
- Idempotent builds: same plan.json gives the same model. Keep 3-5 sample plans with expected net room areas for regression.

## Risk and failure table

| Risk / failure | What happens | Defence |
|---|---|---|
| Wrong scale (OCR misread, not-to-scale plan, resized scan) | Whole house wrong by a constant factor, looks fine | Tiered policy; single-source scale is flagged and needs confirmation of the overlay ruler; agreement within 5 percent when two sources exist |
| Door gaps break room detection | Rooms merge or fail to polygonize | Wall-run merge bridges gaps up to 3.5 m into openings before polygonize |
| Gap wider than 3.5 m (garage door, open plan) | Free wall end, exterior not closed | Stop with the gap location; user adds an `arch`/`door` opening or a wall by hand |
| Furniture, hatch, text, dimension lines read as walls | Phantom walls | Stroke-width classification; crop title block; overlay review |
| Walls drawn as double lines, solid fill or hatch | Thickness wrong or missed | Fill-ratio test; thickness sanity range |
| Door/window symbols vary (sliding, bifold, pocket) | Missed or misplaced openings | Gap-based detection first, swing arcs secondary; unknown opening becomes a flagged generic opening |
| Photographed plan with perspective | Skewed geometry | Detect converging parallels; require four corners for homography, or reject. A flat rotated scan is not rejected |
| Low-resolution or JPEG-artifact scans | Broken lines | Resolution check; upscale only for display |
| Handwritten or non-Latin dimensions | OCR fails | User-supplied distance path; never guess |
| Vision LLM hallucinated coordinates | Wrong plan | Treated as a proposal; grid-assisted input, CV snap, validator and overlay decide |
| Boolean failures (coplanar faces, slivers) | Holes or broken meshes | Piece-based wall construction avoids booleans; if booleans are used, overscale the cutter, merge by distance, manifold check |
| Black or dim renders | Glassless openings, no sun, flipped normals | Mean-luminance check, auto fallback to clay world light |
| Blender not installable (proxy, version, size) | Primary build cannot run | Step-0 check; pinned tarball path; specified fallback with its limits stated |
| Cloud CPU render is slow | Timeouts | EEVEE default, low-sample previews, background run with hard timeout |
| AI mood image looks right but is wrong | User trusts invented rooms | Label as concept; never feed back into plan.json |
| Privacy of a real home's plan | Leak | Process locally; no third-party upload without consent |
| Multi-storey, stairs, curved walls, slanted ceilings | Out of scope | Detect as unsupported where possible; state the limit in the report |
| L/U-shaped room camera placement | Camera inside a wall | `polylabel` plus clearance check |

## Minimal first version (image or PDF in, .glb out)

Goal: one rectilinear one-storey plan, given as an image or PDF, becomes a correct, viewable .glb and a top-down render, with a human correcting the proposal.

1. **Fixtures first (half a day).** Hand-write one `plan.json` (10-20 walls, 3-4 openings) as a test fixture, and write `validate.py` (schema plus the severity table) and `build.py` against it. This proves the 3D half and the checks. It is a fixture, not the product.
2. **Image to plan.json via Claude vision (the v1 front end).** A small script `propose.py` draws a labelled pixel grid every 100 px on the input image, so Claude can report wall endpoints, openings and room labels in pixel coordinates; it asks Claude for JSON in the plan.json schema (with `a_px`, `b_px`); and it converts to metres with the tiered scale (user distance or printed dimension). A CV snap pass aligns endpoints to detected line ends and to a common axis. For a **vector PDF**, `propose.py` instead reads PyMuPDF path objects and text with exact coordinates, groups thick strokes into walls, and uses the printed dimension text for scale, which is more accurate than vision and needs no OCR.
3. **Overlay and fix loop.** Run `validate.py` and render `overlay.png`. Edit plan.json (or tell Claude what is wrong) and re-run until there are no errors. This is the human-in-the-loop step and the main quality control in v1.
4. **Build.** `build.py` produces the .glb and a top-down PNG (Blender if the step-0 check passed, else the fallback), with the bounding-box assertion.
5. **Viewer.** `viewer/index.html` with three.js `GLTFLoader` and `OrbitControls`; Playwright screenshot as a check.
6. Then automate in order of payoff: (a) OCR-based scale with the 5 percent agreement rule, (b) CV wall detection and the wall-run merge replacing vision proposals, (c) CV door and window detection, (d) isometric and eye-level cameras, (e) vision kept only for labels and as a second opinion.

Success tests for v1:
- The model bounds equal the footprint-union bounds within 5 mm.
- Each room's `area_net` matches its printed area within 5 percent where a printed area exists. Where none exists, check two printed face-to-face dimensions against the model within 2 percent.
- The .glb opens in the viewer and the screenshot shows the right number of rooms and doors.
- Three deliberately broken inputs stop with a clear message and no model: a gap in the exterior wall larger than 3.5 m, a single-source scale with no confirmation, and an opening that extends past its wall.

## Decision summary

- Blender 4.2 `bpy` in batch for the full-quality build, with a specified Shapely/trimesh/three.js fallback; three.js for viewing; MCP only as an optional convenience.
- Claude vision proposes in v1 (pixel grid in, plan.json out); classical CV and PDF vector extraction take over measuring as they are built; a validator and a human overlay decide.
- Gaps are kept in stage 3 and bridged into openings in stage 4, so doors and rooms are both correct.
- Net-area and footprint-bounds conventions make every check agree with a correct build.
- Generative AI is for mood images only.
- plan.json with confidences and severity-graded checks means bad input gives a clear error, not a convincing wrong house.
