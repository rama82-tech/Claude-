ATTACK 1 [MAJOR] The overlay check cannot be built from the plan.json schema or from the minimal v1
Where: schema `"scale": {"px_per_m": 118.4, ...}` and "Coordinates are metres, origin at the bottom-left of the outer bounding box, y up"; stage 4 item 6 "draw plan.json over the source image to overlay.png"; Minimal first version "no CV, no OCR ... 1. Claude reads the image and writes plan.json by hand (this replaces stages 1 to 2)"
Problem: To draw metre coordinates over the image you need the pixel position of the origin and the y-flip. The schema stores only px_per_m, not where the bounding-box corner sits in the image. v1 also skips stages 1 and 2, so nothing computes even px_per_m. The "Done when ... the overlay visibly matches" criterion therefore has no defined way to produce an overlay. The overlay is the plan's stated human check, so v1's main safeguard is missing.

ATTACK 2 [MAJOR] Centreline wall lengths are checked against printed dimensions that are usually face-to-face or overall
Where: schema "walls ... a, b ... thickness" with "Extract the wall centreline plus thickness"; stage 4 check 5 "Printed dimensions versus computed lengths: residual below 2 cm, else flagged"; edge-case row "Conflicting dimensions ... least squares"
Problem: Printed room dimensions are normally inside-face to inside-face, and overall dimensions are outside-face. A centreline length differs from both by one wall thickness (10 to 20 cm). With a 2 cm tolerance, every correct plan would raise false flags. Or the least-squares solver would "fix" correct walls by shifting them by half a wall thickness. The plan never states or stores which reference the dimensions use (compare a "dimension_basis" field). A 4.00 m inside-width room with 0.2 m walls is 4.20 m between centrelines and fails the check.

ATTACK 3 [MAJOR] The geometry code crashes or corrupts on ordinary inputs, and a comment makes a false claim
Where: `walls = trimesh.creation.extrude_polygon(foot, H)      # handles MultiPolygon via list` and `cut = trimesh.creation.box(extents=[o["width"], w["thickness"]*3, o["height"]])`
Problem: (a) `extrude_polygon` takes one shapely Polygon. The code passes the result of `unary_union`, which is a MultiPolygon whenever any wall group is disconnected, for example a detached garage or one unsnapped wall (a case the plan itself says it reports). The call is not wrapped in a list or loop, so the comment is untrue and the call fails. (b) The cut is 3x the wall thickness deep and is not clipped to its host wall. A door within 1.5 x thickness of a T-junction or a corner cuts a notch into the perpendicular wall. Example: a 0.1 m wall, a door at offset 0.05 m from a crossing 0.2 m wall. The check `walls.is_watertight` will not catch a wrongly shaped notch.

ATTACK 4 [MAJOR] The install line will not run the code the plan prescribes
Where: "Install `manifold3d` (`pip install trimesh shapely manifold3d pymupdf opencv-python`)" versus stage 2 "`cv2.ximgproc.thinning`" and `extrude_polygon`
Problem: `cv2.ximgproc` exists only in `opencv-contrib-python`, so `opencv-python` raises AttributeError at the thinning call. `trimesh.creation.extrude_polygon` needs a triangulation backend (`mapbox-earcut` or `triangle`), and neither is installed, so it raises on the first wall. The OCR stage names `pytesseract` or `easyocr` but neither is installed, and `pytesseract` also needs the tesseract binary, which is not in the stated container. The user pasting this line cannot reach house.glb.

ATTACK 5 [MAJOR] The code ignores the room, virtual-wall and wall-kind design it claims
Where: edge-case row "Open-plan ... virtual boundary segments (`type: "virtual"`)"; materials "Per-object material names (`wall_ext`, `wall_int`, `floor_<room>`...)"; the schema's `"rooms": [{"id","label","floor"}]`; code `rooms = list(polygonize(...))`
Problem: (a) The build code extrudes every entry in `plan["walls"]` at full height. A virtual wall has zero height by the plan's own words, and the code would build a solid wall across the open-plan kitchen. The schema also defines `kind` only as exterior or interior. (b) `rooms` in plan.json carry no polygon, and polygonize returns anonymous polygons. No step maps a polygon to a label such as Kitchen, so `floor_<room>` names and "bathroom, kitchen get tile" cannot be produced. (c) `wall_ext` and `wall_int` need `kind` but the code never reads it. (d) Floors are polygonized from centrelines, so they overlap the wall volumes.

ATTACK 6 [MAJOR] "Reader A (Claude vision)" cannot be run as a pipeline stage, and the merge rule is ambiguous
Where: stage 2 "Run two readers and compare them"; "Merge rule: semantics from A, coordinates snapped to B's nearest detected line within 10 cm"; assumption "Claude vision (the Claude Code session itself) is the primary reader"
Problem: A script cannot call the session as a function. The plan gives no mechanism (no API key or call, and no step where the user pastes the image and JSON in), so "run two readers and compare" cannot be automated as written. The snap rule is also unclear. For double-line or hatched walls, B's nearest line is a wall face, not the centreline, so snapping moves each wall by half its thickness. The rule does not say what B returns, so the user must guess.

ATTACK 7 [MINOR] The renderer path is under-specified for headless container use
Where: stage 7 "three.js + Playwright (Chromium is already installed) ... Fastest ... runs headless here"; minimal v1 step 4 "`viewer.html` loads the GLB in three.js ... Playwright takes `top.png` and `iso.png`"
Problem: There is no viewer or screenshot code, and no mention that headless Chromium without a GPU often renders a blank WebGL canvas unless software GL flags (for example `--use-gl=swiftshader` or `--enable-unsafe-swiftshader`) are passed. The plan never says how to loading the GLB from file:// works, how to wait for the GLB to finish loading before the screenshot, or how the "iso_cutaway" hides walls. The most likely first failure, blank PNGs, is unaddressed while the claim "runs headless here" is stated as fact.
