ATTACK 1 [MAJOR] Opening detection breaks on piers, corner stubs and collinear partitions
Where: plan2ir.py, `--min-len` default 0.6 and the merge test `0.5 * ppm <= s - cur["e"] <= 2.6 * ppm`; Known limits: "Walls shorter than `--min-len` (0.6 m) are dropped."
Problem: Any wall piece under 0.6 m is deleted before gaps are measured, so the gap logic sees the wrong gap.
(a) Two 1.2 m windows separated by a 0.4 m pier. The pier is dropped, so the measured gap is about 2.8 m. That is over 2.6 m, so nothing is merged. Both windows vanish, and the result is two separate wall bars and no openings.
(b) A door 0.3 m from a corner. The 0.3 m stub is dropped and no gap is recorded. The wall just ends short, leaving the corner open.
(c) The reverse error: two collinear partition stubs on either side of a 1.5 m hall opening are merged into one wall with a "door" hole and a 2.05 m lintel, where the plan shows a full-height opening.
Known limits mentions only the dropped walls. It does not mention that the missing openings are silent, and the risk table does not cover it. This is the core output of the MVP, and it was only tested on one synthetic plan with two clean gaps.

ATTACK 2 [MAJOR] The MVP CV step finds no walls on the most common plan style, and the fix is not in the code
Where: Step 1: "Plans that draw walls as two thin parallel lines (hollow walls) need the gap between the lines filled first (close with a kernel of the wall thickness)"; plan2ir.py `MORPH_OPEN` with k = 0.08 * ppm.
Problem: CAD/PDF exports usually draw walls as double outlines, or as poche/hatch with thin lines. Otsu followed by an opening with an 8 px kernel at ppm 100 erases every such line, so the script prints "0 walls, 0 openings". The suggested closing needs the wall thickness, which is what the script is trying to find. No closing code is given and no flag exists for it. The "vector extraction" alternative for PDFs gets one sentence and no code. The MVP therefore only works on solid-black-wall rasters, and the plan does not say how to detect that case. A user with a typical architect PDF gets an empty plan.json.

ATTACK 3 [MAJOR] Acceptance test and validation steps cannot be run with what is delivered
Where: Section 11 (a) "every printed dimension agrees ... within 2%" and (c) "the overlay shows no unmatched wall"; Section 1 "The first version ... is already built"; Section 9 calibration.
Problem: The MVP code writes no overlay.png and has no scale cross-check or `scale.check_error_pct`. It has no validation checks such as wall-end touching, minimum length or area within 5%. Step 4 describes all of these, but section 9 includes none of them. `--ppm` has to be found by hand ("if a printed 5.00 m dimension spans 612 px between its ticks"), and no tool or procedure for reading pixel positions is given. Test (c) depends on an overlay that the code never makes. The user cannot tell whether the model is right, and "overlay.png: proof the model matches the plan" is listed as an output without being produced.

ATTACK 4 [MAJOR] Floor slab is the wall bounding box, so non-rectangular plans get a floor over empty space
Where: viewer.html "floor slab = bounding box unless plan.rooms supplies polygons"; Known limits: "harmless visually".
Problem: plan.rooms is always empty from plan2ir.py, so the slab is always the bounding rectangle. For an L-shaped house, a courtyard plan or a plan with a notch, the missing corner is covered by a floor-coloured rectangle. In the top-down render, which is the "3D floor plan" view, the building looks rectangular. The "harmless" note only covers the centreline-versus-edge offset, not this case.

ATTACK 5 [MAJOR] The semantic step that the architecture depends on has no concrete method
Where: Architecture box "[2] semantics (Claude vision / OCR)"; Section 7; Roadmap item 1 "auto-apply only if counts match CV".
Problem: The step that supplies room names, door and window types and printed dimensions has no prompt, no output schema and no way to call it. It is not stated whether this means Claude reading the image in the Claude Code session or an API call with a key. "Counts match CV" is undefined, because the MVP labels every opening a door, so door counts and window counts cannot be compared with anything. Until this is built, the user edits the type of every opening by hand, which is the manual step that the recommendation says this approach avoids. The "Claude + CV" claim in the recommendation is not backed by anything the user can run.

ATTACK 6 [MINOR] Shadow light is not set up for real plan sizes
Where: viewer.html `sun.position.set(tmax[0],10,tmin[1]-4); sun.castShadow=true`
Problem: The shadow camera uses three.js defaults, a frustum of about +/-5 m, and the light target stays at the origin, not at the plan centre. The test plan was 6 x 4 m. A real house of 12 m or more, or one whose coordinates sit far from the origin because of image margins (the doc notes margin offsets are kept), has shadows clipped or missing. No `shadow.camera.left/right/top/bottom` or `sun.target` setting is given.

ATTACK 7 [MINOR] Camera and render claims do not match the code
Where: Step 7 "top-down orthographic"; Step 5 "camera up-vector (0,0,-1)"; Step 8 table "render_<room>.png ... Playwright screenshots (MVP)"
Problem: `shot('top')` moves the PerspectiveCamera to (cx, span*1.6, cz+.001). It is not orthographic, so tall walls lean and cover interior floor near the edges. It never sets up (0,0,-1). The orientation is correct only because of the 0.001 offset, and that is not documented. The table credits the MVP with per-room eye-level renders, but render.mjs produces only render_persp.png and render_top.png, and rooms do not exist in the MVP. Acceptance item (e) "a 1 m cube-sized check" is also unclear.
