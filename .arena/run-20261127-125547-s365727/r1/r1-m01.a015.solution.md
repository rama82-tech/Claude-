# Turning a 2D floor plan into a 3D model: build plan

## 1. Recommendation in one paragraph

Do not make an AI image generator, or a live Blender session, the core of the system. Make the core a deterministic geometry pipeline around one reviewable intermediate file, `plan.json`. The pipeline is: raster or PDF in, vectorised walls, openings and rooms with a calibrated scale, human-confirmed, then built into a single GLB solid, then rendered. A floor plan is a measurement document, and generators invent walls. Pixel-to-geometry code can be checked against the drawing. Blender and AI renderers are optional back ends that read `plan.json` or the GLB and are never the source of truth.

The contrarian sequencing choice: build the back end first (plan.json to GLB to render), because it is deterministic and gives the user something visible on day one. Detection (the hard, failure-prone part) comes second and may be partly done by Claude reading a gridded image, with a mandatory review.

## 2. The obvious answer, and why most of it does not survive

| Obvious default | Argument against | What I keep |
|---|---|---|
| Feed the plan to an image generator ("make this a 3D render") | It redraws instead of measuring. It moves walls, invents furniture and text, and gives a picture with no model, no dimensions and no editability. | Only as a final optional "beauty pass" over a clay render made from the real geometry, with the geometry as control image. Never as the model. |
| Drive Blender through MCP | The MCP add-on needs a live Blender GUI on localhost:9876. The cloud container has none. It is also slow for hundreds of simple prisms. | Headless Blender (`blender -b -P script.py`, preferred over pip `bpy`) as an optional stage for Cycles renders and `.blend`. Blender MCP only if the user has desktop Blender attached. |
| Train a wall-segmentation network (CubiCasa5k style) | Large effort, needs GPU and data, still fails on unusual drawings. | Not in v1. A pluggable `detector` interface lets a pretrained model be swapped in later for messy scans. |
| OCR the dimension strings to get scale | OCR gets dimension text wrong most often (`12'-6"`, `3.25`, rotated text, `l` vs `1`), and one wrong digit silently scales the whole house. | OCR only suggests. Scale is confirmed by a visible two-point calibration and then cross-checked against a held-out second dimension. |
| Full automation | A fully automatic result looks done and is silently wrong. | Automatic first draft, quick correction, then build. Review is a feature. |
| three.js vs Blender as either-or | Each is better at something. | three.js (Chromium already installed) for viewer and quick renders, `trimesh` + `manifold3d` for the solid and GLB, Blender headless for photoreal stills and video. All fed from the same JSON. |
| "Vector PDF means detection is easy" | CAD PDFs mix walls with furniture, grids and dimensions, and walls are usually pairs of lines. | Vector input gives exact coordinates and layer/style filtering. Deciding what is a wall still needs a method (section 6, stage 1b). |
| "A verify overlay proves the model is right" | An overlay drawn with the same scale used to build the model always lines up, even if the scale is wrong. | Verify checks only detection fit. Scale is checked separately (stage 9). |

## 3. Assumptions

1. Input is a single-storey floor plan as PNG/JPG/scan or PDF, ideally with some printed dimensions. Multi-storey is an extension (the schema has `levels`).
2. The plan is drawn to scale or has at least one reliable dimension. With none, the output is the correct shape at an unverified size, and every output says so.
3. Walls are thick lines or filled bands (normal for architect drawings). Single-line sketches get a default thickness.
4. Default heights: wall 2.7 m, door 2.05 m, window sill 0.9 m, head 2.1 m. Editable.
5. "3D model" means a viewable, exportable model (GLB, optional OBJ/STL/`.blend`) plus renders. IFC/BIM is an extension.
6. Runtime is the Claude Code cloud container: Linux, Python, Node, Chromium and Playwright. No GPU, no desktop Blender. Packages come from pip, npm and apt (apt availability depends on the environment's network settings; if apt is blocked, skip OCR and Blender).
7. The user knows the building, so ambiguous items can be resolved in minutes.
8. The plan is private. Processing is local; nothing is uploaded to third-party services without the user's say.

## 4. Architecture

```
input.pdf / .png / .jpg
        |
 [1 Ingest]         PDF: inventory vector style groups OR rasterise at 250 DPI. Image: deskew, crop.
        |            Writes page.png, grid.png and ingest.json (the one fixed pixel frame)
 [2 Calibrate]      px_per_m from a user-confirmed known length; a second length is held out
        |
 [3 Detect]         walls, openings, rooms as geometry in plan space (raster or vector method)
        |
 [4 plan.json]      the single source of truth, human-readable, versioned
        |
 [5 Review]         overlay.png (and optional HTML editor); user or Claude fixes plan.json
        |
 [6 Build]          per-wall cut footprints, pieces unioned by manifold3d into one solid; floors
        |
 [7 Export]         model.glb (Y-up, always), model.obj / model.stl / model.blend optional
        |
 [8 Render]         three.js via Playwright (default), Blender headless Cycles (optional)
        |
 [9 Verify]         (a) detection fit vs source ink, (b) scale check by held-out dimension and priors
```

Every stage reads and writes plain files, so each can be tested alone, retried or replaced.

### 4.1 Coordinate conventions (decided once, because mixing them breaks renders)

- Image pixels: origin top-left, y down. All pixel coordinates the user or tool handles live in the single frame stored in `ingest.json` (the output pixel grid of `page.png`). Crop and deskew are applied once during ingest, and the transform is stored, so coordinates read from `grid.png` are always valid.
- `plan.json`: metres, x right, **y up** (`y_m = (H_px - y_px) / px_per_m`). This is the Z-up convention of the build step, with plan y as the world's horizontal axis.
- Build: Z-up (walls extrude along +Z).
- GLB export: glTF and three.js are Y-up and `trimesh` does not convert. Apply one proper rotation of -90 degrees about X when exporting, mapping (x, y, z) to (x, z, -y). This is a rotation, not a flip, so the plan is not mirrored. A test checks the exported bounds have the wall height on Y.

### 4.2 `plan.json` schema (the contract)

```json
{
  "version": 1,
  "units": "m",
  "scale": {"px_per_m": 94.2, "source": "user_calibration",
            "ref_px": [[102,88],[1034,88]], "ref_m": 9.9,
            "check": {"ref_px": [[102,500],[600,500]], "ref_m": 5.3, "error_pct": 0.6}},
  "defaults": {"wall_h": 2.7, "wall_t": 0.15, "door_h": 2.05, "sill_h": 0.9, "head_h": 2.1},
  "levels": [{
    "name": "ground", "elevation": 0.0,
    "walls": [{"id":"w1","a":[0,0],"b":[6.2,0],"t":0.2,"h":2.7,"kind":"exterior"}],
    "openings": [
      {"id":"o1","wall":"w1","type":"door","offset":1.1,"width":0.9,"h":2.05,"sill":0,"swing":"in-left"},
      {"id":"o2","wall":"w1","type":"window","offset":3.4,"width":1.5,"h":1.2,"sill":0.9}
    ],
    "rooms": [{"id":"r1","label":"Kitchen","polygon":[[0,0],[4,0],[4,3],[0,3]],"floor":"tile"}]
  }],
  "confidence": {"w1": 0.97, "o2": 0.6},
  "scale_status": "verified | unverified | estimated"
}
```

Walls are centre-line segments with thickness, so openings and joins are simple and edits are one-line. Every detected item carries a confidence so review can start with the weakest.

## 5. Tools and libraries

| Job | Choice | Notes |
|---|---|---|
| PDF to image or vectors | `PyMuPDF` (fitz) | Renders at any DPI. `page.get_drawings()` returns line, rect and curve paths with stroke/fill colour, width and (where present) layer. |
| Image ops | `OpenCV`, `scikit-image`, `numpy` | Threshold, morphology, distance transform, skeleton, LSD/Hough. |
| Wall detection (raster) | Thickness-band morphology: keep dark regions whose local stroke width is in the wall band (distance transform + opening), drop text, hatching and dimension lines; skeletonise; fit segments; snap to orthogonal within about 3 degrees. | Explainable, no training. Works on clean drawings. |
| Wall detection (fallback) | Pretrained floor-plan segmentation model behind the same `detector` interface | Only for hand-drawn or noisy scans. Needs `torch`, optional. |
| Openings | Doors: quarter-circle arc plus a leaf line of equal length, and gaps in wall bands. Windows: thin parallel lines inside a wall band. | A gap with no evidence is stored as "opening, type unknown", never guessed. |
| Rooms | `shapely.ops.polygonize` on the wall lines | Labels from OCR positions inside each polygon. |
| OCR | `pytesseract`, which also needs the system binary: `apt-get install tesseract-ocr` | Labels and scale suggestions only. EasyOCR/PaddleOCR are heavier alternatives. |
| Geometry | `shapely` (2D footprints, cuts), `trimesh` + `mapbox_earcut` (extrusion), `manifold3d` (union into one valid solid) | 2D-first, then one manifold union. |
| Export | `trimesh` to GLB/OBJ/STL | GLB opens in three.js, Blender, Windows 3D Viewer, macOS Quick Look, Unity. |
| Viewer | `three.js` (`GLTFLoader`, `OrbitControls`) in one static HTML page | Roof toggle; plan image can be layered underneath for review. |
| Headless rendering | Playwright + Chromium screenshotting the page, with `--use-gl=angle --use-angle=swiftshader` (software WebGL; no GPU) | Top-down, isometric cutaway, eye-level PNGs. |
| Photoreal (optional) | `blender -b -P` with Cycles CPU, GLB imported | pip `bpy` wheels exist only for specific Python versions and are large, so prefer the Blender binary or check the version first. Cap samples (64 to 128 plus denoise). |
| AI beauty pass (optional) | Image-to-image with depth/edge control from the clay render | Cosmetic; labelled "illustrative, not to scale". |
| Orchestration | Python CLI `plan2model.py`, one subcommand per stage, plus `pytest` | Claude Code runs it and views the PNGs it writes. |

## 6. Step-by-step pipeline

### Stage 1: Ingest

**1a. Raster (PNG/JPG/scan, or PDF rasterised at 250 DPI).**
1. Crop to the drawing's linework bounding box; remove title block and border by keeping the largest connected linework region.
2. Rotation: estimate the dominant line angle (Hough) and rotate to axis-aligned. A flatbed scan rotated by any angle is simply corrected, silently.
3. Perspective is a different problem and is tested separately, after the rotation fix: collect near-axis lines and measure the spread of their angles (spread above about 1.5 degrees means non-parallel walls) and check whether opposite outer edges are parallel. If perspective is likely (typical of phone photos), ask for the four corners of a known rectangle and apply a homography, or refuse and say why.
4. Binarise: Otsu for clean drawings, adaptive threshold for scans.
5. Write `page.png`, `ingest.json` (all transforms) and `grid.png`: the same image with a labelled grid every 100 px, so that coordinates for calibration, review and Claude-assisted tracing can be read off by eye instead of guessed.

**1b. Vector PDF (the method, not just the claim).** Vector input is valuable for two things: exact coordinates and the ability to throw away everything that is not wall. It does not remove the need to decide what a wall is.
1. Inventory: group `get_drawings()` items by (layer if present, stroke colour, stroke width, fill colour). For each group report item count, total length, share of axis-aligned segments and bounding box. Write `vector_groups.png`, a contact sheet with one thumbnail per group, so Claude or the user can pick groups by looking.
2. Select wall groups: default heuristic is the group with the most long, axis-aligned segments that form parallel pairs (below). The user can override with `--walls-groups 3,5`.
3. Pair parallel segments: for every axis-aligned (or common-angle) segment, find a parallel segment at a perpendicular distance within the wall-thickness band (0.08 to 0.4 m once scale is known; before calibration use the band relative to the page, shown to the user) with at least 50 percent overlap along the axis. Each pair becomes a centre line with thickness equal to the gap. Closed filled dark polygons (poche) are taken directly as wall footprints and skeletonised or fitted by minimum rotated rectangle.
4. Door arcs: `get_drawings()` returns arcs as Bezier curve items. Fit a circle from the endpoints and mid-point, accept a roughly 90 degree arc whose radius matches an adjacent straight segment (the door leaf), and record door width = radius, hinge side from the leaf position.
5. Windows: three or more thin parallel lines spanning a gap in a wall pair.
6. Fallback: if the groups cannot be separated (for example everything is one stroke style), rasterise only the selected groups and run the raster detector on that clean image. Also run the raster route when the PDF is a scan wrapped in a PDF (no vector paths).

### Stage 2: Calibrate scale (the step that decides accuracy)
Priority order:
1. Two-point: the user (or Claude from `grid.png`) gives two points and the true length, for example the overall width printed on the plan. Command: `calibrate --ref x1,y1,x2,y2 --len 9.9`, with coordinates in the ingest pixel frame read from `grid.png`. The tool snaps each point to the nearest line end within 6 px and prints the snapped values. An optional tiny click-to-pick HTML page does the same where the user has a browser.
2. A drawn scale bar: its two ends and its stated length.
3. A stated scale ("1:100") plus the source DPI. Valid only for original-size prints or PDFs. Warn that photos and screenshots break it.
4. OCR-suggested dimensions: detect strings like `3.20`, `10'-4"`, `4200`, pair them with dimension lines and propose a scale. Require two independent dimensions that agree within 2 percent, otherwise stop and ask.
5. Fallback: assume a standard door is 0.9 m (3 ft), set `scale_status: "estimated"` and print "scale estimated" on every render.

**Held-out check (this is what makes scale trustworthy).** Ask for a second known length, different from the calibration one (`--check x1,y1,x2,y2 --len 5.3`), and compare. Under 2 percent: `scale_status: "verified"`. Otherwise stop. If the plan has only one printed dimension, the status stays "unverified", and priors are used (stage 9b).

### Stage 3: Detect
1. Wall mask (raster route): thickness filter, remove blobs under an area threshold.
2. Skeletonise and extract segments. Merge collinear pieces. Snap endpoints into T/L/X junctions within about half a wall thickness. Cluster measured thicknesses into two or three classes (exterior, interior, partition), since per-wall thickness is noisy.
3. Openings: find breaks in wall bands. Classify by evidence (arc present: door; parallel thin lines across the band: window; neither: "opening"). Measure width and offset along the wall.
4. Rooms: polygonise; attach OCR labels if available.
5. Discard: furniture, stairs (a flagged region only in v1), dimension lines, hatch patterns.

Claude-assisted alternative (also the v0 detector): Claude views `grid.png` and writes a draft `plan.json` by tracing; the overlay and review stage then show how far off it is. Reading coordinates by eye is imprecise (a few pixels at best), so snap to the wall mask and treat this as a first draft only.

### Stage 4 and 5: Write `plan.json` and review
Render `overlay.png`: the original plan with detected walls in red, openings in blue and green, low-confidence items dashed. In Claude Code, Claude can look at the image and report problems. For a human, an optional HTML editor (canvas plus drag handles) moves endpoints, deletes or adds walls, changes an opening's type and width, and sets room materials. Walk through the low-confidence list first.

### Stage 6: Build the geometry (tested code)
Rules that avoid the usual failures:
- Each opening is cut only from its own wall's footprint, with a rectangle of exactly the opening width. It is never subtracted from the union of all walls, which would notch neighbouring walls at T-junctions and corners.
- Per-wall height `h` and per-opening `sill` and `h` are used. A door is the opening with sill 0.
- Wall ends that meet another wall are extended by half the wall thickness so L-corners are closed. Free ends are not extended.
- The pieces (wall body, lintel above each opening, under-window piece) are unioned with `manifold3d` into one valid solid. This removes internal coplanar faces and z-fighting that a plain concatenation would leave.

```python
import numpy as np, trimesh
from shapely.geometry import LineString, Point, Polygon

def prism(poly, z0, z1):                       # slab(): extrude a (Multi)Polygon from z0 to z1, Z-up
    if poly.is_empty or z1 - z0 < 1e-6: return []
    out = []
    for g in (poly.geoms if hasattr(poly, "geoms") else [poly]):
        if g.area < 1e-8: continue
        m = trimesh.creation.extrude_polygon(g, height=z1 - z0)
        m.apply_translation([0, 0, z0]); out.append(m)
    return out

def wall_footprint(w, walls):
    a, b, t = np.array(w["a"], float), np.array(w["b"], float), w["t"]
    d = (b - a) / np.linalg.norm(b - a)
    joined = lambda p: any(o is not w and LineString([o["a"], o["b"]]).distance(Point(p)) < o["t"] for o in walls)
    a2 = a - d * t / 2 if joined(a) else a
    b2 = b + d * t / 2 if joined(b) else b
    return LineString([a2, b2]).buffer(t / 2, cap_style=2)

def opening_rect(w, o):                        # exactly o["width"] wide, across this wall only
    a, b = np.array(w["a"], float), np.array(w["b"], float)
    d = (b - a) / np.linalg.norm(b - a); n = np.array([-d[1], d[0]]); h = w["t"] / 2 + 0.01
    p0, p1 = a + d * o["offset"], a + d * (o["offset"] + o["width"])
    return Polygon([p0 - n*h, p1 - n*h, p1 + n*h, p0 + n*h])

def build_walls(level, H=2.7):
    meshes = []
    for w in level["walls"]:
        fp, wh = wall_footprint(w, level["walls"]), w.get("h", H)
        cuts = [(opening_rect(w, o).intersection(fp), o) for o in level["openings"] if o["wall"] == w["id"]]
        body = fp
        for c, o in cuts: body = body.difference(c)
        meshes += prism(body, 0, wh)
        for c, o in cuts:
            meshes += prism(c, o["sill"] + o["h"], wh)               # lintel / above window
            if o["sill"] > 0: meshes += prism(c, 0, o["sill"])       # below window
    return trimesh.boolean.union(meshes, engine="manifold")          # one solid, no internal faces

def to_gltf_yup(mesh):                          # Z-up plan space -> glTF Y-up, a proper rotation (no mirroring)
    m = mesh.copy()
    m.apply_transform(trimesh.transformations.rotation_matrix(-np.pi / 2, [1, 0, 0]))
    return m
```

This code was run on a 6 m by 4 m room with a T-wall and a door placed beside the T-junction. Results: the merged solid was watertight, the T-wall stayed intact beside the door, the door gap was open below the head, the lintel was present above it, and the exported bounds had the 2.7 m height on Y. Run this same test as the first unit test.

Remaining build steps:
1. Floors: one slab per room polygon, 0.1 m thick, with the room's material. Fill any area inside the outer walls not covered by a room (corridors). Floors stay separate meshes in the GLB (so materials differ), and are merged into the wall solid only for STL export.
2. Ceiling: optional, off by default so top-down views work; the viewer has a roof toggle.
3. Door leaves (thin boxes, open 90 degrees using the swing hint), window frames (four thin bars), glass (a transparent plane, alpha 0.25). All simple primitives.
4. Name every mesh node (`wall_w1`, `door_o1`, `floor_r1`) so the model stays selectable. Because the wall solid is merged, keep the per-wall meshes in a `walls_by_id` node group in a second export if per-wall selection is needed.

### Stage 7: Export
- `model.glb` (required, Y-up), `model.obj`/`.mtl`, optional `model.stl` (the merged solid, scale-correct, for printing), `model.blend` if Blender is available.
- `plan.json` (editable source), `overlay.png` and `verify.png` (audit trail).

### Stage 8: Render
Default, always works: Playwright opens `viewer.html?model=model.glb&view=...` and saves:
- `top_down.png` (orthographic, roof off, rooms labelled)
- `iso_cutaway.png` (orthographic 35 degrees, ceiling hidden)
- `eye_level_<room>.png` (perspective, 1.6 m eye height, 70 degree field of view)
- `walkthrough.mp4` (optional: a path through room centres, frames captured with Playwright then `ffmpeg`)

Lighting: a hemisphere light for ambient fill, one directional sun with soft shadows (PCFSoft or VSM, 2048 map), `ACESFilmic` tone mapping, sRGB output, `RoomEnvironment` for reflections, and a point light per room at 2.3 m scaled by area. Keep ambient high enough that a closed room never renders black.

Materials: a table maps `floor` and `wall` tags to simple PBR values (white walls roughness 0.9; oak or tile floors by room label, wet rooms from OCR labels else wood; glass with alpha), with optional tileable textures. Appearance only, never geometry.

Photoreal (optional): import the GLB in headless Blender, Principled BSDF materials, a sun lamp plus an area light per room, Cycles 64 to 128 samples with denoise at 1600 px wide. Expect minutes per image on CPU.

### Stage 9: Verify (two separate checks, because they catch different errors)

**9a. Detection fit (does the model match the drawing's linework?).** Rasterise the model's wall footprints into the ingest pixel frame and compare with the source wall mask: report the fraction of source wall ink covered, and of model area that has no ink under it, and write `verify.png`. Flag anything off by more than half a wall thickness. This checks detection and editing mistakes only. It cannot detect a wrong scale, because the model and the image share the same px_per_m.

**9b. Scale check (is the size right?).**
1. Held-out dimension from stage 2 (the independent check). If present and within 2 percent, scale is "verified".
2. If none, OCR-free plausibility priors against the built model: median door width should be 0.7 to 1.1 m, wall thickness 0.1 to 0.3 m, bedrooms 7 to 20 m2, and the overall footprint of a dwelling in a plausible range. Failing a prior sets `scale_status: "unverified"` with the reason in `report.md`.
3. Where OCR is available, compare printed room areas and dimension strings to the model ("kitchen 4.2 m on plan, 4.18 m in model"). Disagreement is reported, not auto-corrected.
4. Stamp the scale status on every render.

**9c. Structural failures (fail loudly).** Unclosed room polygons, zero-width walls, openings wider than their wall, overlapping openings, more than one disconnected exterior shell, and a final solid that is not watertight per `manifold3d`/`trimesh` after the union (test the merged solid, not the pieces).

## 7. How accuracy is achieved

- Walls: thickness-filtered mask or vector pair-matching, centre-line fitting, orthogonal snapping, junction merging, thickness classes, per-wall cuts and a single manifold union.
- Openings: measured along the wall in metres (offset and width), cut in 2D so edges are exactly straight. Unknown types are flagged, not guessed.
- Floors: derived from polygonised closed regions, so they match the walls by construction.
- Scale: human-confirmed two-point calibration, a held-out second dimension, plausibility priors as the fallback, and a visible status on every output.
- Detection fit: an overlay and a coverage metric against the source ink.
- Materials and lighting: assigned from labels with transparent defaults; appearance only.

## 9. Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Wrong scale | Everything is the wrong size yet looks fine, and an overlay with the same scale will still line up | Two-point calibration, held-out second dimension, plausibility priors, status stamped on renders |
| Phone photo with perspective | Walls are not parallel, scale varies across the image | Perspective test by angle spread and edge parallelism, four-corner homography, otherwise refuse |
| Rotated flatbed scan | Not a perspective problem | Rotation corrected silently |
| Hatched or filled walls (poche), double-line walls | Thickness filter misses or splits walls | `--wall-style solid|double|hatched`. Double lines: pair-match and fill. Hatching: use polygons directly. |
| Text, furniture and dimension lines touching walls | False walls | Area and thickness filters, vector group selection, erase-by-region in review |
| Vector PDF with mixed layers | Furniture and grids treated as walls | Style-group inventory with contact sheet, group selection, rasterise-selected-groups fallback |
| Curved or diagonal walls | Orthogonal snapping flattens them | Snap only within the angle tolerance, keep true angles beyond it, arcs as short segments in v2 |
| Door/window symbols vary by country and drafter | Misclassified openings | Evidence-based classification, "unknown opening" fallback, one-click type change |
| Low-resolution or faded scans | Broken or missing walls | Warn below about 150 DPI equivalent, upscale only for detection, never invent walls |
| Multiple floors or sections on one sheet | Detection mixes them | Crop one drawing at a time in v1 |
| Stairs, split levels, sloped roofs, balconies | Not represented | Out of v1; listed in `report.md` as "not modelled" |
| Boolean or coplanar-face problems | Holes, z-fighting, broken STL | Per-wall cuts, manifold union into one solid, watertight test on the merged result |
| Axis convention error | Walls extrude toward the camera, or the plan is mirrored | One documented convention, one proper rotation at export, a bounds test |
| Headless WebGL without GPU | Black or failing renders | SwiftShader/ANGLE flags, a smoke-test render, fallback to a software rasteriser (`pyrender` OSMesa or `trimesh`) |
| Missing system packages | `pytesseract` fails without the binary | `apt-get install tesseract-ocr`, or skip OCR in v1 |
| AI beauty pass changes layout | Misleading imagery | Optional, labelled illustrative, geometry-conditioned |
| Plan privacy | Home plans are sensitive | Local processing, no third-party upload without consent |
| Overpromising automation | User trusts a wrong model | Mandatory review plus the two verify checks and the scale status |

## 10. Minimal first version

Honest scoping: the detection stage is the hard part and will take real iteration. It is not a one-day job, and it will work reliably only on clean plans. So the first version is split so that something correct and visible exists very early.

**v0 (back end first; this is the smallest thing that is useful).**
1. `build`: `plan.json` to `model.glb` using the tested code in stage 6 (walls, door and window cuts, a floor from the outer boundary), including the Y-up export.
2. `render`: a roughly 60-line `viewer.html` with three.js and `OrbitControls`, and a Playwright script saving `top_down.png` and `iso.png`.
3. `plan.json` source: hand-written for a sample, or drafted by Claude tracing `grid.png` (from `ingest`), then checked with `overlay.png`.
4. `calibrate`: coordinates read from `grid.png`, with the `--check` held-out dimension.
5. `verify`: detection fit and the scale status.

Skip in v0: OCR and room labels, materials and textures, the editor UI, Blender, AI, perspective correction, multi-storey.

**v1 (automatic detection for one clean plan).** Add the raster wall detector (thickness filter, skeleton, line fitting, orthogonal snap), gap-and-arc opening detection, and the vector group inventory for CAD PDFs. Target: one clean, single-floor, straight-walled plan. Expect to tune thresholds per drawing style.

Starter commands:

Acceptance test for v1:
1. The outer dimension, measured on a held-out printed dimension (not the one used to calibrate), is within 2 percent.
2. Every door and window in the drawing exists as an opening in the right wall.
3. The merged solid is watertight, and the exported GLB has wall height on the Y axis.
4. The T-junction test (a door beside a perpendicular wall) leaves the neighbouring wall intact.
5. `verify.png` shows the model aligned with the source linework.
Keep three sample plans (clean CAD PDF, scanned print, hand sketch) as regression fixtures, and expect the third to need manual correction.

## 11. Roadmap after v1

1. Review/editor UI with drag handles, then OCR for room labels and dimension suggestions.
2. Materials and texture library, per-room lighting, Cycles stills, walkthrough video.
3. Pretrained segmentation fallback for noisy scans, perspective correction for photos.
4. Multi-storey (the schema has `levels`), stairs and simple roofs.
5. Furniture from a small GLB catalogue, only on request and only from detected symbols.
6. IFC export for BIM tools (`ifcopenshell`).
7. Optional AI beauty pass, clearly marked illustrative.

## 12. Decision checklist for the user

- Do you have the PDF or vector source? If yes, accuracy is much higher, and the group-selection step makes it practical.
- Which two dimensions on the plan do you trust? One calibrates the scale and the other checks it.
- Do you need an accurate model (design, permits, 3D printing) or an attractive image (marketing)? The first uses this pipeline as is. The second adds the optional beauty pass on top.
- Is a desktop Blender available? If yes, Blender MCP can drive it for finishing, but the pipeline works without it.
