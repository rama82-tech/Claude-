ATTACK 1 [MAJOR] Overlay gate cannot be built from the schema it is given
Where: "Step 2: A 30-line script draws the walls, openings and room names from the JSON over the original image, using a scale taken from one stated dimension." and the plan.json schema in Step 1.
Problem: The JSON holds only metre coordinates. It has no pixel-to-metre transform, no origin, no rotation and no pixel anchor. A scale from one stated dimension gives only a magnification. To draw w1 on the image the script also needs the pixel position of the plan's (0,0) corner and the plan's rotation, and nothing in the JSON or pipeline supplies them. Claude is also said to be "bad at measuring pixels", so it cannot supply them reliably. Overlay.png is the document's "one gate" that "removes most errors", and the user would have to invent the registration step. A wrong anchor makes every correct plan look wrong, or a wrong plan look right.

ATTACK 2 [MAJOR] The 2% dimension check rejects correct plans, and "dimension_basis" has no defined effect
Where: "The script checks that each wall length matches within 2 percent. A mismatch stops the build." with Risks: "decide whether dimensions are inside faces or centre lines ... (`"dimension_basis": "inner"`)".
Problem: Walls are stored as centre lines. Take a 3.0 m interior room dimension (inner faces) with 0.15 m walls. The centre-line wall is 3.15 m, which is 5% off. With 0.25 m exterior walls it is 8%. Printed room dimensions are normally inner-face, so the hard stop fires on correct input. The document names a "dimension_basis" field but never says what the script does with it (subtract thickness? at each end? for T-junctions with a different thickness?). The user cannot implement the check without guessing the conversion.

ATTACK 3 [MAJOR] The "stated" dimensions structure cannot hold the dimensions real plans print
Where: "Every printed dimension is copied into a "stated" list (for example {"wall":"w1","length":6.0})", and the schema example, which has no "stated" key.
Problem: Only a single-wall length is expressible. Real plans print overall dimensions spanning several collinear walls, chain strings (3'-0" + 12'-6" + ...), room interior sizes (12'x14'), and door or window offsets from a corner. None maps to one wall id, so the overall-versus-sum check that catches most misreads cannot be expressed. The stated list is also missing from the schema example, so the user does not know its shape. Imperial input (feet-inches) is never handled, although "Units are metres internally" implies conversion that is left to Claude's reading. A 9'-6" read as 9.6 m passes the "2 percent" test against itself.

ATTACK 4 [MAJOR] No method for unprinted lengths and positions
Where: "make it copy printed dimensions and give wall positions in metres, not pixels" and "Claude is ... bad at measuring pixels".
Problem: Most walls' endpoints and most door and window offsets have no printed number. Telling Claude to give metres without measuring pixels leaves it estimating by eye. No tool is named that converts image positions to metres (a ruler step, a grid overlay, or snapping to detected lines). The only defence is the human eyeballing the overlay (see Attack 1). The central accuracy claim ("Geometry comes only from numbers in the JSON") hides that those numbers are guesses for everything unprinted.

ATTACK 5 [MAJOR] Viewer and render step will fail as written
Where: "viewer.html loads house.glb with three.js ... A Playwright script opens it headless and saves top.png ..."
Problem: A page opened from file:// cannot fetch house.glb in Chromium (CORS/fetch restriction on file origins), and GLTFLoader uses fetch. The canvas stays empty. The fix (a local static server, or embedding the GLB as base64) is never mentioned. The document attributes a blank canvas only to missing software GL, so a user following it would debug the wrong cause. "iso.png (cutaway: hide walls facing the camera)" has no stated rule. A wall's facing-ness is not a property in the GLB, and the camera is not specified. "One eye-level image per room" has no camera position for concave rooms.

ATTACK 6 [MAJOR] Floors come from hand-entered room polygons that nothing ties to the walls
Where: Step 1 schema "rooms":[{"polygon":[[0,0],[6,0],[6,4],[0,4]]}] versus Step 3 item 4 "Triangulate each room polygon".
Problem: Walls and room polygons are independent inputs. No check says the polygon is enclosed by walls, matches the inner faces, or that every enclosed area has a room. The polygon in the example runs to the centre lines (0,0)-(6,4), so the floor extends under the wall thickness, while the 2% check passes it. A room with a wrong polygon gets a floor that pokes through a wall or leaves a gap, and the build passes. The 'area report' then cross-checks the same typed polygon against itself.

ATTACK 7 [MINOR] "Needs only Python, one pip package" is false
Where: Failure table, row 4: "The first version needs only Python, one pip package and the Chromium that is already installed."
Problem: The same document lists `pip install trimesh shapely mapbox-earcut numpy` (four packages), `pdftoppm` from poppler-utils for PDFs (not a pip package and not guaranteed in the container), Playwright's Python or Node bindings for the renders, and an image library for the overlay script. Corner closing "extend each wall by half the thickness" also leaves a notch where two walls of different thickness meet (the optional 0.25 m exterior and 0.10 m interior), which the doc does not address.
