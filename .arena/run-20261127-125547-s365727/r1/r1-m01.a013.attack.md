ATTACK 1 [MAJOR] Stage 9 "verify" is circular and cannot catch the failure it is sold as catching
Where: "Stage 9 closes the loop that AI-only approaches lack"; "Project the model's walls to 2D and draw them over the source image"; acceptance test "outer dimensions are within 2 percent of the printed value"
Problem: The model is built from plan.json using the same px_per_m that was used to project it back onto the image. A wrong calibration (the plan's own top risk: "one wrong digit silently scales the whole house") scales model and overlay together, so verify.png still lines up and passes. The 2% acceptance test is also trivial if the printed value used for the test is the same dimension the user calibrated on. The only independent scale check ("kitchen 4.2 m on plan, 4.18 m in model", printed areas) needs OCR, which the v1 section explicitly skips ("Skip for now: room labels and OCR"). So in v1 nothing independently checks scale, yet the plan claims the loop is closed.

ATTACK 2 [MAJOR] The build code produces a model lying on its side (axis convention never handled)
Where: Stage 6 / "Core of the build step": `trimesh.creation.extrude_polygon(..., height=2.7)` then `model.glb`; schema note "origin at the plan's top-left, y flipped to match 3D"
Problem: trimesh extrudes along +Z (Z-up). glTF/three.js is Y-up and trimesh does not rotate on GLB export. Loaded in the planned three.js viewer, walls extrude toward the camera depth, not upward, and top_down.png / iso_cutaway.png / 1.6 m eye-level cameras all come out wrong. "y flipped" is also ambiguous: flipping one axis mirrors the plan unless the rotation is chosen to compensate. The plan names no rotation step, so the user following it gets a broken first render.

ATTACK 3 [MAJOR] opening_cut removes pieces of neighbouring walls
Where: `opening_cut`: `LineString(...).buffer(w["t"], cap_style=2)`; `build_walls` uses `solid.difference(unary_union(full))`
Problem: buffer(t) gives a strip 2t wide, i.e. t/2 beyond each wall face, over the full height, and it is subtracted from the union of ALL walls. Any perpendicular wall that meets this wall within the opening span (door beside a T-junction or corner, very common in hallways) loses its first t/2 below the head. The lintel `slab` only restores the part above the head. Result: a notch in the neighbouring wall. Also `h` per wall and `door_h` from the schema are ignored (hard-coded 2.7), and `slab` is undefined, so the "part most worth getting right" does not run as given.

ATTACK 4 [MAJOR] The vector-PDF route, called the most accurate, has no method
Where: Stage 1 "use them directly and skip most of stage 3"; tools table "vector extraction is far more accurate than pixels"
Problem: All wall/opening detection described in stage 3 is raster (thickness filter, skeleton, Hough). Nothing says how to turn `get_drawings()` paths into walls. CAD vector walls are usually two parallel lines (or a hatched fill) mixed with furniture, dimension and grid layers. The user has to guess how to pair parallel lines, filter layers or stroke widths, and detect door arcs from Bezier paths. "Skip most of stage 3" is a leap, since the hard part (what is a wall) remains.

ATTACK 5 [MAJOR] The "minimal first version" is not minimal and its calibration step is unusable as written
Where: Section 10, "about one day"; `calibrate --ref 102,88,1034,88 --len 9.9`
Problem: The v1 list includes ingest with deskew, thickness-filter skeletonisation with orthogonal snapping, gap-and-arc opening detection, shapely union with door/window cuts, extrusion, a three.js viewer, Playwright capture and a verify overlay. That is the core of the whole project, not one day of work, and it will fail on anything but a clean plan. Step 2 needs pixel coordinates in a processed image (after crop and deskew) that the user cannot know in a terminal session; no tool is given to display the image with a pixel grid or pick points. The user must guess coordinates.

ATTACK 6 [MINOR] Wrong inference in the deskew rule
Where: Stage 1, "Warn when the skew is above about 5 degrees, since that suggests a phone photo with perspective"
Problem: Skew angle is rotation; perspective is a different distortion. A flatbed scan rotated 8 degrees has no perspective, and a phone photo can have strong perspective at 0 degrees of rotation. The warning fires on the wrong cases and misses the real one. Detecting perspective needs a check such as non-parallel opposite walls.

ATTACK 7 [MINOR] Starter commands and the geometry claim do not hold as written
Where: starter `pip install ... pytesseract`; "`bpy` (pip)"; "no overlapping or z-fighting faces"; "model.stl ... solid shell"; "GLB is watertight per trimesh"
Problem: pytesseract needs the tesseract-ocr system binary (apt), which the command omits. pip `bpy` wheels exist only for specific Python versions and are very large; no version check is given. The build concatenates separate wall, lintel and sill extrusions that share coplanar faces. That leaves internal faces and z-fighting, and "watertight" passes per-piece without being one valid solid, so the STL "solid shell" claim and the acceptance test are unreliable.
