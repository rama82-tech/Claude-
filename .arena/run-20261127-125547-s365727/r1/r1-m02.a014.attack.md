ATTACK 1 [FATAL] Minimal v1 cannot cut openings with the libraries it installs
Where: "pip install opencv-python-headless shapely trimesh mapbox-earcut numpy pymupdf" and "`build.py plan.json` writes house.glb with floor and walls, with the openings cut out."
Problem: trimesh has no boolean engine of its own. `trimesh.boolean.difference` needs `manifold3d` (or Blender/OpenSCAD) installed. The install line has neither, and Blender is stated as "not installed". The v1 build step therefore raises an error at the first door. The text offers "extrude the footprint in segments" as an alternative but gives no recipe, so the user must invent the door-lintel and window-sill geometry. The "Done when" check (watertight, within 3%) cannot be reached by following the plan as written.

ATTACK 2 [MAJOR] Wall extraction only works for solid-filled walls, yet v1 is sold as automatic on a "clean plan image"
Where: Step 3 "keep only thick dark structures: morphological opening with a kernel slightly thinner than a wall"
Problem: Most clean CAD/architect plans draw walls as two thin parallel outlines (with or without hatch). An opening with a kernel thinner than the wall deletes both outlines and returns zero walls. Double-line walls, poche/hatch walls and vector PDFs are never handled. The plan does mention that vector PDFs can be read directly, but never says how walls are picked from the paths. The "Minimal first version" has no fallback for this case, so on a typical CAD export it outputs an empty plan.json.

ATTACK 3 [MAJOR] Room flood fill leaks through every doorway, and the proposed fix does not work
Where: Step 5 "Fill the area enclosed by walls (flood fill on the inverted wall mask)" with Step 4 "gaps in the wall mask along a wall are doors"
Problem: Doors and windows are gaps in the wall mask by the plan's own definition. A flood fill therefore runs through every door gap and merges all rooms into one region (and into the outside). The only mitigation given is "Close small gaps (dilate)", which sits in the open-plan row and would also seal doors unevenly. The plan does not say how to separate interior from exterior or how to bridge door gaps (for example, add a closing segment per opening before polygonising). Room polygons and room-area checks therefore fail on the first ordinary house.

ATTACK 4 [MAJOR] Accuracy test compares centreline lengths with printed face-to-face dimensions
Where: "Walls are centre-lines with a thickness" and "Done when: ... overall length and width match the printed values within 3%"
Problem: Printed overall dimensions are normally outside-face to outside-face, or interior clear dimensions. A centreline model is shorter than outer face by one wall thickness. Example: an 8 m outer dimension with 0.2 m exterior walls gives a centreline of 7.8 m, which is 2.5% off before any detection error. On a 6 m plan it is 3.3% and fails the stated gate. The plan never says which face the clicked scale length refers to, so the scale itself can be biased. The plan also says thickness is "measured" from the distance transform in Step 3 but uses a fixed 0.115 m default elsewhere, which contradicts the first.

ATTACK 5 [MAJOR] v1 scale input cannot be used in this environment, and unit parsing is missing
Where: "`extract.py plan.png --scale "x1,y1,x2,y2,3.6"`" and "two clicked points"
Problem: A Claude Code cloud session is a terminal with no GUI to click in. The user must already know pixel coordinates (x1,y1,x2,y2), and no step shows how to get them, for example by drawing a grid on overlay.png. The length is passed as a bare number (3.6), so a feet-inch value like 12'-6" has to be converted by hand, even though the plan says it supports ft-in dimensions. The user cannot act on this without guessing.

ATTACK 6 [MAJOR] Headless three.js screenshot path is under-specified and will fail as written
Where: "`view.html` (three.js, OrbitControls) loads house.glb. A Playwright script opens it and saves topdown.png and iso.png. No Blender needed."
Problem: GLTFLoader fetches the GLB with XHR/fetch, which Chromium blocks on file:// URLs, so a local HTTP server is required and is not mentioned. Headless Chromium in a GPU-less container also needs software WebGL flags (for example `--use-gl=angle --use-angle=swiftshader`) and a wait for the render loop. Neither is given. There is no code for the iso "cutaway" (hiding near walls) in three.js, though iso.png is a promised output. As a result, v1 has no way to produce either render.

ATTACK 7 [MINOR] Materials and lighting, an explicit requirement, are only named, with no values; Blender install left unresolved
Where: Step 8 "white matte walls, a wood or tile floor per room type, glass for windows, a sun lamp plus a few area lights" and Assumptions "installing it may or may not be possible"
Problem: The task asks how to get accurate materials and lighting, and the Blender renders are listed as outputs. The plan gives no colours, light strengths, camera heights or render settings, and the glass and wood recipes are missing. It never says how to install Blender (`pip install bpy` or apt), so the reader cannot tell whether stage 2 is reachable. The test checklist includes a phone photo, but the risk table has no handling for perspective or keystone correction, so that test case has no stated way to pass.
