ATTACK 1 [MAJOR] Wall corners are notched by the code that claims perfect corners
Where: Step 7 "Corners come out perfect" and the build.py sketch `LineString([w["a"], w["b"]]).buffer(w["thickness"] / 2, cap_style=2, join_style=2)`
Problem: In shapely, cap_style=2 is FLAT. join_style has no effect on a 2-point LineString. Two centre-lines meeting at an L corner, each buffered with flat caps, leave a missing (t/2 x t/2) square at the outer corner, and T-junctions end flush instead of overlapping. Counterexample: walls (0,0)-(6,0) and (6,0)-(6,4), thickness 0.23. The union has a 0.115 m square bite out of the outer corner at (6,0). The first runnable model, and the "width matches" acceptance test, therefore has visibly wrong corners and off-by-t/2 overall dimensions. It needs cap_style=3 (square) or extending each wall end by t/2.

ATTACK 2 [MAJOR] Wall-detection step is specified so that it can remove the walls
Where: Step 3.1 "Erode the image with a kernel roughly the wall thickness. What survives is walls."
Problem: Eroding with a kernel about equal to the stroke width deletes the stroke or leaves a 1 px sliver. The usable operation is an opening with a kernel strictly between the dimension-line/furniture stroke width and the wall thickness. The step also gives no way to get the wall thickness before the walls are found, yet Step 3.4 and the "Two further breaks" note say thickness is measured per wall. A 0.1 m partition and a 0.4 m outer wall in the same plan cannot both be kept by one kernel. The user cannot choose the kernel size from this text without guessing.

ATTACK 3 [MAJOR] Render-speed claim contradicts the stated environment
Where: Assumptions "no GPU and no desktop. Blender runs headless ... fine on CPU" and Step 9 "EEVEE-style quick renders take seconds"
Problem: EEVEE needs an OpenGL context. In a GPU-less container it only runs through software GL (llvmpipe or EGL), and recent EEVEE versions need OpenGL 4.3, which often fails or is very slow there. Only Cycles is a dependable CPU renderer. "Seconds" is unsupported. The plan also never says how to get Blender or `bpy` into the container (pip `bpy` wheel, apt build, or download), though it lists Blender as the Step 3 upgrade path and the render engine for all the final outputs. The "Blender is an upgrade" fallback hides that this part of the pipeline is untested.

ATTACK 4 [MAJOR] The minimal version cannot be built as written
Where: "The smallest version" install line and step 2, "skeletonise, Hough lines"; step 5 "preview.html that loads the GLB ... Playwright"
Problem: (a) Skeletonising is not in `opencv-python-headless`. `cv2.ximgproc.thinning` needs opencv-contrib, and `skimage.morphology.skeletonize` needs scikit-image, which is not in the pip list. Step 2 fails with an AttributeError or ImportError on the first run. (b) A page opened over file:// cannot fetch the .glb with GLTFLoader in Chromium (CORS on file origins). It needs a local HTTP server, which is not mentioned. (c) Headless Chromium with no GPU needs software-WebGL flags (for example `--use-gl=swiftshader` or `--enable-unsafe-swiftshader`, depending on the version) or the canvas renders blank. So the "about a day" first version stalls at its last step, producing no `preview.png`.

ATTACK 5 [MAJOR] Scale sanity check uses an input the plan does not contain and rejects valid plans
Where: Stress test 5 "Reject any scale that gives a room, door or ceiling size outside a sane range (door 0.6 to 1.2 m, ceiling 2.2 to 4 m, room 1.5 to 15 m)"
Problem: Ceiling height is not on a floor plan. The plan's own risk table says heights are defaults (wall 2.7 m), so a "ceiling" check can never detect a wrong scale. The room range wrongly rejects ordinary cases: a 1.2 x 1.5 m WC or closet, or a 20 m hall, retail unit or garage, would be flagged "scale looks wrong". Because the pipeline "refuses to continue", a legitimate plan gets blocked. The rule needs an override, or it should be applied to the door-width check only.

ATTACK 6 [MINOR] Pixel-to-metre conversion and axis handling are never specified, yet plan.json is in metres
Where: Step 2 and the minimal version "one number you type in (a known wall length)"; `"units": "m"` in plan.json
Problem: There is no step that applies the scale, no way to say which wall the typed length belongs to, and no mention that image y runs downward while 3D y/z runs upward. Without the flip, the model is mirrored relative to the plan. The overlay still lines up because it is drawn in image space, so the "overlay matches" acceptance test cannot catch it.

ATTACK 7 [MINOR] Multi-storey support is claimed but not designed
Where: Assumptions "Multi-storey plans are processed one page at a time and stacked."
Problem: Nothing says how floors are aligned (shared origin or an anchor such as stair or column positions), how stair openings are cut in slabs, or how storey height is set. Stairs are detected only as "approximate". Stacking independently scaled and offset pages gives misaligned floors. This is half of the "multi-storey" requirement the plan itself introduces.
