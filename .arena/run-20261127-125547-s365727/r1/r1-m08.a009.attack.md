ATTACK 1 [MAJOR] Wall detector only works on solid-fill walls, but the plan assumes "architect PDF, CAD export or clear scan"
Where: Step 3.1 "Erode the binary image with a kernel about the size of a wall to remove thin lines ... then dilate back. What survives is the wall mask." and Risks row "Support filled walls in version 1, add double-line later."
Problem: Most architect and CAD plans draw walls as two thin parallel lines (hollow, hatched or empty inside). Erosion with a wall-sized kernel deletes both lines, so the wall mask is empty. The stated Assumptions and the "three different clean plans" definition of done never restrict input to filled walls. A typical CAD-exported double-line plan returns zero walls. The "vector PDF" path via get_drawings() is only a one-line fallback ("group long thick line pairs") with no method for pairing lines into walls.

ATTACK 2 [MAJOR] GLB from trimesh will be Z-up, but the viewer and screenshots assume three.js Y-up
Where: Step 5.3 "Extrude ... with trimesh.creation.extrude_polygon" then Step 6/7 "model.glb ... top-down (orthographic), isometric cutaway, eye-level view"
Problem: extrude_polygon extrudes along +Z, and trimesh does not rotate to glTF's Y-up convention on export. Loaded in GLTFLoader the building lies on its side, so top.png shows a wall elevation, iso.png is wrong, and eye-level cameras sit inside the floor. The plan says "Y points down in image space and is flipped once, at build time" but never specifies the Z-up to Y-up rotation. The first runnable step ("When this looks right, half the project is done") would fail on first load, and the user has no instruction on how to fix it.

ATTACK 3 [MAJOR] Room-area accuracy check compares incompatible quantities
Where: Accuracy check 1 "Total area of detected rooms versus any 'total area' text on the plan, within 5 percent" with Floors "One polygon per room from polygonize" on centrelines
Problem: Rooms are polygonized from wall centrelines, so each room includes half of every bounding wall. Printed room areas are net (inside finish to finish). Counterexample: a 3.0 x 4.0 m net room with 0.115 m walls has a centreline polygon of 3.115 x 4.115 = 12.82 m2 against 12.0 m2 printed, a 6.8 percent error, so a correct detection fails. With 0.23 m exterior walls the error is larger. The check fails good results and also masks real errors. The plan needs to inset the polygons by half the wall thickness first, and it does not say so.

ATTACK 4 [MAJOR] Scale step relies on dimension-string-to-dimension-line matching with no method
Where: Step 2.1 "Match '4200' or '13'-9\"' to the pixel length of the line it labels. Take the median metres-per-pixel across all matches."
Problem: This is the hardest part of the pipeline and the plan calls it "the step that decides whether the model is accurate", yet it is one sentence. Tesseract returns text boxes, not associations to a dimension line, its extension lines or arrows. No algorithm is given for deciding which line a number belongs to (nearest line? rotated text on vertical dimensions?). Rotated and vertical dimension text is not mentioned. The user would have to invent this. The fallback (step 2.3, door as ruler) needs doors detected, but door detection is Step 6 of the build order and depends on the wall mask, so the order is circular in the first version.

ATTACK 5 [MAJOR] Viewer and screenshot script will not load the GLB as described
Where: Step 7 "viewer.html loads model.glb with three.js ... A Playwright script opens the page headless"
Problem: GLTFLoader fetches the file with fetch/XHR. Opened from a file:// URL, Chromium blocks this and the page never sets window.ready = true, so shot.py hangs or times out. The plan never says to serve the folder over HTTP (for example python -m http.server). It also lists two ways to get three.js (npm i three or a CDN) but does not say that ES-module imports from node_modules need an import map or bundler. In a sandboxed container the CDN may also be blocked by the agent proxy. The "build this today" path stalls at its first visual check.

ATTACK 6 [MINOR] Install line and Blender step ignore container constraints it itself flags
Where: Install block "pip install ... pytesseract" with Tools table "needs apt install tesseract-ocr"; Step 8 "blender -b -P build.py"; Assumptions "Blender is not assumed to be installed"
Problem: pytesseract does not work without the tesseract binary, but the install block omits the apt step and nothing says whether root or network access for apt exists. Step 8 gives no install route for Blender (apt blender is old, and the tarball download needs a network host that may be blocked). The minimal version is not affected by Blender, but "Photoreal render (version 2)" and the lighting section's Blender-specific advice cannot be acted on as written.

ATTACK 7 [MINOR] Time estimates and "done" criterion are not actionable
Where: "Wall detector (about 2 hours)" and "Definition of done ... on three different clean plans"
Problem: Total first-version estimate is about 5 hours, and the wall detector alone covers erosion tuning, skeletonize, Hough, snapping and gap merging, none of which is realistically done in 2 hours on real plans. No source for the "three different clean plans" is given, and "within a few percent" and "a handful of JSON lines" are not measurable thresholds. The user cannot tell when version 1 is finished.
