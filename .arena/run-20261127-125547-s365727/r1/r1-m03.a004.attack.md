ATTACK 1 [MAJOR] The 2% accuracy target and Test 1 equate a printed dimension with a wall centreline length
Where: Assumptions "wall lengths within 2% of printed dimensions"; schema example `"a": [0.0, 0.0], "b": [3.81, 0.0], "thickness": 0.15` with `"ref": "bottom wall 12'-6\" = 3.81 m"`; Test 1 "yields a wall length of 3.81 m +/- 2%".
Problem: Walls are stored as centrelines with thickness, but printed plan dimensions are almost always face-to-face (interior) or outer-face to outer-face. A 0.15 m wall on a 3.81 m printed interior dimension gives a centreline length of about 3.96 m, which is 3.9% off. The plan never says which datum a dimension refers to, so Test 1 either fails on a correct model or passes on a wrong one. The schema has no field for "dimension measured face-to-face / centre / outer". The user cannot hit the stated 2% target without guessing the datum.

ATTACK 2 [MAJOR] The recommended v1 path contradicts the privacy constraint, and gives no way to get correct coordinates
Where: Constraints table "Local CV by default. Vision-LLM extraction is opt-in per plan, because it uploads the user's floor plan" versus Tools "first choice: the person or Claude reads the image and writes plan.json ... This is the reliable v1" and Minimal v1 step 2 "Have Claude read the image, write plan.json ... Correct by hand."
Problem: The v1 that the plan calls reliable is itself the opt-in upload path it said to avoid by default. It also says "reliable" without support: a vision LLM estimating pixel coordinates and converting them to metres is the weakest step. Nothing says how the person finds the correct coordinates to "correct by hand". `overlay.png` has no metre grid or ruler, and plan.json is in metres while the image is in pixels. Step 2 of the minimal v1 also skips the scale step entirely, so it does not say where `metres_per_pixel` comes from in the first build.

ATTACK 3 [MAJOR] The viewer and render design will not run as described in headless Chromium
Where: "`viewer.html` (self-contained, vendored three.js)"; "Playwright loads `viewer.html?model=model.glb&preset=topdown`"; Test 8 "no console errors".
Problem: Loading model.glb from a page opened over file:// fails in Chromium (fetch and XHR to file:// are blocked), so the render step errors unless a local HTTP server is started. The plan never mentions one. GLTFLoader is an addon, not part of the core three.js bundle, so the page is not self-contained without an import map or bundling, and none is specified. In a no-GPU container WebGL needs SwiftShader flags (for example `--use-angle=swiftshader` or `--enable-unsafe-swiftshader`). Without them Playwright often gets no WebGL context, or logs GPU console warnings that fail the "no console errors" test. None of this appears.

ATTACK 4 [MAJOR] Prescribed wall geometry produces rounded corners and ends
Where: Step 6 "buffer each wall centreline by half its thickness, union all. Round-join corners so T-junctions are clean."
Problem: With shapely, a round join and the default round cap turn every convex outer corner into a quarter-circle and put semicircular ends on free-ending walls. A rectangular room therefore gets rounded outside corners, which is wrong for a floor plan. Square caps and mitre joins are what is needed, and T-junctions need no rounding. The bounding-box test (+/-1 cm) would still pass, so the error would go unnoticed. The instruction is wrong and no test catches it.

ATTACK 5 [MAJOR] The geometry step contradicts the per-wall nodes and the per-piece watertight test
Where: Step 6 "Footprint: ... union all", then "split the wall solid into a lower strip, a lintel, and the full-height wall either side", and "named nodes (`wall_w1`, `door_o1`)"; Test 5 "watertight per wall piece".
Problem: Once all wall footprints are unioned, per-wall identity is lost, so `wall_w1` and an opening's `wall` reference cannot be mapped back to a solid. It is also unspecified how an opening box is clipped when it sits at a T-junction, or how pieces of one wall get stitched so they do not leave internal faces. A door with `sill: 0.0` gives a lower strip of zero height, a degenerate mesh that fails `is_watertight`. The "no mesh booleans" claim is asserted but the described procedure does not work on a unioned footprint.

ATTACK 6 [MAJOR] No axis and handedness mapping from plan space to glTF
Where: "origin at the plan's bottom-left, y up in plan space"; Test 5 "expected bounding box (+/-1 cm of plan.json)"; Test 8 "wall pixel positions match the overlay within 3 px".
Problem: glTF and three.js use Y-up, so plan (x, y) must map to (x, 0, -y) or similar. If the plan y goes straight to world z, the model comes out mirrored. A mirrored model passes the bounding-box test and every closure test, and a top-down render is a flip of the image. Test 8 also needs a defined orthographic camera and a pixel-to-world calibration, and the plan gives neither. The 3 px match is not achievable from what is written.

ATTACK 7 [MINOR] Eye-level camera at the room centroid
Where: Step 8 "`eye_<room>.png` at 1.6 m height from each room centroid looking to the longest wall".
Problem: The centroid of an L-shaped or U-shaped room, or a room with a notch, can fall outside the polygon or inside a wall. The camera then sits in a wall or in the next room, and the render is blank or shows the wrong space. A point guaranteed inside the polygon (`representative_point`, or the pole of inaccessibility) is needed. Nothing handles this, and the Render test only checks "non-blank", so it would pass.
