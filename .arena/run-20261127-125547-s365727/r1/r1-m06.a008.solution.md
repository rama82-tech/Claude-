# Floor Plan to 3D Model: Build Plan

## Recommendation

Do not generate the 3D model straight from the image. Turn the plan into a small, checked, human-readable data file (`plan.json`: walls, openings, rooms, dimensions, unit, scale). A deterministic generator builds every 3D output from that file.

Why:

- Image generators and vision models recognise things well and place them badly. They invent walls and drift dimensions.
- A text file can be validated, diffed, hand-corrected and re-run. A picture cannot.
- GLB, renders and viewer all come from one file, so they agree.

**Division of labour (the key design rule):** classical CV (and vector data, when the PDF has it) supplies the **geometry**. The vision model (in this session, Claude looking at the image) supplies the **meaning**: which strokes are walls and which are furniture, door versus window, room names, which number labels which dimension line. A vision model's coordinates are never used as final geometry; they are snapped onto CV evidence or flagged.

**Stack, checked against this container.** I inspected the session environment: Python 3.13, Node 22, `trimesh` and `shapely` are installed; Blender, OpenCV, PyMuPDF and Tesseract are **not** installed. So:

- v1 (needs `pip install opencv-python-headless pymupdf pytesseract`, and `apt install tesseract-ocr`): Python + OpenCV + trimesh/shapely, GLB out, three.js viewer, Playwright (preinstalled Chromium) for PNG renders. Each install must be tested at the start; if pip or apt is blocked by the network policy, the fallback is plan.json written from Claude's reading of the image plus a human check, with the same validation.
- v2 (optional quality upgrade): Blender headless (`blender -b -P build.py`) for materials, lighting and Cycles renders. Install is not assumed to work. Step "Blender gate" below tests it and falls back to v1 on failure.

## The analogy: cheque processing

A cheque states its amount twice: digits and words. Two readers read them. The cheque is accepted only if they agree; otherwise it goes to a human clerk. Nobody trusts one noisy reader.

| Cheque processing | Floor plan |
|---|---|
| Two readings of the same amount | Two independent readings of the same geometry: vision reading vs CV/vector extraction |
| Accept only if they agree | Accept a wall only if both agree within a defined tolerance (defined below) |
| Reject pile for a clerk | Review overlay with flagged items in red |
| Format and limit rules | Sanity rules: closed rooms, door 600-1300 mm, plausible footprint |

Where the analogy breaks, and the fix:

- A cheque has one number; a plan has hundreds. Add the **dimension chain** check: room widths along a wall must sum to the stated overall dimension.
- Cheques are standardised; plans are not. Unit and scale are recorded explicitly, declared once per plan, and echoed back for confirmation.
- A bad cheque is caught at the bank; a bad wall silently makes a convincing wrong house. Two different checks are therefore needed, and they catch different things: (1) a **build check** that the 3D model matches plan.json, and (2) a **human overlay** that plan.json matches the drawing. The first cannot prove the second. The earlier idea of one round-trip test covering both was wrong, because phantom walls appear in both masks.

## Options considered

Scores 1 (poor) to 5 (good). "Works here" is as tested in this container.

| Option | Accuracy | Fails loudly | Editable | Works here | Effort | Verdict |
|---|---|---|---|---|---|---|
| A. AI image generator makes a 3D-looking picture | 1 | 1 | 1 | 3 | 5 easy | Not a deliverable. Mood image only, labelled "illustrative". |
| B. Classical CV (lines, contours, OCR) to geometry | 3 | 3 | 4 | 4 (pip needed) | 2 | The geometry reader. Weak at meaning. |
| C. Trained segmentation (CubiCasa5k-style) | 3 | 2 | 3 | 2 (weights, GPU) | 2 | Later, as a third reader. |
| D. CV geometry + vision meaning + validation + human review + scripted build | 4 | 5 | 5 | 4 | 3 | **Chosen.** |
| E. Manual tracing in Blender/SketchUp | 5 | 5 | 5 | 1 | 1 | Fallback and ground truth. |
| F. Vector PDF extraction | 4 | 4 | 4 | 4 (pymupdf) | 3 | Fast path when the PDF has real vectors. Still needs classification (below). |

D wins because it is the only option that is accurate, loud on failure, editable and runnable without a GPU. Its weak point, the vision model hallucinating, is covered by CV evidence and human review.

## Architecture

```
input (PNG/JPG/PDF)
 -> 0 INTAKE GATE          PASS / WARN / REJECT
 -> 1 NORMALISE            deskew, crop, keep pixel transform
 -> 2 SCALE & UNIT         declared unit + multiple scale estimates
 -> 3 READER B (geometry)  raster CV or vector paths -> centre-lines, thickness
    READER A (meaning)     vision model -> classes, openings, names, dimension labels
 -> 4 RECONCILE            defined match metric; snap A onto B
 -> 5 VALIDATE             hard rules; exit non-zero on failure
 -> 6 HUMAN REVIEW         overlay on source, approve -> frozen plan.json
 -> 7 BUILD                trimesh (v1) or Blender (v2) -> .glb (.blend)
 -> 8 RENDER               top, isometric, eye-level PNGs
 -> 9 CHECKS               build check + source overlay for sign-off
```

## Pipeline, step by step

### 0. Intake gate

Runs before any cost. Writes `intake_report.json` with PASS / WARN / REJECT and a plain-words reason.

- File opens and is not blank (more than about 2 percent dark pixels).
- Raster resolution: under 600 px on the long side is REJECT; 600 to 1500 px is WARN ("dimension text may be unreadable; expect lower accuracy"). Typical listing images of 800 to 1200 px are expected to run, not to give high accuracy.
- Perspective or shadow (a photo of paper): large brightness gradient or non-parallel wall directions is REJECT with advice to rescan flat.
- Skew: up to 15 degrees is corrected automatically (step 1) and reported; 15 to 20 degrees is WARN; beyond 20 degrees is REJECT.
- Blur (variance of Laplacian) below a threshold calibrated on the three test plans is WARN, much lower is REJECT.
- PDF: count pages and ask which one if more than one. Probe for vector content.

### 1. Normalise

Deskew, crop margins, grey, adaptive threshold. Keep the pixel-to-normalised-pixel transform so every coordinate traces back to the source image.

### 2. Scale and unit

Pixels mean nothing until pixels per millimetre is known.

**Unit** is one plan-wide value, taken in this order: `--unit mm|cm|m|ft-in` from the user; a title-block note read from the image ("all dimensions in mm"); inference from magnitude. Inference: if most dimension strings are integers between 300 and 20000 with no unit marks, the unit is mm. That inference is **echoed back for confirmation** ("assuming mm; 3750 reads as 3.75 m"). Feet-and-inches strings (`12'-6"`) are parsed with a strict grammar. A bare small number that fits more than one reading (e.g. "12" with no declared unit) is refused. This accepts the normal metric case (bare mm figures) and refuses only real ambiguity.

**Scale** sources, in priority order: (1) one reference length supplied by the user (`--ref W3=4200`); (2) dimension strings matched to dimension lines; (3) a scale bar or "1:100" note combined with known print size (least trusted; resized PDFs break it).

Each dimension gives its own px/mm estimate. If estimates differ by more than 3 percent, stop and list the disagreeing dimensions (misread digit, stretched scan, or "not to scale"). If the plan is not to scale and no reference is supplied, stop. If scale came from the user, output is labelled `SCALE: USER-SUPPLIED`.

### 3. The two readers

**Reader B, geometry (raster).** OpenCV:
1. Remove text via connected components.
2. Estimate the dominant stroke width (distance transform on the dark mask); this is the wall thickness in pixels.
3. Morphological opening with a kernel just under that thickness keeps wall-like thick strokes and drops dimension lines, hatching and thin furniture.
4. Skeletonise the kept mask; extract segments (LSD or probabilistic Hough on the skeleton); snap near-horizontal and near-vertical lines to axes within 3 degrees; merge collinear fragments.
5. Output: centre-line segments with measured thickness in mm.
Door arcs: detect quarter-circle arcs adjacent to wall gaps. Windows: double or triple thin lines inside a wall gap. Dimension and room text: Tesseract, with the vision model as second opinion.

**Reader B, geometry (vector PDF).** `pymupdf` `page.get_drawings()` returns paths with stroke width, colour and fill. A CAD export puts walls, furniture, dimensions, hatching, grids and the title block in the same path list, so the vector route does not skip classification. The method:
1. Drop paths outside the plan area (title block) and hairline strokes (typically dimension and grid lines).
2. Cluster by stroke width and colour; the wall cluster is the heaviest line or the filled-polygon set.
3. Walls are usually **double outlines**: pair parallel segments closer than 450 mm and overlapping along their length; the midline is the centre-line and the gap is the thickness. Filled polygons: take their medial axis via shapely.
4. Treat the result exactly like raster Reader B output.
What vectors buy is exact positions (no pixel noise), not meaning. If the PDF's vectors are a scanned image embedded in a PDF, it is a raster: go the raster route.

**Reader A, meaning.** In this session Claude reads the normalised image directly (no separate API assumed) and fills a strict JSON schema: for each B segment ID, label it wall-external, wall-internal or not-a-wall; doors (host wall ID, position along it, width, swing); windows (host wall, position, width, sill if shown); rooms (name, label point); stairs; and which dimension string labels which line. A also lists "could not see clearly" items instead of filling gaps. A malformed reply is retried once, then flagged. If A is unavailable, the run continues with B's geometry and manual labelling in `plan.json`, with the same safety checks and a WARN.

### 4. Reconcile (defined)

A's walls are first drawn **on B's segment IDs** (A is asked to classify B's segments), so most matches are by construction. When A also proposes walls B did not find, a proposed wall A matches a B wall if all hold:
- angle difference under 5 degrees;
- perpendicular distance from both of A's endpoints to B's centre-line under 2 measured wall thicknesses (in mm, via the scale, never a fixed pixel count);
- overlap along the line at least 50 percent of the shorter segment.

Outcomes:
- Match: use B's coordinates, A's class.
- B-only, long and thick (over 800 mm and at least 70 percent of the stroke width): kept as `status: "unconfirmed"`.
- A-only: no geometry exists to build from. Reported as "vision sees a wall here, CV does not" and shown on the overlay; A's endpoints are used only if the user confirms the item.
Unconfirmed items are drawn red. The default build is **draft mode**: unconfirmed walls are built too, coloured red, so the model is never near-empty and the user sees exactly what is in doubt. A clean build (`--final`) refuses to run while any unconfirmed item remains.

### 5. Validate (hard rules; exit non-zero)

- Walls snap at junctions: no gaps over 50 mm, no overlaps; T and L junctions explicit.
- Every room is a closed loop (shapely `polygonize`); an open room reports the two ends that do not meet.
- Dimension chains: along each wall line, the sum of segment dimensions equals the stated overall within 1 percent.
- Plausible ranges: wall thickness 70 to 450 mm, door 600 to 1300 mm, window 400 to 3000 mm, room at least 1.5 m2, total footprint at most 2000 m2 (larger almost always means a scale error).
- Openings lie inside their host wall and never overlap each other.
- Failure writes `validation_report.md` with item IDs and image coordinates. The build refuses a failed plan.

### 6. Human review

`overlay.png`: the source image with walls (blue), openings (green), unconfirmed (red) and IDs. The user edits `plan.json` or answers "W12 is real". Approval freezes plan.json with its own hash and the source image hash.

### 7. Build

All geometry comes from plan.json. Z up, metres, origin at the lowest-left corner, every object named with its plan ID.

**v1 (trimesh + shapely, runs here).**
- Walls: shapely `buffer` of centre-lines with flat caps by half thickness, union so junctions merge, subtract opening rectangles from the 2D footprint for the door and window parts (door full height up to 2.1 m; window as wall below the sill and above the head), then extrude with `trimesh.creation.extrude_polygon`. Doing openings in 2D plus separate lintel and sill blocks avoids 3D boolean failures altogether.
- Floors: one slab per polygonised room, with optional ceiling.
- Materials: a named lookup by room name (kitchen/bath tile, bedroom/living wood) as vertex or PBR colours; no texture files in v1.
- Export `house.glb` and a `viewer.html` using three.js or `<model-viewer>`.
- Defaults when the drawing is silent (wall height 2.7 m, exterior 200 mm and interior 100 mm thickness, sill 0.9 m, window height 1.2 m) are applied and listed in the report.

**v2 (Blender, optional).** Test first ("Blender gate"): `blender --version`, then a 10-second headless Eevee test render. If the download or install fails, or Eevee needs OpenGL the container does not have, fall back to Cycles CPU with a denoiser, and if that fails too, stay on v1. Never assume Blender works. The Blender build reads the same plan.json and offers materials, lights (sun plus area lights) and `clay`/`day` presets.

### 8. Renders and outputs

| Output | Format | Purpose |
|---|---|---|
| `plan.json` | JSON | Source of truth, versioned and hashed |
| `intake_report.json`, `validation_report.md`, `overlay.png` | JSON/MD/PNG | Evidence and review |
| `house.glb` | glTF binary | Web, AR, engines |
| `viewer.html` | HTML | Orbit viewer (three.js), loads the GLB |
| `top.png`, `iso_cutaway.png`, `room_<name>.png` | PNG | Playwright screenshots of the three.js scene (v1), or Blender renders (v2) |
| `house.blend` | Blender | v2 only, editable |
| `build_check.json`, `source_overlay.png` | JSON/PNG | Checks, below |

### 9. Checks (two different jobs)

**(a) Build check: does the model match plan.json?** Count walls and openings in the mesh against plan.json; compute each wall's actual centre-line from the exported mesh and confirm it is within 25 mm or half the wall thickness of the plan.json value, whichever is larger. This catches build bugs only, and the report says so.

**(b) Source overlay: does plan.json match the drawing?** Render the model top view at the source scale and overlay it semi-transparent on the original image (`source_overlay.png`). Then compute a one-sided distance score: the share of model wall pixels that lie within one stroke width of source dark ink (catches phantom walls), and the share of heavy source strokes that lie within one stroke width of a model wall (catches missing walls). Both are reported with the offending wall IDs highlighted; below 0.9 flags for review (the first threshold is tuned on the three test plans). Because the source's ink includes furniture and text, this is evidence for a human to look at, not an automatic pass. Final approval is the person looking at the overlay.

## Accuracy summary

- Walls: positions from CV or vector data, class from the vision model, snapping, junction merging, dimension chains, then both checks.
- Openings: positioned by distance along the host wall so they cannot drift; widths from the drawing; defaults labelled.
- Floors: derived from closed wall loops, so they always fit the walls.
- Scale: several independent estimates and a spread limit.

## Risks and failure cases

| Risk | Detection | Response |
|---|---|---|
| Photo with perspective or shadow | Brightness gradient, non-parallel walls | REJECT; ask for a flat scan |
| Rotated scan (up to 15 degrees) | Skew estimate | Auto-deskew, reported |
| Low resolution | Size | Under 600 px REJECT; 600-1500 px WARN |
| Unknown or inconsistent scale | Spread over 3 percent | Stop; ask for a reference length |
| Bare mm numbers | Magnitude inference | Accept with echoed confirmation |
| Ambiguous bare numbers (feet vs inches) | Strict parser | Refuse and ask for `--unit` |
| Furniture, hatching, grids read as walls | Stroke-width filter, A's classes, overlay check | Unconfirmed, red, draft mode only |
| Vision model invents or omits walls | A-only and B-only items | Flagged, never silently built in final mode |
| Vector PDF is really a scan | No path data | Use raster route |
| Vector PDF mixes layers | Stroke/colour clustering | Walls from the heaviest cluster; unknown clusters listed in report |
| Curved or diagonal walls | Not axis-snapped | v1 flags as unsupported |
| Multi-storey sheet | Several outlines or stair markers | One storey per run; user splits |
| Handwritten dimensions | Low OCR confidence | User types them in |
| Blender or pip install blocked | Install test at start | Stay on v1 with the tools that work |
| Boolean failures | Avoided by 2D opening subtraction | n/a in v1 |
| Model looks right but is wrong | Source overlay plus human sign-off | Flags with IDs |
| Over-trust in AI mood images | Policy | Labelled "illustrative, not to scale" |
| Confidential plans | Policy | Local processing; image goes to a remote vision model only with the user's agreement |

Fixed seeds, pinned versions, and a run folder holding inputs, versions and hashes make every result reproducible.

## Minimal first version (one to two days)

Scope: one storey, straight orthogonal walls, one clean raster or vector PDF, metric.

1. Environment check script: install `opencv-python-headless pymupdf pytesseract`, test each import, and print what is missing. Everything below degrades to a stated fallback if an install fails.
2. `intake.py`: size, blank, blur, skew, PDF vector probe.
3. `scale.py`: `--unit` and `--ref` from the command line first; dimension OCR in v2.
4. `read_geometry.py`: Reader B (raster or vector) writes `segments.json` (centre-lines, thickness, IDs) and an overlay with the IDs drawn.
5. Meaning step: Claude views the overlay and fills `labels.json` (class per segment ID, doors, windows, room names). This step is in the loop by design.
6. `reconcile_validate.py`: the match rules above, the hard validation rules, `plan.json` out, non-zero exit on failure.
7. `build.py` (trimesh/shapely): walls with 2D openings, floors, colours, GLB export.
8. `render.py`: Playwright screenshots of a small three.js page (top, isometric).
9. `check.py`: build check and `source_overlay.png`.

Acceptance tests, each with its expected result:
- (a) clean rectangular two-room plan with known dimensions: PASS.
- (b) the same plan plus furniture and text: PASS with flagged or filtered items and no furniture walls built in final mode.
- (c) the same plan rotated 12 degrees: PASS after auto-deskew, with the angle reported (this must not be a reject).
- (d) wrong dimension typed (e.g. 4200 changed to 2400): stop at the scale spread or chain check with the item named.
- (e) blurry 500 px version: REJECT with the reason.
- (f) photo of a plan taken at an angle: REJECT.
If (d), (e) or (f) ever produces a model without a warning, the pipeline is broken.

**Later versions:** dimension OCR and auto scale, Blender materials and lighting, stairs, a web review UI, textures and furniture, multi-storey, curved walls, a trained segmentation model as a third reader.

## Assumptions

- Single-storey, mostly orthogonal plan with at least one printed dimension, or the user supplies one reference length.
- Outputs are for visualisation, not construction or permit use.
- The vision step is done by Claude reading the image within the session; no separate API is assumed. A remote service is used only with the user's agreement.
- Python package installs may or may not be allowed by the network policy; the environment check in step 1 finds out on day one, and the plan has a stated fallback for each failure.
- Blender is optional and unverified; the product works without it.
- Defaults (wall height 2.7 m, door 2.1 x 0.9 m, window sill 0.9 m, thicknesses above) are used only when the drawing is silent and each is listed in the model's report.
