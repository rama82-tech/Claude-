# Turning a 2D floor plan into a 3D model: build plan

## 1. The finished result (what v1.3 produces)

One command:

```
python fp23d.py plans/house.pdf --page 1 --scale-line "412,880,1190,880=14'-6\"" --out out/house
```

`--scale-line "x1,y1,x2,y2=LENGTH"` gives two pixel points (read off `overlay.png` or any image viewer, in the 300 DPI raster) and the real length between them. It works in v1 because it needs no rooms, names or OCR. (From v1.3 you may also write `--known "Living=14'-6\""` to use a named room's inner width.)

`out/house/` then contains:

| File | What it is |
|---|---|
| `plan.json` | Single source of truth: scale, walls, openings, rooms (schema in section 5) |
| `overlay.png` | Original plan with detected walls (red), doors (green), windows (blue), wall IDs, room labels. The human check step. |
| `house.glb` | Walls, door leaves, floors, ceiling, window glass. Flat PBR colours (and baked floor PNGs from v1.3). |
| `house.blend` | Same model, procedural materials and lights, editable in Blender |
| `top.png` | 1920x1080 top-down orthographic render (the "3D floor plan") |
| `iso_cutaway.png` | Isometric render, all walls cut to 1.2 m, ceiling removed |
| `room_<name>.png` | One eye-level (1.6 m) render per room |
| `index.html`, `three/` | three.js viewer next to `house.glb`, with vendored three.js; open it through a local server (section 6, step 9) |
| `report.json` | Scale source, scale error, per-room area vs labelled area, warnings |

Everything below works backwards from that: each file needs the step before it.

## 2. Open questions, and how I resolve them

1. **Input vector or raster?** Support both and detect. In a vector PDF (CAD export) `page.get_drawings()` returns exact geometry. If it returns more than 200 paths, take the vector route; otherwise rasterise at 300 DPI.
2. **How is scale determined?** Priority: (a) `--scale-line` (two points + length), (b) from v1.2, OCR of dimension strings paired with dimension lines, (c) a scale note such as `1/4" = 1'-0"` plus PDF page size, (d) refuse and ask. Never guess silently; scale is the one error that makes every other number wrong.
3. **Automatic or human in the loop?** Human in the loop. One missed wall merges two rooms and one false wall splits one, so the pipeline auto-detects, writes `overlay.png`, and the user corrects `plan.json` before the build. This is the biggest design decision. I do not quote a specific segmentation accuracy; the loop exists because detection errors are expected on scans, hatched walls and furniture.
4. **Which 3D engine?** Blender headless via `bpy`: boolean cuts, PBR, Cycles, and `.glb`/`.blend` export from one script. three.js is only the delivery viewer.
5. **AI image generators?** Optional style pass only. They hallucinate walls and furniture, so never for geometry. If wanted, feed the clay `top.png` as an edge/depth condition.
6. **Units?** Internal metres. Parser accepts `12'-6"`, `12' 6"`, `12.5'`, `3750`, `3.75m`.
7. **Multi-storey?** v2 (one page = one storey in v1).
8. **Furniture, stairs, curved walls?** Out of scope for v1; flagged as warnings.
9. **How do v1 and later steps identify the measured span?** By pixel points (`--scale-line`), because rooms do not exist at the scale step.

## 3. Assumptions

- Typical architectural plan: walls are thick dark bands or double lines, doors are quarter-circle swings, windows are thin parallel lines in a wall, one storey per file, mostly orthogonal walls.
- Ceiling 2.44 m (8 ft). Exterior wall 0.20 m, interior 0.115 m if thickness cannot be measured.
- Door 0.81 x 2.03 m. Window sill 0.91 m, head 2.03 m (height 1.12 m).
- Linux container, Python 3.11+, Node 20, Chromium and Playwright installed, no GPU (use Cycles on CPU; Eevee needs GL and is unreliable headless).
- Package installs (pip, npm, apt) work through the proxy. No other external service is required for v1.

## 4. Architecture

```
input (PDF/PNG/JPG)
  |
[1 ingest] --vector?--> PyMuPDF get_drawings() -> wall candidates --+
  | raster                                                          |
[2 clean] deskew, binarise (OpenCV)                                 |
  |                                                                 |
[3 raster walls] thickness bootstrap -> opening -> skeleton -> Hough |
  +-----------------------------------------------------------------+
  |
[4 scale] --scale-line | OCR dimensions | scale note
  |
[5 openings] gaps + door arcs + window double lines
  |
[6 rooms] polygonize centrelines, subtract wall footprints, OCR labels
  |
plan.json + overlay.png   <-- human review/edit
  |
  +--> [7 build_blender.py] .blend .glb renders
  +--> [8 viewer] three.js loads house.glb over http://localhost
```

Rule: **everything after plan.json only reads plan.json.** You can hand-write a plan.json, skip all computer vision, and still get a model. That is also what makes testing possible.

## 5. plan.json schema

```json
{
  "units": "m",
  "scale": {"source": "scale-line", "px_per_m": 118.4, "error_pct": 0.8},
  "ceiling_height": 2.44,
  "walls": [
    {"id": "w1", "a": [0.0, 0.0], "b": [6.40, 0.0], "thickness": 0.20, "exterior": true}
  ],
  "openings": [
    {"id": "d1", "type": "door", "wall": "w3", "offset": 1.10, "width": 0.81,
     "height": 2.03, "sill": 0.0, "swing": "in-left", "leaf": "open90"},
    {"id": "n1", "type": "window", "wall": "w1", "offset": 2.00, "width": 1.50,
     "height": 1.12, "sill": 0.91}
  ],
  "rooms": [
    {"id": "r1", "name": "Living", "polygon": [[0.1,0.1],[6.3,0.1],[6.3,4.1],[0.1,4.1]],
     "floor": "oak", "label_area_m2": 24.8}
  ]
}
```

- Wall `a`/`b` are centrelines. `offset` is the distance along the wall from `a` to the opening's left edge. y is up (flip image y once at ingest, nowhere else).
- `swing` is one of `in-left|in-right|out-left|out-right` (hinge side and direction). `leaf` is `open90|closed|none`.
- Room `polygon` is the clear interior (wall footprints already subtracted), so its area is comparable to printed areas.

## 6. The pipeline step by step

### Step 1: Ingest
```
pip install pymupdf opencv-python-headless numpy shapely scikit-image pytesseract trimesh bpy
sudo apt-get install -y tesseract-ocr
```
- PDF: `fitz.open(p)[page]`. If `len(page.get_drawings()) > 200` go vector, else `page.get_pixmap(dpi=300)`.
- Images below 1500 px on the long side: warn and upscale 2x. Below 800 px: stop, thin lines are gone.

### Step 2: Clean (raster only)
- Grayscale, `cv2.fastNlMeansDenoising(h=10)`.
- Deskew with the dominant Hough angle; rotate if the absolute angle is between 0.3 and 10 degrees.
- `cv2.adaptiveThreshold(blockSize=35, C=10)` (global Otsu fails on uneven scans).

### Step 3: Walls
**3.0 Thickness bootstrap (before any morphology).** On the binarised image, collect the lengths of dark runs along every row and every column. Build a histogram. The first peak (1-4 px) is line work; the next prominent peak is wall thickness `T_px` (take the lowest-length peak whose count is above 20% of the tallest, excluding the line-work peak). If no second peak exists the plan has double-line walls: use route 2.

Expected `T_px` at 300 DPI, for orientation only (do not hard-code):

| Drawing scale | 4.5 in interior wall | 8 in exterior wall |
|---|---|---|
| 1/4" = 1'-0" (1:48) | about 28 px | about 50 px |
| 1/8" = 1'-0" (1:96) | about 14 px | about 25 px |
| 1:100 metric | about 12 px (115 mm) | about 24 px (200 mm) |

**Raster routes, in order:**
1. *Filled walls*: morphological opening with a square kernel of `0.6 x T_px` (so 17 px at 1/4" scale), which removes thin lines and text, then `skimage.morphology.skeletonize`, then `cv2.HoughLinesP(threshold=0.8*T_px+40, minLineLength=2*T_px, maxLineGap=T_px)`. Merge collinear segments within `0.15*T_px`; snap angles within 3 degrees to 0/90.
2. *Hatched or double-line walls*: find parallel line pairs whose separation is within 20% of `T_px`, take the midline; for hatching, close with a kernel the size of the hatch gap first.
3. *Optional, v2 only*: CubiCasa5K (repo `CubiCasa/CubiCasa5k` on GitHub, PyTorch). Its weights are not on pip; they are a manual download linked from the repo README (a Google Drive file), which the container's proxy may block. It segments walls, doors, windows and room types on its training distribution and gives **no metric scale**, so the scale step still applies. Nothing in v1 depends on it.

**Vector route:** filter `get_drawings()` by fill colour or the top-20% stroke widths; cluster, merge collinear, snap the same way.

Final wall thickness: median distance-transform value along the skeleton, times 2, converted with the scale. A wall is exterior if it touches the outer hull of the polygonised footprint.

### Step 4: Scale
- **v1:** `--scale-line "x1,y1,x2,y2=LENGTH"`. `px_per_m = hypot(dx,dy) / length_m`.
- **v1.2:** `pytesseract.image_to_data(config="--psm 11")`, keep tokens matching `\d+['"]` / `\d+\.?\d*\s?m`; pair each with the nearest dimension line (long line with end ticks); one `px_per_m` per dimension; take the median; `error_pct = MAD / median`. If above 3%, stop and ask for `--scale-line`.
- Sanity: an interior door leaf must come out 0.7-1.0 m wide and a room 1.5-10 m wide. Otherwise suggest the likely factor (2.54, 12, 10) and flag it.

### Step 5: Openings
- Find gaps in the wall mask along each wall line where the run is interrupted by 0.7-1.2 m of wall length; confirm doors with a quarter-arc: a straight leaf of length L with a curve of radius L from its end. Door width = L. (`HoughCircles` is unreliable here.)
- Windows: wall fill replaced by 2-3 thin parallel lines. Width = run length.
- Gap above 1.2 m with no arc: `type: "opening"`, no leaf.
- Project each onto its wall centreline to get `{wall, offset, width}`.
- In v1 these are typed by hand into `plan.json`.

### Step 6: Rooms
1. `unary_union` + 5 cm snap of the wall centrelines, `shapely.ops.polygonize`.
2. Footprint = `unary_union` of each wall's `LineString(a,b).buffer(thickness/2, cap_style=2)`. **Room polygon = centreline polygon minus footprint**, i.e. the clear interior. This is what is compared with printed area.
3. OCR text inside a polygon names it.
4. Area check: |area - label| / label above 3% is a warning; above 8% is an error (that usually means a missed or false wall). Only rooms with a printed area label are checked, and printed gross vs net area conventions are noted in `report.json`.

### Step 7: Human check
`overlay.png` shows walls with IDs, openings and room names. Edit `plan.json` by hand and re-run only the build. A 150-line canvas `editor.html` (drag endpoints, click a wall to add a door or window) is v2.

### Step 8: Blender build (`build_blender.py`)
Run: `python build_blender.py out/house/plan.json out/house` (with the `bpy` wheel) or `blender -b -P build_blender.py -- out/house/plan.json out/house`; if apt gives an old Blender, require `bpy.app.version >= (3, 6)`.

Function `build(plan, mode)`, where `mode` is `full` or `cutaway`.

For each wall (kept as its **own object**; walls are never unioned, so heights can change):
1. Box: length `|b-a| + thickness` (corner overlap), width `thickness`, height `H(wall, mode)`, rotated to the wall angle, centred on the midpoint.
2. For each opening on it, a cutter box (`width x thickness*1.5 x height`) at `sill`, with **height clipped to `H - sill`**; skip the cut if `H <= sill`. Apply a Boolean `EXACT` / `DIFFERENCE` modifier, then delete the cutter.
3. Door: a frame (0.05 m reveal) plus, if `leaf != "none"`, a 0.04 m slab of the opening's width, hinged on the side given by `swing` and rotated 90 degrees (`open90`) or left in the plane (`closed`).
4. Window: glass plane set 0.01 m inside the wall (Principled, transmission 1.0, IOR 1.45, roughness 0.02). In the GLB export, use alpha 0.3 instead of transmission (transmission extension support varies).
5. T-junction z-fighting: avoided by the corner overlap and by giving all walls one material, so coplanar faces look identical.

`H(wall, mode)`: `full` -> ceiling height. `cutaway` -> 1.2 m for every wall, except exterior walls on the far side of the camera, which stay at full height: with the camera direction vector `v` (horizontal projection), a wall is far-side if `dot(wall_midpoint - footprint_centroid, v) > 0`. Interior walls are always 1.2 m, so no "outward normal" is needed.

Floor: `bmesh` fill of each room polygon plus the wall-footprint area, extruded down 0.1 m. Ceiling: the same at `ceiling_height`, normals down, in its own collection excluded from `top.png` and the cutaway.

Materials:
- In the `.blend` (Cycles): Principled; wall (0.92, 0.91, 0.88) roughness 0.8; floors `oak` (Wave + Noise), `tile` (Brick at 0.6 m), `carpet` (flat grey-blue, roughness 1.0). UVs by Box mapping in object coordinates, so scale is physical.
- In the `.glb`: **procedural nodes do not export**, so v1 exports flat base colours only. From v1.3, a step generates `oak.png`, `tile.png` and `carpet.png` with numpy (512x512, tileable), assigns them as Image Texture nodes with UVs scaled to physical metres (`Cube Project`, scale 1 UV = 1 m), so the same look survives glTF.

Lighting: a Sun (strength 3.0, angle 5 degrees, 45 degrees elevation, from the north-west) and a Nishita sky (strength 0.8); per room an area light (1.0 x 1.0 m, 150 W) at ceiling height minus 0.05 m for interior shots.

Renders (Cycles, `device='CPU'`, 96 samples, OIDN denoise, 1920x1080):
- `top.png`: orthographic camera at z = 12 m looking down, `ortho_scale = max(bbox) * 1.1`, ceiling collection excluded.
- `iso_cutaway.png`: re-run `build(plan, "cutaway")`, orthographic, rotation (60, 0, 45) degrees, ceiling excluded.
- `room_<name>.png`: 24 mm lens, camera at the polygon's pole of inaccessibility (shapely `polylabel`, never the centroid, which can lie outside L-shapes), z = 1.6 m, aimed at the furthest corner.

Export (from `full` mode): `bpy.ops.export_scene.gltf(filepath="house.glb", export_format="GLB", export_apply=True)` and `bpy.ops.wm.save_as_mainfile(filepath="house.blend")`.

Time on a 4-core CPU container: build about 5 s, each render 30-90 s.

### Step 9: Web viewer (served, not file://)
`file://` cannot be used: Chromium blocks fetch and module loading from it, and the GLB would not load. So:
```
cd out/house && npm init -y && npm install three@0.160.0
cp -r node_modules/three/build node_modules/three/examples/jsm three/   # vendored, no CDN
python -m http.server 8000 &
```
`index.html` sits **in the same folder as `house.glb`** and uses an import map pointing at `./three/build/three.module.js` and `./three/jsm/`, then `new GLTFLoader().load("house.glb", ...)`, `OrbitControls`, and one checkbox that sets `ceiling.visible = false`.
Test it in Playwright: `page.goto("http://localhost:8000/index.html"); page.wait_for_function("window.__loaded === true"); page.screenshot(path="viewer.png")`, where `index.html` sets `window.__loaded = true` in the loader callback. Run Chromium with `--use-gl=swiftshader` (or `--enable-unsafe-swiftshader`) in a GPU-less container.

## 7. Getting accuracy (the checks that matter)

1. **Scale cross-check**: two independent dimensions agree within 3%.
2. **Room area check**: clear-interior area vs printed area, warn above 3%, error above 8% (single rule, see step 6).
3. **Closed shell**: the wall graph must `polygonize` to a bounded exterior polygon; dangling ends longer than 0.3 m are warned.
4. **Opening check**: each opening is inside its wall (offset >= 0.1 m from either end) and not overlapping another.
5. **Round trip**: render `plan.json` back to a 2D PNG and compute IoU against the input wall mask. Target above 0.85 on clean plans.
6. **Synthetic tests**: 10 hand-written `plan.json` files (L-shape, T-junction, diagonal wall, no windows, wide opening), rasterised with Pillow at 150/300 DPI at two scales (1/4" and 1/8"), with noise and 2 degree skew. Assert wall count, room count and area within 5%. One day of work; it catches most regressions, including the thickness bootstrap.

## 8. Risks and failure cases

| Failure | Symptom | Mitigation |
|---|---|---|
| Wrong scale | Door 2 m wide, rooms tiny or huge | Sanity ranges; two agreeing dimensions or `--scale-line` |
| Wrong wall-thickness estimate | Walls vanish or text becomes walls | Run-length histogram; the overlay shows it; override with `--wall-px` |
| Text/dimension lines over walls | Fake walls | Blank OCR bounding boxes in the mask before skeletonising |
| Hatched or poche walls | Mask splits into stripes | Close with hatch-gap kernel; or vector route |
| Photo of paper, perspective | Walls not parallel | `cv2.getPerspectiveTransform` with four user-clicked page corners |
| Furniture/fixtures drawn | Short fake walls | Drop segments under 0.5 m not touching another wall |
| Curved walls | Polygon approximation | v1 unsupported; 15 degree segments if flagged |
| Open plan | Rooms merge | Virtual divider in `plan.json` (`"virtual": true`) |
| Boolean fails on tiny gaps | Missing or spiky openings | Round coordinates to 1 mm; cutters oversize 1 cm in depth |
| Cutaway cuts through windows | Slivers | Cutters clipped to wall height (step 8) |
| Headless Blender GPU errors | Crash | `-b`, Cycles, `device='CPU'` |
| GLB loses procedural look | Flat grey in the viewer | Baked/numpy PNG textures from v1.3 |
| Viewer blank | Empty scene under `file://` | Serve over `http.server` |
| Multiple plans on one sheet | Wrong plan | `--crop x,y,w,h` |
| Stairs/levels | Missing | v2: extruded steps from a hatched rectangle |
| AI geometry hallucination | Extra rooms | Never use image generators for geometry |
| Plan privacy | Client plans | Everything runs locally; no external APIs in v1 |

## 9. Minimal first version (about 1 day)

Goal: from a clean image, a correct GLB and a top render, with the human fixing what the code gets wrong.

1. `fp23d.py in.png --scale-line "x1,y1,x2,y2=LENGTH" --out out/`.
2. Raster only: grayscale, adaptive threshold, thickness bootstrap, opening, `skeletonize`, `HoughLinesP`, snap, merge. Writes `plan.json` with walls only.
3. Scale from `--scale-line` only (no OCR, no rooms needed).
4. Writes `overlay.png` with wall IDs and a pixel grid every 100 px, so the user can read off scale-line points and edit walls.
5. `build_blender.py` extrudes separate walls, adds one floor slab from the wall hull, one sun, `top.png` and `house.glb`, with flat colours.
6. Doors and windows: typed into `plan.json` by hand (wall, offset, width).
7. Viewer: `index.html` + vendored three.js, served by `python -m http.server`.

Then: v1.1 door/window detection; v1.2 OCR dimensions; v1.3 rooms, names, `--known`, materials with baked PNGs; v1.4 cutaway and room renders; v2 vector route, CubiCasa5K, click editor, multi-storey, stairs.

Acceptance test for v1: a 3-room synthetic plan at 1/4" scale gives a GLB whose bounding box is within 2% of the true size, with the right wall count, in under 60 s; and the same plan rendered at 1/8" scale also passes.

## 10. Decision summary

- **Geometry source**: vector PDF if available, else OpenCV with a thickness bootstrap; learned models optional (v2). Never an image generator.
- **Single source of truth**: `plan.json`, hand-editable.
- **Builder**: headless Blender, separate wall objects, Boolean cuts, Cycles on CPU; cutaway is a second build pass.
- **Delivery**: `.glb` + `.blend` + PNG renders + a served three.js viewer.
- **Quality control**: scale cross-check, clear-interior area check, closed shell, human-reviewed overlay.
