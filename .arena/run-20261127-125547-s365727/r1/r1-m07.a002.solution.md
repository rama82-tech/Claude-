# Build plan: 2D floor plan to 3D model

## Recommendation

Build a small Python pipeline in which **a vision model reads the plan and writes a JSON description, and deterministic code turns that JSON into geometry**. Do not use an AI image generator for geometry, and do not train a CV model.

```
plan.png/pdf -> normalise -> read (text layer / OCR + vision) -> plan.json -> check + overlay -> you fix -> build.py -> house.glb + previews
```

Everything runs in the Claude Code container with no GPU. The user gets a file that opens anywhere, plus a JSON file to hand-edit when the reading is wrong.

## Who does the reading (decided up front)

There are two modes. Build mode A first.

- **Mode A, no API key (default).** The user drops the plan in the working folder and asks Claude Code to read it. Claude views the image with its Read tool, follows `extract_prompt.md` (the schema and rules below), and writes `plan.json`. No script calls a model and no key is needed. This is a conversation step, and the human sees the result straight away.
- **Mode B, scripted (optional).** `extract.py` calls the Anthropic API with the image and the same prompt. It needs `ANTHROPIC_API_KEY`, outbound access to api.anthropic.com through the session proxy, and it bills per call. Add it only if the user wants batch runs.

Both modes write the same `plan.json`, and everything after that is identical code.

## Questions that decided the design

**What must be accurate?** Wall positions, room sizes, and door and window positions. A render that merely looks like a house is not enough. Image generators cannot hold dimensions and they invent walls and furniture, so geometry comes from code.

**Where is the hard part?** Reading the drawing. Classic CV (Hough lines, contours, thickness heuristics) is fragile on scans, hatching, text and furniture symbols. A vision model lists rooms, walls and openings well but misplaces coordinates by a few percent. So the model proposes, and code and a human check.

**Can the scale be trusted?** Not from one model-read number. Digits get misread and pixel endpoints drift. So scale is taken from dimension text read by machine (PDF text layer or OCR), fitted over several dimensions and cross-checked (step 2).

**Which 3D tool?** Blender is heavy and needs an install or a live GUI, so it is optional for photoreal work. `trimesh` + `shapely` + `manifold3d` make clean meshes headless in pure Python and export GLB/OBJ. For previews, three.js with an orthographic camera in the preinstalled Chromium.

**What is the output?** `house.glb`, `house.obj`, `top.png`, `iso.png`, `plan.json`, `overlay.png`. Photoreal rendering is a later step.

## Pipeline

1. **Normalise.** Vector PDFs: keep the vector page and also rasterise at 200 DPI with `pymupdf`. Images: deskew, crop to the drawing, record pixel size. Upscale low-resolution scans 2x before OCR.
2. **Establish scale.**
   - Get dimension strings with their pixel positions from a machine source. A vector PDF gives these exactly through `page.get_text("words")` (pymupdf). A raster image uses `tesseract` (pytesseract) on the image, restricted to number patterns such as `12'-6"`, `3.75`, `3750`.
   - Each dimension must be tagged by what it measures: **interior face to face**, **outer face to outer face**, or **centreline**. Architectural plans mostly use the first two. The tag comes from the dimension line's end ticks (on the wall faces or centres). If unclear, ask the user once, and do not guess.
   - The pixel endpoints are measured on the faces the tag names. Compute `mm_per_px` from every usable dimension, then take the median. Require at least three dimensions, or one dimension plus a printed overall size. Hard stop if any dimension disagrees with the median by more than 1%. A misread digit shows up here as an outlier, so drop that one and report it.
   - The model's reading of the same dimensions is a second vote. A disagreement with OCR is reported, not silently resolved.
   - No printed dimension at all: stop and ask the user for one measurement (a scale bar is an alternative).
3. **Extract to JSON** (schema below), in plan pixel coordinates, then converted to metres using step 2. Rules for the prompt: one wall per straight segment, centreline coordinates, openings attached to a wall by an offset along it, no furniture, tag each wall `exterior`, `interior`, `partial` (free-standing or balcony) or `halfheight`. Room names are points (a label position), not polygons. Run a second, zoomed pass per quadrant if the plan is dense.
4. **Validate and snap** (all steps configurable in `plan.json` under `"options"`):
   - Snap endpoints within `min(5 cm, thinnest wall / 3)`. This never merges the two faces of a 10 cm partition.
   - Snap to axis-aligned only if the wall is within 3 degrees of an axis. Set `"axis_snap": false` for plans with deliberate angles. Walls at other angles are kept as drawn.
   - Closed-loop check is a **warning only** and ignores `partial` and `halfheight` walls, so balconies, porches and free-standing walls pass.
   - Each opening must lie within its wall, with its width fitting in the wall length.
   - Derive the rooms (step 6) and compare each room's **interior** area to any printed area, with a 3% tolerance.
   - Write `overlay.png` that draws walls, openings, derived room outlines, room labels and the dimension endpoints used for scale, all over the original plan.
5. **Human review.** Open `overlay.png`, edit `plan.json`, re-run from step 4. Expect one or two rounds. This is the main quality control.
6. **Build geometry** (`build.py`):
   - **Walls:** buffer each centreline by half its thickness (flat caps) with shapely, union into one footprint, and extrude to the wall height from z=0. Unioning gives clean corners and T-junctions. `halfheight` walls use 1.0 m.
   - **Rooms are derived, not read:** run `shapely.ops.polygonize` on the wall network, with each door gap bridged by a temporary line so rooms close, then subtract the wall footprint. Assign each label point to the polygon containing it. Report polygons with no label and labels outside every polygon. This guarantees that floors fit the walls and never overhang them.
   - **Openings:** for each door or window, build a box through the wall thickness and subtract it. A door runs from the floor to 2.1 m, and a window from sill 0.9 m to head 2.1 m. Subtract with `manifold3d` (through trimesh) and keep `is_watertight` checks.
   - **Floors:** the derived room polygons, extruded from z=-0.1 to z=0, so they sit under the walls and never overlap them. One material per room type (wood, tile, carpet by label).
   - **Ceiling:** optional, off by default so top-down views work.
   - **Materials:** flat PBR colours (walls off-white, glass blue and semi-transparent). They are applied as named GLB materials.
   - **Result:** one scene of separate bodies (walls, one floor per room, glass panes), each checked watertight. It is not fused into a single solid, which keeps materials editable.
7. **Export and preview.**
   - Write `house.glb` and `house.obj`.
   - **Preview with three.js, vendored locally:** `npm i three` and copy the files, so no CDN is needed. Serve the folder with `python -m http.server` because `file://` cannot fetch the GLB. Use `OrthographicCamera` for both a true top-down (`top.png`) and an isometric view (`iso.png`), one directional light plus ambient light.
   - **Headless Chromium has no GPU,** so launch Playwright with `args=["--use-gl=angle","--use-angle=swiftshader","--enable-unsafe-swiftshader","--ignore-gpu-blocklist"]`. After the screenshot, check that the image is not blank (pixel variance above a small threshold). On failure, fall back to `render_fallback.py`, which draws the top-down view in matplotlib from the same polygons with no WebGL.
8. **Optional photoreal stage.** Import the GLB into Blender (headless `bpy`, or the Blender MCP if the user has Blender running locally), add a sun and area lights, set Cycles to about 64 samples, and render. This is not part of the first version.

## `plan.json` schema (minimal)

Walls are centrelines in metres. The dimension in the example is interior (face to face).

```json
{
  "units": "m",
  "options": {"axis_snap": true, "wall_height": 2.7},
  "walls":   [
    {"id":"w1","a":[0,0],"b":[5.2,0],"thickness":0.2,"kind":"exterior"},
    {"id":"w2","a":[5.2,0],"b":[5.2,4.0],"thickness":0.2,"kind":"exterior"},
    {"id":"w3","a":[5.2,4.0],"b":[0,4.0],"thickness":0.2,"kind":"exterior"},
    {"id":"w4","a":[0,4.0],"b":[0,0],"thickness":0.2,"kind":"exterior"}
  ],
  "doors":   [{"wall":"w1","offset":1.0,"width":0.9}],
  "windows": [{"wall":"w3","offset":3.0,"width":1.2,"sill":0.9,"height":1.2}],
  "labels":  [{"name":"Kitchen","type":"kitchen","at":[2.6,2.0],"printed_area_m2":19.0}]
}
```

The centreline rectangle is 5.2 x 4.0 m, so with 0.2 m walls the interior is 5.0 x 3.8 = 19.0 m2. The printed area is the interior area, and the check compares that, not the centreline area. Curved walls, stairs and multiple storeys are out of scope for version 1.

## Minimal first version

About 250 lines of Python, built in one sitting:
- `pip install trimesh shapely manifold3d pymupdf pillow numpy matplotlib pytesseract` (plus `apt install tesseract-ocr` if missing), `npm i three`, and the already-present Playwright.
- `make_test_plan.py`: draws the test plan below with PIL, so the user needs no plan of their own.
- `plan.json`: written by Claude in mode A (or by `extract.py` in mode B).
- `check.py`: scale, snapping, validation, room derivation, `overlay.png`.
- `build.py`: step 6, writes `house.glb`.
- `preview.py` (+ `viewer.html`, `render_fallback.py`): step 7.

**Acceptance test.** `make_test_plan.py` draws a 9.0 x 6.0 m outer-face plan with 0.2 m exterior walls and 0.1 m interior walls: a living room, a kitchen, two bedrooms and a bathroom, with one entrance door in an exterior wall, 4 interior doors and 4 windows. It prints interior face-to-face dimensions as text. Pass criteria:
- The extracted scale matches the true value within 1%.
- The GLB's overall outer size is 9.0 x 6.0 m within 2%, and each room's interior size is within 2% of its printed size.
- All 5 doors and 4 windows are visible as openings in `top.png` and `iso.png`, and the number of derived rooms equals 5.
- Every body is watertight.

Only after this passes, try a real scan. To test the build half alone, hand-write `plan.json` for the test plan (this tests geometry only, not extraction).

## What makes it accurate

- Scale comes from machine-read text, fitted over three or more dimensions, with each one tagged face or centreline.
- Geometry is deterministic: the same JSON gives the same model.
- Rooms are derived from the walls, so floors always fit.
- The overlay and area check expose errors, including scale errors, instead of hiding them.
- Real wall thickness is kept, so interiors come out at the printed size.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| No printed dimensions | Wrong size | Require one user-supplied measurement |
| Dimension misread (8'-6" as 3'-6") | Wrong scale | Machine text source, 3+ dimensions, 1% outlier stop |
| Face versus centreline confusion | About 5% size error | Dimension tagging, interior-area check |
| Low-resolution or skewed scan | Walls misplaced, OCR fails | Deskew, upscale, per-quadrant pass |
| Furniture, hatching, text read as walls | Phantom walls | Overlay review, prompt excludes furniture |
| Thin or merged walls, open plans | Missing walls, rooms merge | Manual edit, unlabelled-polygon and area checks |
| Open doorways without doors | Rooms do not close | Door gaps bridged, openings listed explicitly |
| Angled walls, balconies, partial walls | Bent or rejected input | Snapping thresholds, `axis_snap` off switch, `partial` kind |
| Doors drawn as arcs, sliding doors | Wrong opening type | Treated as width plus offset |
| Boolean cut fails | Missing holes | manifold3d, `is_watertight` check |
| Blank headless screenshot | No preview | SwiftShader flags, blank check, matplotlib fallback |
| Several storeys, stairs, curves, roofs | Not modelled | Out of scope, per-storey JSON later |
| Model gives different JSON each run | Inconsistent results | Save `plan.json` as the source of truth |
| Photoreal render invents furniture | Misleading | Render only the extracted geometry |
| Plan is private | Data sent to a model | Use only plans the user may share |

## Assumptions

- The input is a single-storey, mostly orthogonal residential plan with at least three printed dimensions (or one plus an overall size).
- "3D model" means a viewable, exportable file (GLB/OBJ) plus preview images, not CAD or BIM.
- The default reading is done by Claude Code viewing the image in the session. A scripted model call is optional and needs an API key.
- No GPU. Chromium runs WebGL in software.
- Defaults: wall height 2.7 m, exterior walls 0.2 m, interior 0.1 m, door 0.9 x 2.1 m, window sill 0.9 m, all overridable in the JSON.
- The user will review an overlay and edit JSON to correct mistakes.
