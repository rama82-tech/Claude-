ATTACK 1 [MAJOR] The extraction step cannot run as written in the stated environment
Where: "`extract.py`: calls the model with the image and the schema prompt, saves `plan.json`" and the assumption "A model with vision capability can be called from the session"
Problem: The task context is a Claude Code cloud session with Python and Node. It states no API key and no SDK. A script that "calls the model" needs an API key, network access through the proxy and a billing path. None of these are given or checked. The plan never says the alternative, which is that Claude Code reads the image itself and writes plan.json with no script. The user cannot tell which of the two to build. Step 3 is the core of the pipeline, and it is left to guesswork. The offered fallback (hand-write plan.json) skips the part the user wants.

ATTACK 2 [MAJOR] Centreline geometry contradicts the printed-dimension scale and area checks, and the 2% acceptance test
Where: Step 2 "Compute units_per_pixel" from a printed dimension; Step 4 "Compare each room's computed area to any printed area"; schema example `"polygon":[[0,0],[5.2,0],[5.2,4],[0,4]],"printed_area_m2":20.8`; "Walls keep their real thickness through centreline buffering, so room interiors come out the right size."
Problem: Plan dimension strings such as 12'-6" usually run between wall faces (interior) or between outer faces. They are not centreline to centreline. The plan never says which pair of pixel endpoints to use for scale, and never converts centreline to face. The schema example is itself inconsistent. The room polygon equals the centreline rectangle (5.2 x 4 = 20.8 m2). The walls are 0.2 m thick, so the real interior is 5.0 x 3.8 = 19.0 m2. A printed 20.8 m2 would then be wrong by roughly 9%. The claim that interiors come out the right size is therefore false for this example. With 0.2 m walls on a 3.8 m room, the face-versus-centre mix-up is about 5%. That alone fails the plan's own "within 2 percent" acceptance test.

ATTACK 3 [MAJOR] Preview stack cannot deliver the promised top-down and isometric renders in a headless container
Where: Step 7 "Render a top-down and an isometric PNG with Playwright loading `model-viewer` or three.js on a local HTML page, with ... soft shadows"; Minimal first version "`preview.py`: Playwright screenshot of the GLB"
Problem: (a) `<model-viewer>` has only a perspective camera. It has no orthographic mode, so a true isometric or plan view is not possible with it. (b) The container has no GPU. Headless Chromium needs software-WebGL launch flags (SwiftShader) to render WebGL at all. The plan names none, so the likely result is a blank screenshot. (c) `model-viewer` is normally loaded from a CDN, which in this proxied sandbox may be blocked. (d) A GLB cannot be fetched from a file:// page because of CORS, so a local HTTP server is needed. None of this is mentioned. The "every opening must be visible in the preview" acceptance test depends on this step working.

ATTACK 4 [MAJOR] Scale reading relies on unverified model-read digits and model-supplied pixel endpoints
Where: "Dimensions are printed as text, so OCR is not needed as a separate step." Step 2 "Ask the model for one or two printed dimensions with their pixel endpoints"; "If several dimensions disagree by more than 3 percent, warn."
Problem: The plan itself says vision models "misplace coordinates by a few percent". It then takes the scale from those same model-read pixel endpoints. Reading digits on a low-resolution scan can also go wrong (8'-6" read as 3'-6"). With only one or two dimensions, the cross-check cannot catch a misread digit. The 3% warning threshold is looser than the 2% accuracy target. The task explicitly lists CV/OCR for dimensions. The plan dismisses OCR and offers no independent check, such as running OCR on the dimension strings. A wrong scale gives a wrong-sized model, and the overlay does not reveal that.

ATTACK 5 [MAJOR] Validation rules break on common plans
Where: Step 4 "Check that every wall is part of a closed loop"; "Snap near-horizontal and near-vertical walls to axis-aligned"; "Snap endpoints that are within about 15 cm"
Problem: Plans with a balcony or porch wall, a free-standing partial wall or a half-height partition, or a drawn exterior only, have walls that are not in a closed loop. This check would reject or flag valid input. The 15 cm snap on 0.1 m interior walls can merge distinct endpoints, such as the two faces of a 10 cm partition or a door jamb, or collapse short wall stubs. Forced axis alignment bends any plan with a 5 to 10 degree angled wall. The assumption says "mostly orthogonal", so the plan admits the case. It still gives no rule for it and no way to switch the snapping off.

ATTACK 6 [MAJOR] Rooms and walls are two independent model outputs with no consistency rule
Where: schema `"walls": [...]` and `"rooms": [{"polygon": ...}]`; Step 6 "Floors: each room polygon extruded 0.1 m"
Problem: The model must emit wall centrelines and room polygons separately. Step 4 checks only area against a printed value, which is often absent. Nothing derives rooms from the wall graph or checks that the polygons lie inside the walls. A floor can overhang a wall or leave a gap, and a room can have no enclosing wall. The floor is a 0.1 m slab from z=0 and the walls start at z=0, so the two overlap. The plan says nothing about whether the final mesh is one watertight solid or separate bodies. `is_watertight` is mentioned only for the boolean cut.

ATTACK 7 [MINOR] First-version acceptance test has no test input
Where: "Acceptance test: use one simple rectangular plan with 4 rooms, 3 doors and 4 windows."
Problem: The user has no stated plan, and the plan gives no source or sample. The counts are also underspecified. Four rooms joined by 3 interior doors would leave no entrance. The "overall dimensions within 2 percent of the printed ones" check is not defined as centreline or face (see Attack 2). The user cannot run this test without guessing what is being asked.
