ATTACK 1 [FATAL] The minimal first version has no plan.json schema and no code, so it cannot be built as written
Where: "Version 1: one afternoon... 1. Python script `plan_to_3d.py` that takes `plan.json` and writes `model.glb`... 2. Write the first `plan.json` by hand with Claude's help (about 30 lines for a small flat)"
Problem: The task asks for a "minimal first version the user could build". Everything depends on plan.json, but the plan never defines its fields. It does not say whether walls are centrelines or faces, whether coordinates are in pixels or metres, how an opening refers to its wall, or how rooms and materials are keyed. The only hint is `"floor": "oak"` in one bullet. "About 30 lines" cannot be checked against any format. The user, or Claude in a fresh session, has to invent the schema, and the later claims (Manhattan snapping, `declared` dimensions, mismatch highlighting) all depend on it. The only artifact for the "afternoon" version is a prose description of plan_to_3d.py. The wall-union and boolean steps also never say whether openings are cut in 2D or 3D.

ATTACK 2 [MAJOR] Scale cross-check contradicts the stated input assumption
Where: Assumptions: "with at least one printed dimension... or a known room size". Step 1.3: "Cross-check with a second dimension on a different wall. If the two scales differ by more than 2 percent, stop... refuse to build on a mismatch."
Problem: The assumption admits plans with only one printed dimension or none (a known room size, or the 0.9 m door fallback in step 1.2). The pipeline then makes a second dimension mandatory and blocks the build without one. A plan with a single overall dimension, such as `30'-0"`, has nothing to cross-check against, and the document says to stop. No fallback is given, such as accepting a single-source scale flagged as unverified. Meanwhile the "single check catches most wrong-size failures" claim rests on a second dimension that the assumptions do not guarantee exists.

ATTACK 3 [MAJOR] The printed-versus-measured check compares different quantities and will raise false alarms
Where: Step 2 "Rooms: polygonize the closed space between walls... compare with any printed area"; Step 3 "any mismatch between a printed dimension and the measured size highlighted. A mismatch above 3 percent is flagged"; Version 1 "rooms match the printed dimensions to within 2 percent"
Problem: Printed room dimensions are normally clear interior sizes, or sometimes centreline sizes. The document never says which is measured. Polygonizing wall centrelines gives centreline-to-centreline sizes, which are larger than the clear size by one wall thickness. Example: a printed 3.0 m clear-width room with 0.2 m exterior walls measures 3.2 m, a 6.7 percent mismatch, which is over the 3 percent flag and the 2 percent "done" criterion. The user would be told a correct model is wrong. The only fix offered is to edit plan.json, which does not address it. The document never says to subtract half-thickness before comparing.

ATTACK 4 [MAJOR] "Self-contained" viewer.html that loads a GLB, plus headless-Chromium screenshots, will not work as described
Where: Output table: "`viewer.html` | Self-contained orbit viewer (three.js)"; Tools table: "Quick preview image without Blender | Playwright screenshots of the three.js page | Already installed; good enough"
Problem: GLTFLoader fetches model.glb over HTTP. Opened from file://, Chromium blocks the fetch, so the page shows nothing unless the GLB is base64-embedded or a local server is run. Neither is mentioned. three.js itself needs a pinned local copy or a CDN, and the session network may not allow it. Playwright's headless Chromium in a no-GPU container also needs software-GL flags (swiftshader) for WebGL to render at all. The document states "no GPU assumed" but never mentions this, so the first top-down and isometric screenshot, a stated v1 output, is likely to come back blank or error. The viewer also has no camera-preset code, so "top-down" and "iso" are unspecified.

ATTACK 5 [MAJOR] Blender is claimed to be installable headless in the session without any basis, and the photoreal render path depends on it
Where: Assumptions: "Blender can be installed there headless; no live Blender window is needed." Tools: "Photoreal renders | Blender headless (`blender -b -P build.py`)"
Problem: This is an unverified factual claim about the environment. It gives no install route (apt, tarball download, or `pip install bpy`), the version, or whether the proxied network allows the download host. It never says how long Cycles takes on a CPU-only container, and the render outputs (render_iso, render_room_*) rest on this claim. There is no fallback if the install fails. The document also says the same `plan.json` drives Blender, but does not say how lights and room materials (defined "keyed by the room label") get into a GLB, which has no lights in this pipeline.

ATTACK 6 [MINOR] Coordinate and axis handling is stated but contradictory or incomplete
Where: Step 4.7: "Units and orientation: metres, Y-up for GLB (Z-up inside Blender); origin at the plan's lower-left corner"
Problem: trimesh and shapely extrusions are Z-up, and trimesh does not rotate to Y-up on GLB export unless told to. Image rows run top to bottom, so the plan's y must be flipped. Neither the flip nor the axis conversion is specified. If it is skipped, the model lies on its side in the viewer and renders come out mirrored. "Origin at the lower-left corner" is also unreachable for plans whose walls do not start at the image corner, and no offset rule is given.
