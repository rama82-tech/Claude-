# Turning a 2D Floor Plan into a 3D Model: Build Plan

## The short answer

Build a small pipeline with one rule at its centre: **the picture is never turned straight into 3D. It is first turned into a plain, human-checkable description of the plan (a `plan.json` file), and only that file is turned into 3D.**

```
plan image / PDF
   -> 1. clean up + set the scale
   -> 2. find walls, doors, windows, rooms (computer vision + Claude's vision, a first guess)
   -> 3. YOU check and fix the guess on an overlay        <- accuracy comes from this step
   -> plan.json  (the single source of truth)
   -> 4. build 3D from plan.json (deterministic code, no AI guessing)
   -> 5. outputs: model.glb, browser viewer, top-down/isometric/eye-level renders
```

Why this shape: a floor plan is only pixels. No tool reads every plan perfectly, because plans differ in style, scan quality and symbols. A pipeline that hides its guesses will give you a confident-looking 3D house with a wall in the wrong place. A pipeline that shows its guesses and lets you correct them in two minutes gives you a model you can trust. The 3D step is then simple, repeatable code.

## Assumptions

- You are a builder or designer, not necessarily a 3D or computer-vision specialist. You want something that works on your own plans soon, not a research project.
- Input is one floor (one level) per image or PDF page, mostly straight walls at right angles, with at least one printed dimension (for example `12'-6"`, `3.75 m`) or a known room size. Curved walls, multi-storey stacks and sloped roofs are later phases.
- Scans can be skewed, but are not hand sketches or photos taken at an angle (those are handled as a flagged risk, see below).
- Wall height is not on a floor plan. Default 2.7 m (9 ft), door 2.05 m by 0.9 m, window sill 0.9 m and head 2.1 m. All are editable.
- "3D model" means: a file you can open and share (GLB), something you can orbit in a browser, and rendered images. Not CAD or BIM (no IFC output in v1).
- Environment: your Claude Code cloud session (Linux, Python, Node, Chromium and Playwright installed, no GPU assumed). Blender can be installed there headless; no live Blender window is needed.

## Tools and why each earns its place

| Job | Tool | Why this one |
|---|---|---|
| Rasterize PDF, clean image | `pymupdf` (PDF to PNG at 200-300 dpi), `Pillow` | Pure pip install, no system dependencies |
| Deskew, threshold, find thick lines | `opencv-python-headless` | Walls are the thickest dark strokes; morphology separates them from thin dimension and furniture lines |
| Line/segment cleanup | `shapely` | Snap, merge, intersect and buffer geometry; builds wall polygons and room polygons |
| Read dimensions and room labels | Claude's own image reading first; `pytesseract` as a cross-check | Plan text is rotated and tiny; vision models read it better than classic OCR, and the second reader catches errors |
| Spotting doors and windows | Claude vision on cropped tiles, plus the geometric clue that a wall has a gap or a thinner double line | Door arcs and window symbols vary by drafter; a model that reads symbols beats hand-written rules |
| Optional trained detector | Pretrained floor-plan segmentation models (CubiCasa5k-style) | Phase 3 only. Heavy, needs more setup, and still needs your check |
| Build the 3D geometry | `trimesh` + `numpy` (Python) | Extrude polygons, cut openings (via `manifold3d` boolean), export GLB; works anywhere, no app needed |
| View in the browser | `three.js` with `GLTFLoader` and `OrbitControls` | One HTML file; opens the GLB; works on phone; you can share it |
| Photoreal renders | Blender headless (`blender -b -P build.py`), Cycles or EEVEE | Better light, materials and camera control than a browser. Reads the same `plan.json` |
| Quick preview image without Blender | Playwright screenshots of the three.js page | Already installed; good enough for a first picture |
| Check overlay | `matplotlib` or OpenCV drawing | Draw detected walls over the original image so you can see mistakes |

Not recommended as the core: an AI image generator ("make this plan 3D"). It makes pretty pictures with invented walls, wrong room sizes and no dimensions. It can serve as an optional last step for mood images only (see Phase 4). Live Blender through MCP is great for hands-on tweaking, but a headless script is easier to repeat and test, so use scripts as the base and MCP only if you want interactive editing.

## The pipeline, step by step

### Step 1. Clean the input and set the scale (the step that decides all accuracy)

1. If PDF, render the page at 300 dpi. If a photo or scan, deskew using the dominant line angle and crop the border.
2. **Scale** is the number of pixels per metre. Get it from the best available source, in this order:
   - Two points you click (or Claude picks) at the ends of a printed dimension, with the number typed or read.
   - A drawn scale bar, if present.
   - A known object (standard door about 0.9 m) as a last, flagged fallback.
3. Cross-check with a second dimension on a different wall. If the two scales differ by more than 2 percent, stop and show a warning. This single check catches most "the model is the wrong size" failures.
4. Save `scale_px_per_m` and the image path to `plan.json`.

### Step 2. First-guess extraction

- **Walls:** binarize, then use morphological opening with a kernel about as wide as a wall to keep only thick strokes. Skeletonize, trace centre lines, snap endpoints within a tolerance (about half a wall thickness), then force near-horizontal and near-vertical lines to be exactly so (Manhattan snapping). Record each wall as `{start, end, thickness}`.
- **Hatched or filled walls:** if walls are shown as double thin lines (common in CAD exports), fill the gap between parallel lines instead of using thickness. Detect which style it is first and say so in the overlay.
- **Openings:** find gaps in wall lines and door arcs. Classify each as door, window or open archway with width and position along its wall. Claude vision on a cropped region resolves doubtful ones.
- **Rooms:** polygonize the closed space between walls with `shapely.polygonize`; attach label text (Kitchen, Bed 1) by the label's position; compute area and compare with any printed area as a sanity check.
- **Dimensions text:** read all dimension strings; keep them as `declared` values to compare with the measured geometry in step 3.

### Step 3. Human check (the bit most plans skip)

Produce `check.png`: the original image with walls in red, doors in green, windows in blue, room labels and measured sizes written in each room, and any mismatch between a printed dimension and the measured size highlighted. A mismatch above 3 percent is flagged.

You then fix problems in either of two ways: edit `plan.json` directly (it is short and readable) or tell Claude "the wall at the top of the hall is missing; the bathroom door is on the east wall, 0.8 m wide" and it updates the file and redraws the overlay. Loop until the overlay looks right. Expect 1-3 rounds on a clean plan, more on a messy scan.

### Step 4. Build the 3D from `plan.json`

Pure code, no guessing:

1. **Floor:** union of room polygons, extruded 0.1 m down (or a flat slab).
2. **Walls:** for each wall, a box from its centre line and thickness, height 2.7 m. Join corners by unioning all wall polygons first (shapely), then extruding once. This avoids gaps and overlapping faces at T-junctions and corners.
3. **Openings:** for each door or window, make a cutter box (door: floor to 2.05 m; window: 0.9 m to 2.1 m; width from the plan) and subtract it from the wall with a boolean. Add a simple frame, and a glass pane for windows, so openings read visually.
4. **Ceiling:** optional, off by default for cutaway views, on for walkthroughs.
5. **Materials by room type:** wall paint, wood or tile floors (bathroom/kitchen tile, others wood), glass. Defined in a small table keyed by the room label.
6. **Lighting:** sun plus sky for exterior and cutaway; one soft area light per room plus window light for interior renders.
7. **Units and orientation:** metres, Y-up for GLB (Z-up inside Blender); origin at the plan's lower-left corner so the model sits on the ground.

### Step 5. Outputs

| File | What it is |
|---|---|
| `plan.json` | The checked description of the plan (re-usable, versionable) |
| `check.png` | The overlay used for checking |
| `model.glb` | The 3D model; opens in Blender, three.js, Windows 3D viewer, Quick Look, most web tools |
| `viewer.html` | Self-contained orbit viewer (three.js) |
| `render_topdown.png` | Orthographic top-down view with ceiling hidden, shows the layout like a classic 3D plan |
| `render_iso.png` | Isometric cutaway, good for presentations |
| `render_room_*.png` | Eye-level view per room |
| `house.blend` (Phase 2) | Editable Blender scene |
| `walkthrough.mp4` (Phase 3) | Camera path through the rooms |

## How to get each element accurate

- **Walls:** accuracy is limited by scale and by pixel size. At 300 dpi on a typical 24x36 in sheet, one pixel is a couple of millimetres, which is more than enough. The real error source is a wrong scale, so the two-dimension check in step 1 matters more than any clever algorithm. Snap to right angles only when the angle is within about 3 degrees; otherwise keep the angle (angled walls exist).
- **Thickness:** measure it from the image per wall type (exterior thicker than interior). Do not assume one number.
- **Doors and windows:** width from the symbol, height from defaults unless a schedule or elevation gives it. Swing direction is cosmetic in v1.
- **Floors and rooms:** use the closed polygons. If a room will not close (a missing wall segment), the overlay lists "room X is open here" with a marker, rather than inventing a wall.
- **Materials:** the plan rarely says. Use a sensible default by room name, and let the user override per room in `plan.json` (`"floor": "oak"`).
- **Lighting:** light is what makes renders feel real. Keep it simple: soft shadows, a warm sun at a fixed angle, enough exposure that rooms are not black. Windows must actually be openings with glass, or interiors render dark.

## Phased build: the smallest useful first version

### Version 1: one afternoon, no AI detection, no Blender

Goal: one plan in, a correct 3D box-house out that you can orbit.

1. Python script `plan_to_3d.py` that takes `plan.json` and writes `model.glb` (steps 4 and 5 above).
2. Write the first `plan.json` **by hand with Claude's help**: you give Claude the image; it reads walls, openings and dimensions by eye and writes the JSON (about 30 lines for a small flat). You check it with the overlay script.
3. `check.py` draws the overlay on the original image.
4. `viewer.html` with three.js loads the GLB; Playwright takes one top-down and one isometric screenshot.

This proves the hard parts (scale, wall union, opening cuts, export) and gives you a result to look at. It does **not** need OpenCV, OCR or Blender yet. If the version 1 model matches your plan, the idea works.

Done when: the model's rooms match the printed dimensions to within 2 percent, every door and window is a real hole, and the GLB opens in an outside viewer.

### Version 2: automate the first guess

Add OpenCV wall extraction, gap-based openings, shapely rooms, and tesseract/vision dimension reading. Add Blender headless script for good renders. Measure success on 5 of your own plans: how many edits did each need?

### Version 3: polish and breadth

Multiple levels, stairs, curved walls, a furniture library, walkthrough video, an optional trained segmentation model for hard scans, simple web upload page.

### Version 4 (optional): style images

Feed the render (as a structural reference) to an image generator for a mood or "styled interior" picture. Label these clearly as artwork, not measurements.

## Risks and failure cases

| Risk | What it looks like | What to do |
|---|---|---|
| Wrong scale | House 15 percent too small | Two-dimension cross-check; refuse to build on a mismatch |
| Furniture, text and hatching read as walls | Extra short walls everywhere | Filter by thickness and length; the overlay shows them; delete in the JSON |
| Thin-line CAD walls | Walls not detected | Fill between parallel line pairs; detect style first |
| Low-resolution or skewed scans | Wobbly lines, broken corners | Deskew; require at least 150 dpi; snap tolerances scaled to wall width |
| Door vs window confusion | Window cut as a door | Vision check on crops; flagged in the overlay with a confidence note |
| Unclosed rooms | No floor, odd area | List the open gaps; do not auto-invent walls |
| Sketches, photos and hand-drawn plans | Curved, uneven lines | Out of scope for v1; use the manual JSON route with Claude's reading |
| Bad boolean cuts | Holes that do not appear, or broken meshes | Cut from the unioned wall once; validate with `mesh.is_watertight`; fall back to building walls in segments around the opening |
| Missing information (ceiling height, sill height, materials) | Plausible but invented values | Defaults are stated in the output and can be overridden |
| Over-trusting an AI | A confident but wrong model | The human check step is mandatory; there is no "skip" in v1 |
| Copyright or privacy of plans | Plans may be client documents | Process locally in the session; do not upload plans to third-party generators without the owner's consent |

## How to know it worked: a short test set

1. **Rectangle test:** a 5 m by 4 m room, 4 walls, 1 door. Expect 20 m2 floor and exact wall lengths.
2. **L-shape with an interior wall:** tests corners and T-junctions (no gaps, no double faces).
3. **Window and door heights:** the render should show daylight through windows and a walkable door.
4. **Your real plan:** compare each room's measured size with its printed size, all within 2-3 percent.

## What to do next (in order)

1. Pick one real plan (a simple one, with printed dimensions) and share it in the session.
2. Ask Claude to read it into `plan.json` and draw `check.png`. Correct what is wrong.
3. Run `plan_to_3d.py`, open `viewer.html`, and compare against the plan.
4. When that works, tell Claude which step cost you the most correction effort (usually walls or openings) and automate that one first.
