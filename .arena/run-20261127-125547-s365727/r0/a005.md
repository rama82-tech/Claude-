# Floor plan to 3D model: build plan

## Recommendation in one paragraph

Do not go straight from pixels to a 3D mesh. Put one small, versioned, human-readable file in the middle: `plan.json`, a description of walls, openings, rooms and a real-world scale. Everything before it (image reading) is replaceable and may be wrong. Everything after it (3D geometry, renders) is deterministic code. You can open `plan.json`, fix a wrong wall by hand, and rebuild. This keeps the project maintainable as detection methods change, which they will.

```
image/PDF -> [1 ingest + scale] -> [2 extract] -> plan.json -> [3 validate] -> [4 build geometry] -> model.glb
                                      ^ swappable                                  |-> [5 viewer]  three.js page
                              (manual / vision LLM / CV)                           |-> [6 renders] PNG, top-down + eye-level
```

## Assumptions

- Input is one floor plan (PNG, JPG, or one PDF page) of one storey, drawn roughly top-down, with at least one printed dimension or a known door width.
- "3D model" means walls, floors, door and window openings, simple materials, lighting. It does not mean furniture, roofs or structural accuracy.
- Work runs in the cloud Linux container: Python, Node, Chromium and Playwright available, no GPU, no live Blender GUI. A person is available to review one overlay image per plan.
- Metric internally (metres), whatever units the plan prints.
- Accuracy target for v1: wall lengths within 2% of printed dimensions, every opening in the right wall.

## Hard constraints and what they force

| Constraint | Consequence |
|---|---|
| Headless container, no GPU | No GUI Blender MCP. Geometry in pure Python (`trimesh`, `shapely`), renders via headless Chromium + three.js. Blender is optional, behind the same `plan.json`. |
| Output must be inspectable and shareable | glTF binary (`.glb`) is the primary output: opens in any viewer, three.js, Blender, Windows 3D Viewer. |
| Dimensions are the truth, pixels are not | Scale comes from a dimension, never from image size. Every plan carries its scale source. |
| Scans are noisy and skewed | Extraction is allowed to be wrong, so a human-visible overlay and a validator sit before geometry. |
| Maintainable for 6+ months | One schema, pinned dependencies, golden-file tests, no stage reaching into another's internals. |
| Cost / privacy | Local CV by default. Vision-LLM extraction is opt-in per plan, because it uploads the user's floor plan. |

## Tools and why

- **Schema and validation:** JSON Schema (or `pydantic`), with a `schema_version` field. Migrations are a function per version.
- **Image prep:** OpenCV (deskew, threshold), `pdf2image`/PyMuPDF for PDFs.
- **Text and dimensions:** Tesseract (`pytesseract`) for dimension strings like `12'-6"` or `3.80`. Parse with a tested regex module that handles feet-inches, mm, m, fractions.
- **Walls and openings, first choice:** the person or Claude reads the image and writes `plan.json` (Claude Code can view images). This is the reliable v1.
- **Walls and openings, assisted:** OpenCV line detection (probabilistic Hough, morphological thinning), snapping to a grid, and door-arc detection (arc plus gap in a wall line). Optionally a vision model proposes a draft `plan.json`, which still goes through validation and review.
- **Rooms:** `shapely` `polygonize` over wall centrelines. Room labels from OCR text inside each polygon.
- **Geometry:** `shapely` for 2D (buffer centrelines to wall footprints, subtract openings), `trimesh` to extrude to a mesh and export GLB.
- **Viewer and renders:** three.js (pinned version, vendored locally, not CDN) in a static HTML page. Playwright screenshots it headlessly at fixed camera presets.
- **Optional photoreal path:** Blender via the `bpy` Python module in a script that reads `plan.json`, for Cycles renders and material work. Treat it as a second backend, not the core. An AI image generator can make a stylised top-down picture, but it invents walls, so it is a presentation extra and never the source of geometry.

## The `plan.json` contract

```json
{
  "schema_version": 1,
  "source": {"file": "plan.png", "sha256": "..."},
  "scale": {"metres_per_pixel": 0.0123, "method": "dimension", "ref": "bottom wall 12'-6\" = 3.81 m", "confidence": "measured"},
  "wall_height": 2.4,
  "walls": [{"id": "w1", "a": [0.0, 0.0], "b": [3.81, 0.0], "thickness": 0.15, "kind": "exterior"}],
  "openings": [{"id": "o1", "wall": "w1", "type": "door", "offset": 1.0, "width": 0.9, "height": 2.1, "sill": 0.0, "swing": "in-left"}],
  "rooms": [{"id": "r1", "label": "Kitchen", "floor": "tile"}],
  "materials": {"floor:tile": "#bfb8a8", "wall": "#f2efe9"}
}
```

Rules that prevent future traps: all coordinates are metres, origin at the plan's bottom-left, y up in plan space. Openings reference a wall by id plus an offset along it, not a world position, so editing a wall moves its doors. Unknown fields are preserved. Anything guessed carries `"confidence": "guessed"` and is highlighted in the overlay.

## Pipeline, step by step

1. **Ingest.** Convert to a 300 DPI raster, deskew with the Hough dominant angle, record a hash. Reject images with no detectable straight lines (photos of curved sketches).
2. **Scale.** Priority order: (a) two points picked on a printed dimension, (b) OCR'd dimension string matched to the nearest line, (c) a standard door width (0.9 m) as a last resort. Method 3 is flagged `guessed`, and the report says so in its first line. Never silently assume a scale.
3. **Extract.** Produce walls (centreline plus thickness), openings, room labels. Thickness: measure the dark band width in pixels, convert, snap to the nearest of 0.1, 0.15, 0.2, 0.3 m. Snap all endpoints to a 5 cm grid and merge endpoints within 10 cm so rooms close.
4. **Overlay and review.** Render walls (red), openings (blue), room polygons (translucent) on the source image to `overlay.png`. A person approves or edits `plan.json`. This step is required for anything but a throwaway.
5. **Validate** (see tests below). Fail loudly with the wall id, not a stack trace.
6. **Geometry.**
   - Footprint: buffer each wall centreline by half its thickness, union all. Round-join corners so T-junctions are clean.
   - Cut openings: for each opening make a box (width x wall thickness plus margin x height) at its offset, and split the wall solid into a lower strip (below sill), a lintel (above head), and the full-height wall either side. Doing this on the 2D/3D parts, not with mesh booleans, avoids the fragile boolean failures that plague scripted CAD.
   - Windows: add a thin glass pane (transparent material) in the cut. Doors: leave open by default, optional leaf mesh.
   - Floors: one slab per room polygon, thickness 0.1 m, material from `rooms[].floor`. Ceiling optional and off by default so top-down views work.
   - Export `model.glb` with named nodes (`wall_w1`, `door_o1`, `floor_r1`) so edits and tools can find things.
7. **Materials and lighting.** A small named palette in the schema. Lighting presets in the viewer: a hemisphere light plus one directional sun with soft shadows. Keep presets in one config file.
8. **Renders.** Playwright loads `viewer.html?model=model.glb&preset=topdown` and saves PNGs: `topdown.png`, `iso_cutaway.png` (walls clipped at 1.2 m), `eye_<room>.png` at 1.6 m height from each room centroid looking to the longest wall. Also `overlay.png` and a `report.md`.
9. **Optional Blender pass.** `blender --background --python build_from_plan.py -- plan.json` (or `bpy`) reading the same file for Cycles quality renders and a walkthrough video.

## Output files

`plan.json` (source of truth), `overlay.png` (what the machine thought it saw), `model.glb`, `viewer.html` (self-contained, vendored three.js), `renders/*.png`, `report.md` (scale source, counts, warnings, which values were guessed).

## Tests first (acceptance checks the build must pass)

Write these before the code. Use 3 fixture plans: a clean one-room rectangle, a three-room plan with doors and windows, and a deliberately ugly scan (skewed, noisy).

1. **Scale:** On fixture 1, the 3.81 m printed dimension yields a wall length of 3.81 m +/- 2%. If no dimension is found, `scale.confidence` is `guessed` and `report.md` says so.
2. **Schema:** Every `plan.json` validates; a file with a wall of zero length, an opening wider than its wall, or an opening id pointing to a missing wall fails with that id in the message.
3. **Closure:** Every room polygon is closed; the sum of room areas plus wall area is within 3% of the outer footprint area.
4. **Openings:** Each opening lies fully inside its wall, and two openings on one wall do not overlap or sit closer than 0.2 m to a corner.
5. **Geometry:** `model.glb` loads, is watertight per wall piece (`trimesh.is_watertight`), has the expected bounding box (+/-1 cm of `plan.json`), and contains one named node per wall, opening and room.
6. **Determinism:** Running the pipeline twice from the same `plan.json` produces byte-identical GLB (golden-file test). Changes to the output require updating the golden file on purpose.
7. **Round trip:** Move wall `w1` in `plan.json`; the door on it moves with it and the model still passes tests 3 to 5.
8. **Render:** Playwright produces non-blank PNGs (not a single colour, size above a threshold) and no console errors. The top-down image's wall pixel positions match the overlay within 3 px.
9. **Failure behaviour:** A photo of a hand sketch is rejected with a clear message; an image with no scale produces output flagged `guessed`, never a silent default.
10. **Pinned environment:** `pip install -r requirements.lock` plus `npm ci` plus `make test` passes on a clean container.

Pass means all ten green. Add every real-world bug you meet as a new fixture plus a test.

## Minimal first version (build this first, about one day)

No computer vision at all.

1. Define `plan.json` and its validator (steps above).
2. Take one real plan. Have Claude read the image, write `plan.json`, and render `overlay.png` so you can see mistakes. Correct by hand.
3. Write `build_glb.py` (shapely + trimesh): walls with door and window cut-outs, floor slab, GLB out.
4. Write `viewer.html` plus a Playwright script that takes `topdown.png` and `iso.png`.
5. Run tests 1 to 8 on the fixtures.

This proves the part that is hard to fix later (schema, geometry, scale) and delivers a real result. Add extraction automation only once you have 5 to 10 reviewed plans to measure it against.

## Roadmap

- **v2:** OCR dimensions and automatic scale; Hough wall detection; door-arc detection; accuracy reported as wall precision/recall against your reviewed `plan.json` files.
- **v3:** Bring-your-own materials, furniture from a symbol library, ceilings, multi-storey (`levels[]` in the schema), Blender backend for photoreal renders and walkthrough video.
- **Later:** a small web editor that drags walls over the overlay. The schema is already what it edits.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Wrong scale | Everything is the wrong size, looks plausible | Scale method recorded and shown; cross-check second dimension, warn if they disagree by more than 3% |
| Curved walls, diagonals | Hough yields staircase segments | v1 supports straight walls only; flag arcs and ask for manual entry |
| Scan noise, hatching, furniture symbols | False walls | Overlay review; ignore short isolated segments; filter by thickness |
| Open-plan or unclosed rooms | `polygonize` returns nothing | Validator names the gap and its coordinates; offer to add a virtual wall (`kind: "virtual"`) |
| Doors in plan drawn as symbols varying by country | Missed openings | Manual opening entry is first class; detection is only a suggestion |
| Boolean or mesh failures | Holes, non-manifold walls | Build from 2D polygons and separate pieces, no mesh booleans; watertight test |
| AI-generated 3D images | Invented rooms, walls moved | Never used as geometry source; label as illustrative |
| Vision-LLM drafts | Plausible but wrong coordinates | Always validated and overlaid; confidence `guessed` |
| Private plans uploaded | Privacy | Local CV default; external services opt-in per file |
| Dependency drift (three.js, bpy, trimesh) | Breaks in six months | Lock files, vendored three.js, golden-file tests, schema version with migrations |
| Several storeys or very large plans | Slow, wrong stacking | Out of v1; schema leaves room for `levels` |

## Trade-offs I made on purpose

- GLB plus three.js over Blender-first: runs headless in your container, no install fight, easy to share. Blender stays as an optional backend because it reads the same file.
- Human review is a required step, not a failure of automation. Plans are too varied for fully automatic accuracy, and a visible overlay turns silent errors into fixable ones.
- A boring schema over clever detection: detection tools will change, the data contract should not.
