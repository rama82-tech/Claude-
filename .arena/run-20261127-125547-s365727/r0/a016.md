# Turning a 2D floor plan into a 3D model: build plan

## Bottom line

Build a pipeline in which **geometry is extracted once into a small, human-checkable JSON file (the "plan IR"), and everything downstream (3D model, renders, viewer) is generated deterministically from that file.** Use computer vision for walls, OCR for dimensions and room labels, and a vision-language model to label and cross-check. Use AI image generators only for decorative renders, never as the source of geometry.

Confidence in this architecture: high (about 85%). Walls extracted from a raster plan are never perfect. A pipeline with a verification step the user can see and correct beats a "magic" one-shot converter, because wrong geometry can't be repaired once it is baked into a render or an image.

Recommended stack (all verified installable in the container by `pip install`, see "What was tested"):

| Layer | Tool | Why |
|---|---|---|
| PDF/scan intake | PyMuPDF (`fitz`) rasterise, or vector paths extracted directly | Vector PDFs give exact lines with no CV |
| Wall extraction | OpenCV (threshold, morphology, contours, Hough) | Deterministic, debuggable, no GPU |
| Dimensions and labels | Tesseract (`pytesseract`) or a VLM (Claude vision) | OCR for numbers; VLM for "which text is a room name vs a dimension" |
| Geometry | Shapely (2D polygons, boolean ops) | Clean wall unions, door cuts, floor slabs |
| 3D mesh | trimesh (+ scipy, mapbox_earcut) to GLB | Pure Python, watertight extrusions, one file |
| Viewer | three.js (or `<model-viewer>`) in a static page | Interactive, shareable, and renderable by Playwright |
| Photoreal renders | Blender headless (`blender -b -P`) or Blender via MCP | Materials, lights, Cycles/EEVEE, walkthrough video |
| Optional "pretty" images | AI image generator on top of a clay render | Mood boards only; geometry stays authoritative |

## Assumptions

1. Input is a single-storey floor plan as PNG/JPG/scan or PDF, mostly orthogonal walls (90 degree corners), drawn in a conventional style: thick dark wall lines, thinner lines for dimensions, text for labels.
2. At least one real-world length is known (a written dimension, a scale bar, or a user-supplied "this wall is 4.2 m"). Without any, the model has no true scale and the pipeline must say so instead of guessing. Standard door width (about 0.8 to 0.9 m) can give a rough fallback, flagged as "estimated, plus or minus 15%".
3. Ceiling height defaults to 2.7 m, wall thickness is measured from the drawing, not assumed.
4. The user wants a viewable model and renders, not a BIM/IFC deliverable (IFC is listed as a later extension).
5. Runtime is the Claude Code cloud container: Linux, Python 3.13 and Node 22 present, outbound `pip`/`npm` working, Chromium and Playwright present. Blender and Tesseract were **not** found in the container, so they need installing (`apt`/download) or running on the user's machine; the minimal version avoids them.
6. Curved walls, multiple floors, sloped roofs and hand-sketched plans are out of the first version.

## Architecture

```
plan.pdf/png/jpg
   |
   v
[1 Intake]  rasterise PDF at 200-300 dpi (or read vector lines), deskew, crop, greyscale
   |
   v
[2 Scale]   px_per_m  <- OCR'd dimension + its pixel endpoints, or scale bar, or user input
   |
   v
[3 Extract] walls (thick strokes) | openings (gaps, arcs, window glyphs) | rooms (enclosed regions) | text
   |
   v
[4 Plan IR] plan.json  (metres, y-up): walls[], openings[], rooms[], scale{source, confidence}
   |        ^
   |        +-- human/VLM review: overlay.png (IR drawn on the original) -> fix -> re-run
   v
[5 Build]   Shapely cleanup -> extrude walls, cut openings, floor slab, optional ceiling -> house.glb
   |
   v
[6 Present] three.js viewer (index.html) + Playwright screenshots; Blender renders + video
```

The contract between stages 4 and 5 is the IR. Because it is plain JSON, a person (or Claude) can fix a wall by editing two numbers instead of re-running a vision model and hoping.

### Plan IR (suggested schema)

```json
{
  "units": "m", "up": "z", "height": 2.7,
  "scale": {"px_per_m": 50.0, "source": "ocr_dimension|user|door_default", "confidence": 0.9},
  "walls": [{"id": "w1", "a": [0,0], "b": [8,0], "thickness": 0.2, "kind": "exterior|interior"}],
  "openings": [
    {"id": "d1", "type": "door",   "wall": "w5", "t": 0.40, "width": 0.9, "sill": 0.0, "head": 2.1},
    {"id": "n1", "type": "window", "wall": "w2", "t": 0.50, "width": 1.2, "sill": 0.9, "head": 2.1}
  ],
  "rooms": [{"id": "r1", "label": "Kitchen", "polygon": [[0,0],[4,0],[4,3],[0,3]], "floor": "tile"}],
  "needs_review": ["w7 length ambiguous", "n3 might be a door"]
}
```

Walls as centre-line segments with thickness (rather than raw polygons) is deliberate: it lets you snap corners, close small gaps and cut openings by position along the wall (`t`), all of which are hard on pixel-derived outlines. The minimal version below uses the pixel-derived polygon route first, then migrates to centre-lines in step 3.

## Pipeline detail and how to get each element accurate

### 1. Intake

- **Vector PDF** (exported from CAD/Revit/SketchUp): extract line segments with PyMuPDF `page.get_drawings()`. This skips CV entirely and gives exact geometry; check for it first. Confidence it is worth checking: high, because it is cheap and when it applies it removes most error.
- **Raster/scan**: rasterise at 200-300 dpi. Deskew by estimating the dominant line angle (Hough) and rotating. Crop title blocks and legends if they contain thick borders, otherwise the border becomes a "wall".

### 2. Scale (the single biggest accuracy lever)

Every error in scale multiplies through every dimension of the model, so treat scale as a first-class output with a source and confidence.

Priority order:
1. User-supplied: "the wall from A to B is 4.20 m" (two clicks or two coordinates).
2. OCR of dimension strings (`4200`, `4.20 m`, `13'-6"`) paired with the nearest dimension line and its extension lines' pixel endpoints. Parse feet-inch carefully (`13'-6 1/2"`), and detect unit (mm vs m) by magnitude and plausibility (a room cannot be 4 mm).
3. Scale bar or "1:100" note. Caution: a "1:100" note is only valid at the original print size; a screenshot or resized PDF breaks it. Use only with a known DPI/page size.
4. Door-width fallback, flagged low confidence.

Cross-check rule: with 3 or more dimensions available, compute px_per_m for each; if the spread is above 3%, set `needs_review` (the drawing may be not-to-scale, which is common for sketches and marketing plans). Arithmetic check: dimension chains must sum to the overall dimension within rounding.

### 3. Walls

Approach in order of increasing sophistication; stop at the first that works on the user's plans.

- **A. Thick-stroke mask (minimal version, built and tested below).** Otsu-threshold, then a morphological *opening* with a square kernel just under the wall thickness. Anything thinner than the kernel (text, dimension lines, furniture outlines, hatching) disappears; walls stay. Choose kernel from the expected minimum wall thickness in pixels (`min_wall_m * px_per_m`).
- **B. Centre-line extraction.** Skeletonise the mask (`skimage.morphology.skeletonize`), trace the skeleton graph, simplify with Douglas-Peucker, snap angles to 0/90 degrees when within 3 degrees, merge collinear segments, close gaps shorter than a wall thickness, and measure thickness as twice the distance-transform value along the skeleton. This produces the IR walls.
- **C. Hatched or double-line walls** (common in architectural drawings: two thin parallel lines, sometimes with fill hatching): fill closed thin-line regions by flood fill, or close the gap between parallel lines with a dilation, then continue as A. This is the most frequent failure of A.
- **D. Learned segmentation** (e.g. a CubiCasa5k-style model) for messy raster plans. Higher recall on noisy scans, but needs a GPU or slow CPU inference, model licensing checks, and produces masks that still need B. Use only if A to C fail. Confidence that a classical pipeline suffices for clean plans: about 75%. For hand sketches or photographed paper: below 40%, then go to D or to VLM-assisted tracing.

### 4. Openings: doors and windows

Detection cues, strongest first:
- **Gaps in the wall mask.** Where the wall centre-line mask has a break with both ends on the same line, that is an opening (width = gap length).
- **Door swing arc**: a quarter circle plus a straight leaf, detected with Hough circles or contour curvature; it also tells hinge side and swing direction.
- **Window glyph**: parallel thin lines inside the wall thickness, or a wall segment drawn with a thinner outline.
- **Text/legend tags** (`D1`, `W2`) from OCR.
- **VLM pass**: render a crop around each candidate and ask "door, window, or neither, and which wall side". VLMs are good at this classification (about 90% on clean crops in my estimate) and poor at measuring, so take the type from the VLM and the position and width from CV.

Heights are defaults unless the schedule says otherwise: door 2.1 m head, window sill 0.9 m, head 2.1 m. Modelling: cut a box from the wall (window: sill and head leave solid wall below and above), then add a frame and glass panes as separate meshes so they can carry materials.

### 5. Floors, rooms, ceilings

Rooms are the enclosed regions of the plan not covered by walls: compute with Shapely `polygonize` on the wall boundary lines, or flood-fill the free space after closing door gaps with a temporary bar. Assign labels by point-in-polygon of OCR text. Floor: one slab per room (so each can have its own material) or one slab for the footprint (minimal). Ceiling is optional and should be hidden in the top-down view.

### 6. Materials and lighting

- Material table keyed on room label (kitchen/bath: tile; bedroom/living: wood; others: concrete), applied by the build step. In GLB use PBR (base colour, roughness); in Blender add real shaders.
- **Interactive viewer**: three.js `HemisphereLight` + one shadow-casting `DirectionalLight`, `PCFSoftShadowMap`, ACES tone mapping, sRGB output, `OrbitControls`, and a clipping plane or ceiling toggle for cutaway views.
- **Photoreal**: Blender, Sun lamp plus Sky texture, area lights at windows, Cycles with denoising (CPU Cycles at 64-128 samples and 1280x720 is feasible but slow, minutes per frame; EEVEE needs a GPU or software GL and is less reliable in a container). Confidence that Blender renders in this container without extra setup: low (about 30%); expect to install it and test with a trivial scene first.

### 7. Outputs

| File | What it is |
|---|---|
| `plan.json` | The IR; the source of truth, editable |
| `overlay.png` | Extracted walls/openings/rooms drawn over the original plan, for verification |
| `house.glb` | The 3D model (opens in three.js, Blender, Windows 3D Viewer, macOS Quick Look via USDZ conversion if needed) |
| `index.html` | three.js viewer with orbit, ceiling toggle and room labels |
| `top.png`, `iso.png`, `eye_*.png` | Top-down, isometric cutaway, and eye-level renders |
| `walkthrough.mp4` | Optional camera path (Blender or Playwright frame capture + ffmpeg) |
| `report.md` | Scale source and confidence, items in `needs_review`, measured vs drawn dimension deltas |

## Minimal first version (built and tested)

Smallest thing that works end to end: a plan image in, a watertight GLB with walls and a floor slab out, scale from one number. No OCR, no Blender, no openings beyond what the wall mask already contains (a door drawn as a gap in the wall becomes a gap in the 3D wall, so doors work if the drawing leaves a gap).

Setup:

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install opencv-python-headless numpy shapely trimesh mapbox_earcut scipy
```

`scipy` is mandatory: `trimesh` fails at GLB export with a coloured mesh without it (this failed in testing before scipy was added).

`plan2glb.py`:

```python
#!/usr/bin/env python3
"""v0: plan image -> GLB. Usage: plan2glb.py plan.png --px-per-m 50 [--height 2.7] [--min-wall-m 0.08] [-o house.glb]"""
import argparse, cv2, numpy as np, trimesh
from shapely.geometry import Polygon
from shapely.ops import unary_union

def extract_wall_polys(path, px_per_m, min_wall_m):
    img = cv2.imread(path, cv2.IMREAD_GRAYSCALE)
    if img is None: raise SystemExit(f"cannot read {path}")
    _, bw = cv2.threshold(img, 0, 255, cv2.THRESH_BINARY_INV + cv2.THRESH_OTSU)
    k = max(3, int(round(min_wall_m * px_per_m)))
    walls = cv2.morphologyEx(bw, cv2.MORPH_OPEN, cv2.getStructuringElement(cv2.MORPH_RECT, (k, k)))
    cnts, hier = cv2.findContours(walls, cv2.RETR_CCOMP, cv2.CHAIN_APPROX_SIMPLE)
    if hier is None: raise SystemExit("no walls found")
    hier = hier[0]; H = img.shape[0]
    def to_m(c):
        c = cv2.approxPolyDP(c, 1.5, True)[:, 0, :].astype(float)
        return [(x / px_per_m, (H - y) / px_per_m) for x, y in c]
    polys = []
    for i, c in enumerate(cnts):
        if hier[i][3] != -1 or len(c) < 3: continue          # outer contours only
        holes = [to_m(cnts[j]) for j in range(len(cnts)) if hier[j][3] == i and len(cnts[j]) >= 3]
        p = Polygon(to_m(c), holes).buffer(0)
        if p.area > 0.05: polys.append(p)
    return unary_union(polys)

def build(walls, height, slab=0.15):
    meshes = []
    geoms = list(walls.geoms) if hasattr(walls, "geoms") else [walls]
    for g in geoms:
        m = trimesh.creation.extrude_polygon(g, height); m.visual.face_colors = [225, 225, 220, 255]; meshes.append(m)
    env = unary_union([Polygon(g.exterior) for g in geoms])
    envs = list(env.geoms) if hasattr(env, "geoms") else [env]
    for e in envs:
        f = trimesh.creation.extrude_polygon(e, slab); f.apply_translation([0, 0, -slab]); f.visual.face_colors = [150, 130, 110, 255]; meshes.append(f)
    return trimesh.Scene(meshes)

if __name__ == "__main__":
    a = argparse.ArgumentParser(); a.add_argument("plan"); a.add_argument("--px-per-m", type=float, required=True)
    a.add_argument("--height", type=float, default=2.7); a.add_argument("--min-wall-m", type=float, default=0.08)
    a.add_argument("-o", default="house.glb"); a = a.parse_args()
    w = extract_wall_polys(a.plan, a.px_per_m, a.min_wall_m)
    sc = build(w, a.height); sc.export(a.o)
    print(f"wall area {w.area:.2f} m2, bounds {[round(v,2) for v in w.bounds]}, wrote {a.o}")
```

Run it:

```bash
python plan2glb.py plan.png --px-per-m 50 -o house.glb
```

### What was tested

A synthetic plan (`mkplan.py`) with an 8 x 6 m footprint, 0.2 m walls, one interior partition with a 1.2 m door gap, a text label and a thin dimension line (the last two must be ignored):

```python
import cv2, numpy as np
s=50  # px/m ; 8m x 6m house, 0.2 m walls (10px)
img=np.full((400,500,3),255,np.uint8)
cv2.rectangle(img,(50,50),(450,350),(0,0,0),10)            # outer
cv2.line(img,(250,50),(250,350),(0,0,0),10)                # partition
cv2.rectangle(img,(240,150),(260,210),(255,255,255),-1)    # door gap in partition (1.2m)
cv2.putText(img,"Living 4.0 x 6.0",(70,120),cv2.FONT_HERSHEY_SIMPLEX,0.6,(0,0,0),1)  # text must be dropped
cv2.line(img,(50,30),(450,30),(0,0,0),1)                   # dimension line must be dropped
cv2.imwrite("plan.png",img)
```

Result of running it in this container (Python 3.13, OpenCV 5.1, Shapely 2.2, trimesh 5.2):

- Wall area reported: **6.50 m2**. Hand calculation: outer ring 8.2x6.2 minus 7.8x5.8 = 5.60; partition 0.2x5.8 = 1.16 minus the 0.24 door gap = 0.92; total 6.52 m2. Difference 0.3%, from `approxPolyDP` rounding.
- Bounds in metres matched the drawing (8.2 x 6.2 m plus the slab 0.15 m below zero, walls to 2.7 m).
- Both meshes (walls, floor slab) are watertight.
- Text and the dimension line were removed by the morphological opening, as designed.

Not tested: real scanned plans, PDF input, rendering in Chromium, Blender. Treat the first run on a real plan as the next experiment, not a given.

### Acceptance test for each real plan (do this before trusting a model)

1. `overlay.png`: walls drawn in red over the original; visually no missing or phantom walls.
2. Pick 3 dimensions printed on the plan; measured value in the GLB (`trimesh` `bounds` or ray cast) within 2% each.
3. Each room polygon is closed (no leakage through the wall mask) and its area is within 3% of any printed area.
4. Mesh watertight, no zero-area faces.

## Extension path (each step keeps the previous one working)

1. **Viewer.** Static `index.html` loading `house.glb` with three.js (`GLTFLoader`, `OrbitControls`), screenshot with Playwright to `top.png` and `iso.png`. In the container Chromium has no GPU: launch with `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`. Confidence it works: about 80%; if WebGL context creation fails, that flag set is the first thing to adjust.
2. **Scale from OCR.** Add Tesseract (`apt-get install tesseract-ocr`) and dimension parsing; fall back to the CLI flag when the spread check fails.
3. **Centre-line IR.** Skeleton, snap, merge, `plan.json`; rebuild from the IR instead of from the mask. Add `overlay.png`.
4. **Explicit openings.** Door/window detection + VLM classification; cut with sill and head heights; frames and glass.
5. **Rooms and materials.** `polygonize`, label assignment, per-room floors.
6. **Blender renders.** Run `blender -b -P render.py -- house.glb`: import GLB, add sun/area lights, Cycles denoised, render top/iso/eye-level PNGs. If a live Blender is available through MCP, use it for interactive tweaking, but keep the headless script as the reproducible path.
7. **Video and pretty images.** Camera path to MP4; optionally feed a clay render to an image generator for style variants, clearly labelled as illustrations.
8. **IFC/DXF export.** Only if the user needs CAD/BIM hand-off.

## Risks and failure cases

| Risk | Symptom | Mitigation |
|---|---|---|
| Wrong scale | Model looks fine but all dimensions off by one factor | Scale has a source and confidence; multi-dimension cross-check; user override flag |
| Hatched or double-line walls | Walls vanish after opening, or become fragmented | Fill/close step (approach C); lower kernel size; vector input |
| Text, furniture, stairs, hatching mistaken for walls | Phantom thin walls or blobs | Opening kernel; area and aspect filters; review overlay |
| Door arcs and glyphs merge into walls | Missing or filled doorways | Detect arcs before masking and subtract them; VLM crop check |
| Gaps in wall outline (scan breaks) | Room polygons leak, wrong floors | Close gaps smaller than a wall thickness; check polygon count |
| Non-orthogonal or curved walls | Snap distorts angles | Make snapping optional; support arcs later |
| Drawing not to scale | Dimensions contradict each other | Spread check flags it; trust printed numbers over pixels |
| Multi-storey sheets or several plans on a page | Several buildings merged | Segment by connected components; process each region separately |
| Imperial units | `13'-6"` parsed wrong | Unit tests for the parser, magnitude plausibility check |
| AI image generator used for geometry | Hallucinated rooms/walls that do not match the plan | Do not use it for geometry; use it only on top of a clay render |
| No GPU in the container | Slow or failing renders | CPU Cycles, low samples, or render on the user's machine |
| Tool availability | Blender/Tesseract absent here | Minimal version avoids them; install as steps 2 and 6 |
| Privacy: plans can show a person's home | Leaks via external APIs | Keep CV local; send crops only to a VLM the user has approved |

## Decision summary

- Extract to JSON, build from JSON. High confidence.
- Start with thick-stroke morphology and one scale number: ships in an hour, verified above. Expect to need hatched-wall handling on real plans (about 40 to 60% of professional plans use some hatching or double lines, my estimate).
- Add OCR and VLM for scale and opening classification; keep CV for measurement.
- three.js for sharing and quick checks, Blender for photoreal output; AI image generators only decorate.
