# Turning a 2D floor plan into a 3D model: build plan

## 1. The finished result (what you get on day 1 of v1)

Run one command:

```
python fp23d.py plans/house.pdf --page 1 --known "Living room width=14'-6\"" --out out/house
```

and out/house/ contains:

| File | What it is |
|---|---|
| `plan.json` | The single source of truth: scale, walls, openings, rooms (schema in section 5) |
| `overlay.png` | Original plan with detected walls (red), doors (green), windows (blue), room labels. This is the human check step. |
| `house.glb` | Walls, floors, door and window cut-outs, ceilings. Opens in any viewer. |
| `house.blend` | Same model, materials and lights set up, editable in Blender |
| `top.png` | 1920x1080 top-down orthographic render (the "3D floor plan") |
| `iso_cutaway.png` | Isometric render with the roof and near walls removed |
| `room_<name>.png` | One eye-level (1.6 m) render per room |
| `viewer/index.html` | three.js viewer that loads `house.glb`, with orbit controls and a wall-hide toggle |
| `report.json` | Scale source, scale error, per-room area vs labelled area, warnings |

Everything else below works backwards from that: each file needs the step before it.

## 2. Open questions, and how I resolve them

1. **Is the input vector or raster?** Unknown. Resolution: support both, and detect which. A vector PDF (CAD export) has exact line geometry; `PyMuPDF` `page.get_drawings()` returns it directly and skips computer vision entirely. Check first: if `get_drawings()` returns more than 200 paths, take the vector route. Otherwise rasterise at 300 DPI.
2. **How is scale determined?** Priority order: (a) a user-supplied known dimension (`--known`), (b) OCR of dimension strings paired with their dimension lines, (c) a scale note such as `1/4" = 1'-0"` with the PDF page size, (d) refuse and ask. Never guess silently. Reason: scale is the one error that makes every other number wrong.
3. **Fully automatic, or human in the loop?** Human in the loop. Public floor plan datasets show wall segmentation at roughly 85-95% quality, which is not good enough for a model where one missing wall leaks a room. So the pipeline auto-detects, writes `overlay.png`, and the user fixes `plan.json` (or a tiny click-editor) before building. This is the biggest design decision.
4. **Which 3D engine?** Blender, headless, driven by `bpy`. It gives boolean cuts for openings, PBR materials, Cycles renders and `.glb`/`.blend` export from one script. three.js is the delivery viewer, not the builder.
5. **AI image generators?** Optional, only for a "make it pretty" pass. They hallucinate walls and furniture, so they are never used for geometry. They can be fed the Blender top-down clay render as a ControlNet depth/edge conditioning image if the user wants photoreal output.
6. **Units?** Internal metres. Input may be feet-inches. Parser handles `12'-6"`, `12' 6"`, `12.5'`, `3750`, `3.75m`.
7. **Multi-storey?** Out of scope for v1. One page = one storey. v2 stacks storeys by z offset.
8. **Furniture, stairs, curved walls?** Out of scope for v1; detected as warnings.

## 3. Assumptions

- The plan is a typical architectural plan: walls are thick dark lines or filled/hatched bands, doors are quarter-circle swings, windows are thin parallel lines inside a wall, dimensions are in text with a scale or a known dimension.
- One storey per file, orthogonal walls dominate (diagonals supported, curves not).
- Ceiling height 2.44 m (8 ft) unless stated. Exterior wall 0.20 m (8 in), interior 0.115 m (4.5 in) if thickness cannot be measured.
- Door 0.81 m x 2.03 m (32 in x 80 in). Window sill 0.91 m (36 in), head at 2.03 m (matches door head, so the window height is 1.12 m).
- Environment: Linux container, Python 3.11+, Node 20, Chromium/Playwright present, no GPU (Cycles CPU, 64-128 samples is fine; Eevee needs a GPU or software GL and is unreliable headless, so use Cycles).
- No internet-hosted model needed for v1.

## 4. Architecture

```
input (PDF/PNG/JPG)
  |
  v
[1 ingest] --vector?--> PyMuPDF get_drawings() ----------------+
  |raster                                                       |
  v                                                             v
[2 clean] deskew, binarise (OpenCV)          [3b vector geometry: lines -> wall candidates]
  |
  v
[3a raster geometry] morphology + Hough/skeleton, or CubiCasa5k model
  |
  +----------------------> [4 scale] OCR dimensions (Tesseract/PaddleOCR) or --known
                                  |
                                  v
                [5 openings] door arcs, window double lines, gaps
                                  |
                                  v
                [6 rooms] polygonize wall graph (shapely), OCR room labels
                                  |
                                  v
                       plan.json  +  overlay.png   <-- human review/edit
                                  |
              +-------------------+-------------------+
              v                                       v
   [7 build_blender.py] bpy headless          [8 viewer/ three.js]
   .blend  .glb  renders                      loads .glb
```

One rule: **everything after plan.json only reads plan.json.** That lets you hand-write a plan.json, skip CV completely, and still get a model. It is also what makes testing possible.

## 5. plan.json schema (exact)

```json
{
  "units": "m",
  "scale": {"source": "known", "px_per_m": 118.4, "error_pct": 0.8},
  "ceiling_height": 2.44,
  "walls": [
    {"id": "w1", "a": [0.0, 0.0], "b": [6.40, 0.0], "thickness": 0.20, "exterior": true}
  ],
  "openings": [
    {"id": "d1", "type": "door", "wall": "w3", "offset": 1.10, "width": 0.81,
     "height": 2.03, "sill": 0.0, "swing": "in-left"},
    {"id": "n1", "type": "window", "wall": "w1", "offset": 2.00, "width": 1.50,
     "height": 1.12, "sill": 0.91}
  ],
  "rooms": [
    {"id": "r1", "name": "Living", "polygon": [[0,0],[6.4,0],[6.4,4.2],[0,4.2]],
     "floor": "oak", "label_area_m2": 26.9}
  ]
}
```

Wall `a`/`b` are centrelines. Opening `offset` is distance along the wall from `a` to the opening's left edge. Coordinates have y up (flip image y once, at ingest, and nowhere else).

## 6. The pipeline step by step

### Step 1: Ingest
```
pip install pymupdf opencv-python-headless numpy shapely scikit-image pytesseract trimesh
sudo apt-get install -y tesseract-ocr
```
- PDF: `fitz.open(p)[page]`. If `len(page.get_drawings()) > 200` go vector. Else `page.get_pixmap(dpi=300)`.
- Images below 1500 px on the long side: warn and upscale 2x (Lanczos). Below 800 px: stop, the thin lines are gone.

### Step 2: Clean (raster only)
- Grayscale, `cv2.fastNlMeansDenoising(h=10)`.
- Deskew: `cv2.minAreaRect` on the largest connected component, or Hough dominant angle; rotate if abs angle is between 0.3 and 10 degrees.
- Binarise: `cv2.adaptiveThreshold(blockSize=35, C=10)`. Scans with uneven lighting fail on a global Otsu threshold.

### Step 3: Walls
Raster route, in order of preference:
1. **Filled-wall plans** (walls are solid black bands): remove thin lines by morphological opening with a kernel just under wall thickness (about 0.6 x measured thickness, usually 5-9 px at 300 DPI), leaving only thick strokes. Then `skimage.morphology.skeletonize`, then `cv2.HoughLinesP(threshold=60, minLineLength=40, maxLineGap=12)`. Merge collinear segments within 4 px and snap angles within 3 degrees to 0/90.
2. **Hatched or double-line walls**: find parallel line pairs 0.1-0.3 m apart (after scale), take the midline as centreline.
3. **Fallback learned model**: CubiCasa5K pretrained network (open weights, outputs wall, door, window, room-type masks). Run on CPU; a 1000 px plan takes a few seconds. Vectorise the wall mask with the same skeleton and Hough code.

Vector route: filter `get_drawings()` by stroke width and fill. Walls are usually the paths with a fill colour or the stroke width in the top 20%. Cluster, merge collinear, same snap.

Wall thickness is measured: median distance-transform value along the skeleton times 2. Exterior if the wall touches the outer hull of the polygonised footprint.

### Step 4: Scale
- Run `pytesseract.image_to_data(config="--psm 11")` and keep tokens matching `\d+['"]` patterns. Find the nearest dimension line (two short ticks + a long line) and compute pixels between ticks.
- Compute `px_per_m` from every dimension; take the median; report `error_pct` as median absolute deviation divided by the median. If this is above 3%, stop and ask for `--known`.
- `--known "Living room width=14'-6\""`: the user picks the room, the pipeline measures that room's inner width in px.
- Sanity: an interior door leaf must come out 0.7-1.0 m wide, and a room 1.5-10 m. Otherwise the scale is off by a likely factor (2.54, 12, 10); flag it.

### Step 5: Openings
- **Doors**: quarter circles. `cv2.HoughCircles` is unreliable here; instead find arcs by looking for a straight line (the leaf) of length L with a curve of radius L starting at its end, adjacent to a wall gap. Door width = L. Easier and more robust: find gaps in the wall mask where wall length is interrupted by 0.7-1.2 m, then confirm with arc evidence.
- **Windows**: segments inside a wall where the wall's fill is replaced by 2-3 thin parallel lines. Width = run length.
- **Wide openings** (no arc, gap above 1.2 m): classify as `opening`, no door leaf.
- Output each as `{wall, offset, width}` by projecting onto the wall centreline.

### Step 6: Rooms
`shapely.ops.polygonize` over wall centreline linework (after `unary_union` and a 5 cm snap). Each resulting polygon is a room. OCR text inside it gives the name. If area differs more than 8% from a printed `NNN SF`/`m²` label, add a warning to `report.json` (this catches missed walls, since a missed wall merges two rooms into one big area).

### Step 7: Human check
`overlay.png` is generated with room names and wall IDs. Fix mistakes in `plan.json` by hand. A 150-line `editor.html` (canvas, click-drag wall endpoints, click wall to add door/window) is a v2 upgrade.

### Step 8: Blender build (`build_blender.py`)
Run: `blender -b -P build_blender.py -- out/house/plan.json out/house`. Install via `pip install bpy` (Python 3.11 wheel) or `apt-get install blender`; if apt gives an old Blender, confirm `bpy.app.version >= (3, 6)`.

For each wall:
1. Create a box: length = |b-a| + thickness (so corners overlap, no gaps), width = thickness, height = ceiling height. Rotate to wall angle, place at midpoint.
2. For each opening on it, create a cutter box (width x thickness*1.5 x height, at sill) and apply a Boolean modifier (`EXACT` solver, `DIFFERENCE`), then apply the modifier.
3. Add a frame: door frame is a 0.05 m reveal; window gets a glass plane (material: Principled, transmission 1.0, IOR 1.45, roughness 0.02) set 0.01 m inside the wall.
4. Join all walls with one Boolean `UNION` into one mesh per storey to avoid z-fighting at T-junctions. Fallback if EXACT is slow (above about 150 walls): skip the union, accept overlap.

Floor: for each room polygon, `bmesh` fill, extrude down 0.1 m. Ceiling: same polygon at `ceiling_height`, normals down, hidden in the cutaway render via a collection exclude.

Materials (Principled BSDF, all procedural so no texture files are required):
- Wall: base colour (0.92, 0.91, 0.88), roughness 0.8.
- Floors by `room.floor`: `oak` uses Wave Texture + Noise for grain, `tile` uses Brick Texture at 0.6 m (scale it by metres, not UV units), `carpet` is a flat grey-blue with roughness 1.0.

UVs: use Box Projection mapping set in object coordinates so scale is physical.

Lighting:
- Sun (strength 3.0, angle 5 degrees, rotation from NW at 45 degrees elevation) + Nishita sky world (strength 0.8). This works with no HDRI download.
- For each room, an invisible area light (1.0 x 1.0 m, 150 W) at ceiling height minus 0.05 m for interior shots.

Renders (Cycles CPU, 96 samples, OIDN denoise, 1920x1080, PNG):
- `top.png`: orthographic camera at z = 12 m looking down, `ortho_scale` = max(plan bbox) x 1.1, ceiling collection excluded.
- `iso_cutaway.png`: orthographic, rotation (60, 0, 45) degrees, ceiling and any wall whose outward normal faces the camera and is taller than 1.2 m is set to 1.2 m tall (cut-away look).
- `room_<name>.png`: perspective 24 mm lens, camera at room centroid, z = 1.6 m, aimed at the room's furthest corner.

Export: `bpy.ops.export_scene.gltf(filepath="house.glb", export_format="GLB", export_apply=True)` and `bpy.ops.wm.save_as_mainfile(filepath="house.blend")`.

Time budget on a 4-core CPU container: model build about 5 s, each render 30-90 s.

### Step 9: Web viewer
`viewer/index.html` with three.js `r160` (import map from `cdn.jsdelivr.net/npm/three@0.160.0`), `GLTFLoader`, `OrbitControls`. Add one toggle that sets `ceiling.visible = false`. You can screenshot it in headless Chromium via Playwright to test the glb: `page.goto("file:///.../viewer/index.html"); page.screenshot(path="viewer.png")`.

## 7. Getting accuracy (the checks that matter)

1. **Scale cross-check**: two independent dimensions must agree within 3%.
2. **Room area check**: model area vs printed area within 8%, warn above 3%.
3. **Closed shell check**: wall graph must produce a bounded exterior polygon with `polygonize`; dangling ends longer than 0.3 m are warned.
4. **Opening check**: each opening is wholly inside its wall (offset >= 0.1 m from either end) and not overlapping others.
5. **Round trip test**: render `plan.json` back to a 2D PNG and compute IoU against the input wall mask. Target IoU above 0.85 on clean plans.
6. **Synthetic test set**: write 10 plan.json files (L-shape, T-junction, diagonal wall, no windows, wide opening), rasterise them at 150/300 DPI with Pillow, add noise and 2 degree skew, and run the pipeline. Assert wall count, room count and area within 5%. This is 1 day of work and it catches most regressions.

## 8. Risks and failure cases

| Failure | Symptom | Mitigation |
|---|---|---|
| Wrong scale | Door 2 m wide, rooms tiny or huge | Sanity ranges; require two agreeing dimensions or `--known` |
| Text/dimension lines over walls | Fake walls from text strokes | Remove OCR bounding boxes from the mask before skeletonising |
| Hatched or poché walls | Wall mask splits into stripes | Close with kernel the size of hatch gap; or vector route |
| Photo of paper plan, perspective | Walls not parallel | Four-point homography (`cv2.getPerspectiveTransform`) with user clicks on page corners |
| Furniture and fixtures drawn | Fake short walls | Drop segments shorter than 0.5 m not touching another wall |
| Curved walls, circular rooms | Polygon approximation | v1 not supported; approximate with 15 degree segments if flagged |
| Open-plan, no wall between rooms | Rooms merge | Add manual virtual divider in `plan.json` with `"virtual": true` |
| Boolean fails on tiny gaps | Missing or spiky openings | Round all coordinates to 1 mm; cutter 1 cm oversize on each side in depth |
| Headless Blender crash (GPU) | `GPU` errors | Always `-b`, Cycles, `device = 'CPU'` |
| Multiple plans on one sheet | Wrong plan processed | User gives a crop box `--crop x,y,w,h` |
| Stairs / multiple levels | Missing | v2: stairs as extruded steps from a hatched rectangle with arrow |
| AI-generated geometry hallucination | Extra rooms, wrong walls | Never use image generators for geometry; only for style on top of a clay render |
| Copyright or privacy of plans | Uploading client plans | Everything runs locally; no external APIs in v1 |

## 9. Minimal first version (build this first, about 1 day)

Goal: from a clean image, get a correct GLB and a top render, with the human fixing what the code gets wrong.

1. `fp23d.py` accepts a PNG or PDF page and `--known`.
2. Raster only: grayscale, adaptive threshold, morphological opening to keep thick strokes, `skeletonize`, `HoughLinesP`, snap to axes, merge. Writes `plan.json` with walls only (no openings yet).
3. Scale from `--known` only (no OCR).
4. Writes `overlay.png` so the user can see and edit `plan.json`.
5. `build_blender.py` extrudes walls, adds a floor from the bounding polygon, one sun light, a top render and a `.glb`.
6. Doors and windows: the user adds them as entries in `plan.json` (offset, width). Detection comes in v2.

Then, in this order: (v1.1) door/window detection from gaps; (v1.2) OCR dimensions for automatic scale; (v1.3) rooms + names + materials; (v1.4) iso cutaway and room renders; (v2) vector PDF route, CubiCasa5K fallback, click editor, multi-storey, stairs.

Acceptance test for v1: a 3-room synthetic plan produces a GLB whose bounding box is within 2% of the true size, with the right wall count, in under 60 s.

## 10. Decision summary

- **Geometry source**: vector PDF if available, else OpenCV skeleton/Hough, with CubiCasa5K as fallback. Never an image generator.
- **Single source of truth**: `plan.json`, hand-editable.
- **Builder**: headless Blender (`bpy`, Boolean cuts, Cycles on CPU).
- **Delivery**: `.glb` + `.blend` + PNG renders + three.js viewer.
- **Quality control**: scale cross-check, room area vs label, closed-shell check, human-reviewed overlay.
