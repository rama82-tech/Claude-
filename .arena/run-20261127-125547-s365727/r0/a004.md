# Build plan: 2D floor plan to 3D model

## Recommendation in one paragraph

Do not go straight from the image to 3D. Go image -> **plan.json** (a small, validated, human-checkable description of walls, openings, rooms and scale) -> 3D. Everything upstream of plan.json (PDF handling, computer vision, OCR, optionally a vision LLM) is untrusted and gets checked. Everything downstream (Blender build, glTF export, renders, a three.js viewer) is deterministic code that only reads plan.json. Generative image models are used only for an optional "pretty preview", never as the source of geometry, because they invent walls and furniture and cannot hold dimensions.

This design fails loudly: if the scale cannot be proven, the walls do not close, or a door has no wall, the pipeline stops and tells you what is wrong. It does not produce a plausible-looking but wrong house.

## Assumptions

1. Input is one floor (one storey) per file: a PNG/JPG scan or photo, or a PDF page. Multi-storey is a later extension (one plan.json per level).
2. The plan has at least one printed dimension, or a known door/scale bar, so real-world scale can be recovered. If not, the pipeline refuses to guess and asks you for one measured distance.
3. Walls are mostly orthogonal. Curved and diagonal walls are supported as a second phase, not v1.
4. Units: the input may be feet-inches or metric; internal storage is metres.
5. Wall height defaults to 2.7 m (configurable), door 2.1 m high, window sill 0.9 m, window head 2.1 m. These are assumptions to be overridden, not read from the drawing.
6. The Claude Code container has Python, Node, Chromium and Playwright. It may not have a GPU, so photoreal rendering is CPU Cycles or EEVEE; this is slow but works. Blender can be installed with pip (`bpy`) or the Linux tarball. This must be verified in step 0.
7. A human (you) reviews a 2D overlay before the 3D build. Fully unattended conversion of arbitrary plans is not reliable and the plan does not pretend otherwise.

## Architecture

```
input (PNG/JPG/PDF)
  -> 1 ingest + normalize (deskew, rasterize, hash)
  -> 2 scale calibration (OCR dimensions + user override)
  -> 3 wall extraction (CV, vector if PDF)
  -> 4 opening + room detection
  -> 5 plan.json  <-- the contract; schema-validated
  -> 6 validation gates + 2D overlay for human review
  -> 7 geometry build (Blender headless, bpy)
  -> 8 materials, lights, cameras
  -> 9 export + renders + web viewer + report
```

Three rules that hold the design together:

- **plan.json is the only interface.** You can hand-edit it, generate it from CV, or have a vision model propose it. The 3D stage does not care.
- **Every stage writes an artifact and a confidence.** A low-confidence item is flagged on the overlay, not silently kept.
- **Stop on failure.** Exit codes and a `report.md` listing every failed gate. No "best effort" 3D.

## Tool choices

| Job | Use | Why / caution |
|---|---|---|
| PDF | PyMuPDF (`fitz`) | Extract vector paths first (lines are real walls, text has exact coordinates). Only rasterize at 300 dpi if the PDF is a scanned image. |
| Raster cleanup | OpenCV, scikit-image | Deskew, threshold, morphology. |
| Wall/line extraction | OpenCV (Canny, Hough, `LSD`), skimage skeletonize, Shapely | Classical CV is predictable and debuggable; prefer it for v1. |
| Dimension text | Tesseract via `pytesseract`, or PaddleOCR / EasyOCR | Dimension strings (`12'-6"`, `3.45 m`, `4200`) need a custom parser plus a sanity check against measured pixels. OCR misreads (`6` vs `8`, `'` vs `"`) are the top scaling failure. |
| Optional semantic help | Claude vision (read the image, return JSON in the plan.json schema) | Good at labels ("Kitchen", "W.I.C."), door swing, rough topology. Poor at exact coordinates. Use it to propose, CV to measure, validators to decide. |
| Trained detectors (later) | Public floor-plan datasets (CubiCasa5k, R2V-style segmentation models) | Heavy; only if classical CV fails on your plan style. |
| Geometry | Shapely + `mapbox_earcut`/Blender boolean | Wall polygons, room polygons, openings as rectangles cut into walls. |
| 3D build | **Blender 4.x/5.x headless, Python `bpy`** | Deterministic scripts, good booleans, Cycles/EEVEE, glTF export. |
| Live driving (optional) | Blender MCP add-on | Handy for interactive tweaking, but needs a GUI Blender instance reachable from the session; a cloud container usually has none. Treat MCP as a convenience, not the architecture. The batch `blender -b -P build.py` path must work without it. |
| Web viewer | three.js with `GLTFLoader` | Loads the exported .glb; screenshot with Playwright for a no-Blender fallback render. |
| Fallback 3D (no Blender) | three.js `ExtrudeGeometry` + CSG (`three-bvh-csg`) built from plan.json, or Python `trimesh` + `manifold3d` to export .glb | Gives a working v1 even if Blender cannot be installed. |
| AI image generators | Optional last step: feed a clay render to image-to-image for a styled mood image, labelled "concept, not to scale" | Never use it to produce geometry or to "fix" the plan. |

## plan.json (the contract)

```json
{
  "schema": 1,
  "source": {"file": "plan.pdf", "sha256": "...", "page": 1},
  "units": "m",
  "scale": {"m_per_px": 0.0121, "method": "ocr_dimension|user|door_prior",
            "evidence": [{"label": "4200", "px": 347, "ok": true}], "confidence": 0.9},
  "levels": [{"id": "L0", "elevation": 0.0, "height": 2.7}],
  "walls": [{"id": "w1", "a": [0,0], "b": [4.2,0], "thickness": 0.2,
             "kind": "exterior|interior", "confidence": 0.95}],
  "openings": [{"id": "o1", "wall": "w1", "type": "door|window|arch",
                "offset": 1.1, "width": 0.9, "sill": 0.0, "head": 2.1,
                "swing": "left-in", "confidence": 0.8}],
  "rooms": [{"id": "r1", "label": "Kitchen", "polygon": [[...]], "floor": "tile"}],
  "flags": ["w14 low confidence", "dimension 3'-8\" disagrees with geometry by 9%"]
}
```

## Pipeline stages, with defensive gates

**0. Environment check (once).** Run `python -c "import cv2, fitz, shapely"`, `blender --version` (or `import bpy`), `tesseract --version`. If Blender is missing, say so and select the three.js/trimesh fallback path. Do not discover this halfway.

**1. Ingest.** Hash the file. If PDF: count vector paths; if many, use the vector route; otherwise rasterize at 300 dpi. If image: reject below roughly 1200 px on the long side, or warn. Deskew using the dominant Hough angle; reject if the skew exceeds about 10 degrees (probably a phone photo with perspective), and if it is a photo, require four corner clicks for a homography. Crop title block and legend (they create phantom walls).
*Gate:* a normalized image and a thumbnail are written; unreadable or password-protected files stop here.

**2. Scale.** Order of trust: (a) a user-supplied distance, (b) a printed scale bar, (c) OCR dimension strings measured against their dimension lines, (d) door-width prior (0.8-0.9 m) as a last resort, flagged "approximate". Fit scale from multiple dimensions, take the median, and reject outliers.
*Gate:* at least two independent dimensions agree within 3 percent. Otherwise stop with "scale ambiguous: here are the candidates, tell me one real distance". Never use a scale that was printed on the sheet without checking it, since scanned or resized plans make "1:100" false.

**3. Walls.** Binarize, then separate thick wall strokes from thin dimension/furniture lines using stroke width (distance transform) and fill (solid hatch). Skeletonize, fit lines, snap to a grid of dominant angles, merge collinear segments, close small gaps (door gaps are not wall gaps; see stage 4). Estimate thickness per wall from the distance transform; round to plausible values (0.1-0.4 m).
*Gate:* every wall endpoint must meet another wall within tolerance (or be a free end by design); wall lengths below 0.15 m are removed and logged.

**4. Openings and rooms.** Doors: a gap in a wall plus an arc (swing) found by Hough circles/arc fitting; windows: thin parallel lines or a thinner break in the wall. Each opening is attached to the nearest wall and given an offset along it; width comes from the gap measurement, not a default. Rooms: polygonize the closed wall network (Shapely `polygonize`); match OCR text labels by point-in-polygon.
*Gate:* each opening lies fully inside one wall's length; each room has an area between 1 and 150 m2; unlabeled rooms are flagged, not guessed. If the exterior is not a closed ring, stop (the floor slab and roof would be wrong).

**5. Write plan.json.** Validate against a JSON Schema. Fill every confidence value.

**6. Validation and review.** Automated checks: closed exterior, no overlapping walls, openings fit, printed dimensions versus measured (flag more than 5 percent disagreement), total area versus any printed area. Then draw an **overlay PNG**: detected walls in red, openings in blue/green, room labels, flags in yellow, scale ruler drawn on the original. Review this before any 3D is built; edit plan.json where wrong and rerun from stage 6 (stages 1-5 are cached by file hash).
*Gate:* any error-level check blocks the build; warnings go into the report.

**7. Geometry build (Blender, headless).**
- Walls: one wall at a time as an extruded box from `a` to `b` with thickness and level height. Join corners by extending to the intersection (or union via boolean), so corners are not notched.
- Openings: a cutter box slightly larger than the opening, boolean-subtracted from the wall (exact solver). Add a door leaf or frame and a window frame plus glass pane as separate named objects.
- Floors: one mesh per room from its polygon, thickness 0.1 m; a ceiling or roof optional (off for top-down views).
- Name everything (`Wall_w1`, `Door_o1`, `Floor_Kitchen`) so edits and exports are traceable.
*Gate:* after the build, assert the bounding box matches the plan within 1 cm and check mesh manifoldness; failures list the object names.

**8. Materials and lighting.**
- Materials: a small library keyed by a plan.json tag (`wall_plaster`, `floor_wood`, `floor_tile`, `glass`). Use Principled BSDF and procedural textures (no external image dependency). Default per room type from its label (bathroom to tile), always overridable. Unknown labels get a neutral material and a flag.
- Lighting: a sun plus sky (Nishita) for daylight through windows; area lights or emissive panels inside rooms; for clean "clay" renders, a white world and ambient occlusion. Window openings need real glass or open holes to let light in; check the render is not black (see risks).
- Cameras: top-down orthographic (the "3D floor plan"), isometric cutaway (hide the roof and the walls facing the camera, or clip with a boolean box), and an eye-level camera at 1.6 m in each room's centroid, aimed along its longest axis.
- Render: EEVEE for speed, Cycles (denoise, 64-128 samples) for finals. Cap sample and time budgets for CPU.

**9. Export and report.**
Write the outputs below plus `report.md` with scale evidence, flags, the stage-by-stage status and anything that was assumed.

## Accuracy: how the numbers stay honest

- Geometry comes from measurement (CV on pixels times a proven scale), never from an AI model's guess.
- Printed dimensions are treated as evidence, not truth: they are compared against the pixel-measured length and flagged on disagreement (plans are often "not to scale").
- Snap angles and wall thickness only within tolerance, so a real 4.37 m wall is not forced into 4.0 m.
- Idempotent builds: same plan.json gives the same model. Regression test with 3-5 sample plans and their expected room areas.

## Risk and failure table

| Risk / failure | What happens | Defence |
|---|---|---|
| Wrong scale (OCR misread, plan "not to scale", resized scan) | Whole house wrong by a constant factor, looks fine | Two-dimension agreement gate; show the ruler overlay; refuse single-source scale |
| Furniture, hatch, text, dimension lines read as walls | Phantom walls | Stroke-width classification; crop title block; human overlay review |
| Walls drawn as double lines vs. solid fill vs. hatch | Thickness wrong or missed | Handle both via a fill-ratio test; thickness sanity range |
| Gaps in wall lines break closure | Rooms fail to polygonize | Gap closing under a threshold; fail loud when the exterior is not closed |
| Door/window symbols vary (arcs, sliding, bifold) | Missed or misplaced openings | Gap-based detection first, swing arcs as secondary; unknown opening shown as flagged generic opening |
| Photographed plan with perspective | Skewed geometry | Detect it, require corner points for a homography, or reject |
| Low-resolution or JPEG-artifact scans | Broken lines | Minimum resolution check; upscale only for display, never to invent data |
| Handwritten or non-Latin dimensions | OCR fails | Fall back to the user's known distance; do not guess |
| Boolean failures (coplanar faces, thin slivers) | Holes or broken meshes | Overscale cutter slightly, merge by distance, manifold check, name the failing object |
| Black or dim renders | Glassless openings, no sun, wrong normals | Light sanity check (mean luminance of the render) and automatic fallback to the clay world light |
| Headless Blender not installable in the container | Build step cannot run | Step-0 check and the trimesh/three.js fallback |
| Cloud CPU render is slow | Timeouts | EEVEE default, low-sample previews, background run with a hard timeout |
| AI-generated image looks right but is wrong | User trusts invented rooms | Label as concept; never feed it back into plan.json |
| Vision LLM hallucinated coordinates | Wrong plan | Treated as a proposal; CV measure + validator decide |
| Privacy of the plan (a real home) | Leak | Process locally; do not upload to third-party services without consent |
| Multi-storey, stairs, curved walls, slanted ceilings | Out of scope | Detected as unsupported where possible; v1 states the limit in the report |

## Minimal first version (build this in a weekend)

Goal: one rectilinear one-storey plan to a correct, viewable .glb and one top-down render, with a hand-assisted scale.

1. **Skip CV at first.** Hand-write `plan.json` for one sample plan (10-20 walls) from your drawing, with the `scale` taken from one known measured length. This isolates and proves the 3D half.
2. `build.py` (runs under `blender -b -P build.py -- plan.json out/`): walls, boolean openings, floors, a basic material, a sun, an orthographic top-down camera, a `.glb` export, and a PNG render. Add the bounding-box assertion.
3. `viewer/index.html` with three.js `GLTFLoader` and `OrbitControls`; take a Playwright screenshot for a check.
4. Add `validate.py` (JSON Schema plus closed-ring, openings-fit and area checks) and run it before the build.
5. Then add automation in order of payoff: (a) PDF vector extraction via PyMuPDF, (b) OCR dimension scale with the two-dimension gate, (c) wall detection with the overlay, (d) door and window detection, (e) the isometric and eye-level cameras, (f) optional Claude vision to propose labels and openings.

Success test for v1: the exported model's room areas match the plan's printed areas within 3 percent, the .glb opens in the viewer, and a deliberately broken plan.json (a gap in the exterior wall) makes the pipeline stop with a clear message rather than produce a model.

## Decision summary

- Blender `bpy` (batch) for the build; three.js for viewing; MCP only as an optional live-edit convenience.
- Classical CV + OCR to measure; a vision model to suggest; a validator and a human overlay to decide.
- Generative AI for mood images only.
- Intermediate plan.json with confidence values and hard gates, so bad input yields a clear error, not a convincing wrong house.
