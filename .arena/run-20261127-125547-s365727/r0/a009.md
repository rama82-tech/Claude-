# Build plan: 2D floor plan to 3D model

## Recommendation in one paragraph

Split the job into two halves joined by one small JSON file (the "plan spec"). The first half turns the image into the spec: walls, doors, windows, rooms and a scale. The second half turns the spec into geometry and renders. Everything that can go wrong with accuracy is then visible and editable in one text file, instead of being buried in a pixel-to-mesh black box. Build the second half first (it is deterministic and quick), feed it a hand-made spec, and only then automate the first half.

## Assumptions

- Input is a clean architectural plan (image, scan or PDF page) with at least one printed dimension or a known door width. Hand sketches and photos of plans are out of scope for v0.
- One storey, straight walls, standard 2.4 to 2.7 m ceilings. Curved walls, stairs, roofs and multi-storey come later.
- The container has Python 3 and Node, Chromium and Playwright (given in the task). I assume `pip install` works through the proxy. Blender is not stated as installed, so I treat it as optional. Verify with `python -c "import bpy"` or `pip download bpy` before relying on it.
- Software GL in headless Chromium usually works but is slow. Check this on your first render rather than trusting it.
- "Accurate" means every wall within about 2 percent of the printed dimensions, not survey grade.

## Three approaches considered, one chosen

1. **AI image generator straight from the plan.** Fastest to a pretty picture. Rejected as the core: generators invent or drop walls and rooms, produce no measurable geometry and no exportable model. Use only as an optional pretty-render step later, with the result checked against the plan.
2. **Pure browser: three.js extruding traced polylines.** Good viewer, but plan tracing, boolean cuts for openings and print-quality renders are all awkward there.
3. **Python spec-driven pipeline, with a swappable builder (chosen).** Image to JSON spec, then JSON to mesh with a quick builder (trimesh/shapely to GLB, viewed in three.js) and later a richer builder (Blender `bpy`). Fastest to something usable, and the accuracy-critical part stays inspectable.

## Architecture

```
plan.png/pdf
   |
[1 Prepare]    PDF -> PNG (pdf2image/pymupdf), deskew, binarise      (OpenCV)
[2 Scale]      pixels-per-metre from one known dimension             (user or OCR)
[3 Extract]    walls, openings, rooms, labels -> plan.json           (see options)
[4 Verify]     draw plan.json over the original, human OKs it        (OpenCV overlay PNG)
[5 Build]      plan.json -> 3D                                       (builder A or B)
[6 Export]     plan.glb, plan.blend (builder B), renders, plan.json
```

### The plan spec (the contract between the halves)

```json
{
  "units": "m", "wall_height": 2.6, "wall_thickness": 0.15,
  "walls":   [ {"id":"w1","a":[0,0],"b":[5,0],"t":0.2} ],
  "doors":   [ {"wall":"w1","at":1.2,"width":0.9,"height":2.05,"swing":"in"} ],
  "windows": [ {"wall":"w1","at":3.0,"width":1.2,"height":1.2,"sill":0.9} ],
  "rooms":   [ {"name":"Kitchen","polygon":[[0,0],[5,0],[5,4],[0,4]],"floor":"wood"} ]
}
```

Walls are centreline segments with a thickness. Openings are attached to a wall by offset along it, which makes them hard to misplace. Rooms are polygons, which gives floors and labels. Coordinates are metres, origin at the plan's top-left, y flipped on build.

## Step-by-step pipeline

### Steps 1 and 2: prepare and scale (the step most people skip)

- PDF to PNG at 200 to 300 dpi with `pymupdf`. Vector PDFs are the best case: you can read line segments directly from the page drawing instructions and skip image processing entirely. Try this first for any PDF.
- Scale options, in order of reliability:
  1. User supplies one length ("this wall is 5.20 m") by clicking two points or giving pixel coordinates.
  2. Read a printed dimension string with OCR (`pytesseract`, or ask Claude to read the image) and pair it with the nearest dimension line.
  3. Scale bar, or a standard door width (about 0.9 m) as a last-resort sanity check, not a primary source.
- Always compute scale from the longest known dimension, then check a second dimension. If the two disagree by more than 3 percent, stop and report it. This is the single most common silent error, because plans are often not drawn to scale even when labelled.

### Step 3: extract walls, openings and rooms

Three options, ranked by speed to first result:

| Option | How | Speed | Accuracy |
|---|---|---|---|
| A. Vision-assisted | Claude looks at the image and writes `plan.json`, then you fix it | Fastest, today | Good on simple plans, needs step 4 |
| B. Classical CV | Threshold, find thick dark lines (morphological open with a long kernel), `cv2.HoughLinesP` or `cv2.findContours`, snap to horizontal and vertical, merge collinear pieces, take thickness from the line width | Hours | Good on clean CAD-style plans, poor on hatching and text |
| C. Trained model | Public floor-plan segmentation datasets and models exist (for example CubiCasa5k-based work). I have not checked licences or current quality, so treat this as a lead to evaluate, not a dependency | Days | Best on in-distribution plans |

Use A for v0. Add B only if you will run many plans. Skip C until you have a plan type that A and B both fail on.

Openings: doors are gaps in a wall line, usually with an arc symbol. Windows are thin double lines inside a wall. Detect them as gaps or breaks, then record offset and width relative to the host wall. Remove text first (OCR bounding boxes painted white) so letters are not mistaken for walls.

### Step 4: verify before building

Draw `plan.json` over the original in a semi-transparent colour (walls red, doors green, windows blue) and save as `overlay.png`. Look at it. Fix the JSON by hand if something is off. This one picture catches most failures and costs minutes.

### Step 5: build

**Builder A (v0, no Blender needed)**

- `shapely`: buffer each centreline by half its thickness, union all into one wall footprint polygon.
- Cut openings: subtract a rectangle per door and window across the wall thickness from the footprint for the full width, then extrude the remainder to wall height. Add a header slab above doors and a sill block plus a lintel above windows by extruding the leftover vertical bands separately. This avoids 3D boolean operations, which are the most fragile part of the stack.
- Floors: extrude each room polygon 0.1 m down, with `trimesh.creation.extrude_polygon`. Triangulation needs `mapbox-earcut` or `triangle`.
- Materials: flat PBR colours per element (walls off-white, floor by room type, glass transparent). Name each mesh (`wall_w1`, `door_d1`) so they are selectable in any viewer.
- Export `plan.glb` with `trimesh.Scene.export`.

**Builder B (v1, polish, optional)**

- Blender in the background: `blender --background --python build.py -- plan.json`, or the pip `bpy` module if it installs. Same logic, but use real boolean modifiers or door and window frames, image textures for floors, and area lights.
- If you are running Blender on your own machine with the Blender MCP add-on, the same `build.py` can be sent live, which gives an interactive edit loop. This is a convenience, not a requirement.
- Render with Cycles on CPU. Do not assume EEVEE works in a container without a GPU.

### Step 6: outputs

| File | Made by | Use |
|---|---|---|
| `plan.json` | step 3 | The source of truth. Edit this, rebuild everything else. |
| `overlay.png` | step 4 | Proof the extraction matched |
| `plan.glb` | builder A or B | Web, AR, any 3D viewer |
| `plan.blend` | builder B | Editing in Blender |
| `top.png`, `iso.png`, `room_*.png` | renders | Deliverables |

Renders in v0: a self-contained `viewer.html` (three.js `GLTFLoader` plus `OrbitControls`, loaded from a pinned CDN version or vendored via npm) opened by Playwright, which screenshots a top-down orthographic view and an isometric view. Lighting: one hemisphere light plus one directional light with shadows is enough for a clear result. Wall-cutaway: hide the two walls nearest the camera, or clip the walls at 1.2 m for a "dollhouse" view.

## Getting accuracy

- **Scale:** two independent dimensions agree within 3 percent (step 2).
- **Orthogonality:** snap angles within 3 degrees of 0 or 90 to exact. Snap endpoints within about 0.1 m of each other to one point so rooms close.
- **Thickness:** exterior walls typically 0.2 to 0.3 m, interior 0.1 to 0.15 m. Measure from the image, then round to those standards.
- **Openings:** store width and offset in metres, and check each fits inside its wall.
- **Closed rooms:** run `shapely.ops.polygonize` on the wall lines. Unclosed rooms (gaps larger than the snap tolerance) will not form polygons, which is a useful automatic test.
- **Automated checks to run every time:** total floor area against any printed area, every wall length against any printed dimension, no door wider than its wall, no zero-area rooms.

## Risks and failure cases

| Risk | Symptom | Mitigation |
|---|---|---|
| Plan not to scale, or scale label wrong | Rooms the wrong size | Two-dimension cross-check, refuse to build on mismatch |
| Hatching, furniture, text, grid lines read as walls | Extra walls everywhere | Remove text via OCR boxes, keep only thick lines, human overlay check |
| Thick walls drawn as two parallel lines or filled black | Doubled or missing walls | Fill-and-thin: close the double line, take the centreline |
| Curved or diagonal walls, bay windows | Straight-wall assumption breaks | Out of scope for v0, support arcs later as polyline approximations |
| Door swing arcs mistaken for walls | Spurious curved fragments | Detect arcs, record them as door metadata, delete from wall set |
| Scanned and skewed or low resolution | Hough fails | Deskew, upscale to at least 200 dpi, or fall back to option A |
| Boolean failures in 3D | Holes or non-manifold mesh | 2D subtraction in builder A avoids 3D booleans |
| Headless rendering stalls without GPU | Black or empty screenshot | Test early; fall back to Cycles CPU or a lower resolution |
| AI vision misreads a dimension | Wrong scale that looks plausible | Overlay check plus cross-check, never trust a single read |
| Licence of any dataset or model used | Legal limits on use | Check before adopting option C |

## Minimal first version (build this today)

Goal: one plan image in, one `plan.glb` and two PNGs out. Target: a few hours, no Blender, no ML.

1. `pip install pymupdf opencv-python-headless shapely trimesh mapbox-earcut numpy pillow`; `npm i three`; `npx playwright` is already present.
2. Pick one simple rectilinear plan with a printed dimension. Write down the pixel coordinates of one dimensioned wall, and compute metres per pixel.
3. Have Claude look at the image and produce `plan.json` in the schema above, in metres. Save it.
4. Write `overlay.py`: draw the spec over the image. Fix the JSON until the overlay matches.
5. Write `build.py` (builder A, roughly 100 lines): footprints, opening cuts, floor extrusion, GLB export.
6. Write `viewer.html` and `shot.py` (Playwright): load the GLB, screenshot top-down and isometric.
7. Run the checks list. If they pass, you have a usable result.

Done criteria: measured wall lengths in the GLB are within 2 percent of the printed dimensions, every door and window sits in the right wall, and the overlay visibly matches the plan.

## Then, in this order

1. Automate step 3 with option B on your real plan style (this is where time goes).
2. Add builder B for Blender renders, textures and furniture placeholders.
3. Add a second storey, stairs, roofs.
4. Optionally run the final render through an AI image tool for photoreal polish, with the original plan alongside as a check on room count and layout.
