# Turning a 2D floor plan into a 3D model: build plan

## The answer in one paragraph

Build a small Python pipeline that turns the plan into a plain JSON description of the building (walls, openings, rooms, scale). A second step turns that JSON into 3D geometry. Do not ask an AI image generator to draw the 3D result. Generators invent walls and ignore dimensions. Use computer vision only to propose the JSON, and let a human confirm it. Build the geometry by extruding polygons in Python (shapely and trimesh), export a GLB file, and render with headless Blender. A three.js page loads the same GLB for browser viewing. The JSON is the one thing everything else depends on, so make it good first. The minimal first version needs no AI and no OCR. It takes a clean plan image, two clicked points with a known length for scale, and automatic wall extraction. It produces a GLB and one top-down render in a few hundred lines.

## Assumptions

- The input is a raster (PNG/JPG), a scanned page, or a PDF page, in a mostly orthogonal plan with dimensions printed on it (feet-inches or metric).
- It is a single storey. Multi-storey is the same pipeline run once per floor and stacked.
- Walls have a uniform default thickness and height (for example 4.5 in / 115 mm and 9 ft / 2.7 m) unless the plan states otherwise.
- Someone will review the result. "Accurate" means within a few percent of the printed dimensions, not survey grade.
- The environment is the Claude Code Linux container: Python, Node and Chromium are available, and I assume you can `pip install` packages. Blender is not installed, and installing it may or may not be possible. That is why the minimal version avoids it.

## Three viewpoints, and how I settled their disagreements

- **Computer-vision engineer:** wants a trained detector for walls, doors and windows. Pretrained floor-plan models exist but generalise badly to new drawing styles. Verdict: not for version 1. Use classical image processing for walls (threshold, morphology, skeleton and line extraction). Add a detector only if real plans show the classical method failing.
- **3D/Blender artist:** wants Blender for everything, including modelling. Verdict: Blender is for rendering and finishing (materials, lighting, camera). Geometry comes from Python, so it is testable without a GUI. If Blender is unavailable, the pipeline still works.
- **Architect / product owner:** wants dimensions right and cares about trust. Verdict: scale is calibrated from one printed dimension, then checked against the others. Every detected element is shown on an overlay image for the user to correct before 3D is built.

Point of dispute: AI image generators, which look impressive and are quick. Verdict: only as an optional last step to make marketing-style images from a finished clay render, never as the source of geometry.

## Architecture

```
plan.png / plan.pdf
   |
1. ingest        -> normalised grayscale image (PDF rasterised at 300 dpi)
2. scale         -> pixels-per-metre (from 2 clicks + a typed length, or OCR later)
3. extract       -> walls, openings, rooms (OpenCV)
4. plan.json     <- the single source of truth; hand-editable
5. review        -> overlay.png showing what was found; user fixes plan.json
6. build         -> shapely polygons -> trimesh extrusion -> house.glb
7. render        -> headless Blender (optional) or three.js screenshot via Playwright
```

Keep steps 1 to 5 and step 6 separate. Step 6 reads only plan.json, so you can write plan.json by hand for tests and fall back to hand-tracing when detection fails.

### plan.json (minimal schema)

```json
{
  "units": "m",
  "wall_height": 2.7,
  "walls":    [{"a":[0,0], "b":[6.0,0], "t":0.115}],
  "openings": [{"wall":0, "type":"door",   "at":1.2, "w":0.9, "h":2.1, "sill":0},
               {"wall":0, "type":"window", "at":3.5, "w":1.2, "h":1.2, "sill":0.9}],
  "rooms":    [{"name":"Kitchen", "poly":[[0,0],[4,0],[4,3],[0,3]], "floor":"tile"}]
}
```

Walls are centre-lines with a thickness. This is the cleanest representation to extrude, and it is easy to edit by hand.

## Tools and libraries

| Job | Use | Why |
|---|---|---|
| PDF to image | PyMuPDF (`fitz`) | Pure pip install, 300 dpi rasterising. If the PDF has vector lines, you can read them directly, which is more accurate than pixels. |
| Image processing | OpenCV, NumPy, scikit-image | Thresholding, morphology, Hough lines, skeletonising. |
| Geometry | shapely | Union of wall rectangles, cutting door/window holes, room polygons. |
| Mesh and export | trimesh (with `mapbox_earcut` for triangulation) | Extrude polygons and write GLB. |
| Viewer | three.js (GLTFLoader, OrbitControls) | The same GLB, in any browser. |
| Render | Blender in background mode (`blender -b -P render.py`) | Materials, sun, interior lights, camera. Cycles for stills, EEVEE for speed. |
| Text and dimensions (later) | Tesseract or PaddleOCR | Read printed dimensions and room labels. |
| Doors/windows (later) | Hough arcs for door swings; double-line gaps for windows | Or a small detector if those fail. |
| Browser testing | Playwright (already installed) | Screenshot the three.js view for an automatic check. |

If a Blender MCP server is connected to the session, the same `render.py` can be sent through it. It is a convenience, not a requirement.

## Step-by-step pipeline

1. **Ingest.** Rasterise the PDF at 300 dpi. Convert to grayscale, deskew (detect the dominant line angle with Hough and rotate), and crop the title block and margins.
2. **Scale.** The user gives two points and a length (for example, "this wall is 12'-6""). Compute pixels per metre. Later, OCR finds the dimension strings and checks scale automatically. Then compare two or three other printed dimensions with measured lengths and warn if they disagree by more than 3%. This check catches bad scans and non-uniform scaling.
3. **Walls.** Threshold, then keep only thick dark structures: morphological opening with a kernel slightly thinner than a wall removes text, dimension lines and furniture. Skeletonise what remains, then snap segments to horizontal and vertical and merge collinear pieces. Measure thickness from the distance transform. Output the wall centre-lines.
4. **Openings.** Version 1: the user lists them (wall, position, width) or clicks them. Version 2: gaps in the wall mask along a wall are doors or windows; a door swing arc confirms a door; a thin double line inside a wall gap marks a window.
5. **Rooms.** Fill the area enclosed by walls (flood fill on the inverted wall mask) to get room polygons. Label them from OCR text or ask the user.
6. **Review.** Draw plan.json back on top of the original image and write overlay.png. The user corrects mistakes in plan.json. Show this step prominently, because it is where trust comes from.
7. **Build the geometry.**
   - Buffer each centre-line to a rectangle, union them in shapely, and the result is the wall footprint.
   - Subtract door and window boxes from the wall volume (extrude the footprint in segments, or boolean the openings out). Doors go from the floor to their height. Windows get a sill piece below and a header piece above.
   - Extrude the room polygons slightly (floor slab, about 0.1 m) and optionally a ceiling.
   - Assign a material name per mesh group (walls, floor, door, glass).
   - Export `house.glb`.
8. **Materials and lighting.** In Blender: white matte walls, a wood or tile floor per room type, glass for windows, a sun lamp plus a few area lights. For a quick look in three.js: hemisphere light plus a directional light with soft shadows.
9. **Render.** Three outputs: a top-down view (orthographic camera above), an isometric cutaway (remove the roof and the near walls), and one eye-level view per room.

## Outputs

- `plan.json` (the editable model), `overlay.png` (detection check)
- `house.glb` (open in any viewer, Blender, or three.js); optionally `house.obj`
- `topdown.png`, `iso.png`, `room_*.png`
- `index.html` plus the GLB, a self-contained orbit viewer

## Accuracy: what keeps it right

- Calibrate scale from a real printed dimension, and cross-check others.
- Snap to horizontal and vertical, and merge nearby lines, so walls meet at clean corners.
- Dimensions in the final model come from numbers in plan.json, not from pixels. The user can type 3.60 and the room becomes 3.60.
- Automated check: for each room, compare the model area with any area printed on the plan, and compare overall width and length with the printed overall dimensions.
- Keep openings as data, not as AI guesses.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Hand-drawn, curved or diagonal walls | Orthogonal snapping distorts them | Allow arbitrary angles (skip snapping per wall); fall back to manual tracing |
| Furniture, hatching, text touching walls | Fake or missing walls | Morphological filter; mask text first with OCR boxes; user review |
| Dimension strings in mixed or odd units (ft-in fractions) | Wrong scale | Parse carefully, cross-check two dimensions, show the computed scale to the user |
| Low-resolution scan or skew | Thin walls vanish; edges wobble | Require 150 dpi or more; deskew; warn when walls are under 4 px |
| Doors misclassified as windows | Wrong openings | Show them in the overlay; the user edits plan.json |
| Open-plan layouts with no closed room | Room fill leaks | Close small gaps (dilate); allow the user to draw a room polygon by hand |
| Polygon boolean errors | Non-watertight mesh | Validate with shapely (`is_valid`) and trimesh (`is_watertight`); fix with `buffer(0)` |
| Multi-storey, stairs, roofs | Not in the model | Out of scope for v1; add stairs and roofs as simple parametric blocks later |
| AI generators used for geometry | Wrong walls, ignored dimensions | Do not use them for geometry |

## Minimal first version (build this first)

**Goal:** one clean plan image in, a correct GLB and one top-down render out, in an afternoon.

Scope:
1. `pip install opencv-python-headless shapely trimesh mapbox-earcut numpy pymupdf`
2. `extract.py plan.png --scale "x1,y1,x2,y2,3.6"` runs the scale step and the wall step, and writes plan.json (walls only, default thickness and height) and overlay.png.
3. The user adds doors and windows to plan.json by hand (a few lines each).
4. `build.py plan.json` writes house.glb with floor and walls, with the openings cut out.
5. `view.html` (three.js, OrbitControls) loads house.glb. A Playwright script opens it and saves topdown.png and iso.png. No Blender needed.

Done when: a test plan with known dimensions produces a model whose overall length and width match the printed values within 3%, and `trimesh` reports it watertight.

Stage 2 (when v1 works): OCR for dimension strings; automatic door and window detection; room labels; headless Blender renders with materials and lighting; floor materials per room type.
Stage 3 (only if needed): a trained wall and opening detector for messy scans; stairs; multiple storeys; AI-generated stylised images from a finished render.

## Test checklist

- One synthetic plan drawn by script with exact dimensions (ground truth).
- One real clean CAD export as a PDF.
- One phone photo or scan, to see where it breaks.
- For each: overlay looks right, scale check passes, GLB opens in three.js and in Blender, and dimensions match.
