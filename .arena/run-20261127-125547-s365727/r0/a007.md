# 2D Floor Plan to 3D Model: Build Plan

## Recommendation in one paragraph

Do not try to make a computer "understand" the plan in one step. Split the job into two stages joined by a small, human-checkable JSON file. Stage 1 (perception) turns the image or PDF into a plan description: wall segments, openings, rooms and a scale. Stage 2 (generation) turns that JSON into geometry with deterministic code. Build Stage 2 first and feed it hand-written JSON. Your 3D output is then correct by construction, and any error in Stage 1 shows up as a visible, fixable edit to one text file. Use Python with `trimesh` and `shapely` to write a GLB, and use three.js with Playwright to preview it and take screenshots. Add Blender later for photoreal renders. AI image generators should not produce the geometry. Use them, if at all, for optional "pretty" renders that are checked against the plan.

## Assumptions

- The plan is a clean, mostly orthogonal drawing of one storey. It is an architect PDF, a CAD export or a clear scan. It is not a hand sketch or a photo taken at an angle.
- It has at least one dimension label, or a known scale such as "1/4 in = 1 ft", or a door you can use as a ruler (a standard door is about 0.9 m wide).
- You want an accurate, editable model first and pretty renders second.
- You work in the cloud container, which has Python, Node, Chromium and Playwright. There is no GPU. Blender is not assumed to be installed, so it is optional.
- Ceiling height defaults to 2.4 m (8 ft) unless stated. Door height defaults to 2.0 m. Window sill defaults to 0.9 m and window head to 2.1 m. Wall thickness defaults to 0.115 m for interior walls and 0.23 m for exterior walls, unless measured from the plan.
- Multi-storey buildings are handled by running the pipeline once per plan and stacking them. This is out of scope for version 1.

## Architecture (how the parts affect each other)

```
 PDF/PNG/JPG
     |
 [1 Ingest]  rasterize, deskew, binarize
     |
 [2 Scale]   OCR dimensions -> metres per pixel
     |
 [3 Detect]  walls, doors, windows, rooms  ->  plan.json
     |                                           ^
 [4 Review]  overlay plan.json on image ---------|  (human fixes JSON)
     |
 [5 Build]   plan.json -> geometry (walls with holes, floors, ceilings)
     |
 [6 Export]  model.glb  (+ .obj / .blend later)
     |
 [7 Show]    three.js viewer, Playwright screenshots
     |
 [8 Render]  (later) Blender Cycles/EEVEE stills, walkthrough video
```

Why this shape. The JSON in the middle is the key design decision.

1. It isolates the hard, error-prone part (reading the drawing) from the easy, reliable part (extruding walls).
2. It lets you swap detectors (classical CV, a trained model, or an LLM with vision) without touching the 3D code.
3. It makes errors cheap to fix. A wrong wall is one line of JSON, not a re-run of a black box.
4. It gives you a test fixture. Hand-written plans give regression tests for the generator.

Second-order effect to watch: a scale error in step 2 silently scales everything. A single wrong dimension makes every room the wrong size and every door look absurd. So step 2 produces a confidence check (see "Accuracy" below), and step 4 always shows it.

## Tools and libraries

| Job | Choice | Why |
|---|---|---|
| PDF to image | `pymupdf` (fitz) | Fast, no system dependencies. For vector PDFs, it can also extract the lines directly, which is far more accurate than pixels. |
| Image cleanup | `opencv-python-headless`, `numpy` | Threshold, deskew, morphology. |
| Line and wall detection | OpenCV (`HoughLinesP`, morphological opening, `connectedComponents`) | Works well on clean plans. No training needed. |
| OCR for dimensions and room names | `pytesseract` (needs `apt install tesseract-ocr`) or `easyocr` | Reads "3.20 m", "12'-6\"" and "KITCHEN". |
| Vision LLM for semantics | Claude with image input (already in your session) | Good at labelling rooms, spotting door swings, and sanity checking. Poor at pixel-accurate coordinates, so use it to label and verify, not to measure. |
| Geometry | `shapely` (2D polygons, offsets, boolean ops) and `trimesh` (extrude, combine, export) | Pure Python, installs with pip, exports GLB. |
| Preview | three.js (`GLTFLoader`, `OrbitControls`) in a static HTML page, with Playwright for screenshots | Runs in the container with Chromium. |
| Photoreal render (later) | Blender 4.x in background mode (`blender -b -P build.py`), or Blender through an MCP add-on | Cycles for stills, EEVEE for fast looks, camera paths for video. |
| Optional ML detector | A pretrained or fine-tuned segmentation model on public floor-plan datasets (for example CubiCasa5k or R2V-style data) | Only if classical CV fails on your plans. Do not start here. |

## The data contract: plan.json

Every unit is metres. The origin is the top-left of the plan. Y points down in image space and is flipped once, at build time.

```json
{
  "units": "m",
  "scale": {"m_per_px": 0.0123, "source": "ocr:dimension", "confidence": 0.9},
  "wall_height": 2.4,
  "walls": [
    {"id": "w1", "a": [0, 0], "b": [8.0, 0], "thickness": 0.23, "kind": "exterior"}
  ],
  "openings": [
    {"id": "d1", "type": "door",   "wall": "w1", "offset": 1.2, "width": 0.9, "height": 2.0, "sill": 0.0},
    {"id": "n1", "type": "window", "wall": "w1", "offset": 4.0, "width": 1.2, "height": 1.2, "sill": 0.9}
  ],
  "rooms": [
    {"id": "r1", "name": "Kitchen", "polygon": [[0,0],[4,0],[4,3],[0,3]], "floor": "tile"}
  ]
}
```

Rules that keep it robust:

- Walls are centrelines plus a thickness. Openings are placed by distance along a wall (`offset`), not by absolute coordinates. If you nudge a wall, its door moves with it.
- Rooms are optional. If missing, compute them from the walls with `shapely.ops.polygonize`.
- Anything the detector is unsure about gets a `"confidence"` field below 0.7 and is drawn in red in the review overlay.

## Step-by-step pipeline

### Step 1. Ingest
- PDF: render at 200 to 300 dpi with `pymupdf`. Also try `page.get_drawings()`. If the PDF is vector, you get exact line endpoints and can skip most of step 3.
- Image: convert to grayscale, deskew using the dominant Hough angle, and threshold with Otsu or adaptive thresholding.
- Crop away title blocks, legends and furniture noise where possible.

### Step 2. Scale (the step that decides whether the model is "accurate")
Try in this order and stop at the first that works:
1. OCR dimension strings and the dimension lines or arrows next to them. Match "4200" or "13'-9\"" to the pixel length of the line it labels. Take the median metres-per-pixel across all matches.
2. A scale bar or a stated ratio on the sheet.
3. A door as a ruler: measure the typical door width in pixels and assume 0.9 m. Flag as low confidence.
4. Ask the user to click two points and type a length. In the first version this is simply a CLI argument: `--scale-from "x1,y1,x2,y2,3.20"`.

Validation: after scaling, check that several OCR'd dimensions agree within 2 percent. If they do not, stop and report instead of building.

### Step 3. Detect walls, openings, rooms
Classical approach, in order of cost:
1. Walls are the thickest dark strokes. Erode the binary image with a kernel about the size of a wall to remove thin lines (dimensions, furniture, hatching), then dilate back. What survives is the wall mask.
2. Skeletonize the mask (`skimage.morphology.skeletonize`) and fit line segments (`HoughLinesP` or `cv2.createLineSegmentDetector`). Snap to horizontal and vertical when within about 3 degrees. Merge collinear segments and close small gaps.
3. Openings are gaps in the wall mask. A gap in a wall that is crossed by a swing arc is a door. A gap with two or three thin parallel lines is a window. A plain gap is a doorway.
4. Rooms: polygonize the closed wall network. Label each polygon using OCR text that falls inside it.
5. Semantic check: send the image plus the detected overlay to a vision model and ask "list rooms, door and window counts, and anything that looks wrong". Compare with your detection. Disagreements go to the review step.

If the plan is a vector PDF, replace 1 and 2 with: group long thick line pairs into walls using `get_drawings()` stroke widths and fills.

### Step 4. Review overlay (do not skip)
Draw `plan.json` over the original image (walls in blue, doors in green, windows in orange, low-confidence items in red) and save `overlay.png`. Look at it. Fix the JSON by hand. For a first version this is the entire "editor", and it is cheaper than building any UI.

### Step 5. Build geometry
For each wall:
1. Make a 2D rectangle from the centreline and thickness with `shapely` (`LineString.buffer(t/2, cap_style=2)`).
2. Union all walls into one polygon so corners and T-junctions are clean with no overlap or z-fighting.
3. Extrude the union to `wall_height` with `trimesh.creation.extrude_polygon`.
4. Cut openings: for each door or window, make a box through the wall thickness, sized `width x height` at `sill`, and subtract it (`trimesh` boolean with the `manifold3d` engine, or do the cutting in 2D elevation if booleans give trouble). Fallback if booleans fail: build the wall in segments around each opening (left piece, lintel above, sill below, right piece). This is more code but never fails.
5. Add a door leaf and a window pane as thin boxes (optional but makes screenshots readable).
6. Floors: extrude each room polygon down 0.1 m. Ceilings: optional flat polygon at wall height, off by default so top-down views work.
7. Assign materials by name (`wall`, `floor_tile`, `floor_wood`, `glass`, `door`) with simple PBR colours.

### Step 6. Export
- `model.glb` is the main output. It is compact, has materials, and loads in three.js, Blender and most viewers.
- `plan.json` is the editable source of truth. Keep it with the model.
- Later: `.obj` via `trimesh`, `.blend` by building in Blender, and `.ifc` if the user needs BIM tooling (out of scope for now).

### Step 7. Preview and screenshots
- `viewer.html` loads `model.glb` with three.js, adds a hemisphere light plus one directional light with shadows, and an orbit camera.
- A Playwright script opens the page headless in Chromium, waits for a `window.ready = true` flag, and saves three images: top-down (orthographic), isometric cutaway (hide the ceiling), and an eye-level view in the largest room.
- No GPU: use `--use-gl=swiftshader` or `--use-angle=swiftshader` in the Chromium flags. Software rendering is slow but fine for stills of a house-sized model.

### Step 8. Photoreal renders (version 2)
- Run Blender headless: import `model.glb` (or rebuild from `plan.json` with `bpy`), add a sun or area lights, set the camera, and render with EEVEE for speed or Cycles for quality (CPU only in the container, so use low sample counts and the denoiser).
- Blender MCP is useful when the user drives Blender interactively on their own machine. In this container, a plain `blender -b -P script.py` is simpler and reproducible.
- Walkthrough video: a camera path through the room centroids, rendered to frames and joined with `ffmpeg`.

## Getting each element right

**Walls.** Use thickness from the plan where possible: measure the stroke width in metres after scaling and snap to the nearest standard value (0.1, 0.115, 0.15, 0.2, 0.23). Snap wall ends to a grid of about 5 cm and snap near-collinear ends together. Always union walls before extruding.

**Openings.** Locate by wall and offset. Door height defaults to 2.0 m, window sill to 0.9 m. If the plan has a door or window schedule (a table), OCR it and use its sizes. Door swing arcs give hinge side and direction for the optional door leaf.

**Floors.** One polygon per room from `polygonize`. Floor under the wall footprint too, so there are no holes at doorways.

**Materials.** Start with flat colours by room type (wet rooms tile, living areas wood, others a neutral). Offer a `materials.json` mapping so the user can swap them. Later, use free CC0 PBR textures from a source such as Poly Haven.

**Lighting.** For the viewer: hemisphere light, one shadow-casting directional light, soft shadows. For Blender: a sky or HDRI plus a sun, and one area light per room at ceiling height for interior shots. Windows should be real holes so daylight actually enters.

**Furniture.** Leave it out of version 1. Furniture symbols in a plan are the main source of false walls, so filtering them out is the goal, not reproducing them.

| `model.glb` | The 3D model. |

## Accuracy checks (cheap, automatic)

1. Total area of detected rooms versus any "total area" text on the plan, within 5 percent.
2. Every OCR'd dimension versus the measured length of the matching wall, within 2 percent.
3. Walls form closed loops (no dangling ends longer than a wall thickness).
4. Every opening lies fully inside its wall with at least 10 cm of wall on each side.
5. Door width between 0.6 and 1.2 m, window width between 0.3 and 3 m. Anything else is flagged.
6. Overlay image is viewed by a person or a vision model before the build is trusted.

## Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Wrong or missing scale | Whole model the wrong size. | Multiple dimension cross-checks, manual two-point override, never build silently on low confidence. |
| Furniture, hatching, text, stairs read as walls | Phantom walls. | Erode before detecting. Review overlay. Allow `--ignore-box` regions. |
| Hand sketches, photos, skewed scans | Detection collapses. | Deskew and perspective-correct. If that fails, route to the manual JSON path. |
| Curved walls, diagonal walls | Snap-to-orthogonal breaks them. | Version 1 supports straight walls only. Keep diagonals if the angle is stable, otherwise flag. |
| Double-line walls versus solid-fill walls versus single lines | Different drawing conventions break one detector. | Detect the style first. Support filled walls in version 1, add double-line later. |
| Open-plan areas without walls | Rooms fail to close. | Let the user add virtual `"kind": "boundary"` segments with zero height. |
| Boolean failures when cutting openings | Broken or non-manifold mesh. | Segment-based wall construction as the fallback. |
| Imperial strings ("12'-6\"") misread by OCR | Silent factor errors. | Parse with a strict regex, reject unparseable strings, and cross-check. |
| Multi-storey sheets, sections, elevations on one page | Mixed content. | Crop to one plan. Version 1 expects one plan per input. |
| AI image generators used for geometry | They invent walls, move doors and change proportions. | Use them only for stylised renders, and check them against the overlay. Never use them as the source of dimensions. |
| Copyright or privacy of the plan | A client's drawing leaves your machine through an online service. | Keep detection local. Tell the user before sending plans to any external API. |

## Minimal first version (build this today)

Goal: one command that takes a plan image plus one known length and writes a GLB and three screenshots. Detection is classical. Everything else is manual and honest about it.

Order of work, each step independently testable:

1. **Generator first (about 1 hour).** `build.py plan.json -> model.glb`. Write a small hand-made `plan.json` of a two-room flat with one door and one window. Open it in `viewer.html`. When this looks right, half the project is done.
2. **Screenshots (about 30 minutes).** `shot.py model.glb` using Playwright, producing `top.png`, `iso.png`, `eye.png`.
3. **Scale from CLI (about 15 minutes).** `--scale-from x1,y1,x2,y2,metres`.
4. **Wall detector (about 2 hours).** Threshold, erode and dilate, skeleton, Hough, snap, merge. Output `plan.json` with walls only.
5. **Overlay (about 30 minutes).** Draw `plan.json` over the image. Review and hand-edit.
6. **Openings (about 1 to 2 hours).** Gap detection in the wall mask. Doors versus windows chosen by a simple rule or by a manual `type` field in the JSON.
7. **Report (about 15 minutes).** Print scale source, counts and the checks above.

Directory layout:

```
floorplan3d/
  ingest.py     # pdf/image -> clean binary + scale
  detect.py     # binary -> plan.json
  overlay.py    # plan.json + image -> overlay.png
  build.py      # plan.json -> model.glb
  shot.py       # model.glb -> screenshots (Playwright)
  viewer.html   # three.js viewer
  samples/      # hand-made plan.json + one real plan
  tests/        # build.py on samples; area and closure checks
```

Install:

```
pip install pymupdf opencv-python-headless numpy scikit-image shapely trimesh manifold3d pytesseract pillow
npm i three            # or load three.js from a CDN in viewer.html
pip install playwright # Chromium is already installed
```

Definition of done for version 1: on three different clean plans, the overlay shows walls within a few percent of the true positions after you fix at most a handful of JSON lines, the room areas match the printed values within 5 percent, and the GLB opens in the viewer with doors and windows in the right places.

## What to add next, in order of value

1. A click-to-edit overlay page (drag wall ends, toggle door or window), saving back to `plan.json`.
2. Blender headless render script with sun and area lights, plus a walkthrough video.
3. Vector-PDF fast path using `get_drawings()`, which is the biggest accuracy gain for CAD exports.
4. Door and window schedule parsing, and swing direction for door leaves.
5. A trained segmentation model for hard plans (double-line walls, scans), used only to produce candidates for the same `plan.json` review step.
6. Optional AI-generated "styled" renders from a checked screenshot of your own model, as a clearly labelled visual extra.
7. Multi-storey stacking and stairs.

## Decision summary

- Use a JSON plan as the contract between "reading" and "building".
- Build the generator first, using hand-written JSON.
- Use classical CV plus OCR for detection, and a vision LLM for labelling and sanity checks only.
- Use `shapely` and `trimesh` for geometry, GLB as the main output, three.js and Playwright for preview, Blender for later photoreal renders.
- Treat scale as the most important single number and verify it twice.
- Always show the overlay before trusting a build.
