# Turning a 2D floor plan into a 3D model: build plan

## 1. Recommendation in one paragraph

Do not make an AI image generator, or a live Blender session, the core of the system. Make the core a deterministic geometry pipeline around one reviewable intermediate file, `plan.json`. The pipeline is: raster or PDF in, vectorised walls, openings and rooms with a calibrated scale, human-confirmed, then extruded into a GLB file, then rendered. The reason is that the output must be correct, not merely plausible. A floor plan is a measurement document. Generators invent walls. Pixel-to-geometry code can be checked against the drawing. Blender and AI renderers are optional back ends that read `plan.json` or the GLB, never the source of truth.

## 2. The obvious answer, and why most of it does not survive

| Obvious default | Argument against | What I keep |
|---|---|---|
| Feed the plan to an image generator ("make this a 3D render") | It redraws instead of measuring. It moves walls, invents furniture and text, and gives a picture with no model, no dimensions and no editability. | Only as a final, optional "beauty pass" over a clay render made from the real geometry, with the geometry as the control image. Never as the model. |
| Drive Blender through MCP | The MCP add-on needs a live Blender GUI on localhost:9876. The cloud container has none, and the user may not have one running. It is also slow for generating hundreds of simple prisms. | Blender through the `bpy` Python package or `blender -b -P script.py` (headless) as an optional stage for Cycles renders and `.blend` files. Blender MCP stays an option only if the user has a desktop Blender attached. |
| Train or fine-tune a wall-segmentation network (CubiCasa5k style) | Large effort, needs GPU and data, and still fails on unusual drawings. No guarantee on a user's one plan. | Not in v1. Keep a pluggable `detector` interface so a pretrained model can be swapped in later for messy scans. |
| OCR the dimension strings to get scale | Dimension text is the part OCR gets wrong most often (`12'-6"`, `3.25`, rotated text, `l` vs `1`), and one wrong digit silently scales the whole house. | OCR is used only to suggest a scale. The scale is always confirmed by a calibration step the user can see: click two points, type the true length. |
| Full automation | A fully automatic result looks done and is silently wrong. | Automatic first draft, then a quick correction view, then build. Human review is a feature. |
| three.js vs Blender as an either-or choice | Each is better at something. | three.js (in Node/Chromium, already installed) for the viewer and quick renders. `trimesh` for GLB export. Blender headless for photoreal stills and video. All fed by the same JSON. |

## 3. Assumptions

1. The input is a single-storey floor plan as PNG/JPG/scan or PDF, ideally with some printed dimensions. Multi-storey is a later extension (the schema supports `levels`).
2. The plan is drawn to scale or has at least one reliable dimension. Without any known length, the output is a correct shape at an arbitrary size, and the tool says so.
3. Walls are drawn as thick lines or filled bands (normal for architect drawings). Single-line sketches are handled by giving a default wall thickness.
4. Default heights: wall 2.7 m (8 ft 10 in), door 2.05 m, window sill 0.9 m, window head 2.1 m. These are editable.
5. "3D model" means a viewable and exportable model (GLB, plus optional OBJ/`.blend`), with renders as screenshots. It is not a BIM/IFC deliverable (an IFC export is listed as an extension).
6. Runtime is the Claude Code cloud container: Linux, Python, Node, Chromium and Playwright. No GPU, no desktop Blender. Packages come from pip and npm.
7. The user is the person who knows the building, so they can resolve ambiguous items in minutes.

## 4. Architecture

```
input.pdf / .png / .jpg
        |
 [1 Ingest]         rasterise PDF at 200-300 DPI (or read vector paths), deskew, crop, binarise
        |
 [2 Calibrate]      pixels-per-metre from user-confirmed known length (OCR suggests, human confirms)
        |
 [3 Detect]         walls, openings (doors/windows), rooms, labels, as polygons/lines in plan space
        |
 [4 plan.json]      the single source of truth, human-readable, versioned
        |
 [5 Review]         HTML overlay (plan image + detected geometry), user fixes, saves plan.json
        |
 [6 Build]          wall solids with door/window holes, floor slabs, ceiling, frames, glass
        |
 [7 Export]         model.glb (always), model.obj, model.blend and model.ifc optional
        |
 [8 Render]         three.js via Playwright (default), Blender headless Cycles (optional)
        |
 [9 Verify]         overlay the model's top-down projection on the original plan, report area/length diffs
```

Why this shape: every stage reads and writes plain files, so each can be tested alone, retried, or replaced. Stage 9 closes the loop that AI-only approaches lack.

### 4.1 `plan.json` schema (the contract)

```json
{
  "version": 1,
  "units": "m",
  "scale": {"px_per_m": 94.2, "source": "user_calibration", "ref_px": [[102,88],[1034,88]], "ref_m": 9.9},
  "defaults": {"wall_h": 2.7, "wall_t": 0.15, "door_h": 2.05, "sill_h": 0.9, "head_h": 2.1},
  "levels": [{
    "name": "ground", "elevation": 0.0,
    "walls": [{"id":"w1","a":[0,0],"b":[6.2,0],"t":0.2,"h":2.7,"kind":"exterior"}],
    "openings": [
      {"id":"o1","wall":"w1","type":"door","offset":1.1,"width":0.9,"h":2.05,"sill":0,"swing":"in-left"},
      {"id":"o2","wall":"w1","type":"window","offset":3.4,"width":1.5,"h":1.2,"sill":0.9}
    ],
    "rooms": [{"id":"r1","label":"Kitchen","polygon":[[0,0],[4,0],[4,3],[0,3]],"floor":"tile"}]
  }],
  "confidence": {"w1": 0.97, "o2": 0.6}
}
```

Coordinates are metres, origin at the plan's top-left, y flipped to match 3D. Walls are centre-line segments with thickness, which makes openings and joins simple and edits one-line. Every detected item carries a confidence so the review view can highlight what to check first.

## 5. Tools and libraries (with the reason for each)

| Job | Choice | Notes |
|---|---|---|
| PDF to image or vectors | `PyMuPDF` (fitz) | Renders at any DPI and can read vector line paths directly. For CAD-exported PDFs, vector extraction is far more accurate than pixels, so try it first. |
| Image ops | `OpenCV`, `scikit-image`, `numpy` | Threshold, morphology, skeleton, Hough, contours. |
| Wall detection (v1) | Thickness-based morphology: wall pixels are the dark/filled regions whose local stroke width is within the wall-thickness band. Use a distance transform and opening to keep thick structures and drop text, hatching and dimension lines. Then skeletonise and fit line segments, snap to orthogonal when within about 3 degrees. | Fast, explainable, no training. Works on clean drawings. |
| Wall detection (fallback) | Pretrained floor-plan segmentation model (CubiCasa5k-type) behind the same `detector` interface | Only for hand-drawn or noisy scans. Needs `torch`, so keep it optional. |
| Openings | Doors: arc (swing) detection with `cv2.HoughCircles` or contour arcs, plus gaps in wall bands. Windows: thin parallel double or triple lines inside a wall band. | Gaps in walls with no arc are flagged "opening, type unknown" rather than guessed. |
| Rooms | Polygonise the closed regions of the free space (`shapely.polygonize` on the wall lines) | Room labels come from OCR positions falling inside each polygon. |
| OCR | `pytesseract` (Tesseract) for labels, and for dimension suggestions only | EasyOCR/PaddleOCR are heavier alternatives. Always human-confirmed for scale. |
| Geometry / booleans | `shapely` (2D unions, offsets, mitred joins) then `trimesh` + `mapbox_earcut` for extrusion; `manifold3d` for 3D boolean cuts | 2D-first is the key trick: subtract door and window rectangles from the wall polygon in 2D for the full-height parts, and extrude the lintel and sill pieces separately. This avoids fragile 3D booleans. |
| Export | `trimesh` to GLB/OBJ/STL | GLB is the universal deliverable: opens in three.js, Blender, Windows 3D Viewer, macOS Quick Look, Unity. |
| Interactive viewer | `three.js` (`GLTFLoader`, `OrbitControls`) as a single static HTML page | Doubles as the review UI when the plan image is layered underneath. |
| Headless rendering | Playwright + Chromium screenshotting the three.js page (use `--use-gl=swiftshader` / `--use-angle=swiftshader` flags in the container, since there is no GPU) | Gives top-down, isometric cutaway and eye-level PNGs. |
| Photoreal render (optional) | `bpy` (pip) or `blender -b`, Cycles CPU or EEVEE, with the GLB imported | Slow on CPU. Cap samples (64 to 128 plus denoise) and resolution. |
| AI "beauty pass" (optional) | Image-to-image with a depth or edge control from the clay render | Strictly cosmetic. Output labelled "illustrative, not to scale". |
| Orchestration | Python CLI (`plan2model.py`), one subcommand per stage, plus `pytest` | Claude Code can run it, read the overlay PNGs, and iterate. |

## 6. Step-by-step pipeline

### Stage 1: Ingest
1. If PDF: first try vector extraction (`page.get_drawings()`). If it returns many line paths, use them directly and skip most of stage 3. Otherwise rasterise at 250 DPI.
2. Auto-crop to the drawing's bounding box. Remove the title block and border by choosing the largest connected linework region.
3. Deskew: estimate the dominant line angle by Hough, rotate to make walls axis-aligned. Warn when the skew is above about 5 degrees, since that suggests a phone photo with perspective, which needs the four-corner perspective fix (user clicks four corners of a known rectangle).
4. Binarise: Otsu for clean drawings, adaptive threshold for scans.

### Stage 2: Calibrate scale (the step that decides accuracy)
Priority order:
1. User picks two points and types the real length (for example the overall width written on the plan). This is the default and takes seconds.
2. A drawn scale bar: user clicks its two ends and types the length.
3. A stated scale ("1:100") plus the known DPI of the source. Valid only for the original-size print or PDF, so the tool shows a warning that photos and screenshots break this.
4. OCR-suggested dimensions: detect strings like `3.20`, `10'-4"`, `4200`, pair them with nearby dimension lines, and propose a scale. Use two or more independent dimensions and compare. If they disagree by more than 2 percent, stop and ask.
5. Fallback: assume a standard door is 0.9 m or 3 ft wide, mark the model "scale estimated", and print that on every render.

Check afterwards: the tool must report the other dimensions it can read against the calibrated model ("kitchen 4.2 m on plan, 4.18 m in model").

### Stage 3: Detect
1. Wall mask from the thickness filter described above. Remove blobs below an area threshold (text, furniture symbols).
2. Skeletonise and extract segments. Merge collinear pieces. Snap endpoints into T/L/X junctions within a tolerance of about half a wall thickness. Estimate thickness per segment from the distance transform and then cluster to two or three values (exterior, interior, partition), because per-wall measured thickness is noisy.
3. Openings: find breaks in wall bands. Classify by evidence (arc present: door; parallel thin lines across the band: window; neither: "opening"). Measure width and offset along the wall.
4. Rooms: polygonise. Attach OCR labels.
5. Discard: furniture, stairs (record stairs as a flagged region only in v1), dimension lines, hatch patterns.

### Stage 4 and 5: Write `plan.json` and review
Render `overlay.png`: the original plan with detected walls in red, openings in blue and green, low-confidence items dashed. In Claude Code, Claude can look at that image directly and report problems. For a human, serve a small HTML editor (canvas plus drag handles) to move endpoints, delete or add walls, change an opening's type and width, and set room floor materials. Saving writes `plan.json`. Walk through the low-confidence list first.

### Stage 6: Build the geometry
For each wall:
1. Build the 2D footprint polygon from centre line and thickness. Union all walls with `shapely` so corners and T-junctions are clean (no overlapping or z-fighting faces).
2. For each opening, cut a rectangle from the footprint wherever the opening runs the full height (doors). For windows, extrude three pieces: below sill, above head, and nothing between. Add a lintel above doors.
3. Extrude to `wall_h`.
4. Floors: one slab per room polygon, 0.1 m thick, with the room's material. Fill any area inside the outer walls not covered by a room (corridors) so there are no holes.
5. Ceiling: optional, off by default so top-down views work. A "roof on/off" toggle lives in the viewer.
6. Door leaves (thin boxes, open 90 degrees using the swing hint), window frames (four thin bars) and glass (a single transparent plane, alpha 0.25). All are simple primitives.
7. Names and metadata: every mesh node is named `wall_w1`, `door_o1`, `floor_r1` so the model stays editable and selectable.

### Stage 7: Export
- `model.glb` (required), `model.obj`/`.mtl`, optional `model.stl` for 3D printing (solid shell, scale-correct).
- `plan.json` (editable source) and `overlay.png` (audit trail).
- `model.blend` if Blender is available.

### Stage 8: Render
Default (fast, always works): Playwright opens `viewer.html?model=model.glb&view=...` and saves PNGs:
- `top_down.png` (orthographic, roof off, rooms labelled)
- `iso_cutaway.png` (orthographic 35 degrees, walls cut at 1.5 m or ceiling hidden)
- `eye_level_<room>.png` (perspective, 1.6 m eye height, 70 degree field of view, one per room)
- `walkthrough.mp4` (optional: path through room centres, frames captured with Playwright then `ffmpeg`)

Lighting for the three.js renders: a hemisphere light for ambient fill, one directional "sun" with soft shadows (PCFSoft or VSM, shadow map 2048), `ACESFilmic` tone mapping, and sRGB output. Add a `RoomEnvironment` for reflections on glass and floors. For interiors, add a point light per room at 2.3 m, intensity scaled by room area. Check that nothing renders black: set the minimum ambient high enough that a closed room stays readable.

Materials: a table maps `floor` and `wall` tags to simple PBR values (colour, roughness, metalness 0), with optional tileable textures. Defaults: white walls (roughness 0.9), oak or tile floors by room label (kitchen, bath: tile; others: wood), glass (transmission or alpha). Wet rooms are detected from OCR labels (kitchen, bath, WC, toilet), otherwise default to wood.

Optional photoreal (Blender headless): import the GLB, replace materials with Principled BSDF, add a sun lamp plus an area light per room, Cycles 64 to 128 samples with denoise at 1600 px wide. Expect minutes per image on CPU.

### Stage 9: Verify (do not skip)
1. Project the model's walls to 2D and draw them over the source image (`verify.png`). Anything off by more than half a wall thickness is flagged.
2. Report: total walls, openings, room areas (m2) against any areas printed on the plan, outer bounding box against calibration.
3. Fail loudly on: unclosed room polygons, zero-width walls, openings wider than their wall, openings that overlap each other, or a model with more than one disconnected exterior shell.

## 7. How accuracy is achieved (summary)

- Walls: thickness-filtered mask, centre-line fitting, orthogonal snapping, junction merging, consistent thickness classes, 2D union before extrusion.
- Openings: measured along the wall in metres, stored as offset and width, cut in 2D so edges are exactly straight. Unknown types are flagged, never guessed.
- Floors: derived from polygonised closed regions, so they match walls by construction rather than being drawn separately.
- Scale: human-confirmed two-point calibration, cross-checked against a second dimension, shown on every output.
- Materials and lighting: assigned from labels with transparent defaults. They affect appearance only and never geometry.
- Overall: stage 9 compares the final model with the original drawing, so errors are visible instead of hidden.

## 9. Risks and failure cases

| Risk | What happens | Mitigation |
|---|---|---|
| Wrong scale | Everything is the wrong size, yet looks fine | Two-point calibration, second-dimension cross-check, scale stamped on renders |
| Phone photo or perspective-distorted scan | Walls are not parallel, scale varies across the image | Four-corner perspective rectification, otherwise refuse and say why |
| Hatched or filled walls (poche), double-line walls | Thickness filter misses or splits walls | Add a mode switch: `--wall-style solid|double|hatched`. For double lines, fill the gap between close parallel lines. |
| Text, furniture and dimension lines touching walls | False walls | Area and thickness filters, an erase-by-region tool in the review UI |
| Curved or diagonal walls | Orthogonal snapping flattens them | Snap only within the angle tolerance. Keep true angles beyond it. Arcs are approximated by short segments in v2. |
| Door/window symbols vary by country and drafter | Misclassified openings | Evidence-based classification with an "unknown opening" fallback and a one-click type change |
| Low-resolution or faded scans | Broken or missing walls | Warn below about 150 DPI equivalent, upscale only for detection, never invent walls |
| Multiple floors or sections on one sheet | Detection mixes them | Crop one drawing at a time in v1 |
| Stairs, split levels, sloped roofs, balconies | Not represented | Out of v1 scope. List them in `report.md` as "not modelled". |
| Boolean failures producing non-manifold meshes | Holes or broken exports | 2D-first construction, then `trimesh` watertight check in tests |
| Headless WebGL without GPU | Black or failing renders | SwiftShader flags, a test render in CI, fallback to a `trimesh`/`pyrender` software raster |
| AI beauty pass changes layout | Misleading imagery | Optional, labelled illustrative, geometry-conditioned, never used for measurement |
| Copyright or privacy of the plan | Plans of real homes are sensitive | Process locally in the container, do not upload to third-party services without the user's say |
| Overpromising automation | User trusts a wrong model | Review step and the `verify.png` audit are mandatory in the workflow |

## 10. Minimal first version (build this first, about one day)

Scope: one clean, single-floor plan (CAD-exported PDF or high-quality PNG), straight walls, rectangular openings.

Do:
1. `ingest`: PDF or image to a binarised PNG (PyMuPDF, OpenCV).
2. `calibrate`: command-line `--ref x1,y1,x2,y2 --len 9.9` (the UI comes later).
3. `detect`: thickness filter, skeleton, Hough or LSD line fitting, orthogonal snap. Openings are found simply as gaps in walls (type from arc presence or "opening").
4. Write `plan.json` and `overlay.png`. Claude looks at the overlay, and the user corrects `plan.json` by hand if needed.
5. `build`: `shapely` union, door and window cuts, extrude with `trimesh`, floor slab from the outer boundary, export `model.glb`.
6. `render`: a ~60-line `viewer.html` with three.js and `OrbitControls`, and a Playwright script that saves `top_down.png` and `iso.png`.
7. `verify`: draw the model's footprint over the original and print the bounding-box size.

Skip for now: room labels and OCR, materials and textures, the editor UI, Blender, AI, perspective correction, multi-storey.

Starter commands:
```bash
pip install pymupdf opencv-python-headless scikit-image shapely trimesh mapbox_earcut manifold3d numpy pytesseract
npm i three playwright    # Chromium is already present
python plan2model.py ingest plan.pdf
python plan2model.py calibrate --ref 102,88,1034,88 --len 9.9
python plan2model.py detect && python plan2model.py build && python plan2model.py render && python plan2model.py verify
```

Core of the build step (the part most worth getting right):
```python
from shapely.geometry import LineString, box
from shapely.ops import unary_union
import trimesh

def wall_polygon(w):                      # centre-line + thickness
    return LineString([w["a"], w["b"]]).buffer(w["t"]/2, cap_style=2, join_style=2)

def opening_cut(w, o):                    # rectangle across the wall at offset/width
    line = LineString([w["a"], w["b"]])
    p0 = line.interpolate(o["offset"]); p1 = line.interpolate(o["offset"]+o["width"])
    return LineString([(p0.x,p0.y),(p1.x,p1.y)]).buffer(w["t"], cap_style=2)

def build_walls(level):
    walls = {w["id"]: w for w in level["walls"]}
    solid = unary_union([wall_polygon(w) for w in walls.values()])
    meshes = []
    full = [opening_cut(walls[o["wall"]], o) for o in level["openings"]]
    meshes.append(trimesh.creation.extrude_polygon(solid.difference(unary_union(full)), height=2.7))
    # the piece above each door / head, and below each sill, is extruded from the cut region
    for o in level["openings"]:
        cut = opening_cut(walls[o["wall"]], o).intersection(solid)
        z0, z1 = (o["sill"]+o["h"], 2.7)           # lintel/head piece
        meshes.append(slab(cut, z0, z1))
        if o["sill"] > 0: meshes.append(slab(cut, 0, o["sill"]))   # window sill piece
    return trimesh.util.concatenate(meshes)
```
(`slab(poly, z0, z1)` is `extrude_polygon` followed by a translate by `z0`, using height `z1 - z0`.)

Acceptance test for v1: on a known plan, outer dimensions are within 2 percent of the printed value, every door and window in the drawing exists as a hole in the right wall, the GLB is watertight per `trimesh`, and `verify.png` shows the model and plan aligned. Keep three sample plans (clean CAD PDF, scanned print, hand sketch) as regression fixtures, and expect the third to need manual correction.

1. Review/editor UI with drag handles, then OCR for room labels and dimension suggestions.
2. Materials and texture library, per-room lighting, `bpy` Cycles stills, walkthrough video.
3. Pretrained segmentation fallback for noisy scans, and perspective correction for photos.

7. Optional AI beauty pass, clearly marked illustrative.

## 12. Decision checklist for the user

- Do you have the PDF or vector source? If yes, the result will be far more accurate. Use it.
- Which one dimension on the plan do you trust most? That is your calibration.
- Do you need an accurate model (design, permits, 3D printing) or an attractive image (marketing)? The first uses this pipeline as is. The second adds the optional beauty pass on top.
- Is a desktop Blender available? If yes, Blender MCP can drive it for finishing, but the pipeline above works without it.
