# Turning a 2D Floor Plan into a 3D Model: Build Plan

## The short answer

Build a pipeline in which **computer vision reads the plan into a small JSON file, and a script builds the 3D model from that JSON**. Do not ask an AI image generator to draw the 3D model. Use the generator only as an optional last step for pretty pictures.

The one idea to remember: **the JSON file is the product.** Everything before it is "reading the plan". Everything after it is "building and rendering". You can fix, hand-edit and re-run either half without touching the other.

```
plan image/PDF -> [1 Prepare] -> [2 Read: walls, doors, windows, scale, text]
   -> plan.json (you review and fix it) -> [3 Build 3D] -> model.glb / .blend
   -> [4 Render] -> PNG images, video, web viewer
```

## Assumptions

- The plan is a typical architect's or agent's drawing: top-down, mostly straight walls, with at least one printed dimension or a known scale.
- Single floor per image. Multi-storey plans are processed one page at a time and stacked.
- "3D model" means a walkable, extruded house (walls with door and window holes, floors, ceilings optional, basic furniture optional), not a surveyed CAD model.
- Your environment is the Claude Code cloud container: Linux, Python, Node, Chromium and Playwright. There is no GPU and no desktop. Blender runs headless (command line, no window), which works fine on CPU.
- The first version should work with no paid services.
- A human is willing to spend two minutes checking the result before it is trusted.

## Two opposing answers, and what I keep from each

**Answer A: "Be exact. Detect the walls with CV, build real geometry."**
Strength: dimensions are right, doors are real holes, you get files that open in Blender, a game engine or a viewer, and the model can be edited.
Weakness: real plans are messy. Scans are tilted, symbols vary, hatching and furniture confuse wall detection. A pure CV pipeline fails silently on odd drawings.

**Answer B: "Skip all that. Feed the plan to an AI image model or a vision LLM and let it make the 3D picture."**
Strength: it works on any style of plan, needs no tuning, and the result looks beautiful in seconds.
Weakness: it invents walls, moves doors, changes room sizes and cannot guarantee scale. The output is a picture, not a model. You cannot measure it or walk through it.

**Synthesis (what this plan does):**
1. Geometry comes from deterministic code (Answer A), because accuracy is the point.
2. A **vision LLM (Claude itself)** is used as a reader and checker, not a drawer (the useful part of Answer B). It names rooms, spots doors and windows the CV missed, and compares a render of the result against the original plan to flag mismatches.
3. A **human confirmation step** on a flat 2D overlay catches errors cheaply before any 3D work.
4. An **AI image generator** is used only after the model exists, taking a clean render as its input to make "photoreal" marketing pictures. It is labelled "illustrative, not to scale".

## Tools to use

| Job | Tool | Why |
|---|---|---|
| PDF to image | `pdf2image` / PyMuPDF (`fitz`) | Rasterises at 200-300 dpi. If the PDF is vector, PyMuPDF can also read the lines directly, which is far more accurate than pixels. |
| Cleanup | OpenCV, scikit-image | Deskew, threshold, remove noise. |
| Wall finding | OpenCV (morphology, Hough lines, contours) | Walls are thick dark lines. Thin lines are dimensions and furniture. |
| Text and dimensions | Tesseract via `pytesseract`, or EasyOCR | Reads "12'-6\"", "3.20 m", room names. |
| Optional ML wall segmentation | A pretrained floor-plan model (for example CubiCasa5k-based networks) | A fallback for messy scans. Heavier to install, so not in version 1. |
| Reading and checking | Claude vision (you are already inside it) | Names rooms, finds doors and windows, verifies the final render. |
| Geometry building | Python with `shapely` (polygons) and `trimesh` (meshes) | Light, no Blender needed for the first version. |
| Full-quality model and renders | Blender run headless, scripted with `bpy` | Booleans for door holes, materials, lights, Cycles/EEVEE renders. |
| Web viewer | three.js plus `GLTFLoader`, screenshots via Playwright | Interactive viewer, and a fast way to produce preview images in your container. |
| Pretty pictures (optional) | An image-to-image AI model (for example via Scenario or Higgsfield, if connected) | Photoreal styling of a render. |

Blender via an MCP server (a live connection to a running Blender) is a good fit when you have a desktop Blender open and want to adjust things interactively. In a cloud container, use headless `blender -b -P build.py` instead. Same scripts, no connection needed.

## The pipeline, step by step

### Step 1. Prepare the input

1. Convert PDF to PNG at about 300 dpi. If it is a vector PDF, keep the vector data too.
2. Deskew: find the dominant line angle with a Hough transform and rotate so walls are horizontal and vertical.
3. Crop the margins and title block.
4. Convert to greyscale, threshold, remove specks.
5. Save a cleaned image and a log of what was done.

### Step 2. Set the scale (do this first, because everything depends on it)

Pick one source, in this order:
1. **A user-supplied number:** "this wall is 4.2 m". Most reliable.
2. **A printed dimension line:** OCR the number, detect the two tick marks at its ends, compute pixels per metre.
3. **A scale bar** (a drawn line labelled "1 m" or "10 ft").
4. **A known object:** a standard interior door is about 0.9 m (36 in) wide. Use as a rough fallback only.

Compute scale from **several** dimensions and compare them. If they disagree by more than 3 percent, stop and show the user both numbers. Never guess silently.

### Step 3. Find the walls

1. Separate thick strokes from thin ones. Erode the image with a kernel roughly the wall thickness. What survives is walls. Thin dimension lines, furniture and text disappear.
2. Skeletonise the result into centre-lines.
3. Snap lines to horizontal and vertical, merge lines that are almost collinear, and connect endpoints that nearly touch.
4. Record each wall as `start`, `end`, `thickness`.
5. Walls that are not at 90 degrees (angled walls) are kept as they are. Only snap lines that are within about 3 degrees of an axis.

### Step 4. Find doors and windows

- **Doors:** a gap in a wall plus a quarter-circle arc is the standard symbol. Detect the gap in the wall run, then look for an arc next to it with `cv2.HoughCircles` or contour fitting. The arc tells you the hinge side and swing direction.
- **Windows:** usually a gap in the wall with two or three thin parallel lines. Detect the gap, then confirm the thin lines.
- **Sliding doors, bifolds, garage doors:** treated as "opening, type unknown" and given a default.
- Claude vision pass: show the cropped plan with detected openings numbered on it, and ask "which openings are missing or wrong?" Merge the answers.

Each opening is recorded as `wall id`, `position along wall`, `width`, `type`, and for windows `sill height` and `head height`.

### Step 5. Find rooms and read text

1. Rooms are enclosed regions. Compute them by turning the wall lines into polygons with `shapely.polygonize`.
2. OCR the text, then assign each label to the room polygon that contains it ("Kitchen", "Bed 2").
3. Read printed room sizes ("12'0\" x 10'6\""). Use them as a **cross-check** against the measured polygon. A mismatch is flagged, not silently resolved.

### Step 6. Write `plan.json` and review it

Example (shortened):

```json
{
  "units": "m",
  "scale_source": "dimension_line:4.20m",
  "wall_height": 2.7,
  "walls": [
    {"id": "w1", "a": [0, 0], "b": [6.0, 0], "thickness": 0.23, "kind": "exterior"}
  ],
  "openings": [
    {"id": "d1", "wall": "w1", "offset": 1.2, "width": 0.9,
     "type": "door", "swing": "in-left", "confidence": 0.92},
    {"id": "n1", "wall": "w1", "offset": 3.5, "width": 1.5,
     "type": "window", "sill": 0.9, "head": 2.1, "confidence": 0.85}
  ],
  "rooms": [
    {"id": "r1", "label": "Kitchen", "polygon": [[0,0],[6,0],[6,4],[0,4]],
     "floor": "tile"}
  ],
  "warnings": ["Room r3 area differs 7% from printed size"]
}
```

**Review step (the most important quality control):** draw `plan.json` on top of the original image as coloured lines, with opening IDs and any warnings. Show it. The user types corrections ("move d1 left 0.2", "w4 is 0.1 thick") or edits the JSON. Re-draw. Only continue when it looks right. This takes two minutes and saves hours.

### Step 7. Build the 3D geometry

For every wall:
1. Make a box of length x thickness x height from the centre-line.
2. Join corners cleanly. Simplest reliable method: build the whole wall layout as 2D polygons in `shapely` (buffer each centre-line by half the thickness, then take the union), then extrude the union once. Corners come out perfect.
3. Cut door and window holes: subtract a box from the extruded solid. In `trimesh` use the `manifold3d` backend. In Blender use a Boolean modifier.
4. Add window sill and lintel pieces (the wall left above and below a window) automatically as a result of the cut.

Then:
- **Floors:** extrude each room polygon down by 0.1 m. Different floor materials per room.
- **Ceilings:** optional, and hidden by default in the preview so you can look in from above.
- **Door and window objects:** simple frames, a door leaf at the right swing angle, and a glass plane for windows. These are more convincing than bare holes.
- **Stairs, if detected:** a run of equal-height steps. Mark as "approximate".

### Step 8. Materials and lighting

- **Materials:** walls white plaster, floors by room type (tile in kitchen and bath, wood elsewhere), glass for windows. Start with flat colours, then upgrade to free PBR textures (for example from ambientCG, which is public domain).
- **Lighting:** a sun lamp plus a sky background for daylight. A soft area light behind each window gives interior glow. For night views add a point light per room.
- **Camera presets:** top-down orthographic (the "3D floor plan"), 45-degree isometric cutaway (ceiling hidden, front walls lowered), and eye-level in each room at 1.6 m.

### Step 9. Export and render

| Output | File | Used for |
|---|---|---|
| Interactive 3D model | `model.glb` | Web viewer, Blender, most 3D tools |
| Editable scene | `model.blend` | Further work in Blender |
| Plain mesh | `model.obj` or `.stl` | 3D printing, other software |
| Overlay check | `overlay.png` | Proof the walls match the plan |
| Renders | `topdown.png`, `iso.png`, `room_<name>.png` | Sharing |
| Walkthrough | `tour.mp4` | Camera path through rooms, rendered frame by frame and joined with `ffmpeg` |
| Viewer | `index.html` with three.js | Orbit around and click rooms |
| Data | `plan.json` | The single source of truth |

Render speed on CPU: EEVEE-style quick renders take seconds. Cycles at moderate samples with the denoiser takes about a minute per image. Use low samples for drafts.

### Step 10. Automatic self-check

Render the top-down view in the same scale and position as the source image, then compare:
- Overlay the render outline on the plan. Compute how many wall pixels agree.
- Ask Claude vision: "Here are the plan and the render. List differences." 
- Fail the build and print the differences if agreement is below a threshold.

## Making the results accurate (summary)

1. Scale from several sources that must agree.
2. Walls from thick-stroke filtering, with straight-line snapping only within 3 degrees.
3. Openings from gap plus symbol, not from guessing.
4. Every number written into `plan.json` carries a source and a confidence value. Low confidence items are listed for review.
5. Human review on a flat overlay before any 3D.
6. Automatic render-versus-plan comparison afterwards.

## Stress test: five hostile inputs and the patches

**1. A tilted phone photo of a paper plan, with shadows and a curved page.**
Breaks: deskew handles rotation but not perspective, and shadows ruin thresholding, so walls break into pieces.
Patch: add a four-point perspective correction (the user clicks the four plan corners, or the code finds the largest quadrilateral). Use adaptive thresholding, not a global threshold. If wall confidence is still low, say so and ask for a flatter scan. Do not produce a confident model from a bad photo.

**2. A plan with no printed dimensions and no scale bar.**
Breaks: no way to get real size. A made-up scale gives a house that is 40 percent too small.
Patch: the pipeline refuses to continue without a scale. It asks for one known length, or offers the "standard door is 0.9 m" estimate clearly labelled "approximate, plus or minus 15 percent". The label stays on every output file name and render.

**3. A cluttered plan: hatched walls, furniture, dimension strings, grids and a huge title block.**
Breaks: hatching looks like many thin walls, and furniture outlines look like short walls.
Patch: (a) crop the title block first, (b) the thick-stroke filter removes thin lines, (c) hatched or filled walls are detected as large solid regions rather than lines, (d) objects closer than a minimum length (for example 0.4 m) that are not connected to the wall network are dropped, (e) the human overlay review catches the rest. If fully solid-filled walls (common in architect drawings) confuse the erosion method, switch to "region mode" and treat dark connected areas as the wall polygons.

**4. A plan with curved walls, angled walls, a spiral stair or an open-plan layout with no walls between rooms.**
Breaks: line snapping flattens curves, and polygonize finds no separate rooms in open plans.
Patch: curved walls are kept as polylines with many short segments (no snapping above 3 degrees). Open-plan areas are handled by letting the user draw "virtual dividers" (invisible zero-height lines) so the room labels still map correctly. Spiral stairs are marked "unsupported, placeholder block". The tool lists what it could not model.

**5. A multi-page PDF with several floors, a site plan and a legend, in feet-and-inches with OCR errors such as "5'-6" read as "56".**
Breaks: the pipeline processes the wrong page, and a misread dimension scales everything wrong by 10x.
Patch: classify each page first (Claude vision: "floor plan, elevation, site plan, legend"), process only floor plans, and ask which page is which floor. Parse feet-and-inches with a strict pattern. Reject any scale that gives a room, door or ceiling size outside a sane range (door 0.6 to 1.2 m, ceiling 2.2 to 4 m, room 1.5 to 15 m), and report "scale looks wrong".

**Two further breaks found while writing this:**
- *Doors that open into walls drawn as double lines at thickness 0.1 m or 0.4 m.* Thickness is measured per wall, not assumed.
- *Slow or failed Blender install in the container.* Version 1 uses `trimesh` only, so Blender is an upgrade rather than a requirement.

## Risks and honest limits

| Risk | How bad | What to do |
|---|---|---|
| Wrong scale | High: everything is wrong | Several sources, sanity ranges, refuse to guess |
| Missed or false walls | High | Overlay review, self-check render |
| Door and window types vary by country and drawing style | Medium | Default type plus Claude vision pass; user edits JSON |
| Plans contain no heights | Medium | Defaults (wall 2.7 m, sill 0.9 m, head 2.1 m), editable |
| AI-image renders look right but are wrong | High if shared as fact | Keep them labelled "illustrative"; never use them to measure |
| Copyright or privacy of the plan | Low to medium | Process locally; do not upload someone else's plans to third-party services without permission |
| Not for construction | Legal | The output is a visualisation, not an engineering document |

## The smallest version you can build first

**Goal:** one clean, simple plan image in, one `.glb` and one preview PNG out. About a day of work. No Blender, no AI image generation.

Scope:
- Input: a clear PNG of a plan with thick black walls, plus **one number you type in** (a known wall length).
- Walls only, found with OpenCV. Doors and windows are cut where you list them in a small hand-written file (version 1 does not detect them).
- Output: `model.glb`, `overlay.png`, `preview.png` (rendered with three.js in Playwright).

Steps:
1. `pip install opencv-python-headless shapely trimesh manifold3d numpy mapbox-earcut pytesseract` (needs `apt install tesseract-ocr` only when you add OCR).
2. Write `read_plan.py`: threshold, erode to keep thick lines, skeletonise, Hough lines, snap, write `plan.json`.
3. Write `overlay.py`: draw the JSON on the image. Look at it. Fix the JSON by hand if needed.
4. Write `build.py`: buffer centre-lines into polygons, union, extrude with `trimesh.creation.extrude_polygon`, subtract door and window boxes, add a floor slab, export `model.glb`.
5. Write `preview.html` that loads the GLB with three.js `GLTFLoader` and `OrbitControls`, plus a short Playwright script that opens it and saves `preview.png`.

Core of `build.py` (sketch):

```python
import json, trimesh
from shapely.geometry import LineString
from shapely.ops import unary_union

plan = json.load(open("plan.json"))
H = plan["wall_height"]

footprint = unary_union([
    LineString([w["a"], w["b"]]).buffer(w["thickness"] / 2, cap_style=2, join_style=2)
    for w in plan["walls"]
])
walls = trimesh.creation.extrude_polygon(footprint, H)

for o in plan["openings"]:
    w = next(x for x in plan["walls"] if x["id"] == o["wall"])
    # place a box at o["offset"] along wall w, width o["width"],
    # z from sill to head, thickness w["thickness"] + 0.02
    cutter = make_cutter(w, o)            # helper you write
    walls = walls.difference(cutter)      # uses manifold3d

walls.export("model.glb")
```

**You know version 1 works when:** the overlay lines sit on the walls of the original image, the model's overall width matches the number you typed in, and the preview shows holes where doors and windows should be.

## Decision checklist

- Do I have one trusted real-world length? If not, stop and get one.
- Does the overlay match the plan? If not, fix `plan.json` first.
- Does the render match the plan? If not, do not share it.
- Are AI-generated images labelled "illustrative"?
