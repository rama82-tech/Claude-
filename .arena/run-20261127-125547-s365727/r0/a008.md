# Floor Plan to 3D Model: Build Plan

## Recommendation

Do not generate the 3D model straight from the image. Build a pipeline in which the plan is first turned into a small, checked, human-readable data file (a "plan.json" describing walls, openings, rooms and dimensions). A deterministic generator then builds the 3D model from that file.

The reasons:

- Vision models and image generators are good at recognising things and bad at exact geometry. They invent walls and drift dimensions.
- A text file can be validated, diffed, hand-corrected and re-run. A picture cannot.
- Every later output (GLB, Blender file, renders, three.js viewer) comes from the same file, so they all agree.

**Recommended stack**

- Python for extraction, validation and the 3D build.
- Claude vision plus OpenCV for reading the plan.
- Blender in headless mode (`blender -b -P build.py`) for the model and renders. The build script is plain `bpy` code.
- Exports to GLB, plus a three.js or `<model-viewer>` page for sharing.

## The analogy: cheque processing

The same problem is already solved in banking. A cheque has the amount twice, as digits (the courtesy amount) and as words (the legal amount). OCR reads both. A cheque is accepted only if the two readings agree. If they disagree, it goes to a human. Nobody trusts one noisy reader.

Ported to floor plans:

| Cheque processing | Floor plan |
|---|---|
| Two independent readings of the same amount | Two independent readings of the same geometry: (a) vision-model reading of the drawing, (b) classical CV line detection plus dimension-text OCR |
| Accept only if they agree | Accept a wall or dimension only if both agree within tolerance, or a human confirms it |
| Reject pile for a human clerk | A "review queue": flagged items drawn in red on an overlay image |
| Amount limits and format rules | Sanity rules: rooms close, walls meet, door widths 0.7 to 1.2 m, ceiling 2.1 to 4 m |

**Where the analogy breaks, and the fix**

- A cheque has one number. A plan has hundreds of related ones. So add a third check that cheques lack: the dimension chain. The room widths along a wall must add up to the overall dimension written for that wall. This is the real "amount in words" for a plan.
- Cheques are standardised. Plans are not (Indian, US and European conventions differ; hand sketches differ again). So the scale and unit are recorded explicitly and never guessed silently.
- A wrong cheque is caught at the bank. A wrong wall silently produces a convincing but wrong house. So the final model is rendered back to a flat top view and compared to the source image (see Verification).

## Options considered

Scores are 1 (poor) to 5 (good). "Fail-safe" means the method fails loudly and leaves a trail when its input is bad.

| Option | Geometric accuracy | Fail-safe | Editable | Works in this cloud session | Effort | Verdict |
|---|---|---|---|---|---|---|
| A. AI image generator makes a 3D-looking picture from the plan | 1 | 1 | 1 | 3 | 5 (easy) | Not for a deliverable. Invented walls, no dimensions. Only for a mood image after the real model exists. |
| B. Pure classical CV (Hough lines, contours, OCR) to geometry | 3 | 3 | 4 | 5 | 2 | Good on clean CAD exports. Breaks on scans, hatching, furniture. Use as the second reader. |
| C. Trained ML wall/room segmentation (CubiCasa5k-style models) | 3 | 2 | 3 | 2 (weights, GPU) | 2 | Too heavy for v1. Revisit later. |
| D. Vision LLM extracts plan.json, CV cross-checks it, human reviews, scripted Blender builds | 4 | 5 | 5 | 5 | 3 | **Chosen.** |
| E. Manual tracing in Blender or SketchUp | 5 | 5 | 5 | 1 | 1 (hard) | The fallback, and the "ground truth" that D's output is judged against. |
| F. PDF vector extraction (if the PDF is CAD-exported) | 5 | 4 | 4 | 5 | 3 | Add as a fast path: try it first when the PDF contains vector lines. |

Why D wins: it is the only option that is high on accuracy, loud on failure and editable, and runs here without a GPU. Its weak point (the vision model hallucinating) is covered by the second reader and the human review step.

## Architecture

```
input (PNG/JPG/PDF)
  -> 0 INTAKE & QUALITY GATE        (reject or warn early)
  -> 1 NORMALISE                    (deskew, crop, upscale, grey, record px)
  -> 2 SCALE & UNITS                (dimension text, scale bar, or user-supplied)
  -> 3 READER A: vision model       -> candidate plan.json
     READER B: OpenCV + OCR         -> candidate lines, text, boxes
  -> 4 RECONCILE                    (agree = accept, disagree = flag)
  -> 5 VALIDATE                     (rules + dimension chains)
  -> 6 HUMAN REVIEW                 (overlay.png with flagged items)
  -> plan.json (frozen, versioned)
  -> 7 BUILD 3D (Blender headless)  -> .blend, .glb
  -> 8 RENDER                       -> top, isometric, eye-level PNGs
  -> 9 VERIFY (round-trip)          -> pass/fail report
```

## Pipeline, step by step

### 0. Intake and quality gate

Checks run before any cost is spent:

- File opens, is at least about 1500 px on the long side (rasters), and is not blank or nearly all white.
- PDF: count pages. Report and ask which page if more than one. Check for vector content (`pdfplumber` or `PyMuPDF`). If vector lines exist, use them directly and skip most of CV.
- Blur check (variance of Laplacian), skew angle, and a shadow or photo-of-paper check (large brightness gradient).
- Output a `intake_report.json` with a status of PASS, WARN or REJECT and the reason in plain words. A REJECT stops the run; the pipeline never "does its best" on a hopeless input.

### 1. Normalise

Deskew, crop margins, convert to grey, adaptive threshold, and keep the original pixel to normalised pixel transform so every later coordinate can be traced back to the source image.

### 2. Scale and units (the step most plans get wrong)

Pixels mean nothing until pixels per metre is known. Sources, in priority order:

1. The user gives one known length ("this wall is 4.2 m").
2. A scale bar or "1:100" note, combined with the known print size (risky for PDFs that were resized).
3. Dimension strings on the drawing (e.g. `12'-6"`, `3750`, `4.2 m`): OCR them (Tesseract or the vision model), match each to the dimension line it labels, compute pixels per unit from each, and take the median.

Defensive rules:

- Each dimension gives its own scale estimate. If the estimates differ by more than 3 percent, stop and report which dimensions disagree. This catches a misread digit, a stretched scan or an unmarked "not to scale" drawing.
- Unit is stored explicitly (`"unit": "mm"`). Imperial feet-inches are parsed with a strict grammar and converted once to millimetres. Bare numbers with no unit are refused, not guessed. A bare "3750" could be mm, but a "12" could be feet or inches.
- If the plan says "not to scale" or has no usable dimension, the run continues only if the user supplies a reference length, and the output is labelled `SCALE: USER-SUPPLIED`.

### 3. Two independent readers

**Reader A (vision model).** Send the normalised image plus a strict JSON schema. Ask for: wall segments (start, end, thickness class: external or internal), doors (host wall, position, width, swing side), windows (host wall, position, width, sill height if shown), rooms (name, label position), stairs, and dimension strings with what they measure. Coordinates in a fixed image-pixel grid. Ask it to report a confidence and a "could not see clearly" list instead of filling gaps. Validate the reply against the schema; a malformed reply is retried once and then flagged.

**Reader B (classical).** OpenCV: remove text (connected components), find long thick strokes with morphological opening, extract line segments (LSD or probabilistic Hough), snap to horizontal/vertical where within a few degrees, merge collinear fragments. Door arcs: detect circular arcs next to wall gaps. Windows: detect thin triple-line or double-line gaps in a wall. Text: Tesseract or the vision model for dimensions and room labels. This reader is weaker at meaning and stronger at positions.

### 4. Reconcile

For each wall from A, look for a wall from B within tolerance (default 1.5 percent of the plan's longest side, or 3 wall thicknesses, whichever is smaller).

- Both agree: accept; use B's coordinates (more precise) and A's classification (more meaningful).
- Only one sees it: mark `status: "unconfirmed"`. Unconfirmed walls are drawn in red on the review overlay and are not built unless the user confirms or the strict flag `--accept-unconfirmed` is set.

### 5. Validate (hard rules that stop the build)

- Walls snap to junctions with no gaps over 50 mm and no overlaps; T and L junctions are explicit.
- Every room is a closed loop (polygon via Shapely `polygonize`). An open room is an error listing the two ends that fail to meet.
- Dimension chains: for each wall line, the sum of segment dimensions equals the stated overall within 1 percent (or the stated tolerance).
- Plausible ranges: wall thickness 70 to 450 mm, door width 600 to 1300 mm, window width 400 to 3000 mm, room area at least 1.5 m2, total footprint at most 2000 m2 (a bigger value almost certainly means a scale error).
- Each opening lies fully inside its host wall, and two openings never overlap.
- Any failure writes `validation_report.md` with item IDs and the image coordinates, then exits non-zero. The 3D step refuses to run on a failed plan.

### 6. Human review

Produce `overlay.png`: the source image with detected walls (blue), openings (green), unconfirmed items (red) and IDs. The user fixes issues by editing `plan.json` (or replying "wall W12 is real"). A tiny local web page with the overlay and a JSON editor is a nice later upgrade. Once approved the file is saved with a hash and the source image hash, so every model can be traced to the exact input.

### 7. Build the 3D model (Blender headless, `bpy`)

Everything is generated from `plan.json`; nothing is hand-modelled.

- **Walls:** polygon of the wall centre-lines offset by half thickness (Shapely `buffer` with flat caps, then union so junctions merge cleanly), extruded to wall height (default 2.7 m, overridable). Exterior walls default to 200 mm, interior to 100 mm if the drawing does not show thickness.
- **Doors and windows:** boolean-subtract a box from the wall at the opening position (door from floor level up to 2.1 m; window from sill 0.9 m, height 1.2 m, unless the plan states otherwise). Add simple frames and a window glass pane; doors as thin slabs with the swing arc recorded as metadata. Booleans are applied once at the end for speed and tidiness.
- **Floors and ceilings:** a polygon face per room from the `polygonize` result, with a thin slab. Ceiling optional (off for the cutaway view).
- **Materials:** a small named library (wall paint, floor tile, floor wood, glass, door wood) assigned by room name keywords (kitchen/bath to tile, bedroom/living to wood). Procedural materials only in v1, so there are no texture files to go missing.
- **Lighting:** Sun lamp for exterior views, area lights in rooms for interior views, plus a neutral sky. Two lighting presets: `clay` (fast, no materials, ambient occlusion) and `day`.
- **Scene hygiene:** metres, Z up, origin at the lowest-left corner, each wall, opening and room an object with its plan ID in the name so a modeller can find it.

### 8. Renders and outputs

| Output | Format | Purpose |
|---|---|---|
| `plan.json` | JSON | The source of truth, approved and versioned |
| `intake_report.json`, `validation_report.md`, `overlay.png` | JSON / MD / PNG | Evidence and review |
| `house.blend` | Blender | Editable model |
| `house.glb` | glTF binary | Web, AR, game engines |
| `top.png` | PNG | Top-down render (orthographic) |
| `iso_cutaway.png` | PNG | Isometric with roof and near walls hidden |
| `room_<name>.png` | PNG | Eye-level view per room at 1.6 m |
| `verify.png` and `verify_report.json` | PNG / JSON | Round-trip comparison |
| `viewer.html` | HTML | three.js or `<model-viewer>` page loading the GLB |

Blender's Eevee in headless mode is fast enough for these on a CPU-only container, but may need software GL; Cycles on CPU with low samples and a denoiser is the slower, safer fallback.

### 9. Verify by round trip (the check that closes the loop)

Render the finished model from straight above at the same scale as the source, extract its wall mask, and compare to the source's wall mask: intersection-over-union and a distance check on each wall. Report passes only if IoU is above a threshold (start at 0.85) and no wall is more than 100 mm out. Also assert: wall count in the model equals wall count in `plan.json`; every opening exists in the mesh. A failed check prints exactly which walls differ and highlights them in `verify.png`. This catches errors in the build step that the input validation cannot.

## How accuracy is achieved (summary)

- Walls: two readers, coordinates from the geometric one, snapping and junction merging, then the round trip check.
- Openings: placed by distance along the host wall (so they cannot drift off the wall), width from the drawing, sill and head heights from stated values or labelled defaults.
- Floors: derived from closed wall loops, never drawn by hand, so they always match the walls.
- Dimensions: multiple estimates of scale, chain sums, plausibility ranges.
- Materials and lighting: assigned by room names through a lookup table, so they are repeatable and not dependent on a model's mood.

## Risks and failure cases, and what the system does

| Risk | Detection | Response |
|---|---|---|
| Photo of a plan with perspective or shadow | Brightness gradient, non-parallel walls | WARN and offer a corrected crop, or REJECT if skew is above 10 degrees |
| Low resolution or blurry scan | Size and blur score | REJECT with the minimum needed |
| Scale unknown or inconsistent | Step 2 dimension spread | Stop, ask for a reference length |
| Imperial vs metric misread, feet vs inches | Strict parser, plausible ranges | Refuse bare numbers; flag implausible results |
| Furniture, hatching, grid lines read as walls | Readers disagree | Unconfirmed, drawn red, not built |
| Curved or diagonal walls | Not snapped to the axes | v1 supports straight walls; flag non-orthogonal ones as unsupported rather than bend them |
| Multi-storey on one sheet or several pages | Multiple "stair up/down" or several outlines | v1 handles one storey per run; the user splits the pages |
| Vision model invents or omits items | Disagreement with CV; schema; round trip | Flagged; never silently accepted |
| Handwritten dimensions | OCR confidence low | Flagged for the user to type |
| Thin walls drawn as one line | Thickness defaults used | Model is labelled with the assumed thickness |
| Boolean cut failures in Blender | Non-manifold check after build | Rebuild that wall with an explicit opening gap polygon instead of a boolean |
| Copyrighted or confidential plans | n/a | Process locally; the image goes to the vision API only if the user agrees |
| Generated model "looks right" but is wrong | Round trip check | Fails loudly with a diff image |
| Over-trust in AI renders | Policy | Any AI-generated mood image is labelled "illustrative, not to scale" and never replaces the model |

Everything runs with a fixed seed and pinned library versions, and each run folder contains the inputs, versions and hashes, so a result can be reproduced or questioned later.

## Minimal first version (build this first, about one to two days)

Scope: one storey, straight orthogonal walls, one clean image or vector PDF, metric.

1. `intake.py`: size, blur, blank checks; PDF vector check; write the report.
2. `scale.py`: take a reference length from the command line (`--ref "W3=4.2m"`) to start. Dimension OCR comes in v2.
3. `read_plan.py`: send the image to Claude with the JSON schema; save `plan.json` and `overlay.png`. Run OpenCV Hough as a cross-check and flag mismatches (no merging logic yet; only report).
4. `validate.py`: closed rooms, plausible ranges, opening inside wall. Exit non-zero on failure.
5. `build.py` (run with `blender -b -P build.py -- plan.json`): wall extrusion, door and window cuts, floor slabs, three plain materials, one sun lamp.
6. `render.py`: top-down and one isometric PNG, plus a GLB export.
7. `verify.py`: top-down round-trip IoU against the source.

Test it on three inputs before trusting it: (a) a clean, simple rectangular plan with two rooms and known dimensions; (b) the same plan with furniture and text added; (c) a deliberately bad input (blurry, rotated 12 degrees, wrong dimension typed). Expected results: (a) PASS, (b) PASS with flagged items, (c) clear REJECT or WARN. If (c) ever produces a model without any warning, the pipeline is broken.

**Later versions:** dimension-text OCR and automatic scale, reconcile logic, stairs, a web review UI, textures and furniture libraries, multi-storey, curved walls, and optionally a trained segmentation model as a third reader.

## Assumptions

- The input is a single-storey, mostly orthogonal plan with at least one printed dimension, or the user can supply one reference length.
- Outputs are for visualisation and communication, not construction documents or permit drawings; the model is no substitute for a survey.
- A vision model API is available from the session. If not, the pipeline falls back to Reader B plus manual `plan.json` editing, with lower automation but the same safety checks.
- Blender can be installed in the container (apt or the official tarball). If it cannot, the build step can be swapped for a `trimesh` or three.js generator that reads the same `plan.json`. Renders then come from Playwright screenshots of the three.js scene, with lower visual quality.
- Default wall height 2.7 m, door 2.1 m by 0.9 m, window sill 0.9 m, and thicknesses as above are used only when the drawing is silent, and each default is listed in the model's report.
